# 项目文档管理

文档的目的只有一个：下一个接手的人（或 Agent）不用重新读一遍源码，就能找到该改哪里、为什么这样、怎么验证。写不出这个价值的文件不要建。

## 项目任务门禁

项目任务开始时使用本技能，需要时配合 `project-vcs`；使用本技能不等于批量生成文档，也不启动 OpenSpec 流程。非项目问答不创建项目文档。

1. 开工前确定 `PROJECT_ROOT` 与 `DOC_ROOT`，读 `AGENTS.md`（有的话）、`DOC_ROOT/README.md` 和 `MODULE-MAP.md`（有的话）；缺失时先读项目入口，按 `init.md` 的「初始化」补最小必要的一套，不假设目标项目已有文档脚本。
2. 按模块地图找到对应模块 README，再由其中的路径、入口和关键符号定位代码。先在模块范围内搜索；文档定位不到或证据不足时才扩大范围，并把新找到的定位信息回写文档。
3. 模块分析完成后创建或更新对应模块 README，记录这次确认的事实、源码定位、证据与待确认项；文档和代码一致、没有新事实时不做无意义改动。
4. 代码或配置改完之前，按「按变化选择文档」检查受影响的文档；已知漂移当场修正，不只在会话里报告。生成物通过源配置或生成工具更新，不手工覆盖。
5. 项目有文档校验脚本就运行；没有就至少核对文档里的路径、入口、链接和状态。写不进去或验证不了时明确报告缺项，不声称文档已经闭环。

## 路径模型

- `PROJECT_ROOT`：代码、资源、构建配置和可执行测试所在的项目根目录。
- `DOC_ROOT`：设计、规范、架构、验收和过程文档所在的根目录。

确定 `DOC_ROOT`：

1. 项目设置或工作流参数里给了文档根，就用它。
2. 项目里已有文档目录（`docs/`、`doc/`、`Docs/` 或配置里指定的位置）时用它，不另起一套。
3. 没有时普通项目用 `PROJECT_ROOT/docs`。
4. 项目由 P4 或 SVN 管理时按「文档」角色的文档位置：默认在项目外，同一工程的各分支（按项目文件夹认，如 `D:/P4/Main/Game` 和 `D:/P4/Dev/Game`）共用一个 `DOC_ROOT`，路径由面板算好；可设成 `PROJECT_ROOT/docs`（随项目纳管、按分支各一份）。面板在提示里给了「文档根」一段时以它为准。
   - `DOC_ROOT` 在 `PROJECT_ROOT` 外面时，文档只落盘：不 `p4 add` / `p4 edit` / `p4 reconcile`、不放进任何 changelist，SVN 不 `svn add`；交接和总结里单独列成「项目外文档（不纳入版本管理）」。在项目里面时随项目正常纳管。
   - 各分支共用 `DOC_ROOT` 时：模块说明、ADR、Bug 记录、openspec、项目教训共用；只属于某个分支的 `p4change/`、`worklog/` 放在 `DOC_ROOT/branches/<分支>/` 下。模块 README 的元数据头写「- 分支：<最近一次更新它的分支>」；读到别的分支写的模块文档照常引用，用到的部分以本分支代码为准，两个分支确实不同的写进「## 分支差异」。
5. 仓库只读、或者项目根下不宜放文档时，问用户要一个位置，不要猜。

代码、构建和测试命令在 `PROJECT_ROOT` 执行；文档和变更状态在 `DOC_ROOT` 管理。

## AGENTS.md 和 DOC_ROOT 的分工

| 文件                     | 给谁看                   | 写什么                                                                  | 不写什么                     |
| ------------------------ | ------------------------ | ----------------------------------------------------------------------- | ---------------------------- |
| `PROJECT_ROOT/AGENTS.md` | 每次对话都会读它的 Agent | 一句话项目说明、硬规则、常用命令、目录速览、文档地图（指向 `DOC_ROOT`） | 模块细节、架构长文、历史记录 |
| `PROJECT_ROOT/CLAUDE.md` | Claude Code              | 只有一行 `@AGENTS.md`，规则只维护 AGENTS.md 一份                        | 和 AGENTS.md 重复的内容      |
| `DOC_ROOT/README.md`     | 人和 Agent               | 项目是什么、怎么开始、文档索引                                          | 完整架构、任务清单           |
| `DOC_ROOT/MODULE-MAP.md` | 人和 Agent               | 模块路径、职责、入口、关联文档                                          | 模块内部实现                 |

AGENTS.md 每次对话都占上下文，保持在 150 行以内；超出的细节挪进 `DOC_ROOT` 的专题文档，AGENTS.md 里只留一行指针。P4 项目的 AGENTS.md 仍在 `PROJECT_ROOT`（随代码提交），文档地图指向外部的 `DOC_ROOT`。

## 模块文档：按需建、简要、元数据是唯一来源

- **按需建**：不给所有模块预先建文档。一个模块第一次要交给子对话、还没有文档时，由「文档」分析这个模块写一份（协调器派，面板拦着没文档就不开子对话）；用不到的模块永远不建。大项目（UE 这类）也一样，不全仓扫描。
- **元数据头**：标题之后、第一个 `## ` 之前，一行一个字段（格式见 `templates.md`）：`状态`、`职责`、`源码`、`入口`、`关键词`、`依赖`、`更新`，P4 / SVN 各分支共用文档根时再加 `分支`。`源码`、`入口` 一律写**相对项目根**的路径（`Plugins/Foo/Source/`、`server/exec/`），不写盘符或 `/` 开头的绝对路径、不写 P4 depot 路径，也不带 `:行号`：文档经 P4 / Git 共用时各人的工作区根不同，绝对路径换台机器就「找不到」，面板按各自本机的项目根核对。协调器按关键词和职责对模块，所以关键词写用户会说的业务术语、类名、日志类别（最多 20 个）。
- **两个状态**：`documented`（分析过，有简要文档）和 `stale`（代码变了不少、文档可能过期，照样能读，下次改到时刷新）。旧文档里的 `inferred` / `analyzed` / `confirmed` / `verified` 都按 `documented` 读，不再新写。
- **简要**：正文只有「做什么 / 不做什么」「关键文件」「对外接口与数据流」「改这里要注意」「怎么验证」，总共约 80 行；不写实现细节、逐函数说明、变更历史。
- **模块清单以元数据头为准**：面板每轮从各模块 README 的元数据现读模块清单给协调器，不靠 `MODULE-MAP.md`。`MODULE-MAP.md` 是可选的：项目的 AGENTS.md 或文档说了它由脚本生成，就改完元数据头跑那个脚本；项目里已经有一份手写的地图，就改受影响的行；没有就不新建。

## 模块文档：先读 → 调查 → 回写

调研、评审、排查某个模块时按这个顺序走，不要从零在代码里乱撞：

1. **先定位**：读模块 README 的元数据（有 `MODULE-MAP.md` 就先读它），确定目标属于哪个模块，拿到它的路径、职责、入口和文档链接；地图里没有才按目录结构找。
2. **有文档就先读**：`modules/<模块名>/README.md` 存在时先读它，把它当已有结论的起点，只做三件事——补它没写的、纠正它写错的、确认它是否还准确；不重复它已经写清的内容，不重新摸索一遍入口和调用链。
3. **没文档再从入口摸**：没有模块文档时，从模块地图或构建文件给出的入口文件往下读，不在仓库里做无目标的全文搜索。
4. **以代码为准**：文档和实现不一致时信代码、测试和配置，回写文档改正，不沿用已知过期内容。

调研形成能长期用的结论（职责、入口、依赖、边界、数据流、扩展点、常见陷阱、回归验证）后必须落盘，不能只写在对话回复里：

- **写入或合并**：写进 `modules/<模块名>/README.md`。文件已存在时合并，不整文件覆盖：保留已有章节和结论，把新内容补到对应小节；和已有结论冲突的地方写清「以哪次改动为准」（附提交号或日期）。
- **模块已经不在了**：代码里目录和入口都没了（被删除或并进别的模块）时，删掉 `modules/<模块名>/` 整个目录（地图跟着重新生成），删除原因写进提交说明；只是移走、改名的改元数据头里的「源码」「入口」。要留迁移线索就写进承接模块的 README，不留墓碑目录。
- **新增模块**：建 `modules/<模块名>/README.md`，元数据头写全；模块表自动生成，不手加行。
- **证据**：结论要能回溯到代码（相对项目根的文件路径 + 函数名、类名或小节，不写行号：改一行代码下面的行号全部偏移，要逐条修）、命令输出或测试；拿不准的写「待确认」，不写成事实。
- **说清落在哪**：结果里写一句「已写入 / 合并到 `modules/<模块名>/README.md`」；没落盘时写明原因（没有可长期用的结论，或超出只读范围）。

## Bug 记录

Bug 记录只记用户报的 Bug：用户提出的问题经分析、修复并验证后才写。AI 自己写代码、自测、评审或跑测试时发现并修掉的问题不写 Bug 记录。写法和索引生成见 `bug-index.md`：有生成脚本时 `bugs.md` 是生成物，只写 `bugs/<bug-id>.md`，不手改索引。

## 按变化选择文档

只更新受影响的文档：

| 变化                                            | 必须检查                                                                                                  |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 新的硬规则、常用命令、目录或文档位置变化        | `AGENTS.md`                                                                                               |
| 新增或修改领域术语                              | `CONTEXT.md`，必要时 `CONTEXT-MAP.md`                                                                     |
| 对外行为变化                                    | 当前 change 的 `specs/`；交付后更新 `openspec/specs/`                                                     |
| 模块职责、入口、依赖或数据流变化                | `modules/<模块名>/README.md`（同步状态），有 `MODULE-MAP.md` 时按上面的规则同步，必要时 `architecture.md` |
| 用户报的 Bug 修复后：根因、修复路径或防复发规则 | 新增或改写 `modules/<模块名>/bugs/<bug-id>.md`，再重新生成同目录 `bugs.md`                                |
| 难以逆转的技术取舍                              | `adr/`                                                                                                    |
| API、资源格式或持久化变化                       | 对应 `tech/` 契约                                                                                         |
| 构建、部署、迁移或排障变化                      | 对应 `runbooks/`                                                                                          |
| 人类协作方式变化                                | `contributing.md`                                                                                         |
| 用户可感知的发布变化                            | `CHANGELOG.md`                                                                                            |
| P4 文件纳入、编辑、shelve、编译或 pending 变化  | `p4change/<任务标识>.p4change.md`                                                                         |

没涉及的文档不强制修改；涉及但没同步更新时，验收记录里写明原因或判定为缺项。

## 完成变更时的核对顺序

当前 change 的验收标准 → 受影响的长期文档 → 模块状态与漂移 → 项目的文档校验脚本（有则运行）→ 版本控制 / P4 台账 → 验收记录。文档只写由代码、配置、测试或明确决策支持的事实。

## 子文件：什么时候读哪个

- `structure.md`：推荐的 `DOC_ROOT` 目录结构、模块怎么划、每类文档写什么（README、bugs、CONTEXT、architecture、adr、tech、runbooks、openspec、CHANGELOG、p4change）、开发前的读取顺序、交付状态的三种说法。要新建文档、拿不准内容该写进哪个文件、要分模块时读。
- `bug-index.md`：Bug 记录怎么写（`bugs/<bug-id>.md` 的元数据头、必填字段）、`bugs.md` 索引怎么生成、冲突了怎么办。要写或改 Bug 记录时读。
- `init.md`：「初始化文档结构 / 初始化项目」的九步。只在用户明确要初始化时读。
- `templates.md`：AGENTS.md、文档根 README、模块 README、Bug 记录的骨架。新建这几类文件时照着写。
