# 项目文档管理

文档的目的只有一个：下一个接手的人（或 Agent）不用重新读一遍源码，就能找到该改哪里、为什么这样、怎么验证。写不出这个价值的文件不要建。

## 项目任务门禁

项目任务开始时使用本技能，需要时配合 `project-vcs`；使用本技能不等于批量生成文档，也不启动 OpenSpec 流程。非项目问答不创建项目文档。

1. 开工前确定 `PROJECT_ROOT` 与 `DOC_ROOT`，读 `AGENTS.md`（有的话）、`DOC_ROOT/README.md` 和 `MODULE-MAP.md`；缺失时先读项目入口，按「初始化」补最小必要的一套，不假设目标项目已有文档脚本。
2. 按模块地图找到对应模块 README，再由其中的路径、入口和关键符号定位代码。先在模块范围内搜索；文档定位不到或证据不足时才扩大范围，并把新找到的定位信息回写文档。
3. 模块分析完成后创建或更新对应模块 README，记录这次确认的事实、源码定位、证据与待确认项；文档和代码一致、没有新事实时不做无意义改动。
4. 代码或配置改完之前，按「按变化选择文档」检查受影响的文档；已知漂移当场修正，不只在会话里报告。生成物通过源配置或生成工具更新，不手工覆盖。
5. 项目有文档校验脚本就运行；没有就至少核对文档里的路径、入口、链接和状态。写不进去或验证不了时明确报告缺项，不声称文档已经闭环。

## 路径模型

- `PROJECT_ROOT`：代码、资源、构建配置和可执行测试所在的项目根目录。
- `DOC_ROOT`：设计、规范、架构、验收和过程文档所在的根目录。

确定 `DOC_ROOT`：

1. 项目设置或工作流参数里给了文档根，就用它。
2. 项目里已有文档目录（`docs/`、`doc/`、`Docs/` 或配置里指定的位置）时用它，不另起一套。
3. 没有时普通项目用 `PROJECT_ROOT/docs`。
4. 项目由 P4 或 SVN 管理时按「文档」角色的文档位置：默认 `DOC_ROOT = <PROJECT_ROOT 的上一级目录>/docs`（和项目文件夹同级），可设成 `PROJECT_ROOT/docs`。面板在提示里给了「文档根」一段时以它为准。
   - `DOC_ROOT` 在 `PROJECT_ROOT` 外面时，文档只落盘：不 `p4 add` / `p4 edit` / `p4 reconcile`、不放进任何 changelist，SVN 不 `svn add`；交接和总结里单独列成「项目外文档（不纳入版本管理）」。在项目里面时随项目正常纳管。
5. 仓库只读、或者项目根下不宜放文档时，问用户要一个位置，不要猜。

代码、构建和测试命令在 `PROJECT_ROOT` 执行；文档和变更状态在 `DOC_ROOT` 管理。

## AGENTS.md 和 DOC_ROOT 的分工

| 文件                     | 给谁看                   | 写什么                                                                  | 不写什么                     |
| ------------------------ | ------------------------ | ----------------------------------------------------------------------- | ---------------------------- |
| `PROJECT_ROOT/AGENTS.md` | 每次对话都会读它的 Agent | 一句话项目说明、硬规则、常用命令、目录速览、文档地图（指向 `DOC_ROOT`） | 模块细节、架构长文、历史记录 |
| `PROJECT_ROOT/CLAUDE.md` | Claude Code              | 只有一行 `@AGENTS.md`，规则只维护 AGENTS.md 一份                        | 和 AGENTS.md 重复的内容      |
| `DOC_ROOT/README.md`     | 人和 Agent               | 项目是什么、怎么开始、文档索引                                          | 完整架构、任务清单           |
| `DOC_ROOT/MODULE-MAP.md` | 人和 Agent               | 模块路径、职责、入口、关联文档                                          | 模块内部实现                 |

AGENTS.md 每次对话都占上下文，保持在 150 行以内；超出的细节挪进 `DOC_ROOT` 的专题文档，AGENTS.md 里只留一行指针。P4 项目的 AGENTS.md 仍在 `PROJECT_ROOT`（随代码提交），文档地图指向外部的 `DOC_ROOT`。

## 推荐结构

```text
DOC_ROOT/
├── README.md                 # 项目入口、用途、快速开始和文档索引
├── MODULE-MAP.md             # 模块路径、职责、入口和关联文档
├── modules/<模块名>/
│   ├── README.md             # 模块职责、入口、依赖、边界、数据流、陷阱、回归验证
│   ├── bugs.md               # 第一次记录这个模块的 Bug 时才建：Bug 索引（生成物，不手工编辑）
│   └── bugs/<bug-id>.md      # 单个 Bug 的根因、修复和回归（手写，元数据头生成索引）
├── CONTEXT.md                # 领域术语和概念边界（有稳定术语时才建）
├── CONTEXT-MAP.md            # 多个上下文之间的关系（只有多个上下文时才建）
├── architecture.md           # 当前已落地的架构快照
├── adr/                      # 难逆转、有真实权衡的决策
├── tech/                     # 资产、API、持久化等跨模块契约
├── runbooks/                 # 构建、部署、迁移和排障操作
├── openspec/                 # 用 OpenSpec 流程时：specs/ 和 changes/<change>/
├── contributing.md           # 人类开发者协作说明
├── p4change/                 # 仅 P4 项目：外部文件变更台账
└── CHANGELOG.md              # 有发布或用户可感知变化时维护
```

`tests/` 属于 `PROJECT_ROOT`，跟随代码的版本控制；测试结果、验收命令和报告属于 `DOC_ROOT`。**没有内容依据的类别不建空文件或空目录**：`adr/`、`tech/`、`runbooks/`、`openspec/`、`bugs.md` 都在第一次有内容时才建。

## 模块怎么划

模块按职责划，不按目录层级机械地取一级目录：

- 一级目录就是职责边界时（`server/`、`web/`、`shared/`）直接用它。
- 代码都在 `src/` 下时往下一层，按 `src/<子目录>` 划。
- monorepo 按包（`packages/*`、`apps/*`）划；UE 项目按 `Source/<模块>` 和 `Plugins/<插件>` 划，Lua 脚本按功能目录划。
- 资源、生成物、第三方代码（`vendor/`、`ThirdParty/`、`Content/`）不建模块文档，在 MODULE-MAP 里一行说明即可。
- 小项目（不到 3 个职责块）不拆模块，只写 `README.md` 和 `MODULE-MAP.md`；大项目先列 3–15 个最重要的模块，其余在 MODULE-MAP 里列出、标「未建文档」。

模块名用目录名或项目里通用的叫法，不自造名字。

## 模块 README 的状态

每份模块 README 开头有一个状态块（格式见本技能目录下的 `templates.md`），字段：

- `status`：`inferred`（扫描推断，还没读代码）、`analyzed`（读过代码，有证据）、`confirmed`（经人工或测试确认）、`stale`（代码变了还没重新分析）、`retired`（模块移除或合并，保留迁移链接）。
- `source_paths`：模块包含的源码路径。
- `entry`：入口文件或关键符号。
- `analyzed_at` / `verified_commit`：最近一次分析的日期和当时的提交（P4 写 changelist 号）。

状态流转：初始化产生 `inferred` → 有证据的代码分析后至少 `analyzed` → 人工或测试确认后 `confirmed`；代码、入口或依赖变了但没重新分析时改成 `stale`，重新分析后回到 `analyzed`。`analyzed` 和 `confirmed` 的文档不能留关键占位内容；结论要能回溯到代码、配置、测试、ADR 或 OpenSpec。

## 文档职责

- `modules/<模块名>/README.md`：职责、入口、依赖、边界、数据流、扩展点、常见陷阱、回归测试、证据来源和待确认项。
- `modules/<模块名>/bugs.md`：按症状、关键词、入口、根因类型、状态和单 Bug 文档链接帮助检索，不重复排查过程。**它是生成物，不要手工编辑**：内容由同目录 `bugs/<bug-id>.md` 的元数据头按 ID 字母序聚合而成，改完详情文件跑一次项目的生成脚本（见下面「Bug 索引的生成」）。
- `modules/<模块名>/bugs/<bug-id>.md`：现象、复现条件、影响范围、根因、排查路径、修复、回归测试和防复发护栏。
- Bug 记录只记用户报的 Bug：用户提出的问题经分析、修复并验证后才写。AI 自己写代码、自测、评审或跑测试时发现并修掉的问题不写 Bug 记录。
- `CONTEXT.md` 只记稳定术语、概念定义和边界；`CONTEXT-MAP.md` 只记多个上下文的关系、责任边界和交叉术语。
- `architecture.md` 只描述当前已落地的模块、依赖、数据流和运行边界；架构变了同步更新。
- `adr/` 只记难逆转、缺少背景会令人困惑、且确实有取舍的决策；被替代的 ADR 标状态并链接新 ADR。
- `tech/` 记跨模块必须遵守的资产、API、持久化和兼容性契约；已有 schema 或生成文档时引用它们，不维护重复字段表。
- `runbooks/` 记人能照做的构建、部署、迁移和排障步骤，关键命令写适用条件和验证结果。
- `openspec/specs/` 是已确认行为的规范；`openspec/changes/<change>/` 记一个变更从提案到验收的过程，不当永久架构总览。
- `contributing.md` 面向人类开发者，不替代 AGENTS.md。
- `CHANGELOG.md` 只记发布或用户可感知的变化。
- P4 项目的 `p4change/<任务标识>.p4change.md` 只记文件操作时间线和 P4 证据。

## 模块文档：先读 → 调查 → 回写

调研、评审、排查某个模块时按这个顺序走，不要从零在代码里乱撞：

1. **先定位**：读 `MODULE-MAP.md`，确定目标属于哪个模块，拿到它的路径、职责、入口和文档链接；地图里没有才按目录结构找。
2. **有文档就先读**：`modules/<模块名>/README.md` 存在时先读它，把它当已有结论的起点，只做三件事——补它没写的、纠正它写错的、确认它是否还准确；不重复它已经写清的内容，不重新摸索一遍入口和调用链。
3. **没文档再从入口摸**：没有模块文档时，从 `MODULE-MAP.md` 给出的入口文件往下读，不在仓库里做无目标的全文搜索。
4. **以代码为准**：文档和实现不一致时信代码、测试和配置，回写文档改正，不沿用已知过期内容。

调研形成能长期用的结论（职责、入口、依赖、边界、数据流、扩展点、常见陷阱、回归验证）后必须落盘，不能只写在对话回复里：

- **写入或合并**：写进 `modules/<模块名>/README.md`。文件已存在时合并，不整文件覆盖：保留已有章节和结论，把新内容补到对应小节；和已有结论冲突的地方写清「以哪次改动为准」（附提交号或日期）。
- **模块已经不在了**：代码里目录和入口都没了（被删除或并进别的模块）时，删掉 `modules/<模块名>/` 整个目录，并从 `MODULE-MAP.md` 的模块表里删掉那一行；删除原因写进提交说明。要留迁移线索就把线索写进承接模块的 README，不单独留旧目录——留着目录就得保留表格行、状态列写 `retired`，两边缺一边会被文档检查拦住。不保留过期的职责和入口。
- **新增模块**：先在 `MODULE-MAP.md` 的模块表里加一行（模块名、路径、职责、入口、文档链接、状态），再建 `modules/<模块名>/README.md`；表和目录不许留孤项，项目的文档检查脚本会检查两个方向对不上（本项目的 `scripts/rules-check.mjs`）。
- **状态与证据**：内容是本轮代码分析得出的，状态至少 `analyzed`，带 `source_paths`、`entry`、`analyzed_at` 和分析依据（文件路径:行号、命令输出、测试）。
- **说清落在哪**：结果里写一句「已写入 / 合并到 `modules/<模块名>/README.md`」；没落盘时写明原因（没有可长期用的结论，或超出只读范围）。

## Bug 索引的生成

`modules/<模块名>/bugs.md` 是从同目录 `bugs/<bug-id>.md` 聚合出来的生成物：一个 Bug 一个文件，谁都不用改同一张表，多个子对话并行收尾时不会因为都往表末尾追加一行而反复冲突。

**只写详情文件，不手改索引。** 新增或修改 Bug 记录的步骤：

1. 写 `modules/<模块名>/bugs/<bug-id>.md`：`<bug-id>` 用能看懂症状的短英文名，全小写、用连字符，就是这个模块里的唯一标识。
2. 在 `# 标题` 之后、第一个 `## ` 之前写元数据头，字段各占一行（顺序不限）：

```md
# 侧栏普通对话行有一圈虚线边框

- 状态：已修复（`npm run typecheck`、`npm run lint`、`npm run test:unit` 通过）
- 症状：侧栏普通对话行四周有一圈虚线边框，看着像选中态
- 入口：`web/src/components/layout/SidebarTasks.tsx` 的 `TaskRow`
- 根因类型：保活状态被画成整行边框
- 模块：`web`（`web/src/components/layout/SidebarTasks.tsx` 的 `TaskRow`）
- 关键词：侧栏、对话列表、虚线边框、border-dashed、CLI 存活
```

`状态`、`关键词`、`入口`、`根因类型` 四行是必填；`症状` 不写时取标题；`模块` 不参与索引，是归属和涉及面的说明。正文里出现的同名字段（举例、引用的旧状态）不算元数据，脚本只读 `## ` 之前那一块。

3. 跑项目提供的生成脚本把索引重写（本项目的 `node scripts/doc-bugs.mjs`，也可写成 `npm run docs:bugs`），提交时把 `bugs.md` 一起带上。
4. 项目的 `--check` 检查（本项目在 `npm run lint` 里）会发现「手改了索引」「改了详情没重生成」和「详情缺必填字段」，以它为准。

索引按 ID 字母序排，不按日期也不按文件系统顺序：同一个详情文件重复生成的结果完全一样，两个人各自新增一条时行落在不同位置，合并时大概率能自动合。索引冲突了就**以任意一边为准重跑一次生成脚本**，不要手工合并表格。

## 按变化选择文档

只更新受影响的文档：

| 变化                                            | 必须检查                                                                            |
| ----------------------------------------------- | ----------------------------------------------------------------------------------- |
| 新的硬规则、常用命令、目录或文档位置变化        | `AGENTS.md`                                                                         |
| 新增或修改领域术语                              | `CONTEXT.md`，必要时 `CONTEXT-MAP.md`                                               |
| 对外行为变化                                    | 当前 change 的 `specs/`；交付后更新 `openspec/specs/`                               |
| 模块职责、入口、依赖或数据流变化                | `modules/<模块名>/README.md`（同步状态）、`MODULE-MAP.md`，必要时 `architecture.md` |
| 用户报的 Bug 修复后：根因、修复路径或防复发规则 | 新增或改写 `modules/<模块名>/bugs/<bug-id>.md`，再重新生成同目录 `bugs.md`          |
| 难以逆转的技术取舍                              | `adr/`                                                                              |
| API、资源格式或持久化变化                       | 对应 `tech/` 契约                                                                   |
| 构建、部署、迁移或排障变化                      | 对应 `runbooks/`                                                                    |
| 人类协作方式变化                                | `contributing.md`                                                                   |
| 用户可感知的发布变化                            | `CHANGELOG.md`                                                                      |
| P4 文件纳入、编辑、shelve、编译或 pending 变化  | `p4change/<任务标识>.p4change.md`                                                   |

没涉及的文档不强制修改；涉及但没同步更新时，验收记录里写明原因或判定为缺项。

## 规范与交付状态

区分三个状态：**工作区已实现**（本地通过验证，可能还没提交）、**已提交**（进入版本控制历史：Git commit、P4 submit 等）、**已发布**（用户能拿到的版本已更新）。不把「仅工作区已实现」写成已提交或已发布；提前记录时标注「已验收，待提交」。

## 读取顺序

开始开发前按需读：`AGENTS.md` → `README.md` → `MODULE-MAP.md` → 对应模块 README（和 `bugs.md`）→ `CONTEXT.md` → `architecture.md` → 相关 ADR、技术契约、runbook 和当前 OpenSpec change。小改动不必读全部。

分析某个模块时：先读 `MODULE-MAP.md` 和模块 README，再读模块入口、配置和必要代码。分析完把确认的职责、入口、依赖、边界、数据流、扩展点、陷阱和回归验证写回模块 README，没有证据的留在「待确认」；同时修正 `MODULE-MAP.md` 里受影响的行。模块文档和代码不一致时以代码、配置和测试为准，回写文档，不沿用已知过期的内容。

## 初始化

明确要「初始化文档结构」或「初始化项目」时执行。先读项目，后写文档；不对整个源码树做全文搜索。

1. **确定两个根**：按路径模型确定 `PROJECT_ROOT` 和 `DOC_ROOT`；P4 项目的文档不写回项目目录。
2. **读项目**：已有的 AGENTS.md / CLAUDE.md / README / 文档目录；依赖清单和构建配置（package.json、Cargo.toml、go.mod、_.uproject、_.sln、CMakeLists.txt 等）；scripts、Makefile、CI 配置；格式和检查配置（.editorconfig、Prettier、ESLint、clang-format 等）；一级和二级目录；Git 项目再看最近 20 条提交说明，了解提交约定。
3. **AGENTS.md**：不存在就按 `templates.md` 的骨架新建；已存在就保留原有内容和结构，只补缺的段落（常用命令、目录速览、文档地图等），修正和项目实际不符的命令和路径。命令必须是项目里真实存在的，不编 `npm run xxx`。
4. **CLAUDE.md**：不存在时新建，只写一行 `@AGENTS.md`；已存在但没引用 AGENTS.md 时在末尾追加一行 `@AGENTS.md`；已有内容不删。
5. **DOC_ROOT/README.md 和 MODULE-MAP.md**：按 `templates.md` 写；已有的人工文档不覆盖，只补缺的段落和模块行。
6. **模块文档**：按「模块怎么划」选出模块，为每个建 `modules/<模块>/README.md`，状态 `inferred`，写路径、职责、入口、依赖、关联文档和待确认项；不建 `bugs.md`。
7. **其他文档**：`CONTEXT.md`、`architecture.md`、`runbooks/` 等只在读项目时已经看到确定内容（例如 README 里有部署步骤）时才建。
8. **标注推断**：扫描得出的结论写成「待确认」，不把猜测写成已确认的架构事实。
9. **报告**：列出新建和修改的文件、每个文件写了什么、留下的待确认项。

初始化不改源码、不装依赖、不提交；需要提交时按 `project-vcs` 的规则由用户决定。

## 完成变更时的核对顺序

当前 change 的验收标准 → 受影响的长期文档 → 模块状态与漂移 → 项目的文档校验脚本（有则运行）→ 版本控制 / P4 台账 → 验收记录。文档只写由代码、配置、测试或明确决策支持的事实。
