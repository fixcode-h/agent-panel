# 项目文档管理

## 项目任务门禁

项目任务开始时使用本技能，与 `project-workflow` 配合；使用本技能不等于批量生成文档，也不启动 OpenSpec 流程。非项目问答不创建项目文档。

1. 项目任务开始前确定 `PROJECT_ROOT` 与 `DOC_ROOT`，读取已存在的文档入口和模块地图；缺失时先读取项目入口，按本技能初始化最小必要文档，不假设目标项目已有文档脚本。
2. 根据模块地图找到对应模块 README，再由其中的路径、入口和关键符号定位代码。优先在模块范围内搜索；只有文档无法定位或证据不足时才扩大范围，并把新定位信息回写文档。
3. 模块分析完成后必须创建或更新对应模块文档，记录本次已确认的事实、源码定位、证据与待确认项；已有文档与代码一致且无新增事实时不制造无意义改动。
4. 代码或配置变更完成前，按“按变化选择文档”检查受影响文档；已知漂移必须修正，不得仅报告在会话中。生成物通过源配置或生成工具更新，不手工覆盖。
5. 存在项目文档校验脚本时运行校验；不存在时至少核对文档路径、源码入口、关联链接、状态和证据。校验不能证明语义完全一致，仍须以实际代码分析核对内容；无法写入或验证时明确报告缺项，不声称文档闭环完成。

## 路径模型

先确定两个根：

- `PROJECT_ROOT`：代码、资源、构建配置和可执行测试所在的项目根目录；
- `DOC_ROOT`：设计、规范、架构、验收和过程文档所在的根目录。

普通项目：`DOC_ROOT = PROJECT_ROOT\docs`。P4 项目：`DOC_ROOT = <共同外层目录>\ProjectDoc\doc\<实际项目文件夹名>`。P4 文档不得写回 `PROJECT_ROOT`。

代码、构建和测试命令在 `PROJECT_ROOT` 执行；文档和 OpenSpec 状态在 `DOC_ROOT` 管理。无法唯一确定两个根时先询问，不要猜路径。

## 推荐结构

```text
DOC_ROOT/
├── README.md                 # 项目入口、用途、快速开始和文档索引
├── MODULE-MAP.md             # 模块路径、职责、入口和关联文档的粗略导航
├── modules/                  # 模块长期文档、Bug 索引和定位资料
│   └── <模块名>/
│       ├── README.md         # 模块架构、职责、入口、依赖和边界
│       ├── bugs.md           # 模块 Bug 索引和快速定位信息
│       └── bugs/             # 单个 Bug 的根因、修复路径和回归记录
├── CONTEXT.md                # 领域术语、概念边界和不含实现细节的词汇表
├── CONTEXT-MAP.md            # 只有多个上下文/模块存在边界关系时才创建
├── openspec/
│   ├── specs/                # 已确认并已落地的正式行为规范
│   └── changes/<change>/     # 未完成或待归档的变更
│       ├── proposal.md
│       ├── design.md
│       ├── specs/
│       ├── tasks.md
│       ├── grilling.md
│       └── acceptance.md
├── adr/                      # 难逆转、有惊讶性且存在真实权衡的决策
├── architecture.md           # 当前已落地的架构快照
├── tech/                     # 资产、API、持久化等跨模块契约
├── runbooks/                 # 构建、部署、迁移和排障操作
├── contributing.md           # 人类开发者协作说明
├── p4change/                 # 仅 P4 项目：外部文件变更台账
└── CHANGELOG.md              # 只有存在发布或用户可感知变化时维护
```

`tests/` 属于 `PROJECT_ROOT`，跟随代码和资源的版本控制；测试结果、验收命令和报告属于 `DOC_ROOT`。不为没有内容的类别创建空文件或目录。

## 文档职责

- `README.md` 说明项目是什么、如何开始和去哪里找详细文档；不要复制完整架构或任务清单。
- `MODULE-MAP.md` 只记录模块路径、职责、入口和关联文档的粗略导航；可由受控的一级目录扫描生成，不替代模块文档。
- `modules/<模块名>/README.md` 记录模块长期架构：职责、入口、依赖、边界、数据流、扩展点、常见陷阱、回归测试、证据来源和待确认项。
- 模块 README 必须包含文档状态：`inferred`（扫描推断）、`analyzed`（已完成代码分析）、`confirmed`（事实已确认）、`stale`（代码或配置变化后过期）或 `retired`（模块已移除/合并）；`analyzed` 与 `confirmed` 不得保留关键占位内容。
- 模块 README 必须记录 `source_paths`、入口、最近分析时间和最近验证提交；文档结论必须能回溯到代码、配置、测试、ADR 或 OpenSpec 证据。
- `modules/<模块名>/bugs.md` 是模块 Bug 索引，按症状、关键词、入口、根因类型、状态和单 Bug 文档链接帮助快速检索；不重复完整排查过程。
- `modules/<模块名>/bugs/<bug-id>.md` 记录单个 Bug 的现象、复现条件、影响范围、根因、排查路径、修复、回归测试和防复发护栏。
- `CONTEXT.md` 只记录稳定术语、概念定义和边界；不要写实现细节、临时计划或测试结果。
- `CONTEXT-MAP.md` 只记录多个上下文的关系、责任边界、输入输出和交叉术语；单一上下文项目不创建它。
- `openspec/specs/` 是系统已确认行为的规范；只有变更按项目交付状态确认后，才把 change 内容归并为正式规范。
- `openspec/changes/<change>/` 记录一个变更从提案到验收的生命周期，不能作为永久架构总览。
- `architecture.md` 只描述当前已落地的模块、依赖、数据流和运行边界；架构改变后同步更新。
- `adr/` 只记录难以逆转、缺少背景会令人困惑、且确实存在取舍的决策；被替代的 ADR 标记状态并链接新 ADR。
- `tech/` 记录跨模块必须遵守的资产、API、持久化和兼容性契约；已有 schema 或生成文档时优先引用它们，不维护重复字段表。
- `runbooks/` 记录人类可执行的构建、部署、迁移和排障步骤，每条关键命令都要有适用条件和验证结果。
- `contributing.md` 面向人类开发者，记录评审、测试、目录和交付约定；不替代 Agent 的全局规则。
- `CHANGELOG.md` 只记录发布或用户可感知的变化，不记录每次文件编辑、pending 或内部诊断。
- P4 项目的 `p4change/<任务标识>.p4change.md` 只记录文件操作时间线和 P4 证据，不重复需求规范，也不加入 pending。

## 按变化选择文档

只更新受影响的文档：

| 变化 | 必须检查 |
| --- | --- |
| 新增或修改领域术语 | `CONTEXT.md`，必要时 `CONTEXT-MAP.md` |
| 对外行为变化 | 当前 change 的 `specs/`；交付后更新 `openspec/specs/` |
| 模块职责、依赖或数据流变化 | `modules/<模块名>/README.md`，必要时 `architecture.md` |
| Bug 根因、修复路径或防复发规则 | `modules/<模块名>/bugs.md` 和 `modules/<模块名>/bugs/<bug-id>.md` |
| 难以逆转的技术取舍 | `adr/` |
| API、资源格式或持久化变化 | 对应 `tech/` 契约 |
| 构建、部署、迁移或排障变化 | 对应 `runbooks/` |
| 人类协作方式变化 | `contributing.md` |
| 用户可感知的发布变化 | `CHANGELOG.md` |
| P4 文件纳入、编辑、shelve、编译或 pending 变化 | `p4change/<任务标识>.p4change.md` |

未涉及的文档不强制修改；涉及但未同步更新时，验收记录必须说明原因或判定为缺项。

## 规范与交付状态

区分三个状态：

1. **工作区已实现**：代码和资源在本地通过验证，但可能仍在 pending；
2. **已提交**：用户完成 P4 submit 或其他版本控制提交；
3. **已发布**：用户可获得或使用的版本已更新。

P4 pending 阶段不得把“仅工作区已实现”写成已提交或已发布。正式 `openspec/specs/`、架构快照和发布记录应根据项目约定在提交或发布状态确认后更新；若提前记录，必须明确标注“已验收，待提交”。

## 读取与更新顺序

执行初始化时：先读取项目入口和现有文档，再读取模块入口与配置，最后生成模块简略文档和必要目录；不要先对整个源码树做批量全文搜索。

开始分析某个模块时，必须按以下顺序执行：先读取 `MODULE-MAP.md` 和对应的 `modules/<模块名>/README.md`、`bugs.md`（不存在时先创建模块文档骨架），再读取该模块的入口文件、配置和必要代码。分析完成后必须把已确认的模块职责、入口、依赖、边界、数据流、扩展点、陷阱和回归验证同步写入 `modules/<模块名>/README.md`；没有证据的内容保留为“待确认”，不得只把结论留在会话中。模块文档不存在、内容仍是占位符或本次分析发现代码与文档存在明显差异时，必须在分析完成前创建或更新模块文档，并同步修正 `MODULE-MAP.md` 中受影响的路径、职责、入口和关联文档。

后续读取模块时，若模块文档与代码不一致，以代码、配置和测试等最新证据为准；分析结束必须回写文档，不能继续沿用已知过期内容。文档更新应记录当前事实，必要时在“待确认项”或相关 Bug 文档中保留无法确认的差异，不得用猜测覆盖事实。

开始开发前按需读取：`README.md` → `MODULE-MAP.md` → `CONTEXT.md`/`CONTEXT-MAP.md` → `architecture.md` → 相关 ADR → 相关技术契约、runbook 和当前 OpenSpec change。不要为了普通小改动读取全部文档。

## 初始化文档结构

当明确执行“初始化文档结构”时，必须先读取并概览当前 `PROJECT_ROOT`，再按项目实际模块生成简略文档，并创建有内容依据的必备文档文件和文件夹。初始化至少完成：

1. 确认 `PROJECT_ROOT` 与 `DOC_ROOT`；P4 项目不得把文档写回项目目录。
2. 读取项目入口、一级模块目录、构建/测试配置和已有文档，避免默认递归扫描所有源码。
3. 生成或更新 `DOC_ROOT/README.md`、`DOC_ROOT/MODULE-MAP.md` 和机器导航索引。
4. 为已识别且需要长期说明的模块补充简略模块文档，至少包含路径、职责、入口、关联文档、依赖/边界和待确认项。
5. 按项目实际需要创建 `adr/`、`tech/`、`runbooks/`、`openspec/` 等目录；没有内容依据的类别不创建空目录。
6. 只有在术语或多个领域上下文确实存在时，才创建 `CONTEXT.md` 或 `CONTEXT-MAP.md`。
7. 将推断内容标记为“待确认”，不得把扫描猜测写成已确认架构事实。

普通项目的模块文档骨架为已识别的一级代码模块建立 `docs/modules/<模块>/README.md`、`bugs.md` 和 `bugs/`，已有人工文档不覆盖。项目里有文档初始化或校验脚本时，模块新增、移动、职责或入口变化后用它刷新索引并检查模块覆盖、路径、入口和文档链接；没有脚本时手工核对这些项。索引只用于导航，不应成为 Agent 默认递归扫描全项目的理由。

模块文档生命周期为 `discovered → inferred → analyzed → confirmed → stale → revalidated → retired`。初始化产生 `inferred`；完成一次有证据的代码分析后至少更新为 `analyzed`，经过人工或测试确认后才标记 `confirmed`；代码、配置、入口或依赖发生变化而未重新分析时必须标记 `stale`；模块移除或合并时标记 `retired` 并保留迁移链接。状态、最近分析时间、最近验证提交和证据来源必须与内容同步。

完成变更时按此顺序核对：当前 change 的验收标准 → 受影响的长期文档 → 模块状态与漂移 → 项目的文档校验脚本（有则运行） → 版本控制/P4 台账 → 验收记录。文档只写已由代码、配置、测试或明确决策支持的事实；不把计划、猜测或未验证行为写成当前状态。
