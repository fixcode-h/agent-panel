# SVN 细则（简易版）

由 `SKILL.md` 的入口判断确认是 SVN 工作区后使用。SVN 没有本地分支和工作树，改动直接落在工作副本里，所以这里只写「怎么在不越界的前提下收尾」，不铺开第二套流程；收尾门禁和通用安全边界仍以 `SKILL.md` 为准。

## 入口检查

只用只读命令确认身份和基线：

- `svn info`：工作副本根、仓库 URL、相对 URL、修订版本；
- `svn status <任务路径>`：本次任务范围内的 `M`、`A`、`D`、`?`（未纳管）、`!`（丢失）、`C`（冲突）和 `L`（锁）；
- `svn diff <任务路径>`：限定路径的改动内容。

记录基线修订号和任务开始前就存在的改动；这些是用户的，不覆盖、不认领、不还原。工作副本根和仓库 URL 确认不了时停止，不要凭目录猜。

## 禁止操作

不得执行或变相执行：`svn update`（不带任务路径）、`svn revert`、`svn cleanup`、`svn switch`、`svn relocate`、`svn commit`（提交到远端服务器）、`svn lock/unlock`、`svn merge`、`svn add --force .`。`svn status`、`svn diff`、`svn info`、`svn log` 可以只读使用，但必须限定到任务路径。

SVN 的 `commit` 直接写远端仓库，等同于推送：由父对话决定，子对话不执行、不询问用户、也不写进建议。默认收尾停在「工作副本已改、已纳管、已列清单」。

## 怎么收尾

1. 新文件纳入版本控制：`svn add <任务文件>`（逐个文件，不用目录和 `--force`）。删除的文件用 `svn delete <任务文件>`。
2. 再次用 `svn status <任务路径>` 核对：任务文件是 `M` / `A` / `D`，范围外的改动保持原样、不纳入本次清单。
3. 验证按项目规定的步骤跑；验证不过不提交、不宣布完成。
4. 报告：改动文件清单、`svn status` 结果、`svn diff --summarize` 摘要、验证命令和结果、基线修订号，以及「未提交，推送由父对话决定」。

父对话授权后才提交（子对话不执行）：`svn commit <任务文件> -m "<说明>"`，说明写清改了什么，不带全工作副本。提交后回读 `svn info`（新修订号）和 `svn status <任务路径>`（应为干净），确认没有把范围外的文件带进去。

## 更新与冲突

- 更新只在需要拿到别人的改动、且用户或父对话要求时做，并且限定路径：`svn update <任务路径>`；不带路径的整工作副本 `update` 视为同步整个工作区，需要明确授权。
- 冲突（`C`）先理解双方意图和基线：读冲突标记和 `svn info <文件>` 的冲突版本，逐文件手工合并；不得用 `svn resolve --accept=theirs-full` / `mine-full` 粗暴覆盖，也不得 `svn revert` 把别人的改动丢掉。
- 解决后用 `svn resolve --accept=working <文件>` 标记已解决（这一步会改工作副本状态，做之前说明），再跑受影响范围的测试。
- 更新引入的新冲突、以及工作副本被锁（`L`）时报告事实和涉及的文件，不抢占别人的锁。

## 与分支 / worktree 的关系

SVN 的开关走法（`svn copy` 建分支、`svn switch` 切换）属于改远端或切工作副本，默认不做：`SKILL.md` 里的「工作区模式」对 SVN 只按 `不开分支` 理解，并行任务靠文件范围分工，不靠新分支或新工作副本。确实需要按分支并行时，先确认项目自己的分支约定并取得授权。

## 完成前检查

- [ ] 已用 `svn info` 确认工作副本根和仓库 URL，记录了基线修订号；
- [ ] `svn status` / `svn diff` 都限定了任务路径，没有整工作副本扫描；
- [ ] 新增/删除的文件已逐个 `svn add` / `svn delete` 并回读状态；
- [ ] 范围外的用户改动原样保留，未 revert、未 cleanup、未 switch；
- [ ] 没有执行 `svn commit`，或已由父对话提交并回读修订号和状态；
- [ ] 冲突按人工合并解决并跑了受影响范围的测试，没有强推某一方；
- [ ] 结果里写明了改动清单、验证证据和「未提交 / 已提交」的实际状态。
