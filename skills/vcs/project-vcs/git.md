# Git 细则

由 `SKILL.md` 的入口判断确认是 Git 工作区后使用。命令、状态和验收规则都在这里，入口文件只管识别和收尾门禁。

## 入口检查

先读取 `git status --short --branch`、当前分支、仓库根目录和相关文件的限定范围 diff。识别任务开始前已有改动、未跟踪文件、冲突和工作树/子模块状态；已有改动不得覆盖、暂存或提交，除非明确属于本任务。多个 worktree 时用 `git worktree list` 确认自己在哪个工作区、对应哪个分支。

## 安全边界

默认不得执行 `git pull`、`git fetch`、`git checkout`、`git switch`、`git reset --hard`、`git clean`、强制推送、删除分支、覆盖未提交改动或修改远端。需要这些操作时先明确说明影响并请求授权。

可以安全执行只读 `status`、限定路径 `diff`、`log`、`show`、分支信息和本地测试。不得推送、创建 PR 或修改远端。不得自动 amend 已发布提交。

## 提交方式

是否提交由工作流或调用方决定（提交方式：`本地提交` | `只检查`），没有说明时按 `只检查` 处理：

- **本地提交**：代码修改完成且验证通过后，按下文「提交前门禁」创建限定范围的本地提交。
- **只检查**：不暂存、不提交；验证通过后核对限定范围 diff，报告变更文件、验证结果和未包含的已有改动，由工作流后续步骤（例如面板合并工作树）处理提交。

## 模式

分支、worktree 和合并方向不写死成一种流程：按项目配置或调用方传的模式执行，没有配置时用默认值。

| 模式       | 取值                                                   | 默认               | 作用                                 |
| ---------- | ------------------------------------------------------ | ------------------ | ------------------------------------ |
| 工作区模式 | `按需开分支` / `不开分支` / `独立工作树`               | `按需开分支`       | 决定子对话在哪个工作区、哪个分支上改 |
| 合并方向   | `子对话合回父分支` / `父对话统一合并` / `只提交不合并` | `子对话合回父分支` | 决定改动由谁合进父对话所在的分支     |

模式只影响「在哪里改、由谁合」，不改变本细则的其它规则：不推送、不认领用户改动、验证通过才提交。模式由用户或父对话指定后照办，不自行换成更保守或更激进的做法；缺外部信息（例如不知道父分支）时先问，不猜。

## 父子对话的职责

**父对话（统筹一方）**

1. 做入口检查，记下基线：仓库根、当前分支、HEAD、未提交改动，并把这个基线交代给子对话。
2. 按工作区模式决定子对话在哪里干活：`不开分支` 就在同一分支上按文件范围分工；`按需开分支` / `独立工作树` 则开分支（必要时加 worktree）并告诉子对话分支名和目录。
3. 负责合并：按合并方向在子对话交回后把它的分支合进父分支，处理冲突，然后跑一次合并后的验证。
4. 负责清理：子对话彻底完成后（已合回父分支、验证通过、不再需要这个工作区）才删掉它的工作树和分支（`git worktree remove` + `git branch -d`，`git worktree prune` 清残留）。
5. 负责对外：推送、创建 PR、发布由你做，但要用户明确授权；子对话既不执行也不问、不写进建议。

**子对话（执行一方）**

1. 只在自己被交代的分支 / 工作区里改，动手前确认 `git status --short --branch` 是父对话说的那个分支。
2. 不切换分支、不新建分支、不 pull / fetch、不 rebase 父分支、不推送；也不要到父对话的工作区里去改。
3. 本地提交：按本细则的提交方式收尾，一个提交表达一个可审查的变更。
4. 验证通过后交回：写明分支名、commit、改动的文件、跑了什么验证、有没有遗留；合并方向是 `子对话合回父分支` 时才自己合，其它情况交回父对话合并。
5. 交回后自己的分支不推远端、不复用；合并和清理由父对话完成。推送、创建 PR、submit、合并到主干不在子对话的处理范围：不执行、不询问用户、也不写进提问或建议。

## Worktree 管理

- 一个子对话一个独立工作区：`git worktree add <目录> -b <分支> <起点>`，起点默认是父对话当前分支的最新提交，不用远端分支覆盖。
- 目录和分支按项目约定命名并带任务标识，方便认出是谁的；同一个任务不重复开第二份工作区。
- 工作区是完整检出的目录：依赖、构建产物、缓存都不提交，按项目的方式装（例如 `npm ci`），不能把共享目录的 `node_modules`、`DerivedDataCache` 这类中间产物写进提交。
- 清理时机是「子对话彻底完成后」，不是「合并完就删」：合回父分支后可能还要补验证、改后续问题或排查冲突，这些都要再进这个工作区；确认这个子对话不再需要工作区了再清。
- 清理动作：`git worktree remove <目录>`、`git branch -d <分支>`；合并失败、冲突撤回或还要接着改时保留工作区，并说明留着的原因。
- 工作区被别的进程占用、删除失败时用 `git worktree prune` 清残留登记，不要 `rm -rf` 目录后当没发生；残留的分支和目录要报告给用户。
- 不在两个工作区里同时改同一批文件；确实需要并行时按文件范围分工，并在交回时写明各自改了什么。

## 分支与变更范围

- 一个提交应表达一个可审查的逻辑变更，不混入格式化、生成物和无关重构。
- 多个独立功能、修复、文档/配置变更或可独立回滚的变更，拆成多个提交；同一功能涉及多个文件时放在同一个提交中。
- 提交拆分按功能边界、回滚边界和审查边界决定，不按文件数量机械拆分，也不要把一个完整功能拆成过细的碎片提交。
- 修改前后使用限定路径核对 diff；不要用全仓批量命令掩盖变更范围。
- 新分支、工作树、rebase 或 merge 的选择基于协作流程和冲突风险，不是默认动作。
- 冲突先理解双方意图和基线，再逐文件解决；不得用 ours/theirs 粗暴覆盖。

## 提交前门禁

运行项目规定的格式化、lint、类型检查、测试和构建；检查敏感信息、生成物、锁文件与文档同步。验证失败时不提交。

提交方式为 `本地提交` 时，代码修改完成且所有验证通过后，按功能边界分组暂存并创建一个或多个本地提交。提交信息使用项目约定：**标题一行短句（不超过约 40 个字符），细节写进正文分点**，不要把实现过程塞进标题；创建提交时必须包含必要的 co-author trailer。每次提交后必须执行 `git show --stat --check <commit>` 和 `git status --short --branch`，确认提交内容与验证范围一致、工作区没有意外残留；提交钩子产生新改动时重新验证并追加提交。**已有用户改动必须隔离，不得混入本轮 commit；如果无法安全区分，必须暂停并说明阻塞。**提交后报告每个 commit id、对应功能范围、验证命令和未包含的已有改动。本细则不主动推送；推送、创建 PR 或任何远端操作由父对话决定，子对话不执行、不询问用户、也不写进建议。

## 反模式

`git add -A` 混入无关改动；全仓自动格式化；用 reset/clean 清理工作区；强推修复历史；把 merge/rebase 当作同步远端的替代品；未验证就提交；忽略未跟踪文件和子模块状态；子对话自己开分支或推送；子对话彻底完成后不清理工作树和分支。

## 验证方式

验证任务文件清单与限定 diff；测试工作区已有改动隔离；检查提交内容；提交后重新 status；合并后重新跑受影响测试；冲突解决后运行受影响测试和完整 CI 等价检查。涉及发布历史时保留可回滚 tag 或 commit 引用。
