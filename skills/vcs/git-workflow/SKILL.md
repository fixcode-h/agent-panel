# Git 项目工作流

## 入口检查

先读取 `git status --short --branch`、当前分支、仓库根目录和相关文件的限定范围 diff。识别任务开始前已有改动、未跟踪文件、冲突和工作树/子模块状态；已有改动不得覆盖、暂存或提交，除非明确属于本任务。

## 安全边界

默认不得执行 `git pull`、`git fetch`、`git checkout`、`git switch`、`git reset --hard`、`git clean`、强制推送、删除分支、覆盖未提交改动或修改远端。需要这些操作时先明确说明影响并请求授权。

可以安全执行只读 `status`、限定路径 `diff`、`log`、`show`、分支信息和本地测试。不得推送、创建 PR 或修改远端。不得自动 amend 已发布提交。

## 提交方式

是否提交由工作流或调用方决定（提交方式：`本地提交` | `只检查`），没有说明时按 `只检查` 处理：

- **本地提交**：代码修改完成且验证通过后，按下文「提交前门禁」创建限定范围的本地提交。
- **只检查**：不暂存、不提交；验证通过后核对限定范围 diff，报告变更文件、验证结果和未包含的已有改动，由工作流后续步骤（例如面板合并工作树）处理提交。

## 分支与变更范围

- 一个提交应表达一个可审查的逻辑变更，不混入格式化、生成物和无关重构。
- 多个独立功能、修复、文档/配置变更或可独立回滚的变更，拆成多个提交；同一功能涉及多个文件时放在同一个提交中。
- 提交拆分按功能边界、回滚边界和审查边界决定，不按文件数量机械拆分，也不要把一个完整功能拆成过细的碎片提交。
- 修改前后使用限定路径核对 diff；不要用全仓批量命令掩盖变更范围。
- 新分支、工作树、rebase 或 merge 的选择基于协作流程和冲突风险，不是默认动作。
- 冲突先理解双方意图和基线，再逐文件解决；不得用 ours/theirs 粗暴覆盖。

## 提交前门禁

运行项目规定的格式化、lint、类型检查、测试和构建；检查敏感信息、生成物、锁文件与文档同步。验证失败时不提交。

提交方式为 `本地提交` 时，代码修改完成且所有验证通过后，按功能边界分组暂存并创建一个或多个本地提交。提交信息使用项目约定；创建提交时必须包含必要的 co-author trailer。每次提交后必须执行 `git show --stat --check <commit>` 和 `git status --short --branch`，确认提交内容与验证范围一致、工作区没有意外残留；提交钩子产生新改动时重新验证并追加提交。**已有用户改动必须隔离，不得混入本轮 commit；如果无法安全区分，必须暂停并说明阻塞。**提交后报告每个 commit id、对应功能范围、验证命令和未包含的已有改动。本技能不主动推送；推送、创建 PR 或任何远端操作只有用户明确指出时才执行。

## 反模式

`git add -A` 混入无关改动；全仓自动格式化；用 reset/clean 清理工作区；强推修复历史；把 merge/rebase 当作同步远端的替代品；未验证就提交；忽略未跟踪文件和子模块状态。

## 验证方式

验证任务文件清单与限定 diff；测试工作区已有改动隔离；检查提交内容；提交后重新 status；冲突解决后运行受影响测试和完整 CI 等价检查。涉及发布历史时保留可回滚 tag 或 commit 引用。
