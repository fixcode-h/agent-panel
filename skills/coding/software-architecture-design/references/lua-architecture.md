# Lua 架构

## 适用场景

独立 Lua、LuaJIT 与嵌入式 Lua 的模块、对象、协程、热重载和性能设计。先建立运行时画像：PUC Lua/LuaJIT/定制 VM、版本、宿主、`lua_State` 模型、调度器、热更与持久化要求。

## 模块与状态

`require` 按模块名缓存结果到 `package.loaded`。模块默认返回显式 table/callable object；模块加载尽量无副作用，需要资源时提供 `init/start/stop/dispose`。

- MUST 区分 VM 级单例、World/Session 实例和无状态函数集。
- MUST NOT 把 `_G` 作为模块接口或隐式通信总线。
- 多会话、多 World 或隔离测试时，不把 `require` 返回表当可变会话对象；使用工厂创建实例。
- 循环依赖应通过重新划分职责、依赖注入或接口模块消除，不依赖加载顺序。

## 表、对象与元表

表适合数据记录、映射和轻量对象；对象身份、共享原型和继承需要明确。优先组合和显式方法表；元表只用于稳定、可测试的语义，不隐藏远程调用、I/O 或昂贵计算。

数据定义与实例状态分离：共享定义只读，实例拥有动态字段。避免每实例复制大型方法表和静态配置。

## 生命周期与清理

Lua GC 只管理 Lua 可达对象，不保证及时关闭文件、解绑宿主回调或销毁原生资源。所有订阅、Timer、协程和宿主句柄必须有显式 Owner 与清理入口；清理应幂等。

闭包捕获会延长对象生命周期。长生命周期回调避免无意捕获大表、World 或宿主对象；用明确上下文和解绑协议。

## 错误处理

用 `error`/`assert` 表达违反程序不变量，用返回值表达可预期业务失败。系统边界使用 `pcall/xpcall` 添加上下文并决定恢复；不得吞错或把所有函数包进 `pcall`。保留原始 traceback。

## 日志与代码排版

Lua 日志输出格式（`[模块名称] 类名/模块名=>函数名  具体日志内容`，级别由日志接口表达）和代码排版规则统一维护在 `lua-code-style` 技能，本文件不再重复。

## 协程与调度

Lua coroutine 是协作式控制流，不等于线程、并行或自动异步 I/O。必须由宿主/调度器定义可 yield 点、取消、超时、错误传播和销毁。禁止在不允许 yield 的 C 边界或未知调用栈中盲目 yield；具体规则依版本与宿主绑定确认。

## 热重载

清除 `package.loaded` 只影响后续 `require`，不会更新旧 table、闭包、userdata、回调和运行中 coroutine。热更前必须选择语义：

- 新实例使用新模块，旧实例自然退役；
- 保持模块表身份，原位替换允许的方法；
- 显式迁移实例状态与重绑回调。

定义不可迁移对象、回滚、版本兼容和存量 coroutine 处理。没有协议时宁可不热更。

## 序列化与迁移

仅保存稳定、无环、无函数/userdata/thread 的数据模型，并携带 schema version。不要序列化任意运行时 table。迁移函数要幂等、可链式升级，并用真实历史存档回放。

## 性能

先 profile。热路径关注表分配、临时字符串、闭包、全局查找、跨宿主边界和 GC 压力；但局部变量、复用表、池化等优化必须保持所有权清晰。LuaJIT trace/FFI 优化不适用于 PUC Lua；5.4 的语义也不能反推 5.1/LuaJIT。

## 反模式

全局变量通信；模块加载即注册且无清理；深层 prototype 继承；元方法隐藏 I/O；`package.loaded=nil` 宣称完整热更；协程无限挂起；把 userdata 当普通 Lua 对象；每帧大量跨宿主调用；无版本存档。

## 模块运行时接口测试模板

### 定位与运行环境

模块运行时接口测试采用返回显式 table 的轻量、表驱动结构，测试模块命名遵循项目约定。测试在真实 Lua 运行环境或宿主中调用模块公开业务接口，帮助定位入口、绑定、业务处理和结果状态问题，不在测试代码中重新实现业务逻辑。

- 测试文件放到项目既有测试目录，不在生产模块加载时自动运行；没有约定时与模块测试代码归档，执行入口显式调用 `Run(Name)`。
- 先声明所需运行模式、资源、业务状态和模块初始化条件；仅在相关依赖已就绪的环境中运行。工具启动、语法检查或纯 mock 不能替代真实运行时验证。
- 通过项目已有模块访问接口或显式注入获取真实模块，复用项目日志接口；不假设固定的全局变量、模块管理器、引擎或绑定框架，不伪造宿主对象。
- 模块或运行上下文尚未初始化时返回不可执行并记录前置条件，不能计为通过。接口不存在或执行抛错必须明确失败并保留 traceback，不吞异常。

### 固定结构

| 成员 | 职责 |
| --- | --- |
| `LogPrefix` | 固定测试模块标识，完整日志仍必须符合 `lua-code-style` 的日志格式 |
| `RunCounts` | 每个用例独立的数据轮换计数，仅用于手动重复调用，不表达业务成功 |
| `TestData[Name].Data` | 当前测试场景的固定、有序输入数组；用例名对应真实公开业务接口 |
| `TestData[Name].Execute(Module, Data)` | 只映射参数并调用真实接口，不执行内部函数替代入口，不放业务算法 |
| `Run(Name)` | 获取真实模块、查找用例、选择数据、调用接口、记录结果；不得混入生产业务处理 |

通用结构示例：

```lua
local ModuleInterfaceTest = {}
local LogPrefix = "[ModuleInterfaceTest]"
local RunCounts = {}

local TestData = {
    PublicOperation = {
        Data = {
            { Input = "sample-a" },
            { Input = "sample-b" },
        },
        Execute = function(Module, Data)
            return Module:PublicOperation(Data.Input)
        end,
    },
}
```

`PublicOperation`、参数和字符串仅表示结构，不是项目必须提供的接口或有效业务数据。实际编写时替换为真实公开接口及已确认的场景输入；新增用例只扩展 `TestData`，不在通用 Runner 中增加业务分支。测试模块最终返回显式 table，并按以下协议实现 `Run`。

### Run 执行协议与数据规则

1. 获取当前真实模块；确认运行前置条件，再检查 `TestData[Name]` 及 `Execute`。
2. 对有数据的用例检查非空数组；按名称计数，使用 `(RunCounts[Name] - 1) % DataCount + 1` 轮换选取数据，日志始终记录 `Name` 和 `Index`。无参数接口允许不配置 `Data`。
3. 调用 `Execute(Module, Data)`；返回值按被测接口真实契约解释，不能统一把 `nil` 当作失败，也不能统一把“未抛错”当作业务成功。
4. 记录实际结果与验证范围。同步异常向调用者传播；需要 Runner 捕获并收尾时用 `xpcall` 保留 traceback、标记失败，不返回假成功。
5. 切换运行环境或会话、重新开始场景或销毁测试时复位计数并清理本次测试的资源。自动回归必须能明确指定数据索引或从复位状态按固定顺序遍历，不能依赖之前手动调用次数。

本类手动场景模板的输入固定写在 `TestData`，不在 `Run` 中动态读表格或外部业务参数。固定值可根据已确认的配置、数据表、资源和当前场景选取，并记录来源与资源前置条件；运行时业务仍使用真实资源。外部消息用例可构造符合真实协议的 DTO/结构体并送入公开消息入口，但不能据此声称真实网络传输已验证。

数据数组必须有固定顺序且无空洞。输入不得被被测接口污染；接口会修改 table 时，为每次执行构造独立输入。会改变业务状态的用例必须声明前置状态与执行顺序，结束后通过公开接口恢复基线；无法恢复时明确要求重建专用测试环境，不修改生产数据或共享资源。

### 结果语义与调用链验证

- `Execute(...) == true` 仅适用于接口明确返回 boolean 的场景。返回值表示受理时，只能记录为 `bAccepted`，不能命名或报告为完整 `bPassed`。
- 无返回值接口调用后的 `return true` 仅表示同步调用结束；必须查询真实结果，或明确报告“已调用、未断言”，不能伪造受理或测试通过。
- 用例只有同时满足预期返回契约和可观察业务结果才可计为通过。失败输入也可作为成功的回归用例：验证预期拒绝及状态未被污染，而不是把所有 `false` 都当作测试失败。
- 根据接口契约验证最终输出、状态变化或副作用。选择项目实际公开查询、事件或回调，不臆造 getter，不断言私有实现细节。
- 异步接口区分受理和完成，通过实际回调/事件或有界等待验证最终状态，超时为失败。不得用固定延时或打印成功代替断言，并清理计时器和事件订阅。
- 需要自动结果验证时按需为用例增加 `Verify`、准备/清理或异步完成协议，沿用项目已有测试设施；不强制所有手动接口探针引入大型框架。
- 关键流程至少记录真实入口、数据索引、关键参数、预期/实际结果和失败所在层。只运行接口探针时明确标记验证范围，不宣称整个调用链、网络或所有运行环境通过。

测试日志同样遵守 `lua-code-style` 的日志格式，例如：

```text
[ModuleInterfaceTest] Error=>Run  被测模块尚未初始化
[ModuleInterfaceTest] Info=>Run  Name=PublicOperation, Index=1, bAccepted=true, Verification=AcceptanceOnly
```

日志必须包含类型与函数标识符（`类名/模块名=>函数名`）。回归覆盖至少考虑合法输入、非法/缺失参数、重复调用，以及当前接口实际存在的生命周期边界；已发现的问题关联模块 `bugs.md` 和对应 Bug 文档。

## 验证方式

多次 require；重复 init/dispose；模块隔离测试；协程取消和异常；热更前后旧/新实例矩阵；GC 后宿主句柄泄漏；历史存档迁移；LuaLS、Luacheck、Busted；PUC Lua/LuaJIT/目标宿主分别运行兼容测试。
