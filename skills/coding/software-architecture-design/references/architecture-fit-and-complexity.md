# 架构适配与复杂度

## 适用场景

任何新项目、子系统、重大重构或架构评审都先读取本文件。

## 决策问题

先量化业务变化率、领域复杂度、团队数量、部署独立性、负载差异、故障隔离、一致性、延迟与运维能力。架构必须解决已证实的约束，而不是展示模式完整度。

## 候选方案与取舍

| 场景 | 优先候选 | 升级信号 |
| --- | --- | --- |
| 小型工具、稳定 CRUD | 直接结构或轻量分层 | 规则复杂、外部依赖增多 |
| 多业务能力、共同部署 | 模块化单体 | 独立团队/发布/扩缩容/隔离需求成熟 |
| 核心规则复杂、多入口多基础设施 | 端口与适配器 | 不同模块出现独立部署需求 |
| 边界稳定且需独立运维 | 服务化 | 收益持续大于网络、一致性和运维成本 |

分层、六边形、整洁架构不是互斥品牌。统一的是边界、依赖和验证，不是目录形状。限界上下文是模块/服务候选边界，不自动等于部署单元。

## 强制约束

- MUST 记录首要质量属性及可测场景。
- MUST 选择满足当前约束的最小结构。
- MUST 说明新增复杂度、所有者和退出条件。
- MUST NOT 用代码行数、表数量或“以后可能需要”作为微服务依据。
- SHOULD 从模块化单体开始，除非独立部署价值和运维能力已有证据。

## 反模式

模式先行；所有模块套同一层数；一类一接口；分布式单体；共享数据库却宣称服务自治；用空转 Controller/Service/Manager/Repository 证明“分层”。

## 验证方式

建立质量属性场景：触发者、环境、受影响对象、响应、量化指标。评审每个边界是否拥有明确职责、数据与团队；用依赖测试和部署证据验证，而非看架构图。
