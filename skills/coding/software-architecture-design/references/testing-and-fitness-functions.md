# 测试与架构适应度函数

## 适用场景

把架构约束转成持续反馈，设计测试组合与发布门禁。

## 决策问题

从质量属性场景和风险推导验证，而不是追求测试数量。区分静态结构、局部行为、组件协作、契约、完整链路、性能、故障与安全。

## 候选方案与取舍

- 单元/属性测试：快速证明规则和不变量。
- 架构测试：证明依赖、包、模块与循环约束。
- 集成/契约测试：证明边界装配和兼容。
- 少量 E2E：证明关键完整链路。
- 性能/故障/恢复演练：证明非功能属性。

## 强制约束

- MUST 为每项关键适应度函数记录风险、阈值依据、频率、所有者和失败处置。
- MUST 同时采用硬门禁、趋势指标和周期演练。
- MUST 为架构规则准备已知违规样例，证明测试会失败。
- MUST NOT 用覆盖率、测试数量或架构工具替代业务正确性。
- SHOULD 让高层失败沉淀为更低层的精确回归测试。

## 反模式

大量脆弱 E2E；永久冻结遗留违规；契约测试验证所有业务；静态依赖测试声称证明运行时安全；阈值无业务依据且永不复审。

## 验证方式

统计各层执行时间、非确定失败、维护成本和缺陷发现层级；CI 验证依赖/契约/兼容/预算；周期执行恢复、过载和安全演练；复审过期函数。
