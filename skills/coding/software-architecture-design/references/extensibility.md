# 扩展性设计

## 适用场景

插件、策略、玩法/规则扩展、第三方集成和频繁变化的产品能力。

## 决策问题

先识别已经发生的变化轴：算法、数据源、渠道、平台、对象类型、工作流步骤或部署单元。扩展点只隔离真实变化，不为猜测创建框架。

## 候选方案与取舍

- 参数/配置：变化仅为数据时优先。
- 组合与策略：算法可替换且共享稳定契约。
- 注册表/插件：第三方或独立团队需要发现与装配。
- 事件订阅：多个独立反应，不保证即时结果。
- 继承：存在稳定 is-a 语义和受控变体时谨慎使用。

## 强制约束

- MUST 定义扩展契约、生命周期、线程模型、错误隔离、版本和权限。
- MUST 保持组合根集中装配，业务代码不得到处 Service Locate。
- MUST 为插件能力设置最小权限和资源预算。
- MUST NOT 用巨大 switch、复制粘贴或反射扫描隐藏无边界扩展。
- MUST NOT 为单一实现制造接口、工厂、Provider、Manager 多层包装。
- SHOULD 让默认路径简单，扩展路径显式付费。

## 反模式

继承层级承载多个变化轴；公共基类暴露所有内部状态；事件总线成为不可追踪控制流；插件直接访问宿主数据库；“通用框架”没有第二个真实消费者。

## 验证方式

用新增一个真实变体做演练，记录需要修改的模块数；插件兼容矩阵；未注册/重复注册/失败插件测试；依赖图；扩展卸载和资源清理；权限和配额验证。
