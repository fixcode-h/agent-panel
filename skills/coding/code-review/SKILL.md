# 代码评审

评审只读：读代码、跑检查、写结论，不改被评审的代码（调用方明确要求「评审并修复」时除外）。宁可少报，不报错——每条发现在提出前都要对着代码核实过。

## 1. 先弄清意图

动手看 diff 之前，先确定这次改动要做什么、范围是否已经约定：

- 读调用方给的需求、任务说明、OpenSpec change（`proposal.md`、`specs/`、`design.md`、`tasks.md`）、Issue 或 PR 描述，提炼出验收标准和非目标。
- 查相关的历史决定：模块文档、`bugs.md`、ADR、相关提交或 PR。改动和已有决定冲突时要指出出处。
- 读项目约定：`AGENTS.md` / `CLAUDE.md`、贡献指南、lint/格式配置。涉及 C++/UE 时配合 `cpp-code-style` 技能，涉及 Lua 时配合 `lua-code-style` 技能。按项目约定评审，不按个人偏好。
- 没有任何需求说明时，从提交说明和代码推断意图，并在结论里写明「意图为推断」。

## 2. 限定范围读 diff

只评审本次改动，不顺手评审整个项目。先确定基线和文件范围：

- **Git**：`git status --short`；分支改动用 `git diff <基线>...HEAD -- <路径>`，未提交改动用 `git diff` 和 `git diff --cached`；`git log --oneline <基线>..HEAD` 看提交拆分。
- **Perforce**：`p4 opened -c <changelist>` 列文件；未提交改动用 `p4 diff -du <文件或 //路径/...>`；已提交的 changelist 用 `p4 describe -du <cl>`，shelve 用 `p4 describe -S -du <cl>`。只读，不 sync、不 revert、不 submit。
- 调用方给了文件清单或 diff 时，以它为准。
- 读 diff 时打开相关文件的上下文（调用方、被调用方、测试），不能只看变更行就下结论。

## 3. 找什么

### 🛑 必须改（阻塞）

- Bug、逻辑错误、边界条件遗漏、资源泄漏、并发问题、安全问题。
- 没有满足需求或验收标准；做了非目标里的事。
- 与已有决定（ADR、模块文档、历史 Bug 记录）冲突，而改动里没有说明理由。
- 未说明或未经确认的破坏性变更（见下文）。
- 下游会被破坏：例如改了某个错误信息字符串，而别处的条件判断依赖它。
- 新行为没有测试：新分支、校验和错误路径都要覆盖，不只覆盖正常路径。项目确实无法自动测试时，要有可复现的验证说明。
- 重新实现了项目里已有的可复用逻辑：先在项目的公共模块、工具函数、引擎或框架、标准库里找等价实现，找到就指出位置。
- 违反项目约定，或项目规定的测试 / lint / 构建失败。区分「实际运行后失败」和「没有运行」。

### 💭 建议（不阻塞）

- 能明显减少代码量或复杂度的重构。
- 有不同取舍的替代方案（写清取舍）。
- 只在局部实现、但值得提到公共模块的逻辑。
- 工具链能自动修的现代化写法、lint 警告。

### 💅 细节（不阻塞）

- 命名、可读性、注释过长或没有信息量。
- 格式不一致（项目有格式化工具时只建议运行它，不逐条列）。

### 范围与可审查性（不阻塞，单独一节）

除了代码本身，也看改动的形状，给出让它更容易审查的建议：

- **范围**：一次改动只解决一件事。夹带了无关的重构或修复时，指出应该拆出去的部分。
- **提交 / changelist 拆分**：大量机械重复的改动放在一个提交里没问题；但复杂逻辑挤在一个提交里、或历史难以跟读时，读完代码后给出可审查的拆分建议。P4 项目按项目的 pending 分桶规则检查文件是否放对了 changelist。

## 4. 什么算破坏性变更

改动可能是有意的、有道理的、也写了说明，但仍然是破坏性的。不要因为「这是改进」就放过。按「谁在消费这个行为」判断：

- **给人看、人可以临场应对的**（交互界面上的文案、可以重新选择的交互流程）：一般不算破坏性。
- **被程序或数据依赖的**：任何变化都算破坏性。例如：
  - 公共 API、导出函数、类或接口的签名、默认值、行为；
  - 给脚本或其他程序解析的输出（JSON 字段、默认输出格式、stdout 与 stderr 的分工）、退出码、原来成功现在报错；
  - 命令行参数、配置项、子命令的改名，或收紧了原来能接受的输入；
  - 文件格式、存档 / 序列化数据、数据库结构、配置表字段、网络协议、资源路径；
  - 暴露给脚本层或编辑器的接口（例如 UE 的 Blueprint / Lua 可调用的函数和属性、反射名称）；
  - 被其他代码依赖的错误信息、事件名、日志关键字。

对这类变化，要么改动里有说明并经过确认，要么提供兼容或迁移路径；都没有就列为 🛑。

## 5. 安全问题

发现漏洞时，评审结论里只写「存在安全问题，需要按项目的安全流程处理」和必要的位置，不在公开场合（公开 PR 评论、公开 Issue）贴利用细节；按项目的 `SECURITY.md` 或安全流程处理。

## 6. 怎么报告

按严重程度分组：先 🛑 必须改，再 💭 建议，再 💅 细节，最后「范围与可审查性」。没有发现的分组写「无」。

每条发现：

```markdown
🛑 必须改：<一句话概括>

位置：path/to/file.ext:123（函数或类名）
证据：<实际看到的代码、运行的命令和输出、违反的需求条目或约定出处>
影响：<从使用者角度描述，例如「玩家在背包满时拾取会丢失物品」>
建议：<怎么改；需要时附代码块>
```

- 每条都必须有位置和证据。没有证据的猜测不写成发现；确实拿不准时写成「💭 建议：请确认……」，并说明缺少哪项证据。
- 先用平实的话说问题，再展开技术细节。
- 有价值的参考（拒绝过同样做法的历史 PR、引入这段代码的提交、相关 ADR）放在「参考」里。

结尾给出：

- **结论**：`通过` 或 `需修改`（有任何 🛑 即为 `需修改`）。工作流按这个结论走分支时，结论单独一行写在最后。
- **已运行的检查**：命令和结果；没有运行的检查写明原因。
- **评审范围**：基线、文件清单，以及没有评审到的部分。
