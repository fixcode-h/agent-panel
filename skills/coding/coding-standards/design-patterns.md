# 设计模式：先判断，再应用

模式是解决某一类扩展性问题的手段，不是目标。按「要解决什么问题」选，不按 GoF 目录背。

## 怎么用（每次新建模块、或一类东西要继续加时走一遍）

1. **说出问题**：这次的代码会在哪个方向上变？用一句话写出来，并举出**已经存在或需求明确的第二个实例**（第二种格式、第二个平台、第二种状态……）。举不出来就停在这里，写直白的代码。
2. **先看项目里已经有的**：项目里同类问题已经用了什么模式（例如已有一张注册表、一套状态机、一个适配层），**跟着用同一个**，不引入第二种做法。
3. **对照下面的清单选最轻的那个**：能用数据表 / 配置解决的不用策略类；能用函数解决的不用类层级。
4. **按「关键要求」落地**：每个模式的关键要求和坑都要满足，满足不了说明选错了。
5. **用扩展点数验收**：模拟「再加一种」需要改几处。理想是只新增文件或一行注册，实际不超过 2 处；超过就说明模式没用对。
6. **写下来**：结果里一句话说明用了什么模式、解决哪种变化、新增一种要改哪里；跨模块的写进模块文档。

## 2.1 扩展点类：新增功能不改老代码

| 模式            | 解决的问题              | 关键要求                                                          |
| --------------- | ----------------------- | ----------------------------------------------------------------- |
| 注册表 / 自注册 | 加新类型不用改 `switch` | 启动时按名字注册，用字符串 / 枚举做 key；重复注册、找不到都要报错 |
| 工厂            | 创建逻辑和使用分离      | 返回抽象接口，调用方不 `new` 具体类；通常和注册表一起用           |
| 策略            | 同一流程换算法          | 接口 + 多个实现，运行时按配置选择                                 |
| 插件 / 钩子     | 外部扩展不改核心        | 显式声明扩展点、调用时机、出错隔离和卸载                          |

这是「开闭原则」真正的落地方式。**只有一个实现的抽象层是负债**，等出现第二个实现再抽。

## 2.2 状态与流程类

| 模式                    | 适用                                      | 坑                                                              |
| ----------------------- | ----------------------------------------- | --------------------------------------------------------------- |
| 有限状态机 / 分层状态机 | 角色状态、UI 流程、连接状态、任务生命周期 | 状态转移必须集中定义（一张转移表），禁止各处随意 `setState`     |
| 状态模式                | 每个状态的行为复杂、状态内自带数据        | 别和「数据上的状态字段」混为一谈；简单的用状态字段 + 转移表就够 |
| 命令模式                | 撤销 / 重做、网络回放、操作队列           | 命令要可序列化才有复用价值                                      |
| 管道 / 中间件           | 请求处理链、消息过滤                      | 顺序必须显式配置，禁止隐式依赖注册顺序                          |
| 模板方法（谨慎）        | 固定骨架 + 可变步骤                       | 优先用组合（策略 + 钩子）代替继承                               |

## 2.3 通信与解耦类

- **观察者 / 事件总线**：解耦发布和订阅，最大风险是调用链消失。规则：事件名强类型（常量或枚举，不手写字符串）；订阅必须能反注册（防悬空引用），谁订阅谁取消；单次事件链路深度设上限；关键流程不全靠事件，关键路径要能顺着调用栈读出来。
- **依赖注入 / 依赖倒置**：模块只依赖接口或参数，测试时能替换。这是可测试性的前提，也是分层的基石。依赖在组合根（入口处）集中装配，业务代码不到处查全局。
- **中介者**：多个模块互相引用时收敛到一个协调者，避免网状依赖。
- **适配器**：第三方 SDK、平台差异（Android / iOS / PC、不同 CLI、不同存储）全部隔离在适配层后面，业务代码不认识平台。平台差异写成适配器的数据或实现，不在业务里按平台名写分支。

## 2.4 结构与性能类

- **组合优于继承**：树形结构（UI、场景、技能树）用组合；继承层级不超过 2 层。
- **组件模式 / 实体组件**：能力可插拔，避免「上帝类」。
- **对象池**：只在高频创建销毁（子弹、特效、网络包）且有测量证明是瓶颈时用；取出时必须完整重置，防「池化对象残留状态」。
- **门面**：给复杂子系统一个窄入口，限制外部依赖面。
- **双缓冲 / 快照**：配置热更、状态回滚、帧间一致性；新数据完整准备好后一次性切换，读的人永远拿到一致的版本。

## 2.5 明确不要做的（过度设计）

- **单例滥用**：全局可变单例 = 隐式全局变量，测试无法隔离，初始化顺序不可控。需要「只有一个」时由入口创建一份再传下去。
- **为模式而模式**：一个接口 + 一个实现 = 纯成本。
- **过早抽象**：第一个需求就设计成「支持任意未来扩展」，通常猜错方向。
- **事件满天飞**：所有交互都改成事件，最后没人知道谁调了谁。
- **深继承 + 虚函数重写**：改父类炸全部子类。
- **配置万能化**：什么都能配 = 什么都不可控；配置项也要有 schema、默认值和校验。

## 改已有代码时引入模式

- 先在现有结构里找到已经出现重复的地方（一串 `if` / `switch`、三处复制的相似逻辑、按平台名写的分支），以它为起点重构，不凭空加层。
- 重构和功能改动分开：先在不改行为的前提下引入模式（测试保持全绿），再在新结构上加功能。
- 只改这次任务碰到的部分；更大范围的重构写成建议交给发起方，不顺手做。
