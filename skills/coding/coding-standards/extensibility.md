# 扩展点与框架设计

新建模块、子系统、框架，或要让一类东西「能继续加」时读这份。原则：**在真实的变化方向上留口子，其他地方保持简单**。

## 先回答这几个问题

1. **会变的是什么**：已经出现或明确会出现的变化轴是哪个（平台、数据源、格式、算法、对象类型、流程步骤）？说不出第二个具体实例的，就先不做扩展点。
2. **谁拥有什么**：每块状态和数据谁创建、谁能改、谁负责销毁、在哪里持久化。一个数据只有一个写入方。
3. **依赖朝哪边**：底层（通用能力、数据、平台适配）不依赖上层（业务、界面）。核心逻辑不直接依赖 UI、数据库、网络 SDK 这类细节，细节通过参数或接口传进来。
4. **对外暴露什么**：模块的公开入口尽量少，内部实现默认不可见。别的模块只通过公开入口用它，不碰内部文件和数据。

## 比设计模式更决定可扩展性的六件事

模式只是手段，下面这些才是可扩展性的真实来源：

1. **依赖方向单向且显式**：分层（表现 / 逻辑 / 数据 / 平台），只允许上层依赖下层，禁止反向和跨层跳跃；能用 lint 或构建规则强制最好。
2. **稳定契约层 vs 易变实现层**：接口、事件名、存档格式、网络协议、配置结构属于契约，改动要走版本演进；实现随便换。
3. **版本兼容策略**：存档 / 配置 / 协议都带版本号和迁移函数，读到旧版本先迁移再用，否则一次升级就把已有数据弄坏。
4. **扩展点数得清**：新加一个角色 / 技能 / 关卡 / 平台要改几个文件？这是最好用的可扩展性度量（理想：只新增文件，不改核心；实际：≤ 2 处）。
5. **可测试性作为设计约束**：类能不能在没有引擎 / 网络 / 文件系统的环境下构造和测试？不能就说明耦合过重，把依赖改成参数传入。
6. **可观测性**：关键路径有日志、关键状态有快照、失败有明确的错误码和上下文。

## 按变化选手段（从轻到重）

| 变化是什么                         | 用什么                                      |
| ---------------------------------- | ------------------------------------------- |
| 只是数值、文案、开关不同           | 参数 / 配置（见 `configuration.md`）        |
| 一组同类条目各有几个字段不同       | 数据表 + 一段遍历它的通用逻辑               |
| 算法或处理方式不同，但输入输出一样 | 策略函数 / 接口，用表或注册表按键选择       |
| 第三方或其他模块要往里加东西       | 注册表 / 插件：明确注册时机、契约、出错隔离 |
| 多个独立的反应，不需要立即结果     | 事件订阅（但必须同步完成的命令不用事件）    |
| 稳定的 is-a 关系且变体受控         | 继承（谨慎，层级不超过两三层）              |

优先组合而不是继承；优先显式传入依赖，不到处全局查找（Service Locator / 单例）。每种模式的关键要求和坑见 `design-patterns.md`。

## 一个好的扩展点

- **加一种新情况只改一处**：加一条注册 / 一行数据 / 一个新文件，调用方不用动。
- **契约写清楚**：输入、输出、调用时机、线程、出错怎么办、生命周期，写在类型和注释里。
- **默认路径简单**：常用情况开箱即用，扩展的人才付出额外成本。
- **出错隔离**：一个扩展失败不拖垮整体，错误要报出来、带上是哪个扩展。
- **能被测试**：可以单独给一个扩展写测试，也能用一个假实现测宿主。

## 状态与生命周期

- 重要的生命周期用一个状态字段 + 明确的转换（例如 `idle → running → done / failed`），不用几个布尔组合。
- 对象构造完整后才对外可见，不让别人拿到半初始化的对象。
- 共享的配置和定义用不可变快照；实例自己的可变状态和共享定义分开。
- 订阅、定时器、后台任务、句柄由创建者负责释放；关闭时等它们真正结束，不 fire-and-forget。

## 搭骨架

- 只搭最小可构建、可测试的骨架：目录、入口、依赖配置、一个基础测试，跑通构建再往里加东西。
- 新模块的目录、命名、注册方式照项目里最近的同类模块来。
- 模块的职责、入口、依赖写进项目的模块文档（按 `project-documentation` 的规则）。

## 反模式

- 只有一个实现的接口 + 工厂 + Provider + Manager 层层包装。
- 叫 `Common` / `Utils` / `Manager` 的大杂烩，没有明确职责。
- 用一个巨大的 `switch` 或复制粘贴来承载所有变体。
- 继承层级同时承载好几个变化方向。
- 事件总线变成看不清的控制流，或者用事件做必须同步拿结果的查询。
- 为了「以后可能要」加参数、开关、抽象层，但现在没有第二个使用者。
