# 编码规范

目标是让代码**改一处就生效所有地方、加一种情况不用到处改、别人读得懂**。这些规则不分语言和项目，放到哪里都适用；项目自己有更具体的约定时，以项目为准。

细则按需读，本目录下：

| 什么时候                                             | 读                   |
| ---------------------------------------------------- | -------------------- |
| 碰到数值、文案、路径、开关、表格数据、要不要做成配置 | `configuration.md`   |
| 新建模块 / 子系统 / 框架，或者要加插件、策略、扩展点 | `extensibility.md`   |
| 判断能不能用、该用哪个设计模式，以及怎么落地         | `design-patterns.md` |
| 交付前自查（每次改完都过一遍）                       | 本文末「交付前自查」 |

## 一、先读再写

1. **读周边代码**：改一个文件前先读它和它的邻居（同目录的同类文件、调用方、被调用方）。新代码的命名、目录、错误处理、日志、注册方式**跟着最近的同类走**，不引入第二套写法。
2. **先找已有的**：要写工具函数、常量、类型、组件之前，先在项目里搜有没有现成的（`utils`、`shared`、`common`、`constants`、`config` 一类目录，以及同名或近义的函数）。有就复用或小幅扩展它，不另写一份相似的。
3. **找到事实源**：一个值、一条规则、一个类型在项目里由谁定义，就从那里取。不在使用处复制一份「差不多的」。
4. **弄清边界再动手**：这段代码属于哪个模块、谁调用它、改了会影响谁。跨模块的改动先确认依赖方向（底层不依赖上层）。

## 二、不写死：单一事实源

- **魔法数值、字符串不散落在逻辑里**。超时、重试次数、上限、阈值、尺寸、颜色、端口、路径、文件名、URL、事件名、存储键、正则、提示文案……第二次用到、或者有人可能要调的，都提成**有名字的常量或配置项**，所有用到的地方引用这个名字。改一处就全局生效。
- **一个概念只有一个定义**：枚举值、状态名、字段名、默认值、校验规则只定义一次，其他地方（前后端、文档生成、测试）从定义推导，不手抄。列表型的数据（选项、映射、路由、命令）写成**数据表**，逻辑遍历表，而不是写一串 `if` / `switch`。
- **放在哪里**：模块内部用的放模块顶部的常量区；跨模块共享的放项目已有的常量 / 配置文件（没有就新建一个，并告诉调用方从这里取）；用户或策划要改的放配置文件 / 数据表，带默认值和校验。细则见 `configuration.md`。
- **派生值靠计算，不靠同步**：能从别的值算出来的（总数、比例、显示名、版本号）就算，不另存一份再想办法保持一致。
- 例外：`0`、`1`、`-1`、`''`、`[]` 这类含义一目了然的字面量，以及测试里的期望值，不用强行提常量。

## 三、可扩展，但不过度设计

- **按真实的变化方向留口子**：已经出现第二种情况、或需求明确会加（多个平台、多种格式、多个 CLI、多个角色）时，把「会变的部分」抽成数据或可替换的实现（配置项、注册表、策略函数、接口），让新增一种情况只需要**加一条数据或一个实现**，不用改调用方。
- **新增一种情况要改几处**是衡量标准：超过一处（例如要同时改 `switch`、类型、文案、测试数据），就说明该收成一个表或注册点。
- **不为假想的需求加层**：只有一个实现时不建接口 + 工厂 + 管理器；不加没人用的参数和开关；第三次重复再抽象（两次重复可以先忍，但要放在一起、写清楚）。
- **对扩展开放的点要有契约**：输入输出的类型、什么时候调用、出错怎么办、谁负责清理，写在类型或注释里。
- **先判断有没有对口的设计模式**：一类东西要继续加时，按 `design-patterns.md` 的步骤说出变化方向、看项目里已有的做法、选最轻的模式（注册表、策略、状态机、适配器、门面……）并按它的关键要求落地；举不出第二个真实实例就不套模式。
- 新建模块 / 子系统时的分层、依赖方向、契约与版本、生命周期，见 `extensibility.md`。

## 四、代码本身

- **命名说清意图**：变量和函数名说「是什么 / 做什么」，带单位（`timeoutMs`、`sizeBytes`）；布尔值用 `is` / `has` / `can` / `should`；同一个概念全项目一个叫法。不用 `data`、`info`、`tmp`、`flag`、`handle2` 这类空名字。
- **函数只做一件事**：一个函数能用一句话说清它做什么；超过一屏、嵌套超过三层、参数超过四五个，考虑拆分或改传对象。先处理异常情况提前返回，主流程不缩进在一层层 `if` 里。
- **类型和数据结构表达约束**：能用类型、枚举、联合类型、`readonly` / `const` 表达的约束，不靠注释和约定；互斥的状态用一个状态字段，不用几个布尔组合。
- **副作用集中**：计算和 I/O 分开，纯逻辑写成输入 → 输出的函数（好测、好复用）；读写文件、网络、全局状态放在边界层。
- **错误不吞**：捕获异常要么处理、要么带上下文重新抛出 / 上报；不写空 `catch`，不用默认值掩盖失败。外部输入（用户输入、文件、网络、配置）在边界处校验一次，内部信任已校验的数据，不层层重复判空。
- **状态和资源成对**：订阅 / 取消订阅、打开 / 关闭、定时器 / 清除、加锁 / 解锁写在一起；谁创建谁释放；异步回调回来时重新确认对象还在。
- **并发与时序**：不依赖「刚好先执行」；共享可变状态要么只有一个所有者，要么有明确的同步。等待用条件和超时，不用固定 `sleep`。
- **注释写「为什么」**：代码能说清「做什么」，注释讲原因、约束、坑和取舍。改了代码同步改注释，过期的注释比没有更糟。
- **兼容已有数据**：改数据格式、字段名、枚举值、存档、接口时，考虑旧数据怎么读（迁移、默认值、兼容层），不让已有用户的数据坏掉。

## 五、改动范围

- **只改任务需要的**：不顺手重排、改名、格式化无关代码，不改无关文件；看到别的问题记下来交给发起方，不在这次里改。
- **改到底**：改了一个定义，就把所有引用、类型、测试、文档、翻译一起更新；删了功能，就把它的死代码、配置、测试一起删干净，不留注释掉的代码和「以后可能用」的分支。
- **不留临时物**：调试日志、打印、临时文件、硬编码的测试数据、`TODO` 不提交（确实要留的 `TODO` 写清原因和后续怎么做）。

## 交付前自查

改完、报告完成前，把这次的差异（`git diff` 或等价物）从头读一遍，逐条对照：

- [ ] 有没有新出现的魔法数值 / 字符串 / 路径？用到两处以上或可能要调的，提成常量或配置了吗？
- [ ] 有没有和项目里已有函数、常量、类型重复的新代码？
- [ ] 同一个概念有没有在两个地方各定义一份？
- [ ] 新增一种同类情况，需要改几处？超过一处的收成表或注册点了吗？
- [ ] 有没有只有一个实现的接口、没人用的参数、为将来预留的空壳？
- [ ] 用了设计模式的，满足了它的关键要求吗（状态转移集中定义、订阅可反注册、注册重复会报错……）？
- [ ] 命名、目录、错误处理、日志的写法和周边代码一致吗？
- [ ] 错误有没有被吞掉？外部输入在边界校验了吗？
- [ ] 订阅、定时器、句柄、文件有没有成对释放？
- [ ] 改了定义，引用、测试、文档、翻译都跟着改了吗？旧数据还能读吗？
- [ ] 有没有调试代码、注释掉的代码、无关文件混进来？

不符合的先改掉再交付；故意不改的（例如为了不扩大范围）在结果里写明原因。
