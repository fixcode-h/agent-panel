# 系统化调试

先找到原因再修。随手改会浪费时间，还会改出新的 Bug；只把症状压下去的修法会把问题藏起来。

## 走哪条路

| 情况                                                                                              | 走哪条                                           |
| ------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 用户报的、要查原因的 Bug：父对话派单写了 kind: "bug"（有 submit_diagnosis 工具），或用户发了 /bug | 完整流程（下面的「用户报的 Bug：完整查找流程」） |
| 自己写代码、自测、跑测试、评审或测试验收报出的问题                                                | 简易版（下面的「修自己发现的问题」）             |
| 只读的排查分析（分析角色）                                                                        | 完整流程的前五个阶段，改代码的部分写成建议       |

## 修自己发现的问题（简易版）

你自己写代码、自测、跑测试、评审或测试验收报出来的问题，按这个简易版查和修，不交诊断报告、不用用户确认。用户报的 Bug 不按这个：父对话派单写了 kind: "bug"（你有 submit_diagnosis 工具），或者用户发了 /bug，面板会另给完整流程，按那个做。

1. 现象：失败的测试名、断言或报错原文、评审意见原文，照抄不改写；一堆错只盯第一条。
2. 定位：从出错点往回读到入口，按「调用栈怎么写」写出 `calltree` 代码块；用到日志的先在代码里找到打印它的位置。
3. 根因：证据链三环（现象 ← 报错或测试输出 ← 代码 path:line 的条件或赋值）齐了才动手；推不通就先写一个失败用例或加临时日志（前缀 `[排查-<主题>]`）确认，不猜着改。是不是这次改动引入的看自己的 diff 就够；确认改动之前就坏（在独立 worktree 里用改动前的版本跑一次，不动用户的工作区），写一句「历史遗留 / 外部依赖」和依据，列进顺带发现。
4. 修：修根因，写一句为什么这样修；把报错 try/catch 掉、加判空绕过、加重试、在原逻辑外面再兜底一层（再扫一遍、多加一条降级分支）让它「不报了」都不算修。影响面只看要改的函数的调用方和同类写法（同一模块里搜一遍，是同一个原因的一起修）；修法要动接口、数据格式或别的模块时，写两三句比较不同修法再选。
5. 验证：能写测试的先写会失败的用例，改前失败、改后通过；再跑相关的测试和快速检查。

- 同一个问题修了三次还不对，停下来写清查过什么、排除了什么、卡在哪，交给父对话或用户，不在上一次的修法上再叠一层。
- `[排查-…]` 临时日志修完删掉。
- Bug 记录只记用户报的 Bug，自己发现的不写；值得长期记住的写项目教训。交接摘要里写一段：现象、根因（path:line）、怎么修的、验证结果。

### 调用栈怎么写

讲调用路径时写一个 `calltree` 代码块（面板画成树），不写「a → b → c」一长串。一行一跳，缩进两格表示被上一行调用：

```calltree
onDelete  web/src/cart/CartPage.tsx:88  — 点删除  {L1}
  removeItem(id)  web/src/cart/store.ts:48  — 算剩几件  [left=0]
    ! if (left === 0) return  web/src/cart/store.ts:51  — 剩 0 件提前返回  <left === 0 → 真>  [left=0 => 1]
    ~ emit('cart:change')  web/src/cart/store.ts:52  — 该派发却没派发
      => 事件 cart:change
      ? 现象：角标停在 1  web/src/cart/Badge.tsx:15
```

- 函数和位置之间、各段之间至少两个空格；`— ` 后面是这一跳做了什么。
- 行首记号：`!` 出错点、`~` 该执行却没执行、`?` 现象出现的地方、`-` 无关的旁支；`=> 说明` 写在跨异步、事件、进程的那一跳前面。
- 尾巴：`<条件 → 走了哪边>`、`[名字=实际 => 期望]`、`{L1 H2 Q3}` 挂的日志点、假设、原文编号。

## 用户报的 Bug：完整查找流程

这是用户报的、要查清原因的 Bug：要找得准（根因有证据、能解释全部现象、知道是哪次改动引入的），也要修得好（比较几种修法选最优，不引入新问题）。按下面八个阶段做，阶段可以回退（归因推不通回定位或时间线，修完验证不过回归因），不能跳。
起点：用户点名的模块或部分 → 父对话交来的模块 → 都没有时按报错原文、堆栈和 MODULE-MAP 先定到一个模块。父对话已经排除的不要重查。先查这个模块的 `bugs.md` 和历史 Bug 记录：命中的把它的复现条件、根因和排查路径当作优先假设，但要重新验证，不直接套用。

### 级别：按难度定要求

| 级别                                                                                                                       | 典型情况                                                                   | 要求的差别                                                                                                                             |
| -------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 快速                                                                                                                       | 有报错堆栈直接指到出错行、必现、根因读代码就能确定、改一个文件             | 时间线可以只写一行（出错行的 blame 结果）；修复设计可以只有一个方案，但写一句为什么没有别的合理修法                                    |
| 标准                                                                                                                       | 默认                                                                       | 八个阶段全做；候选方案至少两个                                                                                                         |
| 深入                                                                                                                       | 偶发、并发和时序、跨模块、回归但找不到引入点、改了三次不对、只在某些环境出 | 涉及状态的必须排状态流转时间线、变更时间线要完整；引入点要用二分或差异法定下来；假设表至少两个假设；偶发的按原频率估算运行次数并写统计 |
| 派单写了级别就从它开始；没写的自己判断。查的过程中发现更难就升级并写明原因；要降级写明理由（用户审阅时看得到），不悄悄降。 |

### 1. 立案：钉住现象，再去读代码

- 读代码之前先把现象钉死，写成一张「现象卡」：期望是什么、实际是什么（报错原文、截图里的字、错误的值）、怎么触发（步骤、输入、环境、版本）、多久出一次（必现 / 偶发）、什么时候开始的（以前好过吗，哪次改动或升级之后坏的）。拿不到的项写「未知」，不补猜。
- 能复现的先复现一次（跑相关测试或命令、按步骤操作），拿到本轮的真实输出：复现一次抵得上读一小时代码。偶发的记下触发条件和频率，后面靠加日志抓。
- 现象是「一堆错」时只盯第一条，后面的多半是它引出来的；报错原文里的类名、键名、数字原样抄进搜索，不改写。

### 2. 定位：模块文档 → 模块代码 → 调用栈 → 日志（不能跳）

- 模块文档：先读 `MODULE-MAP.md` 找到模块，再读 `modules/<模块>/README.md` 和 `bugs.md` 里相似的历史 Bug；文档写清的入口、数据流直接用，不重新探。
- 模块代码：从文档给的入口文件开始，只读现象实际走的那条路径（入口 → 出错点）；用报错原文、函数名限定在模块目录里搜（按「搜索范围」的规则带排除），不通读整个模块、不扩散到其它模块。
- 调用栈：把这条路径写成树（有 update_bug_case 时记进 stack，每跳 id / parent / role；没有时按「调用栈怎么写」写 `calltree` 代码块），每一跳都是读过的代码。出错点写分支条件和当时的值、期望值；出错点之后本该执行却没执行的也写上（missed），一直写到现象出现的地方——这样用户一眼看出在哪走偏、偏了怎么变成现象。跨异步、事件、进程的地方标出边界。有报错堆栈时每一帧都要对得上（stackFrom 写 trace），对不上说明读错了路径，回到上一步。
- 最后才看日志：要用的每一条日志，先拿它的原文在代码里搜到打印它的位置（path:line），标在调用栈的哪一跳上；再按时间顺序对：哪一跳打了、哪一跳该打却没打（说明没走到）、打出来的值和那里的分支条件对不对得上。代码里搜不到出处的日志（别的进程、第三方库）写明来源，不拿它当这个模块的证据。
- 这一层排除了才往下一层：调用栈这一段读完了，或者日志、测试证明这一层的输入输出都对，才下到它调用的依赖或底层模块；每下一层先写一句「上一层为什么排除、依据是什么」。
- 控制深度：同一层读了不少代码还没有假设，就换成加日志或测试缩小范围，不再扩大阅读范围；换成加日志时按第 4 步「论证的日志一次加够」覆盖从入口到现象的整条调用栈，不是只在正在读的这一层加；下到第三层还没找到，停下来报告查过哪几层、各自的排除依据、下一步要加哪些日志或要用户提供什么。

### 调用栈怎么写

讲调用路径时写一个 `calltree` 代码块（面板画成树），不写「a → b → c」一长串。一行一跳，缩进两格表示被上一行调用：

```calltree
onDelete  web/src/cart/CartPage.tsx:88  — 点删除  {L1}
  removeItem(id)  web/src/cart/store.ts:48  — 算剩几件  [left=0]
    ! if (left === 0) return  web/src/cart/store.ts:51  — 剩 0 件提前返回  <left === 0 → 真>  [left=0 => 1]
    ~ emit('cart:change')  web/src/cart/store.ts:52  — 该派发却没派发
      => 事件 cart:change
      ? 现象：角标停在 1  web/src/cart/Badge.tsx:15
```

- 函数和位置之间、各段之间至少两个空格；`— ` 后面是这一跳做了什么。
- 行首记号：`!` 出错点、`~` 该执行却没执行、`?` 现象出现的地方、`-` 无关的旁支；`=> 说明` 写在跨异步、事件、进程的那一跳前面。
- 尾巴：`<条件 → 走了哪边>`、`[名字=实际 => 期望]`、`{L1 H2 Q3}` 挂的日志点、假设、原文编号。

### 3. 时间线：什么时候、按什么顺序坏的，那段时间里变了什么

两条线分别排，再对齐：现象时间线说明「哪一步先坏的」，变更时间线说明「坏之前变了什么」。

#### 看日志：先划定时间段，再排时间线

- 先定这次问题的时间段，只分析这一段：按现象卡里的触发时间、用户复现的时刻，定出起止（开始操作前一点 → 现象出现之后）；再用时间戳、本次运行的启动行、进程号、会话 / 请求 ID 把日志切到这一段。写明「分析范围：<文件> <起>–<止>（或第 X–Y 行），依据：……」。
  - 这一段以外的日志（之前几次运行、别的会话、轮转前的旧文件、以前排查留下的输出）不进分析，也不拿来当证据：旧报错可能早就修了，或者是另一个问题。同一个文件里有多次运行的，按启动行或进程号分开，只取这次的。
  - 日志没有时间戳、分不清哪段是这次的：复现前先记下文件当前的行数或大小（`wc -l`），复现后只看新增的部分（`tail -n +<行号+1>`）；能清空或换新文件的先换。时间段确实定不下来就问用户，不要整份一起看。
  - 对比实验例外：要比较好的一次和坏的一次、改前和改后、两台机器时，可以看两段或几段，但每段都标清来源和时间（「A 改前 10:02–10:05」「B 改后 10:20–10:23」），每条证据写明出自哪一段，不混着引用。
- 排事件时间线：把这一段里和现象相关的事件按时间排成表 `时间 | 来源（path:line 或进程） | 事件 | 关键值`，包括用户操作、请求和回调、异步任务的开始和结束、重试、报错；把现象出现的那一刻标出来。重点看「最后一个正常事件」和「第一个异常事件」之间发生了什么，问题通常就在这段间隙里；第一个异常之后的报错多半是连锁反应，先不追。多个进程或线程的日志按同一个时钟合并，时钟对不齐的写明偏差。
- 涉及状态的一定要梳理状态流转时间线：问题和状态有关时（状态机、status 字段、标志位、生命周期、连接 / 加载 / 任务状态、界面状态），先列出这段时间里每一次变化 `时间 | 旧状态 → 新状态 | 谁改的（path:line） | 由什么事件触发`，再从代码里整理出允许的流转（哪个状态能到哪个、由什么触发），逐条对照，找出：不该发生的流转、该发生却没发生的、顺序反了的、同一时刻被两处改（竞态）、改了没通知或通知了没改、异步回来时状态已经变了还照旧处理。日志里状态变化没打全时，先在每个改状态的地方加临时日志（旧值 → 新值、调用方、触发事件；只读的分析写成建议）再复现，不靠推测补中间状态。
- 修完复测时用同样的办法切出新的一段，排出新的时间线，和修前的逐条对比，说清哪一步变了。

#### 变更时间线

- 从「以前好过」到现在，列出变了什么：`时间 | 变化（提交 / CL / rev、依赖升级、配置、数据、环境） | 碰到的文件或模块 | 和现象的关系`。代码改动先看出错模块最近的提交（`git log -p -n 10 -- <模块目录>`，P4 用 `p4 changes -m 10 <路径>/...`，SVN 用 `svn log -l 10 <路径>`）。
- 和现象时间线对齐：现象第一次出现之前最近的那几次变化是第一批嫌疑；两处环境一好一坏的，逐项对比版本、配置、数据、系统，差的那一项就是第一个假设（差异法）。

### 4. 归因：为什么坏、是谁那边的问题、还有没有别的可能

- 证据链三环齐全才算根因：现象 ← 日志原文（哪一行、写了什么）或测试输出 ← 代码 path:line 的哪个条件或赋值，并且能从输入一步步推到错误输出。
- 缺一环、有两种以上可能、日志没覆盖关键分支 → 不改代码去猜：能自己复现的（跑相关测试或命令、写一个失败用例）先复现，用结果确认或排除；自己复现不了，就走论证：按下面「论证的日志一次加够」定范围、加临时日志（统一前缀 `[排查-<主题>]`，打出分支条件和关键变量的值，不打密钥和大段数据），先写成日志计划交给用户（有 submit_diagnosis 时交 phase: evidence，见第 6 步），用户同意后再加、请用户复现，拿到日志回到定位那一步。没验证过的不写成结论，也不用「可能 / 应该 / 估计」带过：写成「假设：……，用 X 确认」。
- 论证的日志一次加够：一轮的目标是用户复现一次就能定论，不是每轮只看一处。
  1. 先列全候选假设：沿调用栈从入口走到现象点，每一处能让结果走偏的地方（分支条件、状态改动、异步和回调边界、跨进程 / 网络边界、缓存和配置读取、外部输入）都问一句「它出错能不能解释现象」，能的进假设表（H1、H2…，写依据），已经被代码或测试排除的标已排除并写依据。不止当前读到的那一层。
     按现象类型补齐假设：现象属于几类就对照几类，每类里和现象对得上的都列进假设表，对不上的不硬凑。
     - 数据类（金额、数量、时间、编码、字段值错）：常漏类型、格式、单位、缺字段（以及默认值、精度和取整、时区）；日志打值和类型（typeof）、来源和每一步转换后的值。
     - 状态类（状态不对、卡住、重复执行、少执行一步）：常漏竞态（两处同时改）、顺序（回调、事件先后颠倒）、重入（处理中又被触发）、异步回来时状态已变、改了状态没通知；日志打每次改状态的旧值 → 新值、调用方、触发事件、时间戳和请求 / 会话 ID。
     - 界面类（显示旧数据、不刷新、闪一下又变回去）：常漏缓存没失效、订阅时机（数据先到、订阅后建）、渲染用的是旧引用、组件卸载重挂；日志打数据到达、订阅建立和取消、渲染时用的值和版本号。
     - 环境类（只在某台机器、某个系统或版本上出）：常漏版本（运行时、依赖、CLI）、路径（分隔符、大小写、空格、相对路径的基准）、编码（UTF-8 / GBK、BOM、换行符）、权限（文件、网络、账号）；启动时打一次版本、平台、工作目录、编码设置，出错处打实际路径和错误码。
     - 偶发类（有时出、有时不出）：常漏时序（谁先完成）、资源（并发数、内存、句柄、超时）、外部依赖（网络、上游服务、文件锁）；日志打带毫秒的时间戳和线程 / 进程 ID、等待和耗时、重试次数、外部调用的返回码，记下这次复现跑了几次、出了几次。
  2. 每个待验证的假设至少一处能判它真假的日志：打在它的分叉点上，进入时打调用方或请求 ID，打出走了哪个分支、分支条件里的每个变量；改状态的打旧值 → 新值；异步的在发起和回调各打一次。
  3. 再在调用栈每一跳的入口（或出口）放一处路标（hypothesis 写「路标」）：假设全猜错时，一次复现也能看出走到哪一跳断的，下一轮直接在那一跳收窄，不用从头摸。
  4. 不铺满：每处都要对应一个假设或一跳路标，对应不上的不加；代码或现成测试已经能证明的分支不加；循环和高频回调只在条件命中或值变化时打；不打密钥和大段数据。通常一轮 5～15 处，超过 20 处先看能不能合并到同一跳。
  5. 写判定表（collect.outcomes，一种结果一项）：每个假设看到什么算证实、看到什么算排除；都对不上时看路标停在哪一跳。任何结果都要能证实一个假设或把范围缩到一跳，做不到说明分叉点还没选全。
  6. 要再加一轮只有一个理由：上一轮的日志揭示了没想到的新情况。先写清上一轮看到了什么、为什么没定论、新假设从哪来，再按同样的规则把这条新路径上的分叉一次补齐；上一轮的临时日志留着，最后一起删。
- 一致性检查：根因要能解释现象卡里的每一条——为什么是这个触发条件、为什么偶发（或必现）、为什么只在这个环境、为什么以前没出。有一条解释不了，说明还有别的原因或者根因找错了，不能下结论。
- 鉴别诊断：把查过的其他可能列成假设表（已证实 / 已排除 / 待验证），每条写依据；深入级别至少两个假设。

#### 版本归因：是哪次改动引入的、是谁那边的问题

定位到出错的几行后，查清它是怎么来的。全程只读：P4 不 sync、不 revert，SVN 不 update，Git 不在用户的工作区里 checkout；要跑旧版本就开独立 worktree 或把文件取到临时目录。

| 要查的                                                                                     | Git                                                                                                   | P4                                                             | SVN                                      |
| ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- | ---------------------------------------- |
| 出错的几行最后是谁改的                                                                     | `git blame -w -C -L <起>,<止> -- <文件>`（仓库有 `.git-blame-ignore-revs` 时加 `--ignore-revs-file`） | `p4 annotate -c -i <文件>`                                     | `svn blame <文件>`                       |
| 这段代码怎么演变的                                                                         | `git log -L <起>,<止>:<文件>`、`git log -S '<关键串>'`                                                | `p4 filelog <文件>`、`p4 describe -du <CL>`                    | `svn log -v <文件>`、`svn diff -c <rev>` |
| 那次改动是不是「引入」                                                                     | 读那次 diff；或在独立 worktree 里把复现用例放到它的前一版上跑（`git show <rev>^:<path>` 只读取文件）  | `p4 print <文件>@<CL-1>` 取前一版对比                          | `svn cat -r <rev-1> <文件>` 取前一版对比 |
| 回归了却找不到具体行                                                                       | `git bisect run <复现命令>`（在独立 worktree 里）                                                     | 按 changelist 列表手工二分，每次 `p4 print` 出那一版的相关文件 | 按 rev 手工二分，`svn cat` 到临时目录    |
| 没有版本管理：用文件修改时间、依赖版本、用户描述，或者一好一坏两处环境逐项对比（差异法）。 |

- blame 只说明最后谁动过这几行，不等于是它引入的：要看那次改动之前是不是就有问题。格式化、搬移文件的提交跳过去往前找。
- 结论写成「引入于 <提交号 / CL / rev>《标题》（作者，日期），依据：blame / bisect / diff / 日志」，再标一个责任类别：本次改动（这个分支或对话里还没合进去的）、近期变更、历史遗留（一直有，这次的输入才触发）、外部依赖（第三方库、上游服务、CLI，写版本）、环境配置、数据（旧格式、脏数据）、用户操作（按设计就是这样，结论是「不是 Bug」或「要改提示」）、未确定（写清试过什么、还缺什么）。
- 作者、提交号、时间照版本记录原文写，不加评价。
- 引入那次的 diff 往往直接说明了修法（漏改的调用方、改错的条件、该一起改的另一处），同类搜索也从这次 diff 开始。
- 查下来不用改代码（问题出在配置、数据、本来就这么设计、用法不对、外部依赖）：根因那一版照常交（证据链、归因都要），再写 noFix（kind 和 how：用户怎么处理）。用户同意后不交修复方案，按 how 告诉用户怎么处理、删掉临时日志后请父对话收尾。不要为了「有个修法」去改代码。
- 根因评级（rating，报告最上面醒目显示）：等级写这个错在哪个层次——低级（low）是粗心疏漏：写错名字、漏判空、漏改一处、复制粘贴没改全；中级（mid）是逻辑和边界：条件、顺序、状态没想全；高级（high）是设计、并发时序、跨模块契约。把握写百分比（percent，0–100 的整数）：证据链三环都有原文、复现用例改前失败的 90 以上；有一环靠推断的 60–85；还有解释不了的现象不超过 60。why 用一句话写依据。等级只描述这个错本身，不评价人；提交人照版本记录原文写在 attribution.author。
- 找到就停：找到能完整解释现象的原因并验证后就进入修复设计，不再往更底层找「更根本」的问题；路上看到的其他可疑点列进「顺带发现」，不修。「全面」指根因要解释全部现象，不是往下挖得更深。

### 5. 修复设计：比较几种修法，选最优，不默认选改得最少的

1. 影响面：列出要改的地方会碰到什么，每条写「怎么受影响、用什么验证」——调用方（谁调用了要改的函数或读了要改的字段、几处，用搜索结果不估）；数据和契约（持久化格式、旧数据、接口形状、默认值、配置项）；时序和并发（异步顺序、重入、取消、超时）；平台和变体（不同 CLI、操作系统、Git / P4 / SVN、语言）；界面和文案（空、加载、报错、超长这些状态分支，多语言）；同类现场（同一个原因在别处的其他表现，从引入那次 diff 和同类写法搜索来）。
2. 候选方案：至少两个有实质区别的修法（快速级别可以一个，写一句为什么没有别的）。常见的几组对照：在源头修 / 在边界上校验；只修这一处 / 修掉这一类写法；回退引入的那次改动 / 往前修；修实现 / 修契约（改接口或数据格式，带迁移）。
3. 每个方案写五项，用证据说话：修得全（能解释的现象、同类现场修掉了哪些、漏了哪些）；修改面（改哪些文件、大概几处、动不动契约和数据格式）；风险（可能引入的新问题从影响面哪几条来、怎么防）；契合（合不合现有架构、模块边界、项目约定和 ADR）；可验证（能不能写出改前失败、改后通过的测试，影响面各条能不能逐项验证）。
4. 选定并写理由。底线只有两条：修的是根因（把报错 try/catch 掉、加判空绕过、加重试、在原逻辑外面再兜底一层（再扫一遍、多加一条降级分支）让它「不报了」都不算修）、复现用例改后通过。满足底线的方案之间没有固定优先级，按上面五项权衡，写清「选 A 因为……；不选 B 因为……」。取舍提示：同类现场是同一个根因时，只修一处就是没修全；动契约能一次修掉一类问题但要迁移旧数据时，把迁移成本写进风险让用户判断；修改面差不多时选更容易验证的。
5. 验证计划：复现用例 + 影响面每一条对应的验证（测试名、命令或手测步骤），修完按它逐条给结果。

### 6. 分阶段交报告，每一步等用户同意

- 随查随记：你有 update_bug_case 工具时，每查清一块就记进档案草稿——现象（symptom、repro）、调用栈（stack，一跳一项）、时间线（timeline：event 事件、state 状态流转、change 变更）、归因（rootCause、confirmed、attribution 引入点和责任类别、consistency 根因怎么解释每一条现象、hypotheses 假设表）、修复设计（impact 影响面、options 候选方案和五项比较、chosen 选定和理由、files、verify），级别写在 level（升降级理由写 levelNote）。传哪个字段就换掉哪个字段，数组整组传；它会告诉你现在在哪个阶段、交报告前还缺什么。草稿跨轮次保留，这就是排查记录。
- 用 submit_diagnosis 按阶段交报告，每交一版就结束这一轮，等用户在弹窗里的决定（作为新消息交给你），用户回复之前一个文件都不改：
  1. 论证（phase: evidence）：根因还没证实就先论证。hypotheses 列全候选假设（每条带 id：H1、H2…），logPlan 按第 4 步「论证的日志一次加够」写这一轮要加的临时日志（每处 id 写 L1、L2…，file、print 写要加的那一行语句原文、以 `[排查-<主题>] L<n>` 开头——不写「打出订单 id」这种描述，hypothesis 写它区分的假设编号或「路标」；实际加的日志和 print 一字不差，面板按前缀和编号在用户贴的日志里数每处出现了几次），collect 写复现步骤（steps）、日志在哪（where）、过滤条件（filter）、判定表（outcomes 至少两项：一种结果一项，see 看到什么、means 说明什么——每个假设看到什么算证实或排除、都对不上时看路标停在哪一跳；能用「某处出现了 / 没出现」判断的写 match: { point: 'L2', seen: false }，面板拿到日志自己对）。假设表按第 4 步的现象类型表补齐（数据、状态、界面、环境、偶发各有常漏的几类），日志按表里写的打。复现用的是自己构造的数据时 reproKind 写 constructed：构造的数据只能说明「这样也能出现」，不能拿来排除别的假设。面板会核对：至少两个假设、每个待验证的假设都有日志覆盖。用户同意后按日志计划全部加上（不挑几处先加）、只在计划里的文件加、不改逻辑；自己能复现就自己跑，复现不了调用 request_logs 请用户复现，结束这一轮等日志。用户也可能不用你加、直接贴日志。拿到日志只分析这一段：证实了交根因；还没定论才交下一轮论证，next 写清上一轮的日志看到了什么、为什么没能定论、这一轮的新假设从哪来（面板会核对）。目标是一轮复现就定论，第二轮只因为日志揭示了没想到的新情况，不因为上一轮漏加。
  2. 根因（phase: cause，confirmed: true）：证据链写进 chain，三环各一项（trigger 触发、fault 出错点、symptom 现象，proof 一句说明，refs 写引用的原文编号）。原文不转述：用户贴的日志写进 quotes（kind: log，from 第几份报告、start~end 行号，面板按行号取原文；要抄就一字不差，不用 … 截断、不去前缀），这个对话里跑过的命令输出写 kind: run（原样复制），截图和用户说的写 kind: note（报告上标成「描述」）；highlight 写原文里的关键值。代码写进 codeRefs（一段一项：出错点 role: fault，触发条件、调用方各自另起一段，每段 5~15 行；marks 标出那一行里真正出错的那几个字，例如 `left === 0`，note 写 20 字以内的行尾说明），面板交报告时读出代码存档、逐字核对，对不上会拒收。出错点那一环至少引用一段代码和一条日志或命令输出。expectVsActual 一行一个值写「应该是 / 实际是」，actual 引用原文编号。rootCause 一句话按这个句式写：在〈什么条件下〉，`文件:行` 的 `代码原文片段`〈做错了什么〉，所以〈用户看到的现象〉。已证实的结论不用「可能 / 应该 / 估计」。再写引入点、根因怎么解释每一条现象。用户同意才往下；用户否决（带着疑问和补充）时认真看：用户说得对、证据确实不完整，就回到论证交 evidence（升一版）；证据其实够，就再交 cause 逐条回答（还是这一版）。
  3. 修复方案（phase: plan）：影响面、候选修法和五项比较（每个方案的 grades 给各项判定：good 好、cost 有代价、bad 不满足；动到数据格式、接口、配置的写 touches）、选定和理由、changes（选定方案一个文件一项，写这个文件改什么）、验证计划；模块已有日志体系的，修改处要留的正式日志也写进去。快速级别（必现、读代码就能定、改一个文件）可以不单独交根因：level 写 quick、confirmed: true，根因那几节和修复方案合成一版交 phase: plan，用户确认一次就开始修。用户确认了才写失败测试、按方案修；用户点了「改用方案 X」就按那个方案重新整理再交。
  4. 修复（phase: fix）：按确认的方案改完（先写改前失败的测试）就交，changes 改写成实际改了的每个文件（含测试）：what 改了什么、why 为什么这么改（这处改动怎么解决根因、为什么这样写）；面板取实际 diff 和它对上给用户看，改了却没写的文件会退回。用户确认修复才往下验证。用户在代码上标了疑问：逐条查清再判断，不因为用户提了就照改——说得对就改代码、answers 写 stance: adopted；说得不对就不改，stance: disagree，用事实反驳（引用代码行、测试输出、日志原文）；只是没看明白写 stance: explained；处理完重新交 fix（还是同一版）。复现用例能自动跑的，交 fix 之前先用 update_bug_case 的 result 记下 commands（能在项目根直接跑的命令原文，你在这个对话里跑过、改后通过的那几条）和 reproBefore / reproAfter：面板在这一轮结束后把它们在改前的代码和现在的代码上各跑一次，真实输出给用户看；改前失败、改后通过的，用户确认修复就同时算验证通过，不再交 phase: verify（用户确认时会写明）。
  5. 验证（phase: verify）：用户确认修复后，跑回归测试和影响面逐条的验证，用 update_bug_case 的 result 记下后交，collect 写用户怎么复现验证、看到什么算修好了。用户贴了日志：分析没问题就收尾，有问题回到论证或重新出方案（升一版）；用户点了结束就跳过验证直接收尾。收尾前删掉所有 `[排查-` 临时日志；改到的模块已有日志体系的，必要的正式日志按它的写法留下或补上，没有日志的模块（纯函数、工具库）不加，在 result 里写一句为什么。
- 要用户决定或补充的都写进报告交，不用提问工具（ask_user、AskUserQuestion 这类）问：几种修法拿不准选哪个，照样写进修复方案的候选方案、选定一个写理由，用户在弹窗里确认或点「改用方案 X」；根因没证实就先交论证；缺的信息写进论证的 collect。提问的回答进不了报告，阶段也不会往下走，面板会把这类提问退回。
- 报告里的写法：每个文字字段第一句就是结论，一段只写一件事，几件事分开写进结构化字段（chain、changes、outcomes），不塞成一大段。带目录的文件路径写全、用反引号包（面板画成能点开的文件标记，只显示文件名）；单独的文件名、函数名、变量、字段、配置值也用反引号包，按代码显示；要用户特别留意的（会丢数据、要手工操作、改了公共接口）单独一行以「注意：」开头，面板画成醒目的提示框。
- 用户可能在同意时设了「后面几步没有要注意的就自动通过」：交上来的一版面板核对过没有要注意的，submit_diagnosis 的返回里直接写明已通过、带着用户同意时的那段话，照它接着做，不用结束这一轮；没写已通过的照常结束这一轮等用户。
- 用户标了疑问就只查被问到的几条，改好再交，answers 按编号回答，stance 写态度（adopted 采纳并改了、explained 解释清楚不用改、disagree 不同意并写理由）；第 2 份起 whatChanged 用一两句写这一份相比上一份改了什么。
- 第几版由面板定：按用户意见修改、论证多轮、阶段往下走都还是同一版；回到更早的阶段（根因被否决回到论证、验证没过）或换掉用户确认过的方案才升一版。跟用户说第几版照 submit_diagnosis 返回里的写，不自己数。
- 没有这两个工具（面板没把这个对话标成 Bug，例如没有项目的 Chat 页里用户发的 /bug）：把同样的内容按「排查报告」的前 8 节写在回复里，结束这一轮，等用户回复同意再改。

### 7. 修复与验证

- 先有能复现的失败测试（改前失败、改后通过），没法自动化的写成可重复的手工步骤并登记为延期验证；再按确认的方案修，只改方案里的文件，要多改先重新交方案说明为什么（换掉确认过的方案，升一版）。
- 修的是原因不是症状：把报错 try/catch 掉、加判空绕过、加重试、在原逻辑外面再兜底一层（再扫一遍、多加一条降级分支）让它「不报了」都不算修。
- 按验证计划逐条给结果：复现用例改前改后的输出、影响面每一条的「命令 + 结果」、相关测试；偶发的按原频率跑够次数，写清跑了几次、坏了几次。有 update_bug_case 时把结果记进 result（reproBefore、reproAfter、impactChecks 的 area 照报告里的影响面写、regressionTests、runs）：收尾时面板按它核对，影响面少一条验证、没有回归测试都收不了尾；改动里留着 `[排查-` 临时日志也收不了尾。
- 按确认的方案修完验证不过：不在这次修法上接着改，把修法和失败证据写进「已排除」，回到论证或归因，重新交报告（面板记成新的一版）。
- `[排查-…]` 临时日志删掉；改到的模块已有日志体系的，排查需要的正式日志（关键分支、关键值）按它的写法、级别和前缀留下或补上，下次出同类问题看日志就能定位；没有日志的模块（纯函数、工具库）不加，写一句为什么不加。

### 8. 防复发与归档

- 回归测试留在改动里，名字说清拦住的是哪个现象。
- 同类隐患：根因是一种写法错（少判空、顺序错、单位错、漏同步）时，从引入那次 diff 和同一模块里搜一遍同样的写法：是同一个 Bug 的其他现场就一起修（修复设计里已经算进去的），不是的列进「顺带发现」，不扩大范围。
- 回写模块文档：这次摸清的入口、调用链、关键日志在哪打、怎么复现、易错点，交给「文档」写进 `modules/<模块>/README.md`（模块还没有文档就新建），把调用栈、日志证据、根因、引入点和验证结果原样附上；Bug 记录只记用户报的 Bug：这次就是，修完同时交给「文档」写 Bug 记录。下次同类问题先读文档就能定位。

### 排查记录：不重复返工

- 一开始就在计划里（set_plan）或回复里维护一份排查记录，分三栏：已确认的事实（附证据）、已排除的方向（附排除依据：日志原文、测试结果）、待验证的假设（各自怎么验证）。每做完一次验证就更新；新一轮开始、换假设、续接上次的对话时先读它，排除过的不再重查，试过的修法不再重试。
- 一次只验证一个假设、只改一个变量；同时改几处就分不清是哪一处起的作用。修复没生效时把这次的修法和失败的证据记进「已排除」，回到证据链，不在上一次的修法上再叠一层。
- 复现和复测前先确认跑的是这次的代码和配置：构建产物、缓存、热更新、没重启的进程、改了但没生效的配置、连错的环境或数据目录都会让「改了没变化」或「没改却好了」；能确认的用版本号、日志里的启动时间或一条临时日志确认生效了再看结果。
- 偶发问题不能只跑一次就说修好了：按原来的频率估算要跑多少次才算数（例如原来十次坏一次，就至少跑二三十次），写清跑了几次、坏了几次。

计划（set_plan）按这八个阶段列，快速级别可以合成「立案 → 定位和归因 → 修复设计 → 交诊断报告 → 修复和收尾」五步；论证要用户复现时，计划里列出「加日志（写清加在哪几处）→ 等用户复现 → 分析日志」三步，等用户那一步标等待中。交回按下面的小节写，派你的那一方按同一张表核对：

### 排查报告（交回按这几节写，缺的写「无」或「未知」，不省略小节）

最后一条回复先按「总结格式」写「修复」类的总结（给用户看清重点），排查报告接在总结下面（给父对话逐项核对）。

1. 级别与模块：快速 / 标准 / 深入（升降过的写原因）；问题在哪个模块、哪一层，排除了哪些层（各自的依据）。
2. 现象：期望 vs 实际、触发条件、环境和版本、频率、从什么时候开始。
3. 复现：命令 / 测试 / 操作步骤和本轮的真实输出、复现率；复现不了写清试过什么。
4. 调用栈：按「调用栈怎么写」写成 `calltree` 代码块：入口 → … → 出错点（条件和当时的值）→ 没走到的 → 现象。
5. 时间线：现象时间线（分析的是哪份日志的哪一段、按时间排的关键事件、涉及状态的状态流转，标出最后一个正常和第一个异常）+ 变更时间线（从以前好过到现在，代码、依赖、配置、数据、环境变了什么）。
6. 证据链：现象 ← 日志原文或测试输出 ← 代码 path:line 的条件或赋值。
7. 归因：根因（一两句）；引入点（提交 / CL / rev、作者、日期、怎么确定的）和责任类别；根因怎么解释现象的每一条（为什么偶发、为什么只在这个环境、为什么以前没出）；排除的其他假设和依据。
8. 修复设计：影响面清单；候选方案和五项比较；选了哪个、为什么不选别的；交过诊断报告的写按第几版确认的方案。
9. 修复：改了哪些文件和哪几处。
10. 验证：复现用例改前失败 / 改后通过的输出；影响面逐条的验证「命令 + 结果」；偶发的运行次数和结果；临时日志已清。
11. 回归与隐患：补了哪条回归测试；同类写法搜了哪里、结果如何；顺带发现（不修）。
12. 文档：回写了哪份模块文档 / Bug 记录，或交给了「文档」什么内容。
