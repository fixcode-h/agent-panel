# OpenSpec · 阶段 3 实现

通用规则和命令用法见同目录的 `SKILL.md`。

## 阶段 3 · 实现

先做阶段切换检查。修改文件前按 `project-vcs` 识别 VCS（P4 细则在它的 `p4.md` 里），P4 项目按该细则将明确任务文件纳入 default changelist。只有跨会话、跨多个独立验收边界或明确要求时，才在外部 `DOC_ROOT` 创建简化的 `p4change/<任务标识>.p4change.md`，普通任务不创建；台账不替代 `tasks.md`，也不加入 pending。

按 `tasks.md` 连续执行，每条 task 的顺序：

1. 检查相关 Bug 的防复发约束和回归测试；
2. 修改；
3. 检查「运行期依赖」（下一节）；
4. 运行该 task 声明的验证；
5. 验证通过后，勾选 `[x]` 并在 `acceptance.md` 对应行追加证据（命令、结果）；验证只能延期的，登记延期项后写成 `- [x] <原文>（延期 Dn）`（见 `SKILL.md`「tasks 的勾选」），不要留成 `[ ]`；
6. 继续下一条。

- 验证失败不勾选。同一根因连续失败两次回到根因分析；三次仍未解决则重新规划该任务或报告阻塞。
- 无法执行的非阻塞验证登记为延期验证后继续安全任务；单条任务的实际阻塞或安全风险才暂停并记录。

### 分组派子任务

`tasks.md` 有 3 组以上、组和组之间不改同一批文件时，每组派一个子任务（`spawn_agents`）去做，交代清楚这一组的 tasks、要读的 spec 和 design 章节、验证命令；你只核对它们交回的结果、统一勾选和写证据。一个会话里从头做到尾，上下文会涨到几十万 token，后面每一轮都把整段重读一遍（实跑里实现节点一个占了全程一半的花费）。有先后依赖的组按顺序派；改同一个文件的合成一组。

### 运行期依赖：不能留给别人的坑

改的代码在运行时依赖**这次还没生成出来的东西**时，验证不能只靠桩掉依赖的单测。典型的：

- 引用了要导表、代码生成、编译蓝图、跑脚本之后才有的枚举值、表行、常量、资源（例如新加的枚举要导表后才进生成的 Lua 文件）；
- 改了全局共用的入口（主模块构造、共用的处理器、注册表）来接入新功能。

这时按顺序处理：

1. 能在这里生成就生成（跑导表、代码生成的命令），把生成物和代码一起交。
2. 生成不了（只能用户在界面里点、要别的权限）时，代码里先判空兜底：取不到就跳过新功能、打一行日志，**不能让共用的入口跟着报错**（一个 `table index is nil` 能让整个主模块构造中断）。
3. 两样都做不到：按阻断交回（写明缺哪个生成物、谁来生成、生成前同步这份代码会怎样），**不要登记成延期验证**。

单测桩掉了运行环境（`_SP`、`UE`、无头 Lua）时，在 `acceptance.md` 写明桩掉了什么、哪些只能在真实环境里验证。UE 项目里这些「只能在真实环境里验证」的 Scenario 写成 GameTest 脚本去跑（`gametest.md`），不能只靠桩算通过。

### 结束前做一次加载冒烟（UE 等要连运行中程序的项目）

在项目目录里直接改（不是独立分支）、改动不用编译就能生效（Lua、配置、数据），而且运行中的编辑器能连上（有 `ue_editor` 工具、`ue_status` 能看到编辑器）时，tasks 做完后做一次加载冒烟，不写测试脚本：

1. `ue_editor action=pie_start map=<地图>`：一定带 `map=`（不带时按编辑器当前的图起，常常起不来、超时）。挑这次改动所在主模块的地图，`DOC_ROOT/CONTEXT.md` 的「地图与主模块」有对照就照它；只在 PIE 里玩那张图、编辑器里的图不动；它会等 PIE 世界起来才返回，不要 sleep；
2. PIE 起来后再 `ue_lua action=reload` 热重载（Lua 环境要等游戏世界起来才建好，先 reload 会报「UnLua 环境还没建好」）；
3. 用 `ue_log` 只看这次 PIE 开始之后的 Error（`since=pie`），确认新改的模块能取到；
4. `ue_editor action=pie_stop`。

工作流给这一步带了游戏内测试和执行 Lua 的授权，不会弹卡。离线测试的桩只能补充、不能代替加载冒烟：桩按你的理解写，掩盖不了也发现不了接口用错（复盘 2026-11-26：`.Rotator` 应为 `.Rotation:ToRotator()`，桩里照写所以测试通过）。编辑器中途换了进程（崩溃重启）时先用 `ue_log` 查崩溃原因，是这次改动引起的按回流处理。冒烟里报错按上一节「运行期依赖」或回流处理；编辑器没开、要编译 C++ 的不在这里起编辑器，留给「延期验证项」。

- 实现中自己发现的易错点不写模块 Bug 文档（Bug 记录只记用户报的 Bug）：影响设计的按下面「回流」处理，值得长期记住的写进模块 README 的「常见陷阱」。

### 回流：设计假设被证伪

实现中发现 `grilling.md` / `design.md` / specs 的某个假设不成立，或验收标准无法满足时，按下列顺序处理，不得继续按原设计写代码：

1. 停止当前 task，把事实证据记入 `acceptance.md`。
2. 只对受影响的分支做局部压测（该分支及其下游），不重走整棵决策树。
3. 更新 `grilling.md` 对应结论、`design.md`、受影响的 specs 和 tasks；已完成但受影响的 task 改回 `[ ]`。
4. 重新 `openspec validate <change>`。
5. 变更触及目标、非目标、技术路线或验收标准时，用一次选择交互请用户确认；只是实现细节则自决并记录。
6. 回到剩余 tasks。

### 跨会话交接

change 预计跨会话或有多个独立验收边界时，在 change 目录维护 `handoff.md`：最后确认事实、当前里程碑、阻塞、下一动作、恢复入口。每完成一组 tasks 更新一次；单会话即可完成的 change 不创建。
