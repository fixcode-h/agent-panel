# 项目结构

## 什么时候用

第一次接触一个项目，或者在熟悉的项目里做一件没做过的类型的工作（第一次打包、第一次跑集成测试、第一次碰某个模块）。目标是把「这个项目怎么运转」搞清楚到能动手的程度，不是把整个仓库读一遍。

已经有了 `docs/MODULE-MAP.md` 或模块 README 时先读它们，只补缺的部分。

## 要弄清楚的事实

按这个顺序看，每一层都先看配置再进去读代码，能停就停：

1. **边界**：项目根目录在哪（`.git`、解决方案文件、`.uproject`、`package.json` 所在的那一层），有没有子项目 / workspace / monorepo 分包。
2. **技术栈**：依赖清单（`package.json`、`*.csproj`、`Cargo.toml`、`pyproject.toml`、`go.mod`、`.uproject`）和锁文件；语言、框架、运行时的版本要求。
3. **构建**：构建命令从哪来（`scripts`、`Makefile`、`CMakeLists.txt`、`Build.bat`、CI 配置），产物在哪，增量构建怎么做。
4. **测试**：测试框架、测试文件的位置、跑单个测试和全量的命令，有没有 lint、类型检查、格式检查。
5. **运行**：怎么启动、需要哪些环境变量或本地服务，配置文件在哪、有没有默认值。
6. **入口和模块**：程序入口、路由 / 命令注册、主要模块目录各自负责什么，模块之间怎么调用。
7. **约定**：代码风格配置、目录命名习惯、提交说明格式、生成文件不能手改的地方。

命令一律从项目自己的配置里抄，不凭经验编。

## 怎么找代码（先缩小范围，再搜）

大项目全仓搜一次要几分钟，还会命中几万行编译产物。按下面的顺序收敛，能在前三步停下就不要全仓搜：

1. **已知具体文件就直接读**：报错、堆栈、别人点名给了路径或文件名时，直接读那个文件；不知道路径就用 `rg --files -g '**/名字*'` 按名字找。有明确目标时不做搜索。
2. **先读项目文档定位模块**：`DOC_ROOT` 的模块地图（`docs/MODULE-MAP.md`）、模块 README（`docs/modules/<模块>/README.md`）、`AGENTS.md` / `CLAUDE.md`、构建配置。文档里通常已经写了「这个功能在哪个目录」，比搜代码快得多；文档缺失或过期时才往下走。
3. **从入口 / 构建配置反推目录**：路由表、`package.json` 的 `scripts` 和 `workspaces`、`CMakeLists.txt`、`.uproject` 的模块列表，能确定该看哪几个目录。
4. **在最小目录里搜**：先限定到模块目录，搜完没命中再把范围扩大一级（`src/模块名` → `src/` → 仓库根），不要一上来就 `rg <关键词> .`。
5. **搜索带排除**：项目设置里的「搜索时跳过的目录」会随提示词给出（`搜索时排除：…`），照着加 `-g '!目录'`；没有这份清单时至少排除依赖和产物（`node_modules`、`dist`、`build`、`target`、`out`、`.venv`、`coverage`）。UE 项目的完整清单见 `ue-project-structure`。
6. **可能超过 60 秒的搜索放后台**：先小范围试（限定目录、`--max-count` 看命中量），确认范围对了再扩大；确实要扫大范围时用面板的 `run_background` 放后台跑，不要在前台干等。

可照抄的命令：

```bash
# 只在某个模块里搜，排除产物目录
rg -n --glob '!node_modules' --glob '!dist' --glob '!build' '关键字' src/模块名

# 只列文件名（找「叫这个名字的文件在哪」），比全文搜索快得多
rg --files -g '!node_modules' -g '!dist' | rg '文件名|关键字'

# Git 仓库：只在被跟踪的文件里搜，自动跳过 .gitignore 里的产物
git grep -n '关键字' -- src/模块名

# 不是 Git 仓库时用 find：必须限深度并剪掉产物目录
find . -maxdepth 3 \( -name node_modules -o -name dist -o -name build \) -prune -o -name '*关键字*' -print
```

`grep -r .` / `find .` 不带范围在几十万文件的目录里会跑很久，优先 `rg` / `git grep`；`find` 一定带 `-maxdepth`，并 prune 掉产物目录。

## 产出一份现场说明

第一次弄清楚之后，写一份简短说明（放在项目文档里，位置按 `project-documentation` 的规则），内容只写有证据的事实：

```markdown
# 项目现场

- 项目根 / 文档根：
- 技术栈与版本：
- 构建：
- 测试与检查：
- 运行方式：
- 主要模块（路径 → 职责）：
- 已知的坑：
```

每个命令都实际跑一次只读的部分（例如 `--help`、版本号、列测试用例），确认它存在且写法对；跑不了的写明原因。

## 判断改动该放哪

- 先按模块职责找，不按文件名像不像找。
- 新增的东西跟着最近的同类走：同类文件在哪个目录、怎么命名、怎么注册（路由表、依赖注入、导出清单）。
- 跨模块的改动先确认模块边界和依赖方向，不让底层依赖上层。
- 不确定时在结果里写明「这个位置是按 X 推的，需要确认」，不要硬猜。

## 常见坑

- 有多个构建入口（IDE、脚本、CI）时，用 CI 用的那个作为准，其他可能是旧的。
- 生成物（lock 文件、迁移、快照）跟着生成命令走，不手改。
- 环境变量有默认值时，不设也能跑，但行为可能和文档写的不一样；以配置文件的默认值为准。
- 子目录里还有一份 `package.json` / `*.uproject` 时，确认真正要操作的是哪一个。
- 项目里同时有新旧两套结构（例如两套路由、两套测试）时，先确认哪套还在用，别往废弃的那套里加。

## 输出

结论先写一两句：这是什么项目、用什么构建和测试。然后列上面那份现场说明的字段，每条后面带上依据（文件路径、命令输出）。缺的和没确认的分开写，不要混在事实里。
