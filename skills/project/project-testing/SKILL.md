# 项目测试与验证

## 原则

- 验证跟着改动走：改了哪里就证明哪里，再按影响面加回归。不做和改动无关的全量跑。
- 只有本轮跑出来的输出算证据。上一轮通过、别人说通过了、代码看起来对，都不算。
- 跑不了的验证登记成「延期验证」，写清怎么验证、要什么条件；不能悄悄跳过。
- 测试本身也要能说明问题：失败的用例名、断言、相关文件和行号，比一张截图有用。

细则按需读，本目录下：

| 什么时候                                     | 读                 |
| -------------------------------------------- | ------------------ |
| 写或改测试、要加 mock / 测试辅助、测试很难写 | `writing-tests.md` |

## 测试先行（红-绿-重构）

新功能、修 Bug、改行为时默认测试先行；项目或任务明确不做 TDD（例如 UE 里难以自动化的玩法、一次性脚本、生成的代码、纯配置）时，至少要有一条可执行的验证方式。

1. **红**：先写一个最小的测试，描述「应该怎样」：一个用例只测一个行为，名字说清行为（`超过 3 次重试后报错`，不是 `test1`）。
2. **看它失败**：跑这个测试，确认是**因为功能还没有**而失败（断言不通过），不是拼写错误、导入错误或环境问题。一上来就通过说明测的是已有行为，改测试。
3. **绿**：写刚好让它通过的最少实现，不顺手加功能、不预留参数。
4. **看它通过**：再跑一次，同时确认其他测试仍然通过、输出里没有新的报错和警告。失败时改代码，不改测试去迁就实现。
5. **重构**：测试全绿之后再整理命名、去重复、抽函数，每一步保持全绿，不加新行为。
6. 下一个行为，回到第 1 步。

修 Bug 必须先写一个能复现它的失败用例，修好后这个用例就是回归测试。先写了实现再补的测试，一写就通过，证明不了它能拦住问题：要么先把实现撤掉看测试失败一次，要么在结果里写明「测试是后补的」。

先写测试很难的时候，通常说明接口不好用或耦合太紧：先简化接口、把依赖改成参数传入，而不是堆 mock。

## 选哪些

按改动的影响面从内往外选，够用就停：

| 改动                         | 至少要跑                                 |
| ---------------------------- | ---------------------------------------- |
| 纯文案、注释、格式           | 格式检查、构建 / 类型检查                |
| 函数内部逻辑                 | 覆盖它的单元测试、类型检查               |
| 接口契约、公开 API、数据格式 | 单元 + 调用方所在的集成测试，兼容性检查  |
| 配置、构建脚本、依赖         | 构建本身，加一次能证明配置生效的最小运行 |
| 跨模块、共享基础设施         | 受影响的模块测试、关键路径的回归         |
| 数据迁移、持久化             | 在副本或临时环境上跑一遍迁移，验证回滚   |

有历史 Bug 的模块（`bugs.md`）额外跑那几条的复现用例。

## 命令从哪来

按这个顺序找，找到就用，不要自己拼：

1. 项目配置里的脚本（`package.json` 的 `scripts`、`Makefile`、`*.sln` / `build.sh`、`Build.bat`）
2. CI 配置（`.github/workflows/`、`.gitlab-ci.yml`、`Jenkinsfile`）：CI 怎么跑就怎么跑
3. README、`CONTRIBUTING.md`、文档里的验证章节
4. 都没有时，按框架的常规用法跑一次最小集合，并在结果里写明这是推断出来的

跑单个测试优先于跑全量：大多数框架都有按文件或按用例名过滤的参数，先用它。

失败之后**只复测失败的**，不整套重跑：改完代码先跑上一次失败的那几个文件或用例（项目有现成命令就用，例如 `npm run test:failed`、`--failed`），过了再按需要跑一次全量。
输出很长时只看失败详情和汇总：项目的测试入口把完整输出写进日志文件的，按它给的路径去查具体那一段，不要把整份输出读进来。

## 跑之前

- 确认命令不会改工作区（自动格式化写回、快照更新、自动修复）。会改的加上只读参数，或者先记下基线再跑。
- 需要数据库、服务、端口、凭据的，先确认能不能用本机已有的；不能用就登记为延期验证。
- 长时间的命令放后台跑，先做别的，回头取结果。

## 结论怎么写

逐条对照验收标准写「✓ / ✗ + 证据」：

```
- 新增的解析逻辑：✓ `npm run test:unit -- parse` 通过（12 passed）
- 接口兼容：✗ `npm run test:integration` 里 orders.spec 失败，期望 200 得到 422（见 src/api/orders.ts:88）
- 真机验证：延期，需要设备；步骤见 docs/runbooks/device-check.md
```

- 证据写命令和关键输出，不写「已测试」。
- 失败要区分「这次改动引起的」和「本来就有」；本来就坏的说明基线。
- 最后单独一行写「验收结论：通过」或「验收结论：不通过」，有条件连线的节点必须写。

## 常见坑

- 测试跑在缓存上：改完代码要先确认缓存失效，否则通过的是旧结果。
- 只跑了单元测试就说功能可用：跨模块的路径没有覆盖到。
- 环境不一致：本机能过、CI 不能过，通常是版本、路径分隔符、时区、编码。
- 并发执行时共享状态互相干扰，单独跑过、一起跑失败，要隔离状态或串行。
- 冒烟测试替代了回归：只证明「能启动」，不证明「行为对」。
- 测的是 mock 而不是真实代码：断言 mock 被调用了几次，实际行为对不对没人知道（见 `writing-tests.md`）。
