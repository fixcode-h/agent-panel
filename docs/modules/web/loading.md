## 打开对话时的加载日志

- 打开对话时的加载日志（纯逻辑 `web/src/lib/load-trace.ts`、状态 hook `web/src/lib/useLoadTrace.ts`、界面 `web/src/components/tasks/LoadTrace.tsx`，埋点在 `web/src/components/tasks/TaskView.tsx`）：用户要求「打开对话不再只有一个转圈，把走到哪一步也打出来」，所以打开一条对话时像终端那样逐行列出五步——读取对话（`api.task(taskId)`）、连接实时更新（`useTaskStream` 的 SSE `full` 首包；演示版没有服务端推送，把 700ms 一次的轮询当实时更新，第一份轮询回来走同一个 `open`，任务没在跑时记 `trace.skip('stream', '这条对话没有实时更新')`）、读取子对话（首次 `loadChildren`，4 秒一次的轮询不记；子对话自己没有子对话时记「这个对话没有子对话」）、标记已读（`markTaskSeen`）、渲染消息（`apply` 收到第一份任务就 `start`，两帧 `rAF` 之后 `finish`，detail 写「{n} 条消息」）。**口径是「只记真的发起过的请求和真正画完的那一帧」，不伪造进度**：没发起是 `waiting`（等待中）、发起了没回来是 `running`（进行中，界面每秒 `useNow` 重算显示「已等 38ms」，越卡数字越大）、失败留 `failed` 并把错误原文原样显示在行上，前面失败后没轮到的步骤由 `trace.abort()` 标成 `skipped`（未执行）——它们不是卡住了，是没轮到。**面板只等「挡内容」的步骤**：`BLOCKING_STEPS` 是 `task` / `render`（对话没到、没画上屏幕），其余三步是内容之外的增强。`blockingSettled` / `blockingFailed` 只看这两步决定面板能不能收起、失败要不要停住——用户报过「任务数据和消息都画好了，面板还盖着等『连接实时更新』1.2 秒」，所以 stream / children / seen 慢不慢都不再挡内容，失败也不再让面板停住。收起后由 `LoadTracePill`（同一文件）接着显示：输入框上方一个小胶囊，还在跑时写「正在连接实时更新」这类进行中短语，失败时直接写错误原文（`backgroundSteps` 列出 `running` / `failed` 的非阻塞步骤），点开是五步的完整日志；没有在跑或失败的后台步骤时整块不画（不新增常驻噪音）。`traceSettled` 仍是「全部结束」，`traceRunning` 决定界面要不要每秒重算耗时。三处容易改错的地方：① `startStep` 只对 `waiting` 生效，重复调用不会把已等待的时长清零；`finishStep` 不覆盖已失败的步骤（catch 里记失败、finally 里再走一次结束是常规写法），要撤回失败只能由确认真的好了的调用方走 `recoverStep`——`useTaskStream` 的 `open`（`full` 首包）就调 `trace.recover('stream', '重新连上了')`，否则重连成功后面板会永久停在「加载失败」；② `useTaskStream` 的第 4 个可选参数 `hook`（`open` / `fail`）只有 `TaskView` 传，`error` 只在首包之前记失败、用 `failed` ref 去重（`EventSource` 自己重连会反复报 error，首包之后断开也不影响看对话）；③ `useLoadTrace` 全部是内存里换一个数组，不发额外请求、不拖慢加载，换对话靠 `reset()` 从头记（同一个组件实例会被复用）。界面：等宽字体、主题变量、居中卡片（`max-w-[520px]`），行自上而下按 `ROW_FADE_STEP_MS`（40ms）错开淡入；进行中的行状态与耗时用 accent 色，失败用 `text-danger`；375 窄窗口下先截步骤名（`truncate`），状态和耗时列 `shrink-0` 始终在。有任务数据之后它是盖在对话上的 `overlay`（`pointer-events-none`：卡住也不挡用户滚动看已有内容），阻塞步骤走完停到 `MIN_VISIBLE_MS`（450ms）再淡出 200ms 由 `onHidden` 卸载；**计时基准取第一步的 `startedAt`，不是这块组件挂载的时刻**——没有数据时它就是页面主体，数据到了换成 overlay 会重新挂载，两段各从自己挂载算会把「最少露 450ms」叠两遍白等一截。**阻塞步骤**失败时不自动淡出（错误原文要留在屏幕上），overlay 时右上角给一个「关闭」按钮，卡片只在这一态加 `pointer-events-auto`（否则点不到）；没有任务数据时它就是页面主体，失败也不淡出（淡成空白比转圈更糟）。`TaskView` 里 `render` 那一步用 `Task.id` guard（`traceRenderFor`）防切对话时把后一条错标成已渲染。耗时统一走 `shared/duration.ts` 的 `fmtDuration`，这次给它加了 1 秒以内的毫秒档（`38ms` / `900ms`：0.1 秒的精度分不出加载各步谁慢，四舍五入到 1000ms 的仍写 `1.1s` 不写 `1000ms`）；`scripts/lib/duration.mjs` 是脚本侧副本（界面检查的脚本是 `.mjs`，不能直接 import `.ts`），两份由 `shared/duration.test.ts` 逐条比对，改口径要两边一起改。演示版 `web/src/lib/demo-backend.ts` 的 `DEMO_ROUTE_DELAYS` 给 `GET /tasks/:id` 加 500ms、`GET /tasks/:id/children` 加 900ms（都过 `demoMs`，按 `agent-panel-demo-speed` 缩短），演示版才看得到逐行出现而不是一瞬间全绿。行上带 `data-trace-step` / `data-trace-ms`，界面检查靠它断言「渲染消息」真的记到了耗时（漏了起点会恒显示 0s）。回归：`web/src/lib/load-trace.test.ts` 12 条（初始全等待且只有 task/render 挡内容、进行中按时钟现算、起止耗时、重复发起不清零、detail、渲染必须记起点、失败不被 finally 盖成正常、未发起的步骤直接标完成时补起点不出负耗时、重连恢复到完成并清掉错误、主动 skip 并写明原因、失败后 abort 只动没开始的、全部结束才算 settled 且后台步骤慢或失败都不挡内容、收起后交给胶囊），`scripts/ui/02-task.mjs` 开头「任务-加载日志」（点开对话后立刻出现面板、含「读取对话」一行、相对对话区水平 / 垂直居中、375 不横向溢出、截一张图、加载完 detached），以及「任务-实时更新不挡内容」（把演示对话改成执行中：第一轮轮询 700ms 后才发、内容早已画完，断言面板先 detached、实时更新留在输入框上方的胶囊里继续连、输入框已经可用）。

## 打开对话页的加载链路（2026-10-26 实测，2026-10-27 两轮更新）

「对话页加载慢」先按下面这张表分段量，**不要先怀疑数据量或磁盘**：这台机器（i9-14900KF / 64GB / 三星 990 PRO）磁盘顺序读 3.2GB/s，最大的 `.messages.json` 1.5MB（611 条消息、517 次工具调用）读盘 9ms + `JSON.parse` 5ms，`GET /api/tasks` 79KB / 2ms。真实浏览器（headless chromium 1600×950，访问 `127.0.0.1:8787`）实测：首页 ready 350ms、资源 71 个 / 4.1MB；一条 2.0MB 的对话页 ready 1.6–2.4s、资源 114–119 个 / **总传输 9.4–10.2MB**。下面几条是 2026-10-26 的分项拆解（优化前基线）；2026-10-27 做完 `/seen` 瘦身和静态 gzip + 长缓存后，同一份对话页（2.12MB / 1000 条）ready **575ms**、**75 个请求**、resource timing 传输合计 **3.86MB**；同一轮后续又改成「首屏只取最近 50 条 + SSE 首包只补增量 + 子对话按状态分档轮询」（下面几条写的都是这一轮之后的行为），接口级数字和拆解见 [server 模块](../server/README.md) 的同一节。

- 首屏 JS：`dist/index.html` 里 `modulepreload` 一共 30 个文件 2506KB（gzip 777KB），最大的是 React 那份 756KB 和入口 689KB。这些文件以前按 2.5MB 明文传（`serveStatic` 既不压缩也不给缓存头）；2026-10-27 起 `/assets/*` 改由 `server/static.ts` 的 `serveDist` 发，带 gzip（`zlib` level 6）、`immutable` 长缓存和 ETag，实测 `index-*.js` 705,555 → 200,850 字节、`fonts-*.css` 459,218 → 200,798（都是 gzip 后），字体 woff2 不再被重复压缩。2506KB 仍是构建产物的大小，不是现在实际传输的量。不常用页面已经是 `lazy`（`web/src/App.tsx:35`），但 `ProjectsPage` / `HomePage` / `ChatPage` 仍然是同步 import，别把大库再塞进它们。
- 默认字体（2026-10-31，用户指定）：英文 Maple Mono NL、中文思源黑体、代码 Maple Mono NL，字间距 -0.02em、空格宽度 -0.2em；`defaultsVersion` 3 把还是系统字体的老设置迁过来一次。中文字体可选思源黑体、Maple Mono CN（`@automann/maple-mono-cn` 的 400 / 500 分片，`web/src/fonts-cjk-maple.css`，选了才加载；一个汉字两个英文宽、字距比思源黑体疏，600 以上浏览器加粗）、系统字体。Inter、IBM Plex Sans、系统界面字体仍可选。
- 字体（已瘦身）：`web/src/fonts.css` 只剩拉丁字母（IBM Plex Sans 6 片）、思源宋体 600（101 片，标题和品牌名用的 `--font-serif`）和等宽字体；思源黑体 400/600 拆到 `web/src/fonts-cjk.css`、Maple Mono CN 拆到 `web/src/fonts-cjk-maple.css`，设置里「中文字体」选了哪个内置字体才加载哪个（`web/src/lib/appearance.ts` 的 `ensureCjkFont` 看设置的 `cjkFont` 字段判断，不从字体列表里搜字体名；`primeCjkFont` 在设置取回来之前先按 localStorage 判一次，没记过就按默认值）。`Appearance.cjkFont` 默认是 `noto`（思源黑体，`shared/schema.ts`），`shared/settings.ts` 的默认值版本 3 迁移还会把旧设置里的 `system` 改成 `noto`，所以默认首屏会加载 `fonts-cjk.css`（按 unicode-range 只下载页面用到的分片）；只有手动选「系统字体」时界面中文才走苹方 / 微软雅黑、不下载任何中文字体文件（2026-10-31 按代码更正：此前这里写的「默认 `system`、首屏不下载中文字体」已经不成立）；500 档删掉了（`font-medium` 在这种情况下用 400 显示，界面上看和 400 一致，英文的 IBM Plex 仍有 500）。实测：`dist/assets/fonts` 405 个文件 12MB → 307 个 9.0MB，主 `fonts-*.css` 的 `@font-face` 416 → 113（另有独立的 `fonts-cjk-*.css` 202 个，只在选了对应的内置中文字体时加载），首屏字体请求 31 个 / 698KB → 8 个 / 369KB（只剩思源宋体分片和 Maple Mono；这组数是中文字体选「系统字体」时测的，默认的思源黑体还要加上它用到的分片）。
- Markdown 渲染缓存（`web/src/lib/workflow-doc.ts` 的 `renderDoc`）：模块级 LRU，最多 300 条、200 万字符，key 带上文本、团队成员、是否流式、`hljs` 是否加载完、当前语言——这几样都会改变输出（`@` 提及高亮、代码块高亮、代码栏的「复制」文案）。流式那段每 200ms 变一次，不写缓存，免得把有用的挤出去。组件里的 `useMemo` 只管住单个实例，切走再切回、blocks 重算、滚动回看都会重新解析：30 段 × 3 轮实测 27.9ms → 1.7ms。回归：`web/src/lib/workflow-doc.test.ts`（命中不新增、流式不占缓存、团队成员变了重新渲染、超上限按最久没用淘汰）。
- Markdown 样式只有一套（2026-10-30 用户要求「对话里的表格、标题、代码统一，md 文档也按这个渲染，每种元素能单独调」）：所有显示 Markdown 的地方都用 `components/tasks/Markdown.tsx`（对话回复、工作流 / 角色说明预览 `DocEditor`、项目文档、总结报告、更新说明、项目文件里的 .md 预览），样式类只有 `.chat-md`，窄面板加 `.chat-md-compact` 只改正文字号（`--md-base`）和间距系数（`--md-k`），不另写元素样式。每个元素的每个可调项登记在 `shared/markdown-style.ts` 的 `MD_SPEC`（默认值、范围、选项），设置 → Markdown 样式（`MarkdownSection.tsx`）、校验（`Appearance.markdown` 只存改过的项）、CSS 变量生成（`markdownCss`）都读它；默认值在 `index.css` 的 `:root` 里另写一份 `--md-*`（设置取回来前就要能画），`shared/markdown-style.test.ts` 对照两边。改过的项写进 head 里的 `<style id="md-style">`（自定义颜色要按 `:root` / `:root.dark` 分深浅两份，内联 style 做不到），并记进 localStorage `appearance-md`，`index.html` 加载时先套上。颜色只能选主题色角色或浅 / 深各一个值的自定义色，换配色、切深浅色都跟着变。给 Markdown 加新的块（比如总结格式里的结论框）时用这套 `--md-*` 变量，不另起一套颜色和圆角。
- 配色（2026-10-31 用户要求「参照 Claude Code 弄一套配色作为默认，之前的保留」）：`Appearance.palette` 默认 `code`（「Claude Code」：中性灰、蓝色链接、主按钮深色反白），原默认 `claude` 保留可选；`index.css` 的 `:root` / `.dark` 仍是「Claude」的基础值（不挂 `data-palette`），其余配色是 `[data-palette=…]` 覆盖块，没写的变量沿用基础值。「Claude Code」配色的部件外观（输入框外壳 `.composer-shell`、`IconButton` 的 `.icon-btn` 悬停 / 选中底、悬停提示 `.hint-surface`、分段轨道、滚动条）都写成 `[data-palette='code']` 前缀的覆盖，换回别的配色就是原来的样子；弹出菜单 / 弹层 / 提示的底色走 `--pop`（默认 = `--card`）。老设置靠 `defaultsVersion` 2 迁一次（`claude`→`code`、Inter→系统字体，见 `shared/settings.ts`）。布局不随配色变。
- 同一份对话以前在一次打开里传了三遍：`GET /api/tasks/:id` 2467KB（91ms）+ `POST /api/tasks/:id/seen` **又返回完整任务** 2467KB（133ms）+ SSE 的 `full` 事件 2726KB，三份都是同一个数组的重复序列化。**`/seen` 那份已在 2026-10-27 去掉**：接口只回 `{ turnSeenAt }`（41 字节），`TaskView.tsx` 的 `applySeen` 用 `web/src/lib/tasks.ts` 的 `withTurnSeenAt` 把新值合进本地那份（只换字段、不重造对话），`pushSummary` 把 `turnSeenAt` 变化算进「侧栏马上要反映的变化」（`important` 分支，不吃 1 秒节流），所以橙点立刻消失；首次打开时 `/seen` 常常比 `GET /:id` 先回来（后者要序列化整份对话），这时本地还没有任务，`applySeen` 改用全局列表里的摘要兜底（`tasks.find` → `upsertTask`），侧栏橙点不用等整份对话到齐。**未读怎么判仍然只有一处**：`shared/task.ts` 的 `taskTurnUnread` / `taskDoneDot`，`withTurnSeenAt` 不另造判断。**SSE 那份也不再重复传了**（2026-10-27 第二轮）：`useTaskStream` 建连时带上手头那份对话的版本（`taskMessageRev` 拼的 `<条数>:<最后一条消息 id>`，只在手上有整份时才有值），服务端用 `taskRevOffset` 对上前缀就只发 `patch`，对不上（消息被删、换了对话）才发 `full`；浏览器重连自动带 `Last-Event-ID`，同样只补发之后的变化。**没有基线就不建连**：`boot` 还没到时先不开 `EventSource`，否则服务端发的增量合并不了。同一份 4200 条 / 6.11MB 的对话实测：首包 `full` 6,401,764 字节 / 130.2ms → 带 `rev` 的 `patch` 78,851 字节 / 5.9ms。
- **首屏只取最近 50 条，往前翻页拿更早的（2026-10-27 第二轮）**：`TaskView.tsx` 打开时一律 `api.task(id, { limit: OPEN_MESSAGE_LIMIT })`（`OPEN_MESSAGE_LIMIT = 50`），服务端回 `messageTotal` / `messageHasMore`，页面据此在对话顶部给「显示更早的消息」按钮，点一下走 `loadEarlier`（`?before=<当前最早那条>`）往前接一页；**分页信息跟着当前那份任务走**（`truncated` ref），SSE 推来整份后按钮自动收起，不会同时挂着「还有更早的」和整份对话。实测同一条对话 `GET /api/tasks/:id`：全量 6,401,729 字节 / 63.3ms → `?limit=50` 77,310 字节 / 3.9ms（`?before=` 2.1–14.6ms）；整页打开的总传输从 12.21MB（同一份传两遍）降到 6.18MB。演示后端 `web/src/lib/demo-backend.ts` 的 GET 单任务同步支持 `limit` / `before`，否则演示版里这段翻页逻辑永远走不到。
- 最慢的单个请求曾经是 `GET /api/tasks/:id/children`：首跑 1131ms（`server/tasks/children-routes.ts` 里每个子对话一次 `worktreeStatus`，4 条 git，gate 并发 4），之后按 TTL 命中缓存降到 2–10ms。第二轮把服务端的 `UNMERGED_TTL` 从 10s 提到 15s、`STOPPED_TTL` 仍 60s，前端不再固定每 4 秒刷一次：`CHILD_POLL_ACTIVE_MS`（4000）/ `CHILD_POLL_IDLE_MS`（15000）按「有没有在跑」分档，判定读 `shared/task.ts` 的 `childSpinning`（和子对话行图标、执行中计数同一处，不另写一套），**列表为空时一次都不轮询**——子对话产生由 SSE 推来的 `childrenWorking` / `childrenCli` 和上报信号 `childSignal` 触发重拉（`childrenReload` ref）。实测：有子对话但都静止时请求间隔 15.2 / 15.0 / 15.0 / 15.0 秒；没有子对话时 12 秒内只有首拉 1 次。
- 对话里的附件图：卡片走缩略图（`/api/uploads/raw?path=…&w=160`，宽度是 `shared/schema.ts` 的 `ATTACHMENT_THUMB_WIDTH`，卡片本身 1.25em 见方，160 在 2 倍屏上还有 4 倍余量），点开看大图、复制图片仍取原图（`web/src/components/chat/AttachmentView.tsx` 的 `useAttachmentUrls` 同时给缩略图和原图两个地址，`shownImages` 按缩略图能不能加载出来决定要不要显示破图）。缩略图由 `server/thumbnail.ts` 用 `server/image.ts` 已有的 PNG 解码 / 缩放 / 编码生成（不引入图片库，服务端要打成单文件、不能带原生模块），缓存在 `<DATA_DIR>/cache/thumbs/<sha1(路径+大小+mtime+宽)>`，同一张图的并发请求只算一次、解码缩放串行做；解不开的格式（JPEG / WebP / 隔行扫描 PNG）和小图退回原图。消息里的 `<img>` 带 `loading="lazy" decoding="async"`，一屏之外的图滚到才取。同一批 48 张截图实测：原图 3501KB → 缩略图 266KB（`w=640` 要 2376KB），首屏不再为了 20px 的卡片下载原图；原图和缩略图都带 `cache-control: private, max-age=86400`。回归：`server/thumbnail.test.ts`、`web/src/lib/attachment-image.test.ts`。

复核方式（只读，不落工作区）：`curl -s -o /dev/null -w '%{time_total} %{size_download}' http://127.0.0.1:8787/api/tasks/<id>` 量单个接口（换成 `'...?limit=50'` 就能看到分页后的大小，响应里核对 `messageTotal` / `messageHasMore`，整份都在时还有 `messageRev`；SSE 增量用 `curl -N -H 'Last-Event-ID: <条数>:<最后一条消息 id>' http://127.0.0.1:8787/api/tasks/<id>/events` 看第一个事件是 `patch` 还是 `full`，版本号写错就应该回 `full`）；用 playwright 打开 `http://127.0.0.1:8787/#/projects/<项目>/<任务>`，等 `[aria-label="AI 有问题时问我"]` 出现算 ready，再读 `performance.getEntriesByType('resource')` 分类统计（脚本写在系统临时目录，不要提交）。注意打开对话页只写内存里的 presence，不改用户数据文件。
