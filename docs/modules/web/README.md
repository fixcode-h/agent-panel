- 元素引用的复制与跨窗口粘贴（`web/src/lib/element-ref.ts` 的 `ELEMENT_REF_MARK` / `wrapElementRef` / `parseElementRef` / `isElementRefText` / `pasteElementRefs`）：复制出去时在 `formatElementRef` 输出前加 `[元素引用]`（和首行同一行）、末尾另起一行加 `[/元素引用]` 标记，**原文一字不动**，所以粘到记事本、微信里仍是一段正常可读的说明文字、不带控制字符。粘回输入框时 `web/src/components/chat/composer-chips.tsx` 的 `onPaste` 先于「超长文字存 .txt」和「认本机路径换文件卡片」走 `pasteElementRefs`：认出的每块引用通过 `files.addQuote` 变回真正的引用卡片（背后是原文附件，见 `web/src/components/chat/Attachments.tsx` 的 `addQuote`），其余文字原位保留后 early return，因此引用不会被 `longPasteChars`（默认 5000）误判成 .txt 卡片；原来两条粘贴流程不变。识别很严：标记必须成对、内部第一行是「界面元素 」或「UI 设计控件 」摘要、并且有一行 `- 元素：<标签…`，只复制了一半标记的、或者只是在讲这个标记写法的按普通文字处理，不会被吃掉（`pasteElementRefs` 一段引用都没认出来时返回 `undefined`，交回原流程；返回的 `made` / `kept` 告诉调用方几块换了卡片、几块按原文留下，附件名额不够时据此提示一次）。卡片右键菜单的「复制内容」对元素引用复制的是带标记版（`wrapElementRef`），所以从输入框里复制出去的也能在别处还原。这样选是因为原文和标记都在剪贴板里，不依赖 localStorage（`web/src/lib/quote.ts` 的 `chat-quotes` 旧机制只用于读旧卡片，不跨浏览器、不跨实例），也不依赖服务端附件地址，换浏览器标签页、换面板实例都能还原。回归：`web/src/lib/element-ref.test.ts`（包装幂等、半截标记不认、孤立的头标记不吃掉后面的完整引用、多条、部分替换保留原文、普通文字不误判、超出附件名额时原文留下、选中卡片复制带出完整原文）、`scripts/ui/01-composer.mjs` 的「元素引用-复制」「元素引用-跨窗口粘贴」「元素引用-换浏览器环境粘贴」「元素引用-选中卡片复制」「元素引用-标记不完整」（最后一条：只粘一半标记时按普通文字进输入框，不出现引用卡片）。
  - 在输入框里**选中卡片按 Ctrl+C** 走的是 `RichInput` 的 `onCopy`（不是右键菜单）：卡片 DOM 上的文字是 `quoteLabel(name)`，即 `quoteName` 先把空白压平再截断到 40 个字加 `…`，靠浏览器原生复制带出去的就是这段摘要，粘回去既认不出标记、原文也丢了。所以 `onCopy` 用 `serialize(range, copyOf)` 按 `copyOf`（`useComposerChips` 的 `copyOfChip`）重写 `text/plain`：引用写带标记的完整原文、图片 / 文件写本机路径、Skill / 命令写 `/名字`，和右键菜单「复制内容 / 复制路径」共用同一份取值逻辑（菜单项也改成调 `copyOfChip`，不再各写一遍）。`copyOf` 缺失或返回 `undefined` 时退回卡片标记。**同时写 `text/html`**（`web/src/lib/clipboard-text.ts` 的 `setClipboardText` / `clipboardText` / `textToHtml`）：两种格式由同一份文字生成——`text/plain` 给面板自己的输入框（`onPaste` 只读 `getData('text/plain')`，所以加了 html 也不会覆盖卡片还原路径），`text/html` 把换行换成 `<br>`、外层 `white-space: pre-wrap` 并转义 `& < > "`，粘到 Word / Excel 里换行和行首缩进还在，不加字号颜色以免盖掉粘贴目标自己的格式。
  - **剪切选中内容**走同一个 `onCut` → `copySelection`：拦下原生剪切后用同一份序列化写两种格式，再自己 `range.deleteContents()` + `emit()`（`emit` 会让 `onChange` 按卡片名字对账，卡片背后的附件跟着去掉），光标放回删完的位置；不拦的话浏览器原生剪切写的仍是那段 40 字摘要。没选中输入框里的内容时 `copySelection` 返回 `null`，`onCopy` / `onCut` 都不 `preventDefault`，交回浏览器。
- 复制消息里的卡片与正文的分隔（`shared/composer.ts` 的 `copyText`）：卡片换成路径后，前后各补一个空格——不留的话「…截图-210356.png前面是抓取的元素」会被 `findPaths` 当成一整段路径（`PATH_RE` 的排除字符集只挡标点、不挡汉字，路径里本来就可以有汉字），`/uploads/resolve` stat 不到这个「文件」，粘贴时这一截永远变不回卡片、整条落成纯文本。卡片在开头 / 末尾时不补多余的空格，所以只有一张卡片时输出就是那个路径，`solePath` 仍认得出（复制对话、复制文件路径的行为不变）。引用卡片（附件里带 `quote`）复制的是存原文的 `quote-<编号>.md` 路径，服务端按文件名认回原文和引用卡片（`server/uploads.ts` 的 `/resolve`、演示版 `demoResolve` 同规则）；没有对应附件时留着卡片标记，不凭空编路径。回归：`server/composer.test.ts` 的「复制用户消息：卡片换成路径后和正文用空格隔开，粘回去能按路径认回卡片」、`scripts/ui/01-composer.mjs` 的「消息复制-粘贴成卡片」（发一条「正文 + 紧贴的图片卡片」，点消息的复制按钮，断剪贴板里路径后面不是直接贴着正文，粘回来是图片卡片、正文还在）。`copyText` 的 Skill / 命令分支（`!isAttachChip`）同样在贴着路径时补一个空格：正常发送时 `forSend` 已把 Skill / 命令提到最前并从正文摘掉，用户拼不出「路径紧跟技能卡片」的顺序，但手工造出这种输入时不再拼成 `D:\up\a.png/blender`；正常顺序的输出不变（用例里两条都锁了）。仍留一个极端分支没碰：卡片在附件里找不到（`attachOf` 返回空）时保留 `chipMarker` 的那一支没有 `afterPath` 处理，所以「缺附件 + 手工拼出路径紧跟技能卡片」时仍会拼成 `[图片:a.png]/blender`；`forSend` 已把 Skill 提到最前，真实输入构不出这个顺序，改它要再动一处正常输出的机会，暂不改。
