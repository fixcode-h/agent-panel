# 消息发出去一闪就没了：保活进程挂着两个「等下一句」，消息交给了收完尾的旧等待

- 状态：已修复（`server/exec/waiters.test.ts` 通过）
- 症状：对话停在等下一句时发消息，消息在对话里出现一下就消失，输入框已经清空，CLI 也没有任何回复；状态诊断日志里是「停下等下一句 waiters=2」之后「消息没有记进对话」
- 入口：`server/exec/runner.ts` 的 `listen`；`server/exec/waiters.ts`；`server/exec/rpc/session.ts` 的 `finish` → `keepAlive`
- 根因类型：并发的两次等待共用一个闭包变量，收尾时摘错了对象
- 模块：`server-exec`（`server/exec/runner.ts`、`server/exec/waiters.ts`）
- 关键词：保活、等下一句、waiters=2、消息没有记进对话、消息消失、插话、steer、Claude Code、闪一下

## 现象

用户 2026-11-02 复现（Claude Code，保活中）：在对话里插过一句话之后，再发消息时消息一闪就没了，输入框却清空了。诊断文件里：

1. 这一轮执行中插了一句（`交付：插进这一轮 how=steer`），CLI 先报这一轮结束（`停下等下一句 waiters=1`），又自己把排在输入里的插话当成新一轮跑完，再报一次结束（`停下等下一句 waiters=2`）。
2. 之后某次发消息只有「消息交给等下一句的 CLI」，没有「等下一句结束」，CLI 没有回应；用户停止后重开，新进程第一次停下就是 `waiters=2`。
3. 再发消息：`交付：等下一句 wait=ok` 之后是「消息没有记进对话」，页面上那条消息被服务端的对话覆盖掉。

## 根因

- RPC 会话每次收到结束记录都会调一次保活（`session.ts` 的 `finish` → `keepAlive` → runner 的 `listen`）。CLI 自己多跑一轮时，上一次的 `listen` 还没等到消息，就又挂上了一个。
- `listen` 用一个闭包变量 `waiter` 记「当前的等待」：第二次挂上时被覆盖成新的，先收尾的那个在 `done` 里按这个变量摘，摘掉的是新的，自己却留在等待表里。
- 等待表是模块级的，停止后也不清：之后的消息总交给表里最早的那个——已经收完尾、属于旧调用的等待。它把消息塞进旧调用的任务对象（服务端没记下，回「消息没有记进对话」），`done` 因为已经收过尾不再交给 CLI。

## 修复

- 等待的登记和摘除挪到 `server/exec/waiters.ts`，每个等待只摘它自己。
- 同一次调用里的「等下一句」用 `userWaitSlot`：新挂上的换下还挂着的旧的（旧的摘出等待表、不再接消息，Promise 留到停止时随 signal 结束，免得保活那头当成「不再等」关进程），日志记「换下仍挂着的等下一句」。

## 防线

- `server/exec/waiters.test.ts`：同一进程先后挂两个等待只留最新的、旧的收尾不影响新的、收完尾的不留在表里、重开后只有新挂上的、等子任务的等待各摘各的。
