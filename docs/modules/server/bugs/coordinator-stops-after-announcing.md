# 协调器说完下一步就停住，面板第三次没再推

- 状态：分析中（未修复；分析依据是用户导出的对话 `更新到最新版本`，面板 v0.28.2439，Claude Code + `deepseek-v4.1-flash`，强度 high）
- 症状：项目对话里，协调器做着做着回一句「我看一下 lock 里的标记，然后补装。」「我直接跑一下 Pi 的模型列表，同时查面板里这条 API 配置的 provider 字段。」就结束这一轮，没有调用工具；前两次面板发了「收尾自检」把它推起来，第三次没推，对话停在「等你回复」，看上去不知道接下来要做什么
- 入口：`server/tasks/run.ts` 的 `onTurnEnd` → `server/tasks/drive.ts` 的 `nudgePlan` → `nudgeNoPlan`；`server/exec/turn-info.ts` 的 `turnInfo`（`acts` 的算法）；`shared/turn-rules.ts` 的「回合怎么推进」
- 根因类型：模型提前结束回合（只说不做，CLI 正常报 end_turn）+ 没列计划时的兜底门槛按「这一轮」算，被推起来之后的那一轮动手不到 3 次、又以只读为主，兜底不触发
- 模块：`server`（`server/tasks/drive.ts`、`server/exec/turn-info.ts`）、`shared`（`shared/turn-rules.ts`、`shared/builtin/agents.ts` 协调器设定）
- 关键词：只说不做、提前结束回合、收尾自检、nudgeNoPlan、PLAN_ACTS、acts、只读不算、没有计划、协调器、deepseek、中断、等你回复、插话

## 根因

### 1. 模型在说完打算后结束回合（实测，来自导出记录）

3 次停下都是同一个形状：一段思考把下一步想清楚了（「先看这些」「先读这些」「先找 API 配置」），接着一条只有「我看一下……」「我直接跑一下……」的文字，然后 end_turn。整段对话里协调器 13 条带文字的回复，文字和工具调用从不在同一条消息里：通常是「一条文字 + 紧跟一条工具调用」，有 3 次文字之后就没有下文了。

提示词已经明确禁止这样做：通用约束里的「回合怎么推进」（`shared/turn-rules.ts`）写着「不要单独发一条只有打算或阶段说明、没有工具调用的回复」「不要只回一句『我先看一下』就结束回合」。这个对话的「通用约束」角色在用，规则确实发下去了（导出的 `agents` 里有「通用约束」），模型照样违反。这不是第一次：[chat-ends-turn-after-announcing](./chat-ends-turn-after-announcing.md)、[child-ends-turn-with-plan-open](./child-ends-turn-with-plan-open.md)、[parent-ignores-wrap-request](./parent-ignores-wrap-request.md) 记的都是 `deepseek-v4.1-flash` 的同一个行为。结论：这个模型靠提示词约束不住，只能靠面板兜底。

可能加重它的因素（读记录推断，没有对照实验）：

- **角色里的取舍让它反复犹豫**。思考里多次在争「父对话能不能装依赖」「用户报的 Bug 要不要用 `create_conversation` 开 `kind: "bug"` 的子对话」「父对话分析只做到判断模块为止」，最后又自己就地查了下去。第 3 次停之前的思考有 12.9 秒，是整段最长的，里面列了一长串候选根因和「先别猜了」。犹豫越久，越容易写完一句打算就收尾。
- **一个对话里接了两件事**。「更新」还没收尾，用户插话要查 Pi 报错，协调器把两件事串在同一轮里做，中间没有任何计划记录进度。

### 2. 第三次停下时面板的兜底没有触发（读代码确认）

没列计划的对话只有「收尾自检」这一道兜底（`server/tasks/drive.ts` 的 `nudgeNoPlan`）。它的入口条件是：

```ts
const silent = turn.tools === 0 && fresh
if (!silent && turn.acts < PLAN_ACTS) return false // PLAN_ACTS = 3
```

`turn.acts` 只数**这一轮**里的跑命令和改文件（`server/exec/turn-info.ts`：`kind === 'run' || kind === 'edit'`），读文件、搜索不算。

- 第 1、2 次停：所在那一轮分别跑了 6 次、3 次命令，过了门槛，推了。
- 第 3 次停：那一轮是被第 2 次自检推起来的，只有 1 次 `rg`/`ls`（run）和 2 次读文件。`acts = 1 < 3`，又不是「新输入后第一轮零工具」（`silent` 为假），函数第一行就返回了。所以没推，**也没写「收尾自检」日志**：诊断里看不出面板为什么没管。

预算不是原因：同一条输入（用户的插话）后最多自检 2 次，当时只用了 1 次；总次数上限（10）也远没到。

门槛这么设的本意（ADR 0041 第 3.4 节）是「动手三步以上的事才可能做了一半，小事不推」。它漏掉两种情况，这次正好都碰上：

1. **被推起来之后的那一轮天然很短**：自检把它推起来，它做一两步又停，这一轮的 `acts` 从 0 重新数，几乎不可能再到 3。也就是说，自检只能救第一次中断，救不了「推一下走一两步又停」。
2. **排查类的事以读为主**：读文件、搜代码不算动手，查问题的对话哪怕读了十几个文件、做到一半，也触发不了自检。

### 3. 没有计划，所以更强的那道兜底用不上（读代码确认）

列了计划的对话走 `nudgePlan`：计划没做完就推，同一进度最多推 `nudgeMax` 次（默认 6），推满了还留一行警告。这次协调器一直没调 `set_plan`。它的设定（`shared/builtin/agents.ts`）写的是「要改代码的任务动手前……写计划，只读的问答和排查不用」，自检文案本身也说「不用列计划」。更新依赖、排查报错按规则都不需要计划，于是只剩门槛偏高的收尾自检。

### 不是原因的几项

- **技能没更新**：这个对话没有读、也没有用到任何自带技能（工具调用里没有读 `skills/`），中断和技能版本无关。回合规则和兜底逻辑都在面板代码里。导出的 `app: 0.28.2439` 就是刚合并的版本，所以分析针对的是当前代码。
- **用户插话**：插话按 steer 投递，模型收到了，也处理了（00:49:04 起转去查 Pi），没有丢消息。它只是把收尾自检计数的「输入」换成了插话那条，不影响结论。
- **导出显示 `stopped`**：导出时 CLI 停在保活上（`awaitingUser: true`），这一轮的 `end: panel` 是导出时记的，不是面板把它停掉的。

## 修复方向（待确认，未动代码）

按「改动小、不解析回复文字」的顺序列：

1. **自检门槛按「这条输入以来」累计，不按单轮算**（`nudgeNoPlan`）：同一条用户输入之后跑命令、改文件的总次数到了 3，之后每次没列计划就收尾都做自检；次数仍受「同一条输入最多 2 次」和 `nudgeMax` 限制。这样「推一下走一两步又停」也能接住。这条直接修掉本次第 3 次停住。
2. **读文件、搜索也算进门槛，权重低一些**（例如每 3 次只读算 1 次动手），让排查类对话做到一半也有兜底。
3. **门槛没过时也写一行「收尾自检」日志**（`action: none, reason: few-acts, acts: n`），下次能直接从诊断里看出为什么没推。
4. **自检次数和设置挂钩**：现在没调工具的最多 1 次、动了手的最多 2 次是写死的。对已知会只说不做的模型，用户把「提醒次数」调高时应该一起放宽。按硬规则，模型差异写进模型设置或 CLI 定义里的字段，不按模型名分支。
5. **协调器设定**（可选，需要再定）：一个对话里有两件以上的事，或者排查预计要跨多个文件时，要求先 `set_plan`，让它走计划推进那道更强的兜底；同时理清「排查是就地做还是派子对话」的规则，减少犹豫。

建议先做 1 和 3，补一个 e2e：假 CLI 第一次停下前跑 3 条命令，被自检推起来之后只跑 1 条命令就只说不做；断言面板推了第二次、对话接着做完。
