# 协调器说完下一步就停住，面板第三次没再推

- 状态：分析中（未修复；分析依据是用户导出的两个对话：`更新到最新版本`、子对话 `修复 Pi models.json 写入校验`，面板 v0.28.2439，Claude Code + `deepseek-v4.1-flash`，强度 high）
- 症状：项目对话里，协调器做着做着回一句「我看一下 lock 里的标记，然后补装。」「我直接跑一下 Pi 的模型列表，同时查面板里这条 API 配置的 provider 字段。」就结束这一轮，没有调用工具；前两次面板发了「收尾自检」把它推起来，第三次没推，对话停在「等你回复」，看上去不知道接下来要做什么
- 入口：`server/tasks/run.ts` 的 `onTurnEnd` → `server/tasks/drive.ts` 的 `nudgePlan` → `nudgeNoPlan`；`server/exec/turn-info.ts` 的 `turnInfo`（`acts` 的算法）；`shared/turn-rules.ts` 的「回合怎么推进」
- 根因类型：Claude Code 把 end_turn 当「做完了」，`deepseek-v4.1-flash` 写说明时约 14% 会在没生成工具调用时就 end_turn；面板只能在这一轮结束后另发提醒补救（有计划时必然看到提醒），没计划时兜底门槛按「这一轮」算又有漏洞
- 模块：`server`（`server/tasks/drive.ts`、`server/exec/turn-info.ts`）、`shared`（`shared/turn-rules.ts`、`shared/builtin/agents.ts` 协调器设定）
- 关键词：只说不做、提前结束回合、收尾自检、nudgeNoPlan、PLAN_ACTS、acts、只读不算、没有计划、协调器、deepseek、中断、等你回复、插话、有计划也停、计划推进、面板提醒、end_turn、Stop 钩子、stop_hook_active、--settings

## 根因

### 1. 模型在说完打算后结束回合（实测，来自导出记录）

3 次停下都是同一个形状：一段思考把下一步想清楚了（「先看这些」「先读这些」「先找 API 配置」），接着一条只有「我看一下……」「我直接跑一下……」的文字，然后 end_turn。整段对话里协调器 13 条带文字的回复，文字和工具调用从不在同一条消息里：通常是「一条文字 + 紧跟一条工具调用」，有 3 次文字之后就没有下文了。

提示词已经明确禁止这样做：通用约束里的「回合怎么推进」（`shared/turn-rules.ts`）写着「不要单独发一条只有打算或阶段说明、没有工具调用的回复」「不要只回一句『我先看一下』就结束回合」。这个对话的「通用约束」角色在用，规则确实发下去了（导出的 `agents` 里有「通用约束」），模型照样违反。这不是第一次：[chat-ends-turn-after-announcing](./chat-ends-turn-after-announcing.md)、[child-ends-turn-with-plan-open](./child-ends-turn-with-plan-open.md)、[parent-ignores-wrap-request](./parent-ignores-wrap-request.md) 记的都是 `deepseek-v4.1-flash` 的同一个行为。结论：这个模型靠提示词约束不住，只能靠面板兜底。

可能加重它的因素（读记录推断，没有对照实验）：

- **角色里的取舍让它反复犹豫**。思考里多次在争「父对话能不能装依赖」「用户报的 Bug 要不要用 `create_conversation` 开 `kind: "bug"` 的子对话」「父对话分析只做到判断模块为止」，最后又自己就地查了下去。第 3 次停之前的思考有 12.9 秒，是整段最长的，里面列了一长串候选根因和「先别猜了」。犹豫越久，越容易写完一句打算就收尾。
- **一个对话里接了两件事**。「更新」还没收尾，用户插话要查 Pi 报错，协调器把两件事串在同一轮里做，中间没有任何计划记录进度。

### 2. 第三次停下时面板的兜底没有触发（读代码确认）

没列计划的对话只有「收尾自检」这一道兜底（`server/tasks/drive.ts` 的 `nudgeNoPlan`）。它的入口条件是：

```ts
const silent = turn.tools === 0 && fresh
if (!silent && turn.acts < PLAN_ACTS) return false // PLAN_ACTS = 3
```

`turn.acts` 只数**这一轮**里的跑命令和改文件（`server/exec/turn-info.ts`：`kind === 'run' || kind === 'edit'`），读文件、搜索不算。

- 第 1、2 次停：所在那一轮分别跑了 6 次、3 次命令，过了门槛，推了。
- 第 3 次停：那一轮是被第 2 次自检推起来的，只有 1 次 `rg`/`ls`（run）和 2 次读文件。`acts = 1 < 3`，又不是「新输入后第一轮零工具」（`silent` 为假），函数第一行就返回了。所以没推，**也没写「收尾自检」日志**：诊断里看不出面板为什么没管。

预算不是原因：同一条输入（用户的插话）后最多自检 2 次，当时只用了 1 次；总次数上限（10）也远没到。

门槛这么设的本意（ADR 0041 第 3.4 节）是「动手三步以上的事才可能做了一半，小事不推」。它漏掉两种情况，这次正好都碰上：

1. **被推起来之后的那一轮天然很短**：自检把它推起来，它做一两步又停，这一轮的 `acts` 从 0 重新数，几乎不可能再到 3。也就是说，自检只能救第一次中断，救不了「推一下走一两步又停」。
2. **排查类的事以读为主**：读文件、搜代码不算动手，查问题的对话哪怕读了十几个文件、做到一半，也触发不了自检。

### 3. 没有计划，所以更强的那道兜底用不上（读代码确认）

列了计划的对话走 `nudgePlan`：计划没做完就推，同一进度最多推 `nudgeMax` 次（默认 6），推满了还留一行警告。这次协调器一直没调 `set_plan`。它的设定（`shared/builtin/agents.ts`）写的是「要改代码的任务动手前……写计划，只读的问答和排查不用」，自检文案本身也说「不用列计划」。更新依赖、排查报错按规则都不需要计划，于是只剩门槛偏高的收尾自检。

### 不是原因的几项

- **技能没更新**：这个对话没有读、也没有用到任何自带技能（工具调用里没有读 `skills/`），中断和技能版本无关。回合规则和兜底逻辑都在面板代码里。导出的 `app: 0.28.2439` 就是刚合并的版本，所以分析针对的是当前代码。
- **用户插话**：插话按 steer 投递，模型收到了，也处理了（00:49:04 起转去查 Pi），没有丢消息。它只是把收尾自检计数的「输入」换成了插话那条，不影响结论。
- **导出显示 `stopped`**：导出时 CLI 停在保活上（`awaitingUser: true`），这一轮的 `end: panel` 是导出时记的，不是面板把它停掉的。

- 01:01:25：面板「计划推进」：「你的计划才做了 4/8……」，它马上接着做，导出时还在跑（`working: true`）。

| 对话                                  | 带文字的回复 | 只有工具调用的消息 | 文字之后没有工具、这一轮就结束 |
| ------------------------------------- | ------------ | ------------------ | ------------------------------ |

- **停下的全部发生在「写了一句说明」的那一次回应上**，28 次说明里停了 4 次（约 14%）；只调工具、不写说明的回应一次都没停过（它本来也停不了：没有文字也没有工具就是空回应）。
- 4 次停下前的思考都比平时长：2.0 秒、5.5 秒、12.9 秒、11.5 秒，带文字回复的思考中位数只有 1.2–1.7 秒。相关但不是必然：一次 30.6 秒的思考后它照样接着调了工具。

## 最根本的原因

**Claude Code 把「模型这次回应没有工具调用（end_turn）」当成「这件事做完了」。这条约定对 Claude 模型成立，对 `deepseek-v4.1-flash` 不成立。** 面板目前在 CLI 已经报了结束之后，才用一条新消息去补救。

1. **代理循环本身没有区别**。面板用 `-p --input-format stream-json` 起 Claude Code，和平时在终端里用是同一个代理循环：模型回应带工具调用就执行再问，回应没有工具调用这一轮就结束。中间没有任何「面板把它停掉」的环节，两份导出里 CLI 都是自己报的结束。
2. **「正常对话」看起来不停，是因为它短**。一问一答或一次排查，模型说几句、调几次工具就到了该给结论的时候，这时 end_turn 正好就是对的。有计划的事动辄几十次回应、十几次写说明。照上面约 14% 的概率，15 次说明一次都不停的机会只有 0.86^15 ≈ 10%。**任务越长、越有计划，就越几乎必然中途停一次**。用户看到的「有计划就一定会出提醒」就是这么来的：提醒是结果，不是原因。
3. **这个模型把说明和工具调用当成两件事**。它几乎每次都先写一句说明，再在后面跟工具调用（两份导出里文字和工具从不在同一条消息里）。每一句说明都是一次「要不要就此结束」的分叉，偶尔就走到了结束那一边。提示词（`shared/turn-rules.ts`）已经明说「不用先说明、不要只说打算就结束」，它照样这么写，所以靠提示词压不住。
4. **面板现在的补救是「事后、另起一轮、看得见」的**：CLI 报结束 → 面板等 `PLAN_NUDGE_MS`（2 秒）停稳 → 复查 → 发一条【面板】消息开新的一轮。所以对话里会多出一个提醒气泡；次数有上限（计划推进 `nudgeMax`，收尾自检 1–2 次）；没计划时还有本文前半段说的门槛漏洞。

## 最优方案：用 Claude Code 的 Stop 钩子在同一轮里拦住（已用模拟模型实测可行）

Claude Code 的 `Stop` 钩子在模型准备结束这一轮时调用。钩子输出 `{"decision":"block","reason":"…"}` 时，Claude Code 不结束这一轮，把 reason 交给模型接着生成。钩子输入里带 `stop_hook_active`，已经被拦过一次时为 true，可以用来防止死循环。钩子配置可以通过 `--settings <JSON>` 在启动时传进去，不用改用户自己的设置文件。

实测（本机 Claude Code 2.1.318，`ANTHROPIC_BASE_URL` 指向一个本地模拟服务器，`-p --input-format stream-json --output-format stream-json --settings`）：

1. 模拟模型第一次回应「我先看一下文件。」+ Bash；第二次只回「我再看一下 lock 里的标记，然后补装。」，`end_turn`（复现只说不做）。
2. Stop 钩子返回 `block`，reason「计划还差第 6 步：接着调用工具去做」。
3. Claude Code **没有输出 result**，把「Stop hook feedback: 计划还差第 6 步……」交给模型；模型接着调用 Bash，最后给出结论；第二次触发时 `stop_hook_active: true`，钩子放行。
4. 整个过程只有**一个** result（`num_turns: 4`），流里多了 `hook_started` / `hook_response` 两个事件。钩子收到的字段有 `session_id`、`transcript_path`、`stop_hook_active`、`last_assistant_message`、`background_tasks` 等。

对比现在的「面板提醒」：

|                    | 现在：CLI 结束后发【面板】消息                             | Stop 钩子                                                |
| ------------------ | ---------------------------------------------------------- | -------------------------------------------------------- |
| 发生在             | 这一轮结束之后，等 2 秒再复查                              | 这一轮结束之前，同一轮里                                 |
| 用户看到           | 对话里多一条【面板】提醒，状态先变「等待」再变回「运行中」 | 没有提醒气泡（面板可以在流里认出 hook 事件，记一行日志） |
| 能不能被别的事插队 | 能：2 秒内后台结果、插话、回收都会让复查取消               | 不会：还在同一轮里                                       |
| 判断依据           | 面板的计划、等待状态                                       | 一样：钩子问面板，面板按同样的规则答                     |

做法要点（待定稿再写 ADR）：

- **钩子只做转发，判断全在面板**：钩子脚本把 `session_id` 和对话 id（启动时写进环境变量）发给本机面板（只监听 127.0.0.1，带面板令牌）。面板复用 `planStalled`、等待状态（提问、子对话、后台命令、收尾请求）的判断，回答 block 加 reason（「计划第 6 步『跑 typecheck、lint、test:affected』还没做：直接调用工具去做」）或放行。面板没响应、超时一律放行，不能因为钩子卡住对话。
- **有计划时**：计划没做完、也不在等任何结果，就拦住。同一进度连续被拦的次数仍受 `nudgeMax` 和 `DriveBudget` 限制，拦满了放行并按现在的方式留警告。
- **没有计划时**：这一轮从这条输入以来动过手（跑命令、改文件，或读了几个文件），且这次还没拦过（`stop_hook_active` 为 false），拦一次，reason 用收尾自检那句：「做完了就用一两句话给结论；没做完就直接调用工具接着做」。这样一并修掉本文前半段的门槛漏洞。代价是这类回合在真正收尾时多一次很短的模型回应，不出现在对话里。
- **按 CLI 定义走**：在 `shared/clis/claude.json` 里加一个声明「支持 Stop 钩子、怎么传」的字段（例如 `stopHook: { "settingsFlag": "--settings" }`），代码按字段判断，不按 CLI 名字分支（`scripts/rules-check.mjs`）。没有这个字段的 CLI（Codex、Pi、Command Code）继续用现在的「计划推进 / 收尾自检」，并按下面的第 1–3 条补门槛漏洞。
- **测试**：e2e 里假 CLI 本来就不跑真的 Claude Code，钩子这一层要单测钩子的问答（`planStalled` 各种状态 → block/放行），再加一个可选的真 Claude Code + 模拟模型的冒烟脚本（就是上面这次实测的做法，放 `scripts/`，CI 里有 Claude Code 时才跑）。

不推荐的方向：

- **只改提示词**：已经写得很明确，模型照样违反，两份导出都证明了。
- **解析回复文字判断「是不是只说了打算」**：ADR 0041 已经定了不解析文字；而且有了钩子就没必要猜。
- **换掉 high 强度或关思考**：停下前思考偏长只是相关，没有对照实验。关思考会降低改代码的质量，不值得。可以作为用户自己的选择，不作为修复。

## 其他 CLI 的兜底（Stop 钩子覆盖不到的部分）

按「改动小、不解析回复文字」的顺序列：

1. **自检门槛按「这条输入以来」累计，不按单轮算**（`nudgeNoPlan`）：同一条用户输入之后跑命令、改文件的总次数到了 3，之后每次没列计划就收尾都做自检；次数仍受「同一条输入最多 2 次」和 `nudgeMax` 限制。这样「推一下走一两步又停」也能接住。这条直接修掉本次第 3 次停住。
2. **读文件、搜索也算进门槛，权重低一些**（例如每 3 次只读算 1 次动手），让排查类对话做到一半也有兜底。
3. **门槛没过时也写一行「收尾自检」日志**（`action: none, reason: few-acts, acts: n`），下次能直接从诊断里看出为什么没推。
4. **自检次数和设置挂钩**：现在没调工具的最多 1 次、动了手的最多 2 次是写死的。对已知会只说不做的模型，用户把「提醒次数」调高时应该一起放宽。按硬规则，模型差异写进模型设置或 CLI 定义里的字段，不按模型名分支。
5. **协调器设定**（可选，需要再定）：一个对话里有两件以上的事，或者排查预计要跨多个文件时，要求先 `set_plan`，让它走计划推进那道更强的兜底；同时理清「排查是就地做还是派子对话」的规则，减少犹豫。

Claude Code 走 Stop 钩子以后，这几条只对其他 CLI 起作用。建议先做 1 和 3，补一个 e2e：假 CLI 第一次停下前跑 3 条命令，被自检推起来之后只跑 1 条命令就只说不做；断言面板推了第二次、对话接着做完。
