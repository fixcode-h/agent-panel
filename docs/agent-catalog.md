# 内置 Agent 与工作流职责清单

这份清单是**判定标准**：新增、合并、删除内置 Agent 和工作流之前先对照它，避免又按具体操作把角色拆碎。

## 分工原则

1. **一个 Agent 管一个能力块**，不是管一个动作。能力块是「能独立交付一类结果」的职责，例如「测试与验收」交付带证据的结论；
   「跑单元测试」「跑 e2e」「编译」都是这一类里的具体步骤，交给参数和项目配置决定。
2. **具体做法由参数和项目配置决定**。同一个 Agent 在 Node 项目和 UE 项目里跑的命令不同，靠 `TestStep` 和 `AgentParam` 区分，
   不靠新建 Agent。
3. **工作流负责顺序和门禁**，Agent 负责一类工作。工作流里不要为了「多一个节点」而引入职责重复的 Agent。
4. **通用 Agent（`common: true`）之间不能重复**：同一件事只能有一个通用 Agent 能接（`server/agent-params.test.ts` 会检查测试 Agent 只有一个）。
5. **分两层**（[ADR 0023](adr/0023-role-layers-and-triage.md)）：**基本角色**是一个能力块，派成子任务、当工作流节点、被挂载；**高级角色**是父对话、子对话的负责人，挂载几个基本角色，每个能力定好用法（自动判断 / 就地用 / 派成子任务 / 转交父对话）。需要「一个角色会好几件事」时做成高级角色挂载基本角色，不要把能力的做法抄进它的设定，也不要为它新建一个大而全的基本角色。只挂一层：高级角色不挂高级角色。

## 判定标准

| 判定     | 什么时候用                                                                                                                         |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **删除** | 职责被别的 Agent 完整覆盖；没有任何内置工作流用到；只是换个名字的重复项                                                            |
| **合并** | 同一能力块被切成多个（例如测试 / 验收 / 编译那四个，`docs` 和 `docsync`）                                                          |
| **扩充** | 能力块太大但缺参数或交付标准，换个项目就不能用（例如测试 Agent 缺环境 / 范围参数；版本控制缺 SVN、分支 / worktree 模式和合并方向） |
| **新增** | 现有能力链里确实缺这个角色，且不会被同批 Agent 顺手做掉                                                                            |

新增时的硬条件：写清职责、参数、要用的 Skill（必须是 `skills/` 里存在的，或 `{{槽名}}`），
并且回答「为什么现有 Agent 做不了」。
Chat 类角色只按 Chat 模式的需要增删（回答、读写文件、跑命令、CLI 自带的待办），不复制 Agent 侧的能力块（分派、工作流、挂载、收尾）。

## 必备角色

`orchestrator`（协调器，原名主理、统筹）、`worker`（执行）、`docsync`（文档）、`reviewer`（评审）、`tester`（测试验收）、`vcs`（版本控制）、`helper`（子任务）、`analyzer`（排查分析）是项目对话离不开的八个能力块，再加 Chat 页的 `chat`（助手），共九个必备角色，
定义在 `shared/builtin/core.ts`：启动时自动装好、不能删除，名称、角色设定、Skill、能力开关和参数定义每次启动按内置定义同步，
用户只能改参数取值和运行配置（CLI、模型、思考强度、权限），项目里还能在 `Project.agentParams` 按项目覆盖参数。
其中协调器、执行、排查分析是高级角色，挂载其余基本角色：默认挂哪些、规则、预加载由定义维护；用户在「能力」页加、删挂载或改说明后由用户接管（`mountsCustom`，可一键恢复默认，见 [ADR 0026](adr/0026-advanced-role-mounts-user-owned.md)）。评审是 `independent`，只能派出。
它们之间靠名字协作（协调器和执行把要落盘的文档派给「文档」、把验证派给「测试验收」、收尾时在完整测试前派「评审」、把改完文件后的版本管理交给「版本控制」），所以不能被改成别的角色。
「评审」的时机是子对话收尾：改完并跑过快速检查之后、跑完整测试和编译之前，派它看限定范围的 diff。
评审必须在子对话的计划里占一条独立的主步骤（标 `review: true`）：派的时候标等待中、拿回结论后标完成，
计划面板上能看到这一步和它的状态；按意见修改、复看也各自单列成步。
`submit_merge` 前面板会校验：计划里有标 `review` 的步骤、那一步已完成、评审第一行写了验收结论
（`shared/review-gate.ts`；先读首行，首行没有结论才退回全文最后一条——子任务输出太长时只保留开头，结论写在末尾会被截掉）；
评审列了高级（🔴）或中级（🟠）时，执行角色要逐条写处置（`review_triage`）才合得回去；评审只看代码、不跑测试（[ADR 0010](adr/0010-review-code-only.md)）。用户明确要求带着已知问题合并时，执行角色在 `submit_merge` 传 `review_override` 放行，记录（谁 / 何时 / 为什么 / 原本拦住什么）进任务详情、收尾消息和交接摘要（[ADR 0022](adr/0022-review-gate-override.md)）。
「分析」是面板上所有「AI 分析」「AI 排查」开出的对话默认用的角色，开在哪里由 `shared/analysis-home.ts` 统一决定（见 [ADR 0014](adr/0014-ai-analysis-home.md)）。
「助手」（`chat`）是 Chat 类：Chat 页没选角色的对话（`agentId` 为空，含旧对话）运行时都按它跑，引入「聊天约束」；它的运行配置不生效（Chat 页在输入框选 CLI 和模型），也不进项目设置的必备角色参数区（Chat 没有项目）。
「子任务」（`helper`）保留定义、但**不作为可选角色展示**：它是 `spawn_agents` 不点名时的默认执行角色（`shared/engine.ts` 按 `isHelperAgent` 找它），删了所有子任务就没有默认角色和提示词了；
角色页、内置角色弹窗和角色选择器都按 `shared/builtin/core.ts` 的 `listableAgents` 把它去掉，计数、分组、搜索也不算它，停用和删除由必备角色保护拦下。
改这几个的定义时不用补旧指纹，同步会直接换成新版本；只要保证参数 key 不乱改（改了 key 用户填的值会丢）。
其他内置角色也一样（[ADR 0015](adr/0015-builtin-roles-follow-definition.md)）：设定由面板维护、每次启动和保存都按定义同步，用户只改参数取值、运行配置、分类、标签和启用；区别只是可以删除、可以停用。

### 角色的类别（Chat / Agent）

角色分两类（`AgentInput.scope`，[ADR 0038](adr/0038-chat-roles.md)），各自只在对应的模式里用：

- **Agent 角色**（`agent`，默认）：项目里的对话、子对话、工作流节点、子任务、挂载、通用角色。旧数据没有这个字段，一律按 Agent 角色读。
- **Chat 角色**（`chat`）：只在 Chat 页（没有项目的顶层对话）用。不挂能力、不当通用角色、不分派、不跑工作流，保存时服务端把这些字段归零；只能引入 Chat 角色。内置的是「聊天约束」（`chat-rules`，通用约束的精简版）和必备的「助手」（`chat`）。
- 类别建好不能改：要换就在角色页「复制为另一类」。各入口（新建对话、换角色、定时任务、项目默认角色、工作流、挂载）都按类别校验，选择器只列对应的一类。
- 唯一例外是面板开的「AI 分析」：归不到项目时开在 Chat，用必备角色「分析」（Agent 类），按 `analysis` 字段放行。

### 在哪类对话里能启动（禁止子对话执行）

角色上有一个运行方式开关，字段内部名 `runIn`，界面上叫「禁止子对话执行」，语义是**子对话里不能执行这个角色**（见 [ADR 0019](adr/0019-agent-run-in-parent.md)）：

- `any`（默认）：任何对话里都能直接派它，行为和以前完全一样。
- `parent`：子对话里点名它时不在子对话里跑，面板把它转交父对话创建子任务；子对话点名的计划步骤立即标完成、不挂等待，收尾不被它拦住。
  父对话接不了（没有父对话、父对话自己也是被派出来的子对话）时 `spawn_agents` 返回明确原因，不静默。
- 内置角色默认值：只有 `docsync`（文档）是 `parent`——补文档是长活，而且不依赖子对话本地的分支和 diff。
  `tester`、`vcs`、`reviewer` 保持 `any`：测试重活由 [ADR 0018](adr/0018-test-steps-run-in-parent.md) 的「测试步骤只在父对话里跑」兜住，版本控制在子对话里本来就禁止派，评审必须在子对话看本地 diff。
- 用户可以给任意角色（包括内置角色）改这个开关，保存后下一次 `spawn_agents` 立即生效；内置角色的设定同步（`syncCore`）保留用户选的值，只对已装的旧副本做一次「文档」默认值升级。

`worklog`（每日工作总结）是唯一只输出报告的角色：`docsync` 负责写文档、`explorer` 只读调研代码、`orchestrator` 负责调度，
没有谁会按天把各项目执行过的对话压成一份报告，所以单独新增；它不动代码（`canPlan` / `canDelegate` 都关、不引 Skill）。
它挂进「通用项目」的 `members`：`ensureProjectAgents` 启动时按 `builtinAgentKeys(GENERAL)` 补建角色，
挂在这里才能保证它跟着最基础的安装集合一起建出来。

`uiqa`（界面走查）2026-10-29 新增：评审只读代码、不跑（ADR 0010），测试验收只跑项目配的命令，没有谁会真的打开页面按亮暗主题、宽窄屏看布局和状态；它只看不改，交回带截图的分级清单。
`i18n`（本地化）同批新增：开发管代码、文档管文档，界面文案的译文要拿已有译文当术语表逐条对齐、查漏翻和写死的文案，是单独一类交付。
同批的「重构」「安全评审」是已有能力块的变体，加成 `developer.task` 和 `reviewer.target` 的选项，没有新建角色。

`tester.task` 的「设计用例」「补测试」（2026-10-29，[ADR 0030](adr/0030-delivery-contracts-between-roles.md)）：独立于实现者再想一遍用例是「测试与验收」能力块里的一档，不另建「测试设计」角色——
它和「评审」一样靠独立视角起作用（实现者写的测试只覆盖它想到的路径），所以挂在执行上是 `subtask` 派出，不就地用。
同一批评估过、**没有**新增或合并的：`helper`（子任务）和 `explorer`（调研）都只读（2026-11-03 起都不再自己写模块文档，要点交「文档」，ADR 0048），但 `helper` 是 `spawn_agents` 不点名时的引擎兜底（`isHelperAgent`），
合并会动引擎，收益只是少一份短设定；`spec`（规范撰写）绑着 OpenSpec 的命令和门禁，并进 `analyst` 会让方案设计每次都带一段用不上的流程；`i18n` 并回 `developer` 会丢掉「拿已有译文当术语表」这类独立交付标准。
现有 17 个角色里没有职责被别的角色完整覆盖的，前几轮已经合掉 12 个（见下表），这次不再删。
同日的「清理用例」（[ADR 0031](adr/0031-test-count-report-not-cap.md)）：用例总数不再设上限，重复、被覆盖、过时的用例由它定期一次列出一批候选（只认三类淘汰理由），用户确认后才删。

### 交付契约：角色之间按固定小节交接

角色各自的方法再细，交接时没有固定格式，下游还是要靠追问补信息（Bug 交回只有结论和改了什么，复现、证据链、回归测试都要再问一轮；方案的验收标准是一句话，开发和测试各按自己的理解验）。
2026-10-29 起，`shared/builtin/agents.ts` 里几段共用正文定成契约，上游按它交、下游按它核，缺了哪一节一眼能看出来：

| 契约                                                                                                                | 常量                                       | 谁写                                             | 谁核 / 谁用                                                                  |
| ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ | ------------------------------------------------ | ---------------------------------------------------------------------------- |
| 派单单（目标 / 交付物与验收标准 / 范围 / 已知 / 假设）                                                              | 协调器设定里的「派单写什么」               | 协调器派子对话                                   | 执行接单先复述，缺验收标准就 `message_parent` 问回                           |
| 现象卡（期望 vs 实际 / 触发 / 环境 / 频率 / 何时开始坏 / 报错原文）                                                 | `BUG_FULL_TEXT` 立案、协调器「Bug 怎么交」 | 协调器派 Bug；执行、开发读代码前自己钉           | 子对话从「以前好过」直接查最近改动，不从头翻模块                             |
| 方案摘要（目标 / 现状 / 方案与备选 / 改动清单 / 实现顺序 / 验收标准带测试层级 / 风险与回滚 / 待确认）               | `DESIGN_BRIEF_TEXT`                        | 方案设计                                         | 开发按「实现顺序」展开实现计划、照抄验收标准；评审按目标评；测试验收逐条打钩 |
| 实现计划（目标与验收 / 现状 / 3–7 步各带验证 / 风险）                                                               | `IMPL_PLAN_TEXT`                           | 执行接单后、开发「实现」「重构」动手前           | 自测时逐处对照；计划变了要改计划并说明，验收标准不能中途放宽                 |
| 排查报告（级别与模块 / 现象 / 复现 / 调用栈 / 时间线 / 证据链 / 归因 / 修复设计 / 修复 / 验证 / 回归与隐患 / 文档） | `BUG_REPORT_TEXT`                          | 用户报的 Bug 修完交回；分析的排查类报告用前 8 节 | 协调器按同一张表核对，缺回归测试或修法只消症状的交回补                       |
| 交付前自测（验收逐条 / 测试与快速检查 / 差异自读 / 没留调试物 / 边界 / 遗留）                                       | `SELF_CHECK_TEXT`                          | 执行、开发说「完成」前                           | 协调器只转述有证据的结论                                                     |
| 测试矩阵（行为 / 输入 / 预期 / 层级 / 已有或缺）                                                                    | `tester.task=设计用例`                     | 测试验收（不写代码）                             | 执行、开发对照补缺口；`task=补测试` 按矩阵写用例                             |

写代码的硬规则（`CODING_TEXT`）同批加了两条：用到的接口先读定义再写，不凭记忆；边界（空 / 0 / 很多 / 超长、空值、并发、失败路径、旧数据）先想再写。
这些都是提示词层面的约定，面板不校验小节是否齐全（评审门禁、`submit_merge` 的校验不变）；测试 `server/core-agents.test.ts` 保证各角色的设定里确实带着这些段落。

交回子对话也有约定（2026-10-31，一次 AI 分析发现协调器交回后四次误判子对话接没接到）：协调器按 `send_to_conversation` 的返回判断，
「已送达 / 已交给」是送到了，「上一轮还在收尾…会自动开始」是排上队不用重发，已收尾的子对话照样交回、面板 resume 原会话，返回失败才算没送到；
不拿 busy、「已完成」这类状态字段猜，给用户只说「已交回，等结果」；拿不准时 `list_conversations` 看一次 `lastActivityAt`，超过等待时限没动静再发一次，
还不动就按没送到处理（做到一半卡住的由面板自动问、重启、接手）。通用约束的「执行纪律」同批加了一条：工具回成功不等于已生效，
对外的异步动作以推回结果为准、同步的回读一次，不为此轮询。
2026-11-03 起（[ADR 0048](adr/0048-coordinator-docs-first.md)）这些说法不再写在协调器设定里：`send_to_conversation` 送到后的返回自带一句（`shared/engine.ts` 的 `SENT_NOTE`）。
同批：协调器先提炼关键词再读模块文档定位；「方案设计」只能派出、不再挂「评审」复核大方案；给 Agent 的规则每条只有一个出处（`scripts/rules-check.mjs` 第 20 条）。

### 角色分类

分类名混着两种口径：`必备` / `通用` / `基础` 说的是角色的地位（装不装得掉、能不能被任何角色派），`规划` / `开发` / `质量` / `汇报` / `美术` 说的是领域。
`explorer` 是通用能力却在 `通用` 分类，`reviewer`、`tester`、`docsync`、`vcs` 同样通用却在 `必备`；`uiqa` 通用、在 `质量`；`i18n` 在 `开发`。
没有改成按领域重排的原因：内置角色的分类在安装时按名字建，启动同步保留用户机器上的 `categoryId`（`syncCore` 的 `categoryId` 由调用方传已装副本的），
改定义只影响新装的机器，老机器会同时留着空的旧分类，收益不抵混乱。角色页已经按高级 / 基本分段（ADR 0026），通用与否有 `common` 标记，分类只剩「找得到」一个用途。
要重排时一起做：定义里改 `category`，`install.ts` 加一次性的分类迁移（旧分类空了就删），再更新本表。

不用角色就是直接用 CLI：以前自带的「默认 Agent」已经去掉，Chat 页、默认工作流、AI 修复都不带角色，
旧数据里的 `default-agent` 读出来就是空字符串（`shared/schema.ts` 的 `dropLegacyAgent`）。

## 工作流清单

自带工作流**启动时全部自动加入**（用户 2026-10-25 改掉了 10-19「手动添加」的决定），用到的角色随之建好；
装过的 key 记在数据目录的 `config/builtin-workflows.json`，用户删掉的不再装回来（「通用项目」「UE 项目」缺了照样补），
以后新加的自带工作流下次启动自动装上。删掉的可以在工作流页的「内置工作流」里重新添加。

### 改代码的工作流只做到「实现 + 快速检查 + 文档同步」

工作流只由父对话启动（[ADR 0053](adr/0053-workflow-runs.md)，替代 0044 的工作流子对话）：协调器用 `start_workflow` 起一次工作流运行，
面板按流程图把节点跑完；改代码的运行在自己的独立分支里跑，流程图末尾由面板接一个固定的「收尾」节点（`shared/flow/run-wrap.ts`）：
执行角色补齐并提交，验收流程是「评审 → 测试」，不通过把意见交回修，最多 3 轮；都过了停在待合回，由父对话 `finish_workflow` 合回。所以工作流里**不放**：

- 评审节点、完整验收（`review: 'check'` 挂测试验收）：收尾节点已经按「评审 → 测试」的顺序做，放进流程图会重复跑；
- 提交 / 交付节点（`vcs`）：收尾节点提交，合回由父对话 `finish_workflow` 做；
- UE 编译：编译归父对话（[ADR 0004](adr/0004-ue-build-by-parent.md)），合回后父对话按申请编译。

实现节点改完只跑项目测试步骤里标「快速」的检查；最后一个节点是「文档」同步，Bug 记录只记用户报的 Bug。
测试步骤照样注入这些工作流的说明：带 `project-testing` 技能的角色（开发、执行、依赖）也算要跑测试（`withTestSteps`）。

父对话挑工作流看每个工作流的 `when`（什么时候用）、`notFor`（不用）、`kind`（`change` 改代码、跑完合回；`readonly` 一个文件都不写），
判定规则只写在 `shared/flow/run.ts` 的 `WORKFLOW_PICK_RULES`：用户点名 → 命中适用场景 → 问答 / 排查 / Bug / 小改动一律不起 → 拿不准交子对话。
新增内置工作流必须写这三项，写不出「什么时候用」的说明它不是固定剧本，不该做成工作流。

| key               | 名称                 | 适用场景                               | 默认执行角色   | 节点                                                                                   |
| ----------------- | -------------------- | -------------------------------------- | -------------- | -------------------------------------------------------------------------------------- |
| `project-general` | 通用项目             | 项目默认、边界清楚的功能和改动         | `orchestrator` | analyst（识别现场与方案，确认）→ developer → docsync                                   |

### 为什么留着这三个补环节的

| 工作流                     | 缺口                                     | 为什么现有 Agent 做不了                                                |
| -------------------------- | ---------------------------------------- | ---------------------------------------------------------------------- |
| `deps` 依赖升级与安全      | 没有任何一步会看依赖的漏洞和过期         | `tester` 只跑配置好的步骤；升级依赖需要「体检 → 分批 → 验证」的闭环    |
| `migration` 数据与配置迁移 | 迁移需要「迁移脚本 + 回滚 + 旧数据验证」 | 普通功能开发没有回滚和旧数据样本验证这个环节                           |
| `release` 发布与回滚       | 现有流程只做到合回父对话分支             | 发布范围、产物验证和回滚预案需要有顺序保证；对外的发布动作仍由父对话做 |

**没新增的**：性能排查（用 `developer.task` 扩充）、跨环境适配（由 `testSteps` + Agent 参数派生覆盖）、
安全审计之外的安全加固（`deps.audit` + `reviewer` 覆盖）、文档工程（`docsync.adr` 覆盖）、
Git / Perforce / SVN 分开建角色（版本控制本来就是同一个能力块，按 `vcs` 参数和 project-vcs 技能里的细则区分）。

## Bug 怎么分工

方法只写在 `shared/builtin/bug-method.ts` 一处（[ADR 0046](adr/0046-bug-analysis-pipeline.md)），角色设定、`/bug` 的展开和 `systematic-debugging` 技能都从它来（技能由 `node scripts/gen-debug-skill.mjs` 生成，单测核对一致）。分两条路：

- **完整流程**（`BUG_FULL_TEXT`）：只给用户报的、要查原因的 Bug。八个阶段：立案（现象卡、复现）→ 定位（模块文档 → 模块代码 → 调用栈 → 日志）→ 时间线（现象时间线 + 变更时间线）→ 归因（证据链三环、版本归因写引入点和责任类别、根因要解释现象的每一条、假设表）→ 修复设计（影响面、两个以上候选方案按修得全 / 修改面 / 风险 / 契合 / 可验证比较，选最优并写理由）→ 交诊断报告等用户确认（[ADR 0045](adr/0045-bug-diagnosis-confirm.md)）→ 修复与验证 → 防复发与归档。三个级别（快速 / 标准 / 深入）按难度定要求。面板只在 `kind: "bug"` 子对话的第一轮注入它（`server/exec/bug-prompt.ts`），平时的角色设定不带。
- **简易版**（`BUG_SIMPLE_TEXT`）：Agent 自己写代码、自测、跑测试、评审时发现的问题。现象 → 调用栈 → 证据链 → 修根因 → 改前失败、改后通过；不交报告、不用确认，省掉版本归因、变更时间线、级别、方案对比和 Bug 记录；不猜着改、修根因、三次停、清临时日志、搜同类写法这些底线不省。
- **Bug 档案**（`shared/bug/diagnosis-schema.ts`）：用户报的 Bug 子对话用 `update_bug_case` 随查随记（调用栈、时间线、引入点、假设、影响面、候选方案），`submit_diagnosis` 把草稿冻结成一版、按级别查必填；修完把结果（回归测试、影响面逐条的验证）记进档案，收尾时面板核对，还拦改动里留着的 `[排查-` 临时日志。确认过的那一版附进评审的提示词；收尾请求带上 Bug 记录草稿交给父对话。分析窗口的结论块也带调用栈、时间线、引入点，「按完整流程修」以 `/bug` 发回被分析的对话。
- 看日志的方法 `LOG_TIMELINE_TEXT` 三处共用：只看这次问题的时间段、排事件时间线、涉及状态的排状态流转时间线。

走哪条路：用户发 `/bug <现象>` 一定走完整流程（父对话派 `kind: "bug"` 子对话；直接在子对话里发，面板把它标成用户报的 Bug；Chat 这类会话就地查到修复设计、在回复里给报告）；只描述了 Bug 的由协调器判断，拿不准问用户；`/fix` 明确走简易版。

| 谁                                         | 做到哪                                                                                                                                                                            |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 父对话（`orchestrator`，协调器）           | 只定位到模块、写现象卡和级别初判，用户报的 Bug 派单写 `kind: "bug"`；交回按排查报告核对调用栈、证据链、验证，用户报的还看归因和修复设计，缺了或修法只消症状就交回补；确保回写文档 |
| 子对话（`worker`）                         | `kind: "bug"`：完整流程，交诊断报告、用户确认了方案才修、只改方案里的文件；其余自己发现的问题：简易版                                                                             |
| 工作流节点（`developer` 的 `task=修 Bug`） | 简易版（工作流里修的是流程中发现的问题）                                                                                                                                          |
| 分析（`analyzer`）                         | `BUG_ANALYSIS_TEXT`：完整流程的前五个阶段，只读，修复写成建议（影响面、候选方案、推荐理由）；排查部分按排查报告的前 8 节组织；单列「补模块文档」                                  |
| 评审（`reviewer`）                         | 修 Bug 的改动多看：根因还是症状、回归测试、临时日志、同类写法；附了确认过的诊断报告时对照选定方案、影响面验证、同类现场                                                           |
| 测试验收（`tester` 的 `onFail=自己修`）    | 简易版                                                                                                                                                                            |
| 写代码（`CODING_TEXT`）                    | 动手前一行改动计划：改哪几处、搜出来的调用方 `path:line`、怎么验证；接口先读定义再写；边界先想再写；改完逐处对照                                                                  |
