# 架构决策记录（docs/adr/）

一个决定写了之后不好改，就把「为什么这么定」写在这里。代码说明怎么写，ADR 说明**为什么**这么写、放弃了什么。

不是所有改动都值得占一个号：修 Bug、调参数、换文案、缩进和格式都不写。写的门槛见下面「什么时候要写」。

状态只有四个词，别自己造近义词：

- **提议**：方向定了，还没实施。实施前可以改，也可以废掉。
- **已接受**：已经在代码里生效。改它要先写一份新的 ADR 替代。
- **已废弃**：结论不再成立，代码也删了。文件留着，正文不动，只在状态行注明原因。
- **被替代**：有更新的 ADR 取代了它，状态行写清被哪一条替代（`被 0003 替代`）。

## 命名

```
docs/adr/NNNN-短横线-英文名.md
```

- `NNNN` 四位序号，从 `0001` 起，按提交顺序递增，**不复用、不重排**。删掉的号空着。
- 英文名用 kebab-case，2～5 个词，说清主题：`0002-child-merge-on-done.md`、`0003-child-complete-before-recycle.md`。
- 中文标题写在文件第一行 `# ADR NNNN：中文标题`，文件名不用中文（避免 Windows 和 CI 上的编码问题）。

## 一条怎么写

正文按下面几节，缺哪节就说明为什么缺，不留空标题：

1. **背景**：现在是什么样、谁提的要求、为什么现在要决定。
2. **事实核对**：动笔前读过的代码，写成「位置 → 现状」的表。**写文件和行号前先打开确认**；拿不准就不写行号，写函数名或文件名。事实错的 ADR 比没有 ADR 更坏。
3. **决策**：结论先写，再写理由。候选方案列出来，写清为什么没选。
4. **操作清单 / 契约**：具体做什么，能列成表的就列表（工具名、参数、权限、返回）。
5. **与现有实现的关系**：改动落在哪些文件、和已有的哪套机制并存或替代。
6. **运行时**：数据从哪来、在哪注册、怎么派发、失败怎么表现。
7. **分期**：先做什么、出口条件是什么。没分期就写「一次做完」，别含糊。
8. **风险与代价**：会带来什么问题、怎么防；认下来的代价写明白。
9. **开放问题**：还没定的，每条写倾向和「定下来之前先怎么实现」。

写作要求：

- 中文，代码、路径、字段名、命令保持原样。
- 结论用现在时写，别写「我们计划将」；不确定的进「开放问题」。
- 一个 ADR 只定一件事。顺带定的东西另开一条，互相用相对链接指过去。
- 实施细节（函数怎么拆、循环怎么写）不写进 ADR，写进对应模块文档或代码注释。

## 什么时候要写

出现下面任一情况就写，且**在同一个提交里**写：

- 换技术选型（MCP / CLI / HTTP 接口、库、存储）；
- 改模块边界或依赖方向（谁能调谁、哪层不许调哪层）；
- 定对外契约（接口形状、数据结构、文件和目录约定）且以后不好改；
- 放弃了一个认真考虑过的候选方案，理由以后会有人再问一遍；
- 定了一条「以后都这么做」的约定，靠人记记不住的。

不写的情况：修 Bug、调参数、改文案和样式、重构但行为不变、加一个字段（除非它改了对外的数据约定）。

## 和别的文档怎么分工

| 想写的东西                   | 放哪                                     |
| ---------------------------- | ---------------------------------------- |
| 为什么这么定、放弃了什么     | `docs/adr/`（这里）                      |
| 模块现在怎么工作、有哪些入口 | `docs/<专题>.md`（`docs/` 下的专题文档） |
| 这次改了什么、验收证据       | 提交说明和对应的 change 记录             |
| 踩过的坑、下次怎么做         | `docs/lessons/<领域>.md`                 |
