# ADR 0010：评审只看代码，面板一次附上改动，意见分四级

状态：已接受 · 2026-10-24

## 背景

[ADR 0009](./0009-review-findings-triaged.md) 之后单轮评审变短了，但用户 2026-10-24 反馈「状态栏拆成计划/子对话/子任务三行」那次还是评审了三轮、合计约 20 分钟，要求在保证质量的前提下再缩短。同一天用户追加了几条要求：

- 评审只做代码层面的审查，不跑测试、不搭测试环境、不写测试代码；
- 启动评审时把改动的代码一次带给评审子任务，发文件还是发 diff 由我们定；
- 意见分成高级、中级、低级、建议四级；
- 参照 Claude Code 自带的代码审查做法提升评审能力。

## 事实核对（那次记录）

| 项           | 记录里的事实                                                                                                                                       |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 三轮耗时     | h1 9m50s（输入 2.07M token、输出 27k）、h2 7m16s、h3 3m9s                                                                                          |
| 工具本身耗时 | 三轮合计约 4 分钟；其余是模型来回：h1 一轮约 45 次工具调用                                                                                         |
| 评审在做什么 | 每轮都重跑 typecheck、lint、演示构建、整套界面检查（约 46 秒一次）；h1 有十来次调用在摸索本机 Playwright 路径；h2、h3 自己写 Playwright 脚本量元素 |
| 为什么三轮   | 第 1 轮已经「通过、必须改：无」，执行去落 5 条 💭 建议，其中「+N 移进卡片容器」改出窄屏被裁的问题，第 2 轮查出来，第 3 轮确认修复                  |
| 改动从哪来   | 评审自己 `git diff`，再一个文件一个回合地 Read（`TaskView.tsx` 两千多行）                                                                          |

## 决策

1. **评审只做代码层面的审查**：不跑测试、构建、界面检查和端到端，不搭环境、不装依赖、不写测试或复现脚本。怀疑从代码推出来，写成「失败场景：具体输入或状态 → 错误结果」，复现交给执行角色。执行角色派评审时把跑过的检查写成「命令 + 结果」给它当证据，长检查可以和评审同时跑。
2. **改动由面板一次附进评审的提示词**（派的是 `builtin:reviewer` 且在 git 仓库里时）：文件列表（`git diff --stat`）加 `git diff -W`（每处改动带它所在的整个函数）。发 diff 不发整文件：整文件里大部分是没改的代码，大组件几千行，每个回合都要重新带上；`-W` 给出函数级上下文，大多数判断够用，还要调用方、测试时评审再按路径读那几个。超过 6 万字退回 `-U5`，仍超就存成文件，提示词里只放文件列表和路径。
3. **复看只附增量**：评审开始时用临时暂存区把工作区（含没跟踪的新文件）写成一棵树存进 `TaskStep.snapshot`；`resume` 接着这个会话复看时，面板和这棵树比，只附那之后的改动。
4. **意见分四级**：🔴 高级（必须改：需求要求、用户可见或可复现的错误，有它就判不通过）、🟠 中级（应该改：真问题但影响有限，不判不通过）、🟡 低级（可以改）、💡 建议（这一轮不做）。高级、中级共用 R1、R2… 编号，第二行「必须处置：R1、R2」，门禁要求这两级每条都有处置（通过但列了中级也要）；低级、建议不用处置。执行角色只顺手改不改变行为的低级，改变行为的低级和建议都不在这一轮落，不为它们再开一轮评审。
5. **参照 Claude Code 的代码审查**：两遍——第一遍按正确性找候选（条件、边界、空值、时序、错误处理、状态一致、兼容、缺用例），第二遍逐条回到代码确认失败路径走得到，标「已确认 / 可能」，推不出失败场景的不报；同级里最严重的在前；格式、lint 能拦的、纯风格不报。宁可少报确认过的，不列一串猜测。

候选方案：

- **发整个文件**：没选，理由见第 2 条。
- **评审自己跑一条针对性的复现**：用户明确不要，而且那次 h2 的发现（容器 `flex-1` basis 0 被挤成 0 宽）完全能从代码推出来。
- **只保留三级、改个名字**：没选。三级里 💭 一档同时装着「真问题但不阻塞」和「锦上添花」，执行角色分不清哪些该处置，那次就是把锦上添花的也做了才多出两轮。

## 与现有实现的关系

- `server/exec/git.ts`：`gitSnapshot`、`reviewDiff`；`server/exec/runner.ts` 接成 `EngineHost.reviewDiff`，太长的差异存进交接目录。
- `shared/engine.ts`：`runHelper` 里 `reviewPart` 把改动拼进评审的提示词，记下 `step.snapshot`。
- `shared/review-gate.ts`：`blockingIds` 认「必须处置：」和以 🔴 / 🟠（旧的 🛑）开头的行，只认行首，复看正文里提到上一轮的编号不算。
- 执行、评审两个必备角色的设定，启动时直接同步。

## 风险与代价

- 评审不跑检查后，只在运行时才暴露的问题（布局、样式计算）要靠执行角色的检查和它对评审推导的复现；评审给的「建议执行者用什么方式复现」就是为这个留的。
- `-W` 对没有函数名规则的文件类型只是多带几行上下文，不影响正确性。
