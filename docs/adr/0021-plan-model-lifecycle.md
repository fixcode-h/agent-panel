# ADR 0021：执行计划靠面板机制推进，不靠对话自觉——状态机、时间戳、自动推进、滞后与新输入检测

状态：已接受 · 2026-10-28

## 背景

用户 2026-10-28 的原话：

> 目前这个计划总是更新不及时，现在对话都执行到测试步骤了，但是计划还在第一步，看看怎么约束让后话按照计划的步骤来，完成一个步骤就更新计划进行下一个步骤

随后扩大范围：

> 这个计划模块好好设计下

同一轮补充：

> 对话接受了新的内容导致计划有变，那么计划也需要对应的更新

截图里的现象：计划面板列出 6 步，第 1 步已完成、第 2 步显示「进行中」，而对话实际已经在跑第 4 步的测试。
提示词里「开始做一步、做完一步都马上更新」早就写了，约束不住：Agent 忙起来（连改几个文件、跑长命令）就忘记同步。

问题的本质不是「少写了一段提示」，而是**计划的真假只靠 Agent 自报**：
没有任何一处机制会发现「计划里的状态和真实发生的事情不一致」，也没有任何一处会提醒。

## 事实核对

| 位置                                                      | 现状                                                                                                                                                                                            |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `shared/schema.ts` `PlanStatus` / `PlanItem` / `TaskPlan` | 状态只有 `pending` / `running` / `waiting` / `done`；`PlanItem` 有 `startedAt` / `endedAt`，没有「最后变化时间」；`TaskPlan` 有 `createdAt` / `reopenedAt` / `doneAt`，同样没有「最后变化时间」 |
| `shared/plan.ts` `applyPlan`                              | `set_plan` 的合并入口：完成的锁死、漏写的未完成项在 `partial` 下保留、等结果的项被 `held` 退回 `waiting`；**没有**「同时只有一个 `running`」这条校验                                            |
| `shared/plan.ts` `settleWait` / `holdWait`                | 等的结果回来时收口：成功标 `done`；失败时退回 `running` 并写 `等的结果没成功：` 备注；子对话这一轮没交付完写 `还在等它：` 继续 `waiting`                                                        |
| `shared/plan.ts` `syncKids` / `linkKids`                  | 计划和名下的子对话对齐：提到它的步骤挂成 `waiting`，子对话已完成就按它的结束时间标 `done`                                                                                                       |
| `shared/plan.ts` `markWrapUp` / `endRun` / `closeIfDone`  | 合回（`submit_merge` → `finish_child`）由面板推进收尾步骤；工作流运行结束推进它那一步；全部 `done` 时写 `doneAt` 收起                                                                           |
| `shared/plan.ts` `runningStepId`                          | 派子对话时没点名步骤就挂「正在做的那一步」（`running`，其次 `waiting`）                                                                                                                         |
| `shared/engine.ts` `planPart`                             | 每轮提示里只有计划文本（`planText`）和一段维护规则；没有「现在是第几步、多久没动、下一步是什么」，没有滞后提醒，也没有「新输入先判计划」                                                        |
| `shared/engine.ts` `runBackground` 分支                   | `run_background` 只有**显式带 `step`** 才 `bindWait`；不带 `step` 的长命令在计划里完全不可见                                                                                                    |
| `server/tasks.ts` 后台命令结束回调                        | `settleWait(tk, 'background', job.id, ok)`；子对话收尾 `refreshChildWait` / `syncKids`；合回 `markWrapUp`；这些事件已经是自动推进的锚点，缺的是「失败态」和「计划没跟上」的检测                 |
| `server/orch-mcp.ts` `set_plan`                           | 工具参数：整份 / `partial`；语义稳定，这次不推翻                                                                                                                                                |
| `web/src/components/tasks/PlanPanel.tsx`                  | 每项右侧有用时（`data-plan-time`）、顶部有总用时（`data-plan-total`）、按钮上有当前步骤耗时（`data-plan-current-time`）；没有进度条、没有「N 分钟前更新」、没有滞后警示                         |
| `scripts/ui/02-task.mjs`（执行计划分片）                  | 断言上述 `data-plan-*` 结构、等待中的说明文字必须正好是「等：端到端测试」、状态图标的计算样式；UI 改造要保持这些契约                                                                            |

## 决策

**计划的一致性问题由面板的机制兜住，对话只负责它真正知道的那部分。**

四层机制，各自解决一类失真：

1. **状态机**：六个状态各有唯一含义，`running` 唯一、`waiting` 必须挂着等的东西；终态与失败态分开。
2. **自动推进**：能由真实事件推断的，面板直接改，不等 Agent 报（现有锚点补齐「未带 step 的后台命令」和失败态）。
3. **时间戳 + 检测**：计划、步骤各记「最后变化时间」；每轮构造提示时检测「计划滞后」和「新输入后计划没动」，共用一条注入通道。
4. **可见**：面板上能直接看出最近更新、进度、当前步骤、滞后；判空与渲染仍然同源（`planHeadline` / `planProgress`）。

### 一、数据模型

| 字段                   | 位置               | 含义                                                                                       |
| ---------------------- | ------------------ | ------------------------------------------------------------------------------------------ |
| `PlanItem.updatedAt`   | 每个步骤/子步骤    | 这一项最后一次真正变化（状态、标题、备注、等待项）的时间；旧数据没有，读时退回 `startedAt` |
| `TaskPlan.updatedAt`   | 每份计划           | 这份计划最后一次变化的时间（任何一步的变化都算）；旧数据没有，读时退回 `createdAt`         |
| `PlanStatus` 增加两项  | `shared/schema.ts` | `failed`（做不成、需要处理）、`skipped`（明确不做）                                        |
| `TaskPlan.lastInputAt` | 每份计划           | 最近一次「带新要求性质」的输入到达时间（用户消息、父对话转达、子对话/后台结果带新任务）    |

`lastInputAt` 只用来做「新输入之后计划有没有动过」的判断，不参与状态推进，也不显示成时间。
时间戳统一用 ISO 字符串，和现有 `startedAt` / `endedAt` 一致；旧数据不迁移（缺字段按退回规则算）。

### 二、状态机

| 状态      | 含义                                                                                    | 谁改                                                                                                                     |
| --------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `pending` | 还没开始                                                                                | Agent（`set_plan`）、面板（补步骤、重开步骤）                                                                            |
| `running` | 对话现在正在做这一步；**一份计划里最多一个**                                            | Agent（`set_plan`）；面板把等的结果失败退回时也标它（需要对话去处理）                                                    |
| `waiting` | 在等外部结果（后台命令 / 子对话 / 子任务 / 用户选择），对话应该去做别的步骤或结束这一轮 | 面板（`bindWait` / `holdWait` / `linkKids`）；Agent 不能凭空写 `waiting`（没有 `waits` 的 `waiting` 会被当成 `running`） |
| `done`    | 完成，锁死                                                                              | 面板（结果回来、合回成功、工作流结束）、Agent（`set_plan`，等结果的步骤会被退回）                                        |
| `failed`  | 这一步没做成，需要处理（重做、改做法或明确跳过）——**不是终态**                          | 面板（等的结果失败、工作流失败）+ `note` 写清失败原因；Agent 用 `set_plan` 改回 `running` 或标 `skipped`                 |
| `skipped` | 明确不做 / 不适用，终态                                                                 | Agent（`set_plan`）                                                                                                      |

- **终态** = `done` | `skipped`；`failed` 不是终态：它表示「有件事需要对话决断」，留在计划里直到 Agent 把它改成 `running`（重做）或 `skipped`（放弃）。
- 计划收起（写 `doneAt`）的条件从「全部 `done`」改为「全部终态」（`closeIfSettled`）。
- `leftSteps` / `unfinishedSteps` / `openWork`（收尾门禁）统一按「非终态」算，避免明确跳过的步骤永远挡住收尾。
- **`running` 唯一**：`applyPlan` 发现在同一次提交里有多个项被标成 `running` 时，只保留最后一个（对话刚转向的那一步），其余退回 `pending`，并在返回说明里点名。**退回时还挂着没回来的结果（`waits` 里有 `waiting`）的改成 `waiting`**：`settleWait` / `linkKids` 只在状态是 `waiting` 时收口，退回 `pending` 会让它永远等不到完成。历史数据里已经并存的多个 `running` 不改写（避免翻旧计划），界面上按状态原样显示。
- **`waiting` 必须挂着等的东西**：`set_plan` 写 `waiting` 但没有 `waits` 时按 `running` 处理（Agent 常说「等待中」其实是在做）。长命令、子对话、子任务必须带 `step` 走 `bindWait`，这样状态与原因同时成立。

### 三、推进规则

**A. 面板自动推进（不需要 Agent 参与）**

| 事件                                               | 结果                                                                           |
| -------------------------------------------------- | ------------------------------------------------------------------------------ |
| 带 `step` 的后台命令结束，成功                     | 那一步 → `done`                                                                |
| 带 `step` 的后台命令结束，失败                     | 那一步 → `failed`，`note` 写「等的结果没成功：<命令名>」（原来退回 `running`） |
| **未带 `step` 的后台命令启动**（本次新增）         | 挂到当前唯一的 `running` 步骤上 → `waiting`，命令开始时就算等待                |
| 子对话创建（带 `step`，或标题能对上某一步）        | 那一步 → `waiting`，用时从子对话创建时算起                                     |
| 子对话收尾完成 / 失败                              | 全部成功 → `done`；有失败 → `failed`                                           |
| 子任务结束                                         | 同上（`kind: 'helper'`）                                                       |
| 合回成功 / 失败（`submit_merge` → `finish_child`） | 收尾步骤 `done` / `failed`（失败时 `note` 写原因）                             |
| 工作流运行结束                                     | 成功 → `done`；失败 → `failed` + 「工作流没走完：…」                           |
| 用户点「解决」（`settlePlan`）                     | 全部收口成 `done`，等待项一笔勾掉                                              |

**B. 只能由 Agent 报的**：这一步到底做没做完、做完的内容、要不要跳过、拆分/合并/新增步骤、调整顺序。
这些是「人的判断」，面板不猜——`set_plan` 是唯一入口，语义不变（整份 / `partial`）。

**C. 每轮自检（提示词硬约束）**

`planPart` 在计划文本前面加一句正面提示，不是让 Agent 去读计划找：

```
现在：第 3 步「SummaryPage 接线」进行中（已 6 分钟），下一步是「界面检查加断言」。
```

规则写死：

- 动手前把这一步标 `running`（`set_plan` 带 id + status），一份计划只能有一个 `running`。
- 做完立刻在同一批动作里标 `done`，并把下一步标 `running`；**不允许连着做完几步再一起更新**，也不允许计划里还有 `running` 步骤时去做别的步骤的事。
- 起子任务、派子对话、跑长命令时用带 `step` 的参数（面板标 `waiting`），这时不要标 `running`——`running` 是「我现在在动手」，`waiting` 是「我在等别人」。
- 什么算完成一步：改完代码 **并且** 跑通这一步该跑的检查；只是起了个子任务、只是跑完了一条命令、只是写了一段说明，都不算。
- 计划的步骤全完成后 `finish_plan`；新内容开新计划。

**D. 增量更新还是整份重开（规则表）**

默认**增量更新**：在现有计划上改，`set_plan` 带已有步骤 id、配 `partial: true` 只交变更项，没写到的步骤原样保留。

| 触发条件                                                     | 做法                                   | 调用                                                                 |
| ------------------------------------------------------------ | -------------------------------------- | -------------------------------------------------------------------- |
| 同一件事的细化、补一步、插一步、调顺序、改步骤名、作废某一步 | 增量：原计划上加 / 改                  | `set_plan`（`partial: true`，带已有步骤 id；作废的步骤标 `skipped`） |
| 用户补充的要求属于还没做完的某一步                           | 增量：并进那一步（加子步骤）           | `set_plan`（`partial: true`）                                        |
| 原计划的**目标本身变了**（换方向、需求被推翻、方案整体换掉） | 整份重开：先结束旧计划，再开新计划     | `finish_plan` → `set_plan`（新 `title`）                             |
| 原计划剩下的步骤**大部分作废**（超过一半与当前目标无关）     | 整份重开                               | 同上                                                                 |
| 用户明确说「重新做 / 换个方案 / 别按刚才那个来」             | 整份重开                               | 同上                                                                 |
| 原计划**已经结束**（`finish_plan` 或全部完成）之后的新内容   | 直接开新计划（不需要再 `finish_plan`） | `set_plan`（新 `title`）                                             |

两条边界都是硬约束：

- **只是加内容却整份重开** = 违规：会丢掉已完成步骤的记录和耗时（旧计划收进「以前的计划」，当前计划从 0 开始）。
- **目标已经变了却还在旧计划上打补丁** = 违规：留下和新需求冲突的旧步骤继续跑，`skipped` 只该用于个别步骤，不该拿它凑合一次换方向。

整份重开时旧计划**不删**：`finish_plan` 写 `doneAt`，它连同步骤状态、耗时、摘要留在 `task.plans` 里，界面收在「以前的计划」中；新计划从零开始计时。

面板兜底（不替代规则，只提醒）：

- `applyPlan` 发现这次整份提交里「对不上旧项的未完成步骤」占原未完成步骤的一半以上（`PLAN_RESTART_RATIO`）时，在返回说明里提醒
  「像是换了方向：应该 `finish_plan` 结束这份计划、再 `set_plan` 开新的，而不是在同一份里大换血」。
- 同一份计划里连续重建（一份计划开出来不到 `PLAN_REBUILD_MIN_MS` 就被换掉）时，提示「是不是该在原计划上增量」。
- 界面上显示「最近一次更新时间」，并对「这份计划是上一份结束后新开的」标「重建」，让用户能看出计划变过。

**E. 新输入先判计划**

每一轮如果本轮输入带了「新要求」性质的内容（用户新消息、父对话转达、子对话/后台结果里带了新任务），
Agent 的**第一件事**是判断「现有计划要不要改」：

- 要改 → 立刻 `set_plan`（并入现有步骤加子步骤 / 在合适位置插入主步骤 / 调整顺序 / 把作废的步骤标 `skipped`），再动手；
- 不改 → 用一句话说明「为什么这条消息不改变计划」，再继续；
- 同一件事**不另开一份计划**，也不留着和新要求冲突的旧步骤继续跑（冲突的那一步标 `skipped` 并说明）。

机制兜底与「滞后检测」共用同一个函数和同一条注入通道（`planNotice`），不重复插两条：

| 检测             | 条件                                                                         | 提醒内容                                                                           |
| ---------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 计划滞后         | 有 `running` 步骤，且它的 `updatedAt` 距今 ≥ 3 分钟（`PLAN_STALE_MS`，可配） | 「计划还停在「X」（已 N 分钟没更新）：做完了标完成，在等结果带 step 重新标等待中」 |
| 新输入后计划没动 | `lastInputAt` 晚于计划的 `updatedAt`                                         | 「上一轮进来过新要求，计划之后没变：不改变就一句话说明，要改就现在改」             |

`waiting` 的步骤不参与滞后检测（跑 10 分钟 e2e 是正常的）；`failed` 也不参与（它已经是一个需要处理的状态，由结果推回的消息点名）。
检测结果同时写 `log.warn`（服务端），方便事后确认「到底提醒过没有」。

**不按「本轮是否有实质动作」决定插不插**：提示词在动作发生**之前**构造，这一轮有没有调 `run_background`、改过哪些文件，在这里还不知道；按「上一轮有没有工具调用」判又几乎恒真。所以改用**不依赖动作事实的条件句**（「做完了就标完成，在等结果就标等待中，还在做同一步就不用管」）。`waiting` / `failed` 已经把长命令和失败态排除在外，剩下的「连续做同一步、只是没 set_plan」不会因为一条错误断言被带偏。界面侧的 `itemStale` 也只给 `running` 的步骤画警示，不以动作为依据。

**提醒只算一次**：`inputNotedAt` 记的是**本轮开头那次输入**（`lastInputAt` 的当时值）。轮中用户插话会更新 `lastInputAt`，不能拿轮末的值写 `inputNotedAt`，否则没提醒过的那次输入会被标成已提醒、兜底永远丢失。

**步骤级时间也守同一条**：`PlanItem.updatedAt` 只在 `itemDigest`（标题 / 状态 / 备注 / 等待项）真变时推进，Agent 按「每次交整份」的习惯原样重交一遍不会把滞后计时洗掉（和计划级 `planDigest` 同一套口径）。

### 四、耗时与生命周期

- 每一项：`startedAt` / `endedAt` / 已用时（界面用 `itemElapsed` 计算，已结束的固定、进行中的每秒涨）。
- 整份计划：`planSpan`（已有）。重开的计划（`reopenedAt`）从重开时刻算，不并入上一轮。
- 生命周期：进行中 → 全部终态自动结束（`doneAt`）→ 或 `finish_plan` 提前结束；结束后仍在计划列表里保留（`shownPlan` = 最后一份），
  界面收在「以前的计划」里；之后 `set_plan` 自动开新计划，或用 `ensureChildStep` 重开（`reopenedAt`）。
- 收尾步骤（`wrapUp`）：面板加在最后、不能删、不能挪（`ensureWrapUp`，规则不变）；`merge` 的完成只由合并结果决定，
  Agent 自己标完成会被退回。`openWork` 不拿收尾步骤挡 `submit_merge`，其余非终态步骤照样挡。

### 五、UI 布局（`PlanPanel`）

保持现有 DOM 契约（`data-plan-time` / `data-plan-total` / `data-plan-current-time` / 等待说明的 `line-clamp-2`），只增不改：

```
┌ 计划按钮（输入框上方）──────────────────────────────────────┐
│ ☑ 计划 3/8 ▍▍▍▍▍░░░░  · 当前：SummaryPage 接线 2m16s         │
│                        · 2 分钟前更新（滞后时警示色）        │
└──────────────────────────────────────────────────────────────┘
┌ 计划窗口 ────────────────────────────────────────────────────┐
│ 标题                        总用时 12m  ·  3/8  [进度条]     │
│ 最近更新：2 分钟前（滞后时 ⚠ 3 分钟没更新）                  │
│ ☑ 1 新增 summary-page 纯逻辑与单测      2m49s               │
│ ◐ 2 SummaryPage 接线                    2m16s  ⚠ 滞后        │
│   等：端到端测试 · 还在等它（原因）                          │

│ …                                                            │

```

- 进度：`done/total` 数字 + 细进度条（`role="progressbar"`，`aria-valuenow`），当前步骤高亮（`font-medium` + 强调色图标，已有）。
- 每步耗时：已有（`ItemTime`）；等待原因：已有（`itemLine`：等谁 + 备注）。
- 「N 分钟前更新」：来自 `plan.updatedAt`，用 `timeAgo`；≥ `PLAN_STALE_MS` 时整句改警示色并加 `data-plan-stale`。
- 滞后步骤的小标记：`running` 且超过阈值的步骤行加一个警示图标（`title` 说明多久没更新），不新造弹窗。
- 窄窗口：进度条 `min-w-0 flex-1`，步骤名 `truncate`，「N 分钟前更新」在折叠头上只在空间够时显示（`hidden sm:inline`）。
- 判空与渲染同源：折叠头仍只读 `planHeadline` / `planProgress`，不另写一套判定。

没选的做法：

- **只加强提示词措辞**：现在的措辞已经写了，问题就是措辞管不住「忙起来」。必须加机制。
- **面板按时间猜步骤完成**（例如 `running` 超过 N 分钟就自动标完成）：会把没做完的步骤标成完成，比滞后更糟；只提醒，不改状态。
- **让 `waiting` 兼作「在跑长命令」**：长命令的语义是「等外部结果」，和「对话在动手」必须分开，否则界面分不清是卡住还是在跑。
- **计划结束后删掉历史**：用户需要回看；仍然保留，收进「以前的计划」。
- **另做一套「计划变更记录」**：时间戳 + 一次更新时间足够回答「计划什么时候变过」，不为它单独建表。

## 与现有实现的关系

- **不推翻 `set_plan` 的参数语义**：整份 / `partial` 合并规则、完成锁死、漏写项保留、`auto` 步骤保护、`wrapUp` 的最后一步规则全部不变。
- **自动推进复用已有锚点**：`settleWait` / `syncKids` / `markWrapUp` / `endRun` 是同一个出口，这次只是「失败时写 `failed`」和「未带 `step` 的
  后台命令补挂」两处补齐；没有第二套推进路径。
- **和收尾门禁（`openWork`）一致**：`skipped` 不挡收尾，`failed` 挡（必须处理），`merge` 收尾不挡 `submit_merge`。
- **和评审门禁（`review`）无关**：评审步骤的校验只看标记，不看状态机的新状态。
- **提示词位置**：新增段落放在 `planPart` 内部（计划文本前后），不动提示词第一段——`scripts/fake-cli` 有几处按第一句 `startsWith` 识别
  （见 `docs/lessons` 里的提示词教训），动开头会让 e2e 静默走不到模拟分支。

## 运行时

1. Agent 每轮拿到计划文本 + 「现在第几步」+（命中时）滞后 / 新输入提醒。
2. Agent 动手：`set_plan` 标 `running`；跑长命令：`run_background`（带或不带 `step`）→ 面板 `waiting`。
3. 命令/子对话/子任务结束 → 服务端回调 `settleWait` → 成功 `done`、失败 `failed`，结果推回并点名这一步。
4. `submit_merge` → `finish_child` 合并 → `markWrapUp('merge', 'done')`；失败 `running` + 原因。
5. 每轮构造提示前：`planNotice` 检测；命中时提示词里提醒，服务端 `log.warn('plan', …)`。
6. 界面每秒刷新用时（`useNow`）；`plan.updatedAt` 决定「N 分钟前更新」，超过阈值转警示色。

## 分期

一次做完，三块按依赖顺序落地：

1. 状态机 + 时间戳 + 自动推进（`shared/plan.ts`、`shared/schema.ts`、`shared/engine.ts` 的 `runBackground`）+ 单测；
2. 滞后 / 新输入检测 + 提示词 + 日志 + 单测；
3. `PlanPanel` 重做 + 演示数据 + 界面检查断言；同步 `docs/modules/{shared,server,web}/README.md`。

出口条件：`npm run typecheck` / `lint` / `test:unit` / `build` / 界面检查通过；e2e 由父对话跑（本次动了提示词与执行链路）。
单测覆盖：状态迁移（含 `failed` / `skipped` / 唯一 `running` / 无 `waits` 的 `waiting`）、自动推进每个事件、耗时计算、
滞后阈值边界（差 1 毫秒不提醒）、新输入后计划没动的判定、提示词片段（含「现在：第 N 步」「先判计划」原句）。

## 风险与代价

- **`failed` 让计划多一个「必须处理」的状态**：Agent 可能忘记把 `failed` 改成 `running` / `skipped`，计划一直收不起来。
  兜底：结果推回的消息点名这一步；滞后检测不提醒它（它不是 `running`），但 `openWork` 会挡住收尾，`submit_merge` 的报错里会列出来。
- **唯一 `running` 可能把历史数据里的并行步骤洗掉**：只在同一次 `set_plan` 里纠正，旧计划不动。
- **滞后检测有误报的可能**：Agent 在一次很长的前台操作里（超过 3 分钟）没更新计划时会提醒。提醒本身无害（只是提示先收口），
  且文案是条件句、不假设它在做别的步骤；正确做法本来就是把长命令交给 `run_background`（→ `waiting`，不参与检测）。
- **「先判计划」会增加一轮的输出**：不改计划时也要一句话说明。这是为了让用户看见「判断过了」；代价是回复略长。
- **时间戳增多**：每次计划变化多写两个字段，计划数据略大；这些字段是排障与界面的唯一来源，值得。
- **界面改动可能触到现有 `ui-check` 断言**：`02-task.mjs` 对 `data-plan-*`、等待说明、图标样式的断言必须一起维护，
  否则界面检查会红（本次已列进验证步骤）。

## 开放问题

- **阈值 3 分钟是否合适**：先按 3 分钟；真实使用里误报多就调大，做成项目设置项（现在先常量）。
- **「新要求」的精确识别**：现在按「用户消息 / 父对话转达 / 结果里带新任务」由服务端写入 `lastInputAt`。
  如果以后要区分「纯查询」和「新要求」，再在消息类型上加标记，不在提示词里让模型猜。
- **计划面板要不要显示「这一步被谁推进」**（Agent / 面板自动 / 父对话收尾）：需要时在 `PlanItem` 上加 `by`，
  这次不做——现有状态与时间已经够回答用户的「做到哪了」。
- **「大部分作废」的阈值**：现在按一半（`PLAN_RESTART_RATIO`）。真实使用里如果「目标微调 + 重写大半步骤」很常见，可能要把阈值调高到 2/3，先观察。
