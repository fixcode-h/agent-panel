# ADR 0007：子对话完成时留交接摘要，再被叫醒时上下文大就只带摘要

状态：已接受 · 2026-10-24

## 背景

用户 2026-10-24 问：子对话合回、标记完成后要不要压缩上下文。目的是以后父对话再把消息交给这个子对话时，不把上次读文件、跑命令的工具输出全带进来白花 token，只留下能快速找到代码和文档的关键信息。要求完成总结写得更完整，给出通用模板。

## 事实核对

| 位置                                             | 现状                                                                                         |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| `server/tasks.ts` `completeChild`                | 完成时结束 CLI 进程、停后台命令、删独立分支，置 `resolved`；`task.sessions` 里的会话 id 保留 |
| `server/tasks.ts` `start`（`resolved` 的子对话） | 再收到消息时取消完成标记，`restoreWorktree` 在原路径重建独立分支，CLI 冷启动后接回原会话     |
| `server/exec/runner.ts` `task.rewind.summary`    | 已有「开新会话、带上摘要」的路子（手动压缩用它），用完清掉                                   |
| `server/orch-mcp.ts` `submit_merge`              | 只有 `note`（一句话）和 `tests`                                                              |
| `shared/engine.ts` `summaryOf`                   | 子对话的 `summary` 只是最后一条回复的前 300 字，`list_conversations` 里父对话靠它找子对话    |

## 决策

**不在完成时调 CLI 压缩。子对话在 `submit_merge` 里按模板写「关键信息」，面板补上 git 事实，存成交接摘要；再被叫醒时上下文大就开新会话只带摘要，小就照旧接回原会话。**

关键信息模板（`shared/handoff.ts` 的 `HANDOFF_FIELDS`，`submit_merge` 的 `handoff` 参数）：

| 字段        | 写什么                                                 | 必填 |
| ----------- | ------------------------------------------------------ | ---- |
| `files`     | 改了或关键的文件、模块：每行「路径 — 作用 / 改了什么」 | 是   |
| `docs`      | 相关文档：读过、改过、下次该先看的文档路径             | 否   |
| `decisions` | 关键决定和原因，没选的方案一句话                       | 否   |
| `pitfalls`  | 试过不行的做法、要注意的坑                             | 否   |
| `followups` | 没做的、已知问题、下次接手先做什么                     | 否   |

面板补的部分（不花 token）：原始需求（截断）、`note`、`tests`、合回的分支、分支上的提交、改动文件统计。

叫醒规则：完成时这个对话的上下文占用 ≥ `HANDOFF_MIN_CONTEXT`（30k token）才换成「新会话 + 交接摘要」。小于它时接回原会话更省（摘要本身也要 1～2k），还保留全部细节。

没选的方案：

- **完成时调 CLI 压缩**：每个子对话都多一次读全上下文加写摘要，大多数完成的子对话不会再被叫醒，钱白花；摘要写什么也不受控制。
- **叫醒时再压缩**：那时缓存已经过期，压缩要全价读一遍，和直接接回原会话的第一轮一样贵。

## 操作清单 / 契约

| 入口                 | 行为                                                                                     |
| -------------------- | ---------------------------------------------------------------------------------------- |
| `submit_merge`       | `handoff.files` 必填，空的拒绝并给模板；成功时把整理好的摘要存进 `task.handoff`          |
| 已完成的子对话被叫醒 | 有 `task.handoff` 且上下文 ≥ 30k：写 `task.rewind = { summary }`，这一轮开新会话带上摘要 |
| `list_conversations` | 已完成的子对话「最近结果」换成交接摘要里的关键文件，父对话按它判断该交给谁               |

## 与现有实现的关系

改 `shared/schema.ts`（`Task.handoff`）、新增 `shared/handoff.ts`（模板、拼摘要、判定）、`server/orch-mcp.ts`（参数）、`server/tasks.ts`（`submitMerge` 存摘要、叫醒时判定、列表摘要）、`server/exec/git.ts`（分支提交列表）。复用 `task.rewind.summary`，不新增会话机制。共用目录的子对话没有 `submit_merge`，照旧接回原会话。

## 运行时

摘要在 `submit_merge` 时生成，父对话退回、子对话再请求时覆盖。叫醒时只用一次（`rewind` 用完由 runner 清掉），新会话的 id 写回 `task.sessions`。旧会话的位置还记在各条消息的轮次上，用户要完整过程时可以在对话里回退到旧消息接回去。

## 分期

一次做完。

## 风险与代价

- 换成新会话后看不到上次具体的推理过程，只能靠摘要和代码：认下，目标就是不带这些。
- 摘要是子对话自己写的，写得差就找得慢；`files` 必填，面板补的 git 事实兜底。
- 保活的旧进程拿的是没有 `handoff` 的旧工具列表，调用会被拒并说明要补。

## 开放问题

无。
