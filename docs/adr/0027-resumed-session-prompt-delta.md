# ADR 0027：续接会话只发变了的提示词段落

状态：已接受 · 2026-10-29

## 背景

用户 2026-10-29 要求找出多 Agent 协作（父子对话、子任务、工作流）里浪费 token 的地方并修掉。

对话的每一轮由 `runConversationTurn` 调 `conversationPrompt` 拼一份完整提示：用户消息 + 授权、目标、规则、搜索排除、验证、后台命令、计划规则、收尾、执行目录、分派规则……CLI 保活时（对话页开着）下一条消息走 runner 的 `listen`，原样交给活着的进程，不经过这里；**CLI 没保活时每条消息都开新一轮、续接原会话，这份完整提示原样追加进同一个会话**。子对话通常没人开着页面，父对话转达、合并结果、后台命令结果每来一次就是一轮。

## 事实核对

| 位置                                     | 现状（改之前）                                                                                                  |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `shared/engine.ts` `runConversationTurn` | 每一轮都把 `conversationPrompt` 的整份结果作为 `prompt` 交给 `runAgent`，不看会话是不是续接                     |
| `server/exec/runner.ts` `runAgent`       | 角色设定（没有系统提示词参数的 CLI）、项目教训、编排工具说明只在新会话带一次（`!resume`）；对话规则那份每轮都带 |
| `shared/engine.ts` `mainTurn`            | 工作流主 Agent 已经是「续接只发事件、`fresh` 带完整的」                                                         |
| `shared/engine.ts` `runHelper`           | 接着原来的子任务做（`step.session`）时也重发整份通用开头                                                        |
| `shared/engine.ts` `userRequests`        | 对话里派的子任务、`start_plan` 跑的工作流节点，「用户需求」带对话里**全部**用户消息                             |

实测（真实 Pi 1.x + 记请求的假 OpenAI 接口，`.tmp` 下的测试台，数字是字符数）：

| 场景                            | 改前每轮新增的用户消息   | 改后   | 第 4 轮请求总长 改前 → 改后 |
| ------------------------------- | ------------------------ | ------ | --------------------------- |
| 顶层对话（执行角色），第 2–4 轮 | 约 5,550                 | 约 365 | 48,191 → 32,638             |
| 子对话（独立分支），第 2–4 轮   | 约 7,000（第一轮 7,888） | 约 405 | —                           |

第一轮不变。每轮少的约 5–7 千字既是不命中缓存的新输入，又一直留在会话里，把上下文推向压缩。

## 决策

续接同一个 CLI 会话时，规则段落只发新出现的和内容变了的（`shared/prompt-delta.ts`）：

1. **按拼提示词时的段落记指纹**，不按全文的「## 」重新切——用户消息、目标、子对话转来的文字里也会有「## 」开头的行。键是段落标题行，同名的按次序区分。
2. **每轮必发**：`ALWAYS_SECTIONS`（这一轮的消息、子对话发来的消息、子任务要做的事、重试 / 接着做的说明），不记指纹。
3. **省掉的段落**在末尾写一句「其余规则和之前给过的一样、仍然有效」；**以前发过、这次没有了的**段落列进「不再适用的规则」，免得模型还按旧规则做。
4. **发完整的情况**：没有记录、会话 id 和记录的不一样（新会话、保活进程里开了新会话）、对话在回退（`task.rewind`）、预热、续接满 `FULL_EVERY`（10）轮（长上下文里规则离得太远，定期补一份）、什么都没省下。
5. **兜底**：发增量时同时传 `fresh`（完整的）；runner 这一轮没接上原会话（换了 CLI / 目录 / 回退、会话找不到）就改用 `fresh`。压缩（`compacted` 事件或压缩操作）后 runner 删掉这个会话的记录（`forgetPromptSent`），下一轮整份重发。
6. **记录时机**：这一轮跑完或被停下才记（停下时 CLI 已经读过）；报错的不记，可能根本没交到 CLI。记在 `Task.promptSent[会话键]`，最多 `MAX_SENT`（40）个会话，最久没用的先丢。
7. 计划段拆成「执行计划」（当前计划，每轮在变）和「计划怎么维护」（规则，不变），否则每次改计划都要连规则一起重发。

同一批顺带的两处（不另开 ADR，都是同一个目标）：

- 对话里派子任务、跑工作流节点，「用户需求」只带最新一条（全文），第一条截到 1,500 字（子对话里是父对话交代的任务），中间只留最近 3 条的前 300 字（`nodeRequests`）。工作流任务不变。
- 父对话每轮的「现有子对话」只列最近完成的 8 个（`RECENT_DONE_CHILDREN`），更早的写一句数量，要查用 `list_conversations`。

## 没选的方案

- **规则全挪进系统提示词**：保活的进程里系统提示词是固定的，而这些段落随状态变（授权回答、执行目录、收尾种类、计划）；Command Code 没有系统提示词参数。
- **续接时一律只发用户消息**（像保活那样）：状态变化（推送授权回答了、开了独立分支、收尾种类变了）就传不进去了。
- **整份算一个指纹，变了就整份重发**：「现有子对话」「执行计划」几乎每轮都变，等于没省。

## 风险与代价

- 模型在很长的会话里可能淡忘早先给的规则：靠 `FULL_EVERY` 定期补发、压缩后整份重发兜住。
- CLI 压缩了却没报 `compacted`、面板也没发压缩操作时，记录不会作废，最多到 `FULL_EVERY` 轮后补上。（已由 [ADR 0028](./0028-panel-tools-on-demand-and-input-sources.md) 按上下文骤降识别）
- 任务文件多一个 `promptSent` 字段，每个会话十几条指纹，有上限。
