# ADR 0042：停下就是暂停，继续就是原样回来——子任务、子对话、父对话共用一套暂停 / 继续规则

状态：提议（2026-11-03 第 1 期已实施，第 2～4 期未开始） · 2026-11-03

- 影响范围：`shared/task.ts`（`childReport`）、`shared/resume-kids.ts`、`shared/plan.ts`、`server/tasks/conversation-routes.ts`（`resumeKids`、`/resume`）、`server/tasks/child-messages.ts`（`noteParent`）、`shared/engine.ts`（子任务的 `resume`、`finish`）、`shared/task-settle.ts`、`server/tasks/keepalive.ts`（`stopTree`）
- 取代：无。补全 [0032](./0032-conversations-keep-going.md) 的「继续时连带恢复」和 [0036](./0036-stuck-child-restart-takeover.md) 的卡住接手

## 背景

用户反复报：停下父对话再继续，子对话、子任务没接上；父对话一直等；或者面板新开了一批子任务、子对话重做。用户要求「子任务停了再启动不新开，对应的子对话复用、父对话复用」，并要求先梳理框架、给出更完善的设计。

梳理结论：现在三层各有一套「停下」的表示，「再启动」也分在三处，没有一个地方保证「停下的东西原样回来、等它的一方还在等」。

## 事实核对

| 位置                                                    | 现状                                                                                                                  |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `shared/engine.ts` 的 `runHelper`（被停时）             | 子任务记 `status: 'pending'` + `interrupted: true`，会话 id 留在 `task.sessions[step.session \|\| step.id]`           |
| `shared/resume-kids.ts` 的 `resumeNote`                 | 子任务不自动重跑，只在续接说明里让模型用 `spawn_agents resume:<id>` 接着跑                                            |
| `shared/run-stops.ts` 的 `interruptedBlock`             | 还有被打断没处理的子任务时，另派新的一律拒绝                                                                          |
| `shared/engine.ts` 的 `spawn_agents` 处理 `resume`      | 命中被打断的子任务时复用原记录（同一个 id、`reruns + 1`），按原会话 `--resume`                                        |
| `server/tasks/keepalive.ts` 的 `stopTree`               | 自上而下停，子孙记 `stopReason: 'parent'`，最后杀掉整棵树的 CLI                                                       |
| `shared/task.ts` 的 `childReport`                       | 子对话停下时，除了 `stopReason === 'user'` 记 `hold`，其余（含 `parent`、`restart`、`stalled`）一律 `fail`            |
| `server/tasks/child-messages.ts` 的 `noteParent`        | 先 `settleWait`，再判断是不是连带停下（`cascaded`）；所以连带停下的子对话照样把父计划那一步收成失败、退回「需要修复」 |
| `shared/plan.ts` 的 `settleWait`                        | 只匹配 `state === 'waiting'` 的等待；失败的等待不会再被结果命中                                                       |
| `server/tasks/conversation-routes.ts` 的 `resumeKids`   | 只对顶层对话调用；拉起子对话后不恢复父计划里等它的那条等待；不递归拉起孙对话                                          |
| `shared/resume-kids.ts` 的 `AGAIN`                      | 连带拉起的原因只有 `parent`、`restart`、`stalled`、`lost`，不含 `budget`                                              |
| `server/tasks/conversation-routes.ts` 的 `resumePrompt` | 续接提示里把「原来的要求」原文再发一遍                                                                                |

由此产生的主要问题：随父对话停下的子对话，被拉起并做完后，交回的结果对不上任何等待，父对话不会被叫醒；同时那一步挂着「需要修复」，面板推父对话「查原因重做」，容易重派或另建子对话。

## 决策

**停下就是暂停，不是结束；继续就是原样回来；只有明确「终止」之后，才允许新开一个来替代。**

1. **一套生命周期**。子任务、子对话、工作流节点都按「运行中 → 暂停（谁停的）→ 继续」走；「终止」是另一条路。暂停的单位保留身份（id）和会话绑定（CLI、模型、会话 id、目录、分支）。
2. **等待只在有结果时结算**。父计划里等子对话、子任务的那条等待，只在对方完成、失败、终止时改状态；暂停（不论谁停的）一律保持「等待中」。只有归档、删除、被接手、核对时发现已经没人在跑（`lost`）算结束。
3. **继续由面板按树算出来，不靠提示词**。从继续的那个节点往下：连带暂停的子对话（父对话停、面板重启、卡住重开、用量上限）递归拉起，并把父计划里等它的那条等待恢复成「等待中」；用户单独停的跳过并写进说明。被打断的子任务由面板在原记录、原会话里接着跑（第 3 期）。
4. **继续时不重放原文**。会话接得上时只说明「被中断了，从这里接着做」和继续计划的结果；会话丢了才带上原来的要求和对话摘要（第 4 期）。
5. **进程只是缓存**。复用指同一个 id、同一个会话，不要求同一个进程；停止后继续一律新开进程、`--resume` 原会话。

候选方案：

- **只改提示词，让模型更听话**：放弃。现在的问题恰恰是靠模型读说明来续接，模型没照做就悬着。
- **暂停的子对话直接按失败处理，让父对话自己重派**：放弃。和用户的要求「复用原来的子对话」相反，还会丢掉它独立分支里的进展。
- **继续时新建子对话、把旧对话的总结带过去**：只留给「卡住接手」（0036）这一种情况，平时一律复用。

## 操作清单 / 契约

| 停止原因                                                     | 子对话停下时父计划的等待         | 父对话继续时                 |
| ------------------------------------------------------------ | -------------------------------- | ---------------------------- |
| `user`                                                       | 保持等待中                       | 不拉起，写进续接说明问用户   |
| `parent`、`restart`、`stalled`、`budget`                     | 保持等待中                       | 递归拉起，等待恢复成等待中   |
| `presence`、`idle`、`close`、`switch`、`supersede`、`finish` | 保持等待中                       | 不拉起（由各自的流程接着推） |
| `lost`                                                       | 失败，那一步退回「需要修复」     | 拉起，等待恢复成等待中       |
| `archive`、`delete`、`replaced`                              | 失败（被接手的由 0036 改等新的） | 不拉起                       |

- `rearmKidWait(parent, kidId)`：父计划里等这个子对话、已经收成失败的等待改回等待中；那一步只因它退回「需要修复」的，改回等待中、清掉「需要修复」。拉起子对话时、用户直接继续一个子对话时都调。
- 用户直接继续某个子对话：同样递归拉起它名下连带暂停的孙对话，并恢复它在父计划里的等待。

## 与现有实现的关系

- `childReport` 的 `settle` 改成按上表；`noteParent` 的 `cascaded` 分支不变（连带停下照样不写进对话流、不进收件箱），只是不再把等待收成失败。
- `resumeKids` 改成递归，任何对话模式的对话继续时都调；拉起成功后调 `rearmKidWait`。
- `kidAccepted` 的判定不变：连带停下的等待现在保持「等待中」，不会被误判成已交付。
- 卡住接手（0036）的 `rebindChildWait` 只改 `waiting` 的等待：现在旧对话停下时等待保持等待中，接手时能改到新对话上。

## 运行时

- 停：`stopTree` 照旧自上而下停、杀进程，子孙记 `parent`；`reportChild` → `noteParent` 按新的 `settle` 结算，连带停下的不再动计划。
- 继续：`POST /tasks/:id/resume` → 先恢复本对话在父计划里的等待（如果它是子对话）→ `resumeKids` 递归：每一层先拉起孙对话，再按结果拼本层的续接说明、`start(..., resume=true)` → 本层拉起成功就恢复父计划的等待；拉不起来就把等待收成失败（父对话据此另建子对话接手）。
- 拉起的子对话做完时，`settleWait` 命中等待中的那条，照常叫醒父对话。

## 分期

1. **第 1 期（本次）**：等待在暂停时保持等待中（`childReport`）；`resumeKids` 递归、拉起后恢复等待；用户直接继续子对话时恢复等待；`budget` 也连带拉起。出口：单测覆盖结算规则和恢复等待；端到端「停父对话 → 继续 → 子对话做完 → 父对话被叫醒」通过。
2. **第 2 期**：停止收口统一成 `pauseUnit` / `cancelUnit` 两个入口（现在 `finish`、`settleStopped`、`abandonLive`、`state-sweep`、`dropInterrupted` 各写一份）；「答完」的判定不再把还在跑的子任务记成完成；收口时清掉子任务的排队标记。
3. **第 3 期**：`shared/` 加纯函数 `planResume(树, 起点)`，算出要拉起谁、怎么接回会话；被打断的子任务由面板在原记录、原会话里接着跑；继续计划写进对话日志，「状态」诊断里显示。
4. **第 4 期**：续接提示不重放原文；会话代数（`sessionGen`）记进诊断。

## 风险与代价

- 暂停的子对话不再把父计划收成失败：如果暂停后谁都没把它拉起来（比如父对话还在跑、子对话被页面切走回收后再没人推），父计划会一直等。防线：只有能被自动接回的原因保持等待中，`lost` 照旧失败；「状态」诊断的 `child-idle-parent-waiting` 会报出这种情况。
- 递归拉起会一次起多个 CLI：连带暂停的整棵树都会被拉起来，和停之前的规模一样，受 API 并发名额限制。
- 用户单独停的子对话保持等待中：父对话继续时会在说明里看到它，按说明问用户，不会自己重派。

## 开放问题

- 被打断的子任务由面板自动接着跑，还是保留「模型决定要不要接着跑」：倾向自动接着跑（用户明确要求复用），做成默认开启。第 3 期之前照现状由续接说明提醒模型。
- 面板重启后是否自动按继续计划拉起之前在跑的对话树：倾向加一个设置，默认关。定下来之前照现状由首页「全部继续」手动拉起。
