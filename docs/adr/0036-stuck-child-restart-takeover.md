# ADR 0036：子对话卡住时面板先重启，重启没恢复再换新的子对话接手

状态：已接受 · 2026-10-31

## 背景

用户 2026-10-31 要求：

> 父对话询问子对话是否卡住，如果一定时间没有回复就终止子对话然后 resume 重启子对话，没启动成功就报错，新开一个子对话继续处理内容

之前子对话没有输出时面板只会以父对话的名义问它状态（最多 3 次），问完就不管了；子对话真卡死时只能等用户发现、自己停掉重发。

## 事实核对

| 位置                                                  | 改动前                                                                                                                  |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `shared/task.ts` 的 `childIdleAsk`                    | 静默到阈值（`childIdleAskMinutes`，默认 3 分钟）问一次，同一段静默最多 3 次，只问不停                                   |
| `server/tasks/idle-ask.ts`                            | 定时扫内存里在跑的子对话，经 `deliver` 发询问；收不下（`held`）就撤掉                                                   |
| `server/exec/runner.ts` 的 `stalledTurn`              | 交给 CLI 的东西 90 秒没有任何输出就标「没有响应」；下一条消息交付时 `restartStalled` 停掉它接回会话重开。跑工具期间不标 |
| `server/tasks/run.ts` 的 `restartStalled`             | 停的原因记 `stalled`，`followUp` 接回原会话（`--resume`）开新的一轮；起不来时错误抛给调用方，询问那边只写日志           |
| `server/tasks/run.ts` 里父对话的 `createConversation` | 新建子对话的逻辑写在父对话那一轮的闭包里，面板自己建不了                                                                |
| `server/tasks/conversation-routes.ts` 的 `resumeKids` | 父对话继续时把 `parent` / `restart` / `stalled` / `lost` 停下的子对话一起拉起来                                         |
| `server/tasks/children.ts` 的 `reportChild`           | 子对话停下、失败都给父对话写「已中断 / 失败，交回原子对话重试」                                                         |

## 决策

在自动询问后面接两步，判定写在 `shared/stuck-child.ts`，执行在 `server/tasks/stuck-child.ts`：

1. **问过没回复 → 停掉、接回原会话重启**：询问交出去后再过一个阈值（同一个 `childIdleAskMinutes`）还没有任何输出（`childAskUnanswered`），停掉它（`stalled`，硬停），`followUp` 接回原会话开新的一轮，派一条「【卡住重启】」说明让它先说卡在哪再接着做。询问交付时 CLI 已经被标成没有响应、`deliver` 自己重开了的，也按重启核对。
2. **重启没恢复 → 警告 + 新开子对话接手**：重启后核对（`restartOutcome`）：有了 Agent 的输出就算恢复；`followUp` 抛错、这一轮失败、又被标成没有响应，都算重启失败。失败时停掉原子对话（新的停止原因 `replaced`），在原子对话和父对话里各记一条 `no_response` 警告行，按原任务和已有进展（`takeoverBrief`：父对话交代的、用户直接说的、计划、改过的文件、独立分支目录、最后的回复）新开一个「原标题（接手）」的子对话，角色沿用原来的；父计划里等原子对话的步骤改成等新的（`rebindChildWait`），再给父对话写一封信说明换了人。
3. 同一个子对话被面板重启满 `CHILD_RESTART_MAX`（2）次又卡住，不再重启，直接换人接手。

不算卡住的：等用户、等后台命令、等子任务、等工作流（`childWait`）；正在跑前台工具时等待窗口乘 `CHILD_TOOL_REPLY_FACTOR`（5），CLI 要等工具跑完才看得到询问，不能把编译、跑测试当成卡住杀掉。

## 放弃的做法

- 不问直接按静默时长重启：用户要的是「父对话问过、没回复」才处理，而且等工具的静默很常见。
- 重启失败后只告诉父对话的 Agent，让它自己 `create_conversation`：引擎和上报都在拦「另建子对话重做」（ADR 0032、`retryTarget`），Agent 要绕一圈；用户要的是面板直接新开。
- 换人时复用原子对话的独立分支：原分支可能就是卡住的现场（锁、半截的 git 操作），新子对话照常建自己的，派单里写明原分支目录让它去看。

## 与现有实现的关系

- 自动询问的「最多问 3 次」只在询问一直交不出去（`held`）时还有意义：交出去的询问到时间没回复就进入重启。设置项和文案沿用「子对话没有输出时自动询问」。
- 和 ADR 0012（在运行的子对话不失活）不冲突：这里停的是问过、等过仍没有任何输出的子对话，能解释的等待一律不动。
- 和「重试在原子对话里接着做」（`docs/lessons/retry.md`）的关系：先在原子对话里重启；只有原会话起不来时才另建，标题带「（接手）」，`retryBase` 不会把它当成重试拦掉。
- 新建子对话的逻辑从父对话那一轮的闭包里抽成 `spawnChild`，父对话的 `create_conversation` 和面板接手共用（`TasksScope.spawnChildOf`）。
- 重启、接手期间（`TasksScope.childRecovering`）不往父对话报「已中断 / 失败」；`replaced` 停下的也不报，由换人那封信说明。`resumeKids` 不拉 `replaced` 的子对话。

## 运行时

- 扫描挂在 `server/tasks/idle-ask.ts` 的定时器上：每次先 `checkRestarted` 核对重启过的，再按子对话判断「问过没回复 → 重启」还是「到阈值 → 询问」。
- 重启记录只在内存里（面板重启后所有对话都停了，没有要接着核对的）。
- 新开子对话失败时两边记 `error` 级警告，不再重试。

## 分期

一次做完。

## 风险与代价

- 窗口太短会误杀慢模型：窗口和询问阈值同一个设置，用户调大阈值就一起放宽；跑工具时再放宽 5 倍。
- 接手的子对话从头读一遍现场，会多花 token；派单只带原任务和进展摘要，不带整段对话。
- 原子对话在独立分支里没合回的改动不会自动搬给接手的子对话，靠派单里的目录提示它自己看。

## 开放问题

- 重启后「有输出就算恢复」比较宽：恢复后很快又卡住的，靠重启次数上限兜住。倾向先这样，看实际反馈再定要不要按「恢复后做完一步」判。
