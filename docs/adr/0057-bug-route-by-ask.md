# ADR 0057：用户报的 Bug 按「提问」开关选修法，已有子对话可以升级成 Bug 流程

状态：已接受（2026-11-07 用户定的，已实施） · 2026-11-07

## 背景

ADR 0046 第 0 条：用户只描述了一个 Bug（没发 `/bug` 也没发 `/fix`）时由父对话判断，看出是要查原因的就派 `kind: "bug"`，走完整流程。完整流程每一步都要用户在弹窗里确认；用户没开「提问」、只想快点修好时，也会被父对话判进多轮确认。反过来，已经按直接修派出去的子对话，用户中途想改走完整流程，只能自己进子对话发 `/bug`，在父对话里说一句没有用。

## 决策

- **`/bug`、`/fix` 不变**：`/bug` 一定走完整流程，`/fix` 一定直接修（`kind: "task"`）。
- **只描述了 Bug：跟父对话的「提问」开关走。** 开着：父对话派之前先用提问工具问用户选「完整 Bug 流程」还是「直接修」，按现象卡推荐一个；关着：默认直接修，不问、也不自己改判成完整流程，回复里提一句可以发 `/bug` 或让父对话升级。规则按开关每轮现算，放在父对话提示的「用户报的 Bug 用哪种方式修」一节（`shared/bug-route.ts`），开关在对话中途改了，续接时这一段会重发。
- **已有子对话升级**：`send_to_conversation` 多了可选的 `kind: "bug"`（和 `level`）。面板把子对话标成用户报的 Bug（`Task.bug`，同子对话里发 `/bug`），交过去的话前面加一段说明；续接的会话里没有完整流程，记 `Task.bugMethodPending`，下一轮补带一次（`server/tasks/bug-upgrade.ts`、`server/exec/bug-prompt.ts`）。子对话正在回复时拒绝（这一轮换不了工具），父对话等它这一轮结束再交。已经是 Bug 的原样交，不降级。

## 不做

- 不在界面上加「升级成 Bug 流程」按钮：用户在父对话里说、或在子对话里发 `/bug` 已经够用。
- 不按用户消息的文字自动判断是不是 Bug：仍由父对话按提示决定。

## 后果

- 取代 ADR 0046 第 0 条里「不写 `/bug` 时主理照样判断、拿不准就问用户」那一句。
- 任务数据多了可选的 `bugMethodPending`。
