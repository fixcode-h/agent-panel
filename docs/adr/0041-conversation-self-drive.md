# ADR 0041：对话自己推着把事做完——外部消息只改计划，截断给模型的内容必须留全文指针

状态：已接受（P1、P2 的子对话自驱已落地；其余见「分期」） · 2026-11-02

- 影响范围：`shared/drive.ts`（新增）、`server/tasks/drive.ts`（新增，从 `children.ts` 拆出）、`shared/turn-rules.ts`（新增）、`server/tasks/inbox-file.ts`（新增）、`server/tasks/children.ts`、`server/tasks/merge.ts`、`server/tasks/run.ts`、`server/tasks/conversation-routes.ts`、`server/app-actions/tasks.ts`、`shared/conv-mode.ts`、`shared/peer-message.ts`、`shared/engine.ts`、`shared/helper-batch.ts`、`server/store.ts`、`server/exec/runner.ts`、`server/exec/cli-trace.ts`、`shared/lifecycle.ts`、`server/tasks/lifecycle.ts`、`shared/alerts.ts`、内置约束（`shared/builtin/agents.ts`、`chat-agents.ts`）、`shared/agent-role.ts`
- 修改：[ADR 0032](./0032-conversations-keep-going.md) 第一、二节（推进次数、子对话推一次就报父对话），[ADR 0037](./0037-chat-and-agent-modes.md) 的推进次数（子对话也是 3 次）

## 背景

2026-11-02 用户导出的诊断文件（Claude Code + deepseek-v4.1-flash，项目里的对话，有面板计划）显示：面板只在 20:55:32 推过一次，之后三次「这一轮结束」计划都没做完却没再推，对话停在等下一句；中间两条「继续」不是用户发的，是建它的另一个对话用 `task.send`「以用户的身份」发的。同一天用户还报：父对话说「评审摘要被面板截断，完整结论没拿到」，只能让评审子任务原样重述。

用户定的原则（原话摘要）：

- Agent 对话本身有一套自驱系统，自己推着完成当前计划，而不是父对话检测到再来推；外部消息只会改变计划。
- 父对话和子对话一样：根据输入、自己的消息、子对话的消息更新计划，按计划执行，计划执行完对话就完成；新消息先分析再定计划，这个阶段也不能莫名停下。
- 不需要计划的事这一次处理完就算完成，避免「完全靠计划」的怪圈。
- 说了要做就该去做，但允许直接调用工具不加说明。
- 发给对话的内容要区分是用户发的还是父对话（或其他对话）发的。
- 给模型的数据不能不全。

## 决策

**计划是「做没做完」的主信号，但不是唯一信号；推进（自驱）属于对话自己，每层只推自己；外部输入只改计划；给模型的内容截断必须留读得到的全文指针。**

1. **三档完成信号**：有面板计划按计划；没有计划的事这一轮自然结束就算完成，只在拿不准时补一次「收尾自检」（动手 ≥3 处没计划，或新输入后第一轮一个工具都没调）。自检的结果看那一轮有没有再动手，不解析回复文字。CLI 自带待办那一档不用：Agent 模式的提示要求用 `set_plan`，Chat 页不在自驱范围。
2. **推进账本**（`shared/drive.ts` 的 `DriveBudget`）：只在真推出去时记；同一进度（`planProgressKey`：步骤 id + 状态，改标题备注不算）最多 3 次；同一条输入之后总共最多 10 次；用户亲自发消息、父对话交代新任务清零，其他对话和面板消息不清零。复查时计划变了就按新进度再判一次，不放弃。
3. **子对话和顶层对话一样自驱 3 次**，推满了才向父对话报一次「卡住」，信里写明看卡在哪、回答或改要求，不要只发「继续」。
4. **来源区分**：`task.send` 带发件对话，记成 `peer.rel='peer'`；父对话、其他对话的消息交给 CLI 时前面写明「不是用户说的」（`sourceHeader`，转交的用户回答除外）。
5. **回合规则只有一份**（`shared/turn-rules.ts`）：可以直接调用工具不用先说明；要说明就和工具调用写在同一条回复里；不单独发只有打算的回复。
6. **截断必须留指针**：给模型的长内容用 `clipToFile` / `clipWithFile` 存全文、写明路径；交接目录 CLI 启动前建好并放行（`handoffDirOf`）；评审、验收（要逐条处置）上限 2 万字。

没选的方案：

- **父对话负责催子对话**：父模型每次都要花一轮、和子对话自己的进度打架，用户明确否决。
- **没计划就逼它列计划**：小事也被逼着列计划，「完全靠计划」的怪圈。
- **按回复文字猜「没做完」**：2026-10-29 已经因误判删掉，不加回来。
- **不设总次数上限**：指纹按状态算，模型来回改状态能无限推。
- **重启后自动补推**：已有「重启后继续」名单（`restartUnfinished`）由用户确认，自动推会让一批旧对话同时跑起来。

## 操作清单 / 契约

| 项                                         | 契约                                                                                                                                                                               |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DriveBudget.can / take / reset / state`   | `can` 只看不记，返回 `ok` / `exhausted` / `total-cap`；`take` 返回这一进度第几次，不能推返回 0                                                                                     |
| 对话日志                                   | 「计划推进」`action=none\|stuck\|cancel\|reevaluate\|continue\|send-failed reason=… key=<8 位> nth/max`；「收尾自检」同形；「CLI 报这一轮结束」带 `stopReason`、`endedOn`、`tools` |
| 诊断（`LifeFacts`）                        | `plan: {title, done, total, waiting, open, key}`、`nudge: {key, n, max}`、`trace.lastTurn`；异常 `plan-stalled`、`turn-cut`                                                        |
| `FollowUpInput.from`                       | 别的对话替它发的：发件对话 id；收件方记 `peer`，不当用户的话、不清零推进次数                                                                                                       |
| `sourceHeader(m)`                          | `peer.rel` 为 parent / peer 且不是 answer、不是面板消息时返回一行来源说明                                                                                                          |
| `clipWithFile(taskId, title, text, limit)` | 超长时全文存 `taskId` 的交接目录，返回开头 + 路径（总长 ≤ limit）；写盘失败整段返回                                                                                                |

## 与现有实现的关系

- 推进从 `children.ts` 拆到 `server/tasks/drive.ts`（`createDrive`，由 `createChildren` 组合进来），对外仍是 `nudgePlan` / `nudgeState` / `resetNudge`。
- `merge.ts` 的 `stuckAfterNudge` 改读推满时才记的 `planNudged`；`reportChild` 的「未完成」去重键改用 `planProgressKey`。
- 计划提醒（ADR 0020 的 `inputUnhandled`）不变：它在下一轮提示里提醒新输入要不要改计划，自驱只在一轮结束时看计划。
- 子对话没有输出时自动询问、卡住重启接手（ADR 0036）管「一轮之内」，自驱管「一轮结束之后」，不重叠。
- `nudgeMerge` / `nudgeShared`（只剩合回没请收尾）不变。

## 运行时

一轮结束（`onTurnEnd` / `settleChildTurn`）→ `nudgePlan`：有计划看 `planStalled`，没计划走收尾自检 → 刚结束只 `can` → 等 `PLAN_NUDGE_MS` 让 CLI 停稳 → 复查（有输入交进来就取消、计划变了就重评）→ `take` → 顶层 `wakeConv`、子对话 `sendToChild`（过 `holdWake` 的整树用量检查）。页面切走、闲置回收的保活进程（`stopReason` presence / idle）算正常说完的一轮，照常推。账本在内存，面板重启从头数。

## 风险与代价

- 零工具首轮的收尾自检：项目对话里纯问答每次多一轮，要带整个会话上下文（有缓存时主要是缓存读）。按模型统计自检后真去做了的比例，长期为 0 的在模型设置里提示可关。
- 子对话推 3 次：每次一轮模型调用，但父对话不再发「继续」，那一轮父模型调用省掉了。
- 推进次数在内存：面板重启后从头数，最坏多推 3 次。

## 开放问题

- 共享状态（`write_state`）、运行消息存储时截到 2 万字：倾向超长时拒绝写入并告诉调用方；`shared/engine.ts` 到了行数上限，等下次挪出代码时一起改，之前保持现状。
- 规则检查拦「拼进提示词的 `clip(` 不留指针」：写法难以静态区分摘要和正文，倾向先靠教训（`docs/lessons/self-drive.md`）和评审，定下规则前不加检查。
- 工作流节点内部要不要也按状态行自驱：**这次不做**。很多节点有自己的输出格式（JSON、带分支的「结论：通过」），强制每个节点交「## 总结 + 状态」会打乱用户已有的工作流；没交总结就推又会让旧工作流的每个节点多跑几轮。节点已经有用户配的重试、验收钩子和主角色评估，整条运行停住由所属对话自驱接手，「说了要做却没做」靠共用的回合规则（`shared/turn-rules.ts`）。倾向：以后确有需要时做成节点的可选开关（流程图上勾「按状态行判定做完」），默认关。
