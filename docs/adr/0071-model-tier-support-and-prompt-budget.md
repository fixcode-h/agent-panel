# ADR 0071：按模型档位加强扶持，提示词定预算，情境规则用到时再推

状态：已接受 · 2026-11-21

## 背景

#397（插话没转给子对话）、#398（工具参数名写错）、#399（不用现成接口另造函数）都是往提示词里加一段话修的。这对强模型有效，对 deepseek-v4-flash 这类弱模型效果有限：规则越长越守不住，新加的规则还稀释了旧的。执行角色的设定约 9400 字，加上通用约束约 5400 字。设计稿 `designs/Agent写代码能力-提升与扩展分析.md` 的 C1、D1，用户 2026-11-21 同意开发。

## 事实核对

| 位置                                   | 现状                                                                                        |
| -------------------------------------- | ------------------------------------------------------------------------------------------- |
| `shared/models/catalog.json` 的 `tier` | 每个模型都标了强中弱档（`deepseek-flash` 是 low），只在工作流节点选档时用，钩子和提示词不看 |
| `shared/hooks/builtins.ts` 的档位      | 精简 / 标准 / 严格要用户手动选，说明里写着严格档「适合弱模型」                              |
| `shared/knowledge/push.ts`             | 一次最多推 3 条，固定                                                                       |
| `shared/plan/pace.ts`                  | 计划没跟上提醒默认动手 20 次                                                                |

## 决策

1. **档位扶持是一张注册表**（`shared/models/support.ts` 的 `SUPPORT_ITEMS`）：钩子档位、先列实现计划、情境推送条数、计划没跟上的阈值，一项一行，每档写默认值。runner 每轮按这一轮实际用的模型（经 API 设置的映射，`apiModelInfo`）在模型目录里查档位，算出 `ResolvedSupport` 交给钩子。默认开。
2. **只往严里推**：每一项和原来的设置取更强的（钩子档位取更严、推送条数取多、提醒阈值取小）。项目手动选的钩子档位、钩子页逐个改过的开关照旧优先；扶持只在落到全局档位时生效（`builtinOn` 的 `boost`）。
3. **看得见、调得了**：会话栏「环境」写「已按弱模型加强扶持」，点开列出加强了哪几项（记在 `AgentUsage.support`）；设置 → 钩子 →「按模型档位加强扶持」一项一行、一档一列，每格都能改，存在 `hooks.json` 的 `modelSupport`。
4. **情境规则**（`shared/hooks/situational.ts`）：只在某个情境才用得上的细则做成「触发条件 → 文字」的一行，由内置钩子 `situational-rules` 在工具前 / 工具后推，每条一个对话只推一次，只提醒不拦。一条规则都用不上的轮次不装钩子。第一条：弱档「先列实现计划 = 每次都要」时，第一次改文件前还没计划就推一句。
5. **提示词预算**（`scripts/prompt-budget.mjs`，基线 `scripts/prompt-budget.json`）：渲染每个内置角色的设定和几种典型情况（顶层 / 子对话、Git / P4、UE）下新会话第一轮的完整消息，数字数，`npm run lint` 里只许变短；变长了先想能不能做成情境规则，确实要加用 `--update --grow` 并在提交说明里写原因。

候选方案：

- **按模型名写分支**（`if (model.includes('flash'))`）：没选。模型目录本来就有档位，换模型、加模型只改目录。
- **弱模型直接换一套更短的提示词**：没选。两套提示词要同步维护，规则一改就漂；先用预算把基础提示词压住，细则挪进情境规则。
- **扶持也能把强模型调松**（例如强模型用精简档）：没选。设计稿里强档和中档一样；只往严里推，用户在设置里调低不会让钩子比原来松，免得调错了出事。

## 与现有实现的关系

- `server/hooks/support.ts` 的 `turnSupport`：档位 + 设置 → 这一轮的扶持；`server/exec/runner.ts` 调它，记进会话用量，交给 `hookOptions`。
- `server/hooks/dispatch.ts`：`on()` 带 `boost`；推送教训的条数、计划提醒的阈值按扶持取；情境规则和推送教训走同一个工具前补说明。
- `server/hooks/situational.ts`：按对话记推过几次（`taskMap`）、记日志和「最近触发」。
- 评测用例 `scripts/real-cli/eval-tasks.mjs` 的 `plan-first`：在弱模型上跑，只按 `task.plans` 判有没有先列计划。
- 规则搬迁（2026-11-21，A、B 合进 dev 之后）：`ideMcpLines` 的 JetBrains 调用规矩改成情境规则 `ide-mcp-rules`（第一次调 IDE 服务的工具时推），「搜索」一节只留一行 `ideMcpPointer`；执行角色「先用现成的」里搜一次、写复用检查的细则交给模块入口推送（`server/hooks/module-push.ts` 的新增公开函数提醒），角色里只留找多远的原则。Bug 修复方案阶段的复用检查本来就只在那一阶段发，没有再搬。
