# ADR 0029：角色之间按固定交付契约交接，Bug 流程加「钉住现象」和回归测试，测试验收能独立设计用例

状态：已接受 · 2026-10-29

## 背景

用户 2026-10-29 要求整体审视角色、角色分类、工作流和父对话 / 子对话 / 子任务的分工，加强找 Bug 和写代码的能力，完善 Bug 分析流程和「方案设计 → 编码落地 → 测试」这条链，缺的角色补、弱的加强、多余的合并。

审下来的结论：角色各自的**方法**已经写得很细（按模块逐层定位、三环证据链、评审四级、收尾顺序），短板在**角色之间的交接没有格式**：

- 主理派 Bug 时写的是散文，子对话交回也是散文；复现、调用栈、回归测试缺了哪一环要再追问一轮。
- 方案设计交的「设计摘要」验收标准常是一句话、不标测试层级，开发按自己的理解实现，测试验收按自己的理解打钩。
- 执行接单后直接开改，没有复述、没有计划，验收标准在中途被默默放宽，调用方漏改靠评审兜。
- 找 Bug 的方法从「读模块文档」开始，少了读代码之前的「钉住现象、先复现一次、回归先看最近改动」；修复一步只说「只改根因那一处」，没要求回归测试、没拦「把报错吞掉算修好」。
- 测试验收只会按项目配置跑命令，没有谁独立于实现者再想一遍「哪里会错」；实现者写的测试只覆盖它自己想到的路径。
- 写代码的硬规则没有「接口先读定义再写」这一条，而凭记忆写出来的参数名、选项、返回结构是模型写代码最常见的错。

## 事实核对

| 位置                                       | 改动前                                                                           |
| ------------------------------------------ | -------------------------------------------------------------------------------- |
| `shared/builtin/agents.ts` 的 `BUG_METHOD` | 从「定位顺序」第 1 步开始；第 10 步只写「只改根因所在的那一处」；交回一行列举    |
| 同文件 `CODING_TEXT`                       | 八条硬规则，没有读定义、想边界                                                   |
| 同文件「主理」                             | 「派单写什么」「Bug 怎么交」是要点列表；交回时只核对调用栈、证据链、验证结果三样 |
| 同文件「执行」                             | 「怎么执行」后直接是写代码规范和 Bug 方法；没有接单复述、实现计划、自测清单      |
| 同文件「方案设计」                         | 输出「目标、非目标、方案、改动范围、验收标准初稿、风险和待确认项」一句话         |
| 同文件「测试验收」                         | 参数 `scope` `env` `regress` `onFail` `write` `serial`，只有「跑验收」一种做法   |
| 同文件「评审」                             | 「怎么评」两遍（找候选、逐条复核），没有按改动类型的清单，对修 Bug 的改动不多看  |
| `shared/test-steps.ts` 的 `isTestAgent`    | 靠 `scope` + `env` 两个参数认测试角色                                            |
| `docs/agent-catalog.md`                    | 有分工原则、清单、合并表、Bug 分工；没有角色之间的交接格式                       |

## 决策

**角色之间的交接定成几段共用正文（交付契约），上游按它交、下游按它核；Bug 方法加第 0 步和修复硬要求；「测试验收」加 `task` 参数能独立设计用例、补测试；不新建角色、不合并角色、不动分类。**

1. **交付契约**（都在 `shared/builtin/agents.ts`，被角色设定引用）：
   - `DESIGN_BRIEF_TEXT` 方案摘要：目标 / 非目标、现状与依据、方案与备选、改动清单（含兼容）、实现顺序、验收标准（可执行、标测试层级、标已有 / 要新写）、风险与回滚、待确认。方案设计交它；开发按「实现顺序」展开、照抄验收标准；测试验收逐条打钩。
   - `IMPL_PLAN_TEXT` 实现计划：目标与验收、现状、3–7 步各带验证、风险。执行接单后、开发「实现」「重构」动手前写；计划变了要改计划并说明，验收标准不能中途放宽。
   - `BUG_REPORT_TEXT` 排查报告：现象、复现、范围、调用栈、证据链、根因、修复、验证、回归与隐患、文档。`BUG_METHOD` 的交回按它写，主理按同一张表核对，分析角色的排查类报告按同样小节。
   - `SELF_CHECK_TEXT` 交付前自测：验收逐条、测试与快速检查、差异自读、没留调试物、边界、遗留。执行、开发说「完成」前过一遍并贴证据。
   - 主理的派单单（目标 / 交付物与验收标准 / 范围 / 已知 / 假设）和 Bug 现象卡（期望 vs 实际 / 触发 / 环境 / 频率 / 何时开始坏 / 报错原文）写在主理设定里；执行接单先复述，缺验收标准用 `message_parent` 问回。
2. **Bug 方法**：加第 0 步「钉住现象」（现象卡、先复现一次、回归先看最近改动和 `git bisect`、差异法、一堆错只盯第一条）；修复要先有改前失败、改后通过的复现测试，修根因不修症状（try/catch、判空绕过、加重试不算），再查同类隐患。主理派 Bug 按现象卡写，交回时缺回归测试或修法只消症状就交回补；评审对修 Bug 的改动多看这几条。
3. **写代码**：`CODING_TEXT` 加「不凭记忆写接口」（先读定义或文档）和「边界先想再写」。
4. **测试验收** 加 `task` 参数：`跑验收`（默认，行为不变）、`设计用例`（从验收标准、方案、Bug 根因出发列测试矩阵：行为 / 输入 / 预期 / 层级 / 已有或缺，按正常 → 边界 → 失败路径 → 时序 → 兼容 → 回归枚举，不写代码）、`补测试`（只改测试文件，新用例先确认会失败再写到通过，产品 Bug 不修只报）。仍是唯一的测试角色，`scope` / `env` 不动。执行对重要交付（公共接口、数据格式、用户直接用的功能）评审前派它设计用例。
5. **评审** 的「怎么评」加按改动类型的清单（数据格式 / 签名 / 默认值、异步并发、错误处理、界面状态、修 Bug 的改动），只报能写出失败场景的。
6. **文档** 多接一类派单：标为「教训」的写进项目的教训目录（没有就写模块 README 的易错点）。

没选的方案：

- **新建「测试设计」角色**：独立设计用例确实需要独立视角，但它和「跑验收」是同一个能力块（测试与验收），拆开就违反「一个 Agent 管一个能力块」；做成 `tester.task` 的一档，派出时自然就是独立视角。
- **新建「Bug 分诊」「复现」角色**：父对话到模块的分诊、子对话的钉住现象都是现有角色流程里的一步，拆成角色每次交接都会丢中间线索（和 `debugger` 合并进 `developer` 是同一个理由）。
- **合并 `helper` 进 `explorer`、`spec` 进 `analyst`、`i18n` 进 `developer`**：`helper` 是引擎兜底（`isHelperAgent`），合并要动引擎，只省一份短设定；`spec` 绑着 OpenSpec 命令和门禁，并进去让方案设计每次带一段用不上的流程；`i18n` 的独立交付标准（已有译文当术语表）并回去会丢。
- **按领域重排角色分类**：启动同步保留用户机器上的分类（`syncCore` 的 `categoryId` 由调用方传已装副本的），改定义只影响新装机器、老机器留空分类；要重排得一起做一次性迁移，这次不做，分析写进 `docs/agent-catalog.md`。
- **把契约写进工作流节点说明**：节点说明短，方法在角色里；工作流定义一改要登记旧版本（`LEGACY_WORKFLOWS`），收益小。方案设计、开发、测试验收的节点不改也直接受益。
- **面板校验小节是否齐全**：排查报告、方案摘要是给人和下游角色读的，缺节由下游追问；评审门禁、`submit_merge` 的校验已经够硬，不再加一层解析自然语言的校验。

## 操作清单 / 契约

| 契约     | 常量                   | 谁写                                   | 谁核 / 谁用                                                    |
| -------- | ---------------------- | -------------------------------------- | -------------------------------------------------------------- |
| 方案摘要 | `DESIGN_BRIEF_TEXT`    | 方案设计                               | 开发展开实现计划、照抄验收标准；评审按目标评；测试验收逐条打钩 |
| 实现计划 | `IMPL_PLAN_TEXT`       | 执行接单后、开发「实现」「重构」动手前 | 自测逐处对照                                                   |
| 排查报告 | `BUG_REPORT_TEXT`      | 执行、开发修完 Bug；分析的排查类报告   | 主理按表核对，缺回归测试或修法只消症状交回补                   |
| 自测清单 | `SELF_CHECK_TEXT`      | 执行、开发说完成前                     | 主理只转述有证据的结论                                         |
| 测试矩阵 | `tester.task=设计用例` | 测试验收                               | 执行、开发补缺口；`task=补测试` 按矩阵写用例                   |

## 与现有实现的关系

- 全部是 `shared/builtin/agents.ts` 的内置定义改动，启动同步直接换成新版（ADR 0015），不用登记旧指纹；`tester` 新增参数 `task` 有默认值，已装副本同步后按默认「跑验收」走，`keepParamValues` 保留用户填过的其他参数。
- 工作流定义（`shared/builtin/workflows.ts`）不改：节点仍点名同样的角色和参数，受益来自角色设定。
- `shared/test-steps.ts` 的 `isTestAgent`、`shared/review-gate.ts` 的门禁、`shared/verdict.ts` 的结论读取都不变；「设计用例」不要求写验收结论（没有结论按通过读，它不做验收），「补测试」仍写。
- 测试：`server/core-agents.test.ts` 新增四条，断言契约在各角色里的位置、Bug 第 0 步和修复硬要求、写代码新规则、`tester.task` 三档的渲染和 `isTestAgent` 不变。
- 文档：`docs/agent-catalog.md` 新增「交付契约」「角色分类」两节，更新 Bug 分工表。

## 运行时

契约随角色设定注入；执行角色的设定比之前多约 2k 字（实现计划 + 自测清单），`BUG_METHOD` 多约 1.3k 字；续接会话按段落指纹只发变了的段（ADR 0027），一次会话里只多付一次。`tester.task` 在节点、`spawn_agents` 的 `params`、能力挂载的 `params` 里都能填；不填按默认。

## 分期

一次做完：契约正文、角色设定引用、`tester.task`、测试、文档。

## 风险与代价

- 提示词变长，小任务也要带实现计划和自测清单：执行角色明确「只读的问答和排查不用写计划」，自测是收尾时过一遍清单，不是每批都过。
- 模型可能把契约写成形式（每节一句空话）：小节要求写证据（命令 + 输出、`path:line`），主理按表核对、缺证据当没做；这是提示词层面的约束，没有面板校验兜底。
- `tester.task=补测试` 允许改测试文件，和 `write=false` 的默认看起来矛盾：`write` 只管「跑验收」那一档会不会写工作区，「补测试」自己限定只改测试文件和夹具；文档和参数说明里写清。

## 开放问题

- **分诊 / 交接质量指标**：`Task.routes` 和子对话交回里能统计「交回后被打回补证据的次数」，用来验证契约是否真的减少了追问；放到工作总结页一起做。
- **角色分类重排**：倾向按「调度 / 设计 / 实现 / 质量 / 文档与交付 / 汇报 / 美术」重排，做的时候要带一次性分类迁移；定下来之前保持现状。
