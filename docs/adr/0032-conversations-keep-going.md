# ADR 0032：对话靠面板推着走完——收尾时推进、父子之间只发必要消息、继续时连带恢复

状态：已接受 · 2026-10-30

## 背景

用户 2026-10-29 ～ 10-30 连续报了几类现象，最后要求把这一块整体梳理、必要时重构（原话摘要）：

- 子对话「一直在等待下一条消息」：说了要执行什么，实际上没执行任何操作就停了；父对话也会这样（「我跑 `test:failed`。」然后停住）。
- 父子之间消息太多：「子对话和父类对话之间不要乱发消息，只发送必要的消息」。
- 计划更新是否及时、新要求进来分析完后是否排进计划。
- 后台命令出错、没启动时，对话收不到结果，卡住。
- 「加强对话中断继续的逻辑，确保父对话继续执行可以正确激活子对话、子任务还有工作流」；继续时「尽量使用原来的子对话，而不是新启动一个子对话」，原来的「确实启动不了需要报错，然后再启动新的子对话继续之前的任务」。
- 对话的上下文一直显示 0。

## 事实核对

证据来自用户导出的四份对话（父对话 + 三个子对话，模型 `deepseek-v4.1-flash` 经 Claude Code）和代码。

## 决策

**对话能不能走完，不靠模型自觉：面板在一轮结束时看计划、看有没有在等的东西，停住了就推；父子之间只在「对方需要动手」时发消息；继续执行时面板负责把一起被打断的东西接上。**

### 一、一轮结束时的推进（所有对话）

`server/tasks.ts` 的 `nudgePlan`：一轮正常结束（进程结束，或停在保活上等下一句），`planStalled` 成立（计划没做完、计划里没有在等结果的步骤、不是只剩合回、没收口）、没有待答提问 / 待确认 / 排队消息 / 在跑的后台命令时，面板等 2 秒（让 CLI 停稳）再核对一次，还停着就以【面板】推它「接着做「下一步」，直接调用工具去做」。

- 子对话：任何一轮都算。顶层对话：只在这一轮调用过工具时推——只回答了一句话、没动手的那一轮（用户问了个问题、或让它先停下）不推。
- 同一个进度（计划 id + 已完成几步）只推一次。推过还原地不动：子对话上报父对话一次，顶层对话停着等用户。
- 判定只看计划状态，不看回复文字（a73b88f 去掉的「按文字猜没做完」不加回来）。
- 「子对话没有输出时自动询问」只管还在执行却没输出的子对话，不再管「停在等下一句」的那种，免得和推进重复推。
- 诊断：Claude Code 每轮结束在日志里写 `stopReason`（`end_turn` / `max_tokens` …）和这一轮的工具数。

### 二、父子之间只发必要消息

| 子对话的结论             | 父对话收到什么                                                                                                     |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| 执行中 / 等结果 / 等用户 | 只改父计划那一步的说明，不发消息（不变）                                                                           |
| 未完成：计划没做完       | **不发消息**，改由面板推子对话（上一节）；面板推过、同一进度还停着，才发一次，并写明「交回原来的子对话，不要另建」 |
| 未完成：只剩合回         | 照旧发一次并叫起父对话（父对话要动手）                                                                             |
| 待收尾 / 已完成 / 失败   | 照旧                                                                                                               |
| 已中断，原因是面板重启   | 不发（重启后由恢复流程接着做）；面板退出过程中一律不报                                                             |

- 去重键：「未完成」按计划进度，其余按这一轮。
- 用户亲手停下的父对话（`stopReason === 'user'`）不被子对话的结果叫起，记进收件箱，继续执行时一起处理。

### 三、继续执行时连带恢复

- `POST /:id/resume` 对顶层对话：先 `resumeKids` 拉起名下被连带打断的子对话（`stopReason` 是 `parent` / `restart` / `stalled`，没收口、没归档、不在回收站），再启动父对话。
- 交给 CLI 的话由 `resumePrompt` 拼：对话模式前面加 `resumeNote`（`shared/task.ts`）——为什么被打断、已经拉起来的子对话（不用另建）、没跑完的子任务（`spawn_agents` 带 `resume: <id>`）、没跑完的工作流（`start_plan` 重新启动那一步），后面是「原来的要求」。
- 子对话拉不起来：写报错（对话里的告警 + 日志），父对话可以另建子对话接手；`sendToChild` 等子对话真的开起来再回话，起不来把错误交回父对话。
- `create_conversation` 带的 `step` 还在等一个没做完、没失败的子对话时拒绝，提示交回原来的子对话；原来的失败了才放行，并在派单里写明接手的是谁的活。父对话的提示词同样写明。
- 启动迁移：还标着 `running` 的工作流运行置成 `stopped`，计划里绑着它的那一步按「工作流没走完」标失败；`merging` 退回 `requested`，父对话收件箱里写明要重新 `finish_child`。

### 四、计划跟上新要求

- `TaskPlan.agentUpdatedAt`：对话自己 `set_plan` 成功时写。`inputUnhandled` 只认它（旧数据没有时退回 `updatedAt`），面板替它改的不算对话看过了新要求。
- 排着的消息取出时按对话里记下的那条认出面板消息，不当成新要求。
- 提醒文案按「这一轮刚进来」写，并要求交给子对话的事在计划里有对应的一步。

### 五、消息和结果不丢

- 后台命令跑之前就抛错：置 `failed`、写明「面板没能启动这条命令」并照常推回。
- CLI 停到等下一句上时（`runner.ts` 的 `flushHeld`），排着等下一轮的消息直接交给它，不再等整次执行结束。
- 后台结果重试前撤掉第一次已记进对话的那条，兜底同样，不留重复。
- 上下文：`message_start` 报 0 不当上下文；`message_delta` 报的输入比开头多时补上并按它算上下文。

### 没选的方案

- **按回复文字判断「说了要做却没做」**：用户 10-29 刚因为误判（寒暄、反问被当成没做完）要求去掉。计划状态是结构化信号，误判少。
- **未完成也发消息、只是去重**：父对话收到后能做的也只是再催一遍，正是面板推进做的事；消息多了还会插进父对话正在跑的一轮。
- **继续父对话时让父对话自己决定拉不拉子对话**：导出里父对话正是因为看子对话没动静而另建子对话重做；被连带打断的子对话没有不拉的理由。
- **继续时自动重跑子任务 / 工作流**：子任务和工作流运行挂在上一次执行的宿主上（`orchState` / `pendingPlans` 是按宿主的 WeakMap），面板不知道它们还该不该跑；写进续接说明、由对话用 `resume` / `start_plan` 接，比面板猜更稳。

## 与现有实现的关系

- 延续 [0005](./0005-conversation-states.md) 的「上报只有一个出口」：仍是 `childReport` + `reportChild`，只是「未完成」改成不发消息、按进度去重。
- 延续 [0021](./0021-plan-model-lifecycle.md) 的「计划靠面板机制推进」：在「一轮结束」这个锚点上补了推进；新输入检测改用 `agentUpdatedAt`。
- [0006](./0006-background-commands-supervised.md) 的「结果送不到不丢」补上启动前失败、排队消息在保活时送达两条路径。
- [0012](./0012-running-conversations-never-deactivated.md)：子对话仍只随用户停止结束；这次补的是「继续」的对称面。

## 运行时

1. CLI 报一轮结束 → runner `endTurn` → `onTurnEnd({ tools })`：子对话走 `settleChildTurn`（独立分支先收口、催合并），然后 `nudgePlan`，没推才 `reportChild`；顶层对话这一轮调过工具才 `nudgePlan`。
2. `nudgePlan` 2 秒后核对，推出去用 `sendToChild`（子对话）或 `wakeConv`（顶层），消息显示成面板的一行。
3. 用户点「继续执行」→ `resumeKids` 逐个 `reserve` + `start`，再启动父对话；拉不起来写告警。
4. 面板启动 → 迁移把残留的运行、合并中状态收口。

## 分期

一次做完。出口：类型检查、lint、全量单测、全量 e2e（`04-subagents` 新增「计划做一半就收尾」「父对话被停下后继续」两步）通过；界面检查交给 CI。

## 风险与代价

- 推进会多一次模型调用：只在计划没做完且没在等东西时推，同一进度只推一次，最多一次。
- 顶层对话里用户说「先停下」但对话那一轮调过工具：会被推一次；推的话里写了「确实卡住了就说明」，对话可以回一句。认下，换来的是不再「说了要做就停住」。
- 继续父对话时连带拉起的子对话会各自占一个 CLI：只拉被连带打断的，用户亲手停的不拉。

## 开放问题

- 模型为什么会在说完打算后直接结束（`stopReason` 是不是 `end_turn`）：日志里已经记了，等用户的日志确认是模型自己收尾还是网关截断。倾向是模型侧问题，面板这层的推进保持不变。
