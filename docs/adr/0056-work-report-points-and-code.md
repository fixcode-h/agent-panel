# ADR 0056：工作报告的条目分点写，问题分原因和修复，附带注释的关键代码

状态：已接受（2026-11-07 用户看过设计稿和示例后定，已实施） · 2026-11-07

- 影响范围：`shared/summary.ts`（分项、提示词、拼报告）、`shared/summary-code.ts`（分点、关键代码校验）、`server/summary-diff.ts`（交给 CLI 的代码改动）、`server/exec/git.ts`（`spansDiff`）、`shared/builtin/agents.ts`（「每日工作总结」写法）、`web/src/components/summary/EntryList.tsx`、`web/src/lib/demo-summary.ts`
- 取代：ADR 0043 决策第 3 条的「每条一段话、不加粗、不写标签」和第 4 条里「不写文件名和代码片段」；0043 其余部分（单子链接、再次生成、不写版本管理操作、去 AI 腔用词）照旧

## 背景

用户 2026-11-07 对每日报告提了几点：

1. 报告里的 Bug 要带关键修改代码，代码里加注释。
2. Bug 固定格式：原因（什么导致的）和修复分开展示；没修好的 Bug 不写修复。
3. 有几项的内容加序号一项项写，不挤成一段。
4. 不写和当前内容无关的东西。

ADR 0043 定的是「一条一段话」，正好相反；材料里也只有改动的文件名，CLI 拿不到代码。

## 决策

1. **报告模板**：每个条目一个三级标题 `### 序号. 标题`。需求下面是怎么做的几点；问题下面是加粗的「原因」「修复」「关键代码」三块，各自分点；没解决的标题后加「（未解决）」，只写原因。单子写在条目最后一行。
2. **分项结构**：`content` / `cause` / `fix` 仍是字符串，**每行一点**（CLI 交回数组，解析时按行拼起来，去掉它自带的序号）。老报告的一段话按一点处理，不迁移数据。`fix` 为空就是没解决。新增 `code: { file, lang, text }[]`。
3. **关键代码只来自真实改动**：服务端给可能在修 Bug 的对话（用户报了问题，或写了「修复」总结卡）按每轮的 git 快照区间取差异，去掉测试、文档、锁文件，按对话 1.2 万字、合计 8 万字截断后放进材料。CLI 交回的代码去掉注释后每一行都要在材料里找得到，有一行对不上就整段丢掉；没解决的问题不收代码。
4. **不限段数**：关键的修复有几处就给几段（用户 2026-11-07 改的，设计稿原来写最多 2 段）；`SUMMARY_CODE_MAX = 20` 只防数据无限长。
5. **需求不贴代码**：用户只要求 Bug 带代码，需求贴代码会让报告变得很长。
6. **无关内容清单写进角色**：版本管理操作、测试过没过和写了哪些记录、开场白和套话、和这一条无关的顺手改动。

候选方案：

- **让 CLI 凭记录自己写代码**：放弃。记录里没有代码，写出来的只能是编的。
- **代码只按文件名截一段给 CLI**：放弃。挑哪几行是关键得看完整的改动，交给 CLI 判断，面板只负责校验它没改写。

## 后果

- 提炼提示词变长：只有疑似 Bug 的对话带代码改动，并且有字数上限。
- 快照被清理、项目目录没了时取不到代码：这条 Bug 没有关键代码，报告照常生成，日志里记一条。
- 自己读任务记录跑（定时计划拉起）时，角色按 `turnChanges.spans` 用 `git diff` 只读查看代码，读不到不写。
