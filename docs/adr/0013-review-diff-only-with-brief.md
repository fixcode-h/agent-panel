# ADR 0013：评审只评改动的行，背景由对话整理成交接单

状态：已接受 · 2026-10-25

## 背景

[ADR 0010](./0010-review-code-only.md) 之后评审不再跑测试、改动由面板附进提示词，但用户 2026-10-25 反馈一次评审还是二十多分钟没完成，并定下要求：对话把评审要用的必需信息整理好交给评审子任务；评审只做差异代码的评审，只看修改的部分是否合理、有没有语法问题，没有改动的代码不分析，不要整个文件都去评；约束好评审的边界和能力。

## 事实核对（代码里能确认的原因）

| 原因                                                                                                                                                                              | 在哪                                   |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| 差异用 `git diff -W` 带整个函数：几千行的 React 组件就是一个函数，改一行也带上整个组件，提示词很快过 6 万字被存成文件，评审再一段段读                                             | `server/exec/git.ts` 的 `reviewDiff`   |
| 「全部改动」是任务基线到现在：顶层对话的基线停在第一轮，之后合进来的子对话、对话开始前就没提交的改动都算进去                                                                      | `reviewDiff` 没按 `task.baseline` 过滤 |
| 角色设定第 2 步要先读 `MODULE-MAP.md`、模块文档、`bugs.md`，第 4 步「差异里的上下文不够就读调用方、测试」，还要评「状态在几处一致」「旧调用方兼容」「缺用例」，这些都要去全项目找 | `shared/builtin/agents.ts` 评审设定    |
| 评审的提示词开头和动手的子任务一样：搜索排除（教它怎么全仓搜）、在独立分支里编译测试、授权、文件格式                                                                              | `shared/engine.ts` 的 `commonPart`     |
| 派评审时 `instructions` 是自由文本，需求、跑过的检查常常没交，评审只好自己还原                                                                                                    | `spawn_agents`                         |
| 没有任何时间或读取次数的约束                                                                                                                                                      | —                                      |

## 决策

1. **评审边界**：只评差异里以 + / - 开头的行。上下文行和没改的代码不评、不报；唯一例外是改动让没改的代码出错（改了签名、返回值、默认值、数据格式而调用方没跟），报在改动那一行。不评整体架构、风格、测试覆盖、模块文档是否同步。
2. **交接单**：`spawn_agents` 的任务加 `review`（`goal`、`changes`、`checks`、`focus`、`context`、`files`）。派必备角色「评审」看代码改动、又不是 `resume` 复看时，`goal` 和 `checks` 必填，缺了面板拒绝派并说缺什么。面板把它渲染成「评审交接单」放在差异前面。
3. **材料只有交接单和差异**：评审不读模块地图、模块文档、`bugs.md`，不全局搜索、不通读文件；只为确认一条具体怀疑才读代码，最多 `REVIEW_READ_BUDGET` 次、只读那几行。模块定位那句只留给「方案或结论」的评审。
4. **差异只取该评的**：每处改动带 10 行上下文（不用 `-W`），超长退回 3 行；默认只取「更改」面板里这个对话改过的文件（按 `task.baseline` 过滤），交接单写了 `files` 就只取那几个；锁文件、压缩产物、快照只列在文件清单里，不进差异正文（`REVIEW_SKIP`）。
5. **评审的提示词开头瘦身**：只留用户需求、语言、补充要求、目标和全局规则，不带工作流说明、搜索排除、编译收尾、授权和文件格式。
6. **软时限**：评审跑到 `REVIEW_SOFT_LIMIT_MIN` 分钟，面板往它的会话里传话要它按已确认的交卷；CLI 不支持执行中补充时传不进去，不强行终止（终止会把已经找到的意见一起丢掉）。数字都放在 `shared/review-limits.ts`。

候选方案：

- **到时限直接终止评审**：没选。终止拿不到任何结论，执行角色只能重派，更慢。
- **降低评审的模型档位**：没选。慢的主要是来回读文件，不是单次推理；评审质量是用户明确要保的。
- **保留 `-W`、只在超长时退回**：没选。整个函数的上下文正是引着评审去评没改代码的东西，和第 1 条冲突。

## 与现有实现的关系

- `shared/engine.ts`：`ReviewBrief`、`reviewsCode`、`briefPart`、`reviewPart`、`reviewCommonPart`，`spawn` 里校验交接单，`runHelper` 里的软时限。
- `server/orch-mcp.ts`：`spawn_agents` 的 `review` 字段（`briefOf`）。
- `server/exec/git.ts`：`reviewDiff(cwd, ref, since, files)`、`REVIEW_SKIP`；`server/exec/runner.ts` 默认用 `gitChanges` 的文件列表。
- 执行角色「收尾前评审」第 4 步改成带交接单；文档同步由执行角色判断，评审不再列「文档要更新」。

## 风险与代价

- 评审不再看没改的代码，改动之外早就存在的问题不会被它顺带发现；这本来就不是收尾评审的职责，要查就另开调研。
- 交接单写得差，评审的判断也会差；`goal`、`checks` 是最低要求，其他字段靠执行角色的设定提醒。

## 分期

一次做完。
