## 背景

## 现状：工作流现在是什么样

### 工作流本身

一个工作流（`shared/schema.ts` 的 `WorkflowFields`）由这些部分组成：

- **流程**（`flows`）：主流程加若干子流程，每个流程是节点和连线。连线可以带条件（通过 / 不通过）。
- **节点**：每个节点指定一个角色（基本角色）、模型档位和参数。
  - 节点里可以有按顺序串行的步骤（`steps`），上一步的输出是下一步的输入。
  - 节点上可以挂三个入口（`NodeHooks`）：开始前流程、验收流程（不通过就退回重做，最多 `maxRounds` 轮）、结束流程。
  - 节点还可以设「完成后等用户确认」。
- **主 Agent 调度**（`mainAgentId` + `dispatch`）：子 Agent 的节点做完后交给主 Agent 评估，主 Agent 决定通过、退回、委派另一个工作流还是停下，条件连线也由它选路，最后由它整理结果。
- **其他配置**：
  - 工作流说明（`document`）：每个节点执行时都带上。
  - 对外暴露的配置项（`expose`）：项目设置里填。
  - 每次执行的预算（`budgetUsd` / `budgetTokens`）。

内置工作流（`shared/builtin/workflows.ts`）有十个：通用项目、UE 项目、功能开发（OpenSpec）、数据与配置迁移、Bug 修复、架构设计、代码评审、依赖升级与安全、发布与回滚、Blender 建模与动画。

改代码的工作流只做到「实现 + 快速检查 + 文档同步」（`CHILD_RULES`）。评审、完整测试和编译、合回由执行角色在工作流跑完后做。

（ComfyUI 的生图工作流是另一套东西，不在本 ADR 范围内。）

### 现在有五个入口能启动工作流

| 入口                                                                   | 谁决定                                                                            | 跑在哪                                 | 结果去哪                     |

### 现在的问题

1. **决定权在子对话。** 父对话派单时只能在 message 里写「用某某工作流」，子对话用不用由它的模型决定。父对话的计划里只看到「子对话：xxx」这一步，看不到工作流节点。
2. **运行套在子对话的一轮里同步跑。**
   - 工作流跑多久，子对话的这一轮就占多久。
   - 停下再继续时运行不会接着跑（`resumeNote` 让模型重新 `start_plan`），和 0042「继续就是原样回来」矛盾。
3. **层数太多，职责重叠。** 一个需求要经过「父对话 → 子对话（执行角色）→ 工作流 → 节点 → 子任务」五层，执行角色和工作流里的实现节点都在做实现。
4. **判定口径分散在四处。** 执行角色的 `mode`、主理的分派表、`CHILD_RULES`、`agent-catalog.md` 各写一份。「Bug 什么时候走工作流」几处说法不一样。
5. **看运行的界面有三套，流程图又看不到。**
   - 三套是：中间页签、子对话里就地盖住的 `RunView`、对话里弹出的 `RunDialog`。
   - 对话里的运行看不到流程图：`TaskFlow` 只给老的 `mode: 'workflow'` 任务用。
6. **两种数据形态并存。** `mode: 'workflow'` 的独立任务（主 Agent 常驻）和对话里的运行，状态、暂停继续、诊断各走各的路。

## 决策

**工作流是父对话手里的第三种派单方式，只有父对话能启动。每次启动，在父对话下开一个「工作流子对话」，由面板按流程图推着跑完；收尾、状态、暂停 / 继续、右栏查看都和普通子对话走同一套。**

### 1. 工作流的定位：父对话的三种派单方式

|          | 子任务（`spawn_agents`） | 子对话（`create_conversation`） | 工作流（`start_workflow`，新）                  |
| -------- | ------------------------ | ------------------------------- | ----------------------------------------------- |
| 适合     | 并行收集、核实、出计划   | 一件要边做边定的事              | 一件步骤和门禁事先定好的事                      |
| 谁定步骤 | 派它的一方写清楚         | 执行角色自己定                  | 流程图定好，面板推着走                          |
| 跑在哪   | 派它的对话里，不开分支   | 子对话（独立分支或共用目录）    | 工作流子对话（同子对话）                        |
| 改代码   | 不改                     | 改                              | 看工作流的 `kind`：`change` 改，`readonly` 不改 |
| 结果     | 自动交回派它的一方       | 收尾后合回、回报父对话          | 跑完后收尾（同子对话），回报父对话              |

**工作流承担的：** 顺序、门禁和留痕，也就是「先确认方案再动手」「迁移和回滚成对写」「每批升级都有验证」「出 ADR」这类不能跳步的剧本。

**工作流不承担的：**

- 边查边定的事：Bug 定位、排查、调研。下一步查哪里要看上一步查到了什么，拆成固定节点会丢掉中间的线索。
- 问答、分析、一两个文件的小改动。
- 分派：工作流里不开子对话、不起工作流。
- 对外操作：推送、合并主干、P4 submit、发布。

### 2. 只有父对话能启动

- 项目里的顶层对话（父对话）的角色开了 `canPlan`，才有 `start_workflow`。
  - 内置主理改成默认打开。
  - `canPlan` 的说明改成「可以启动工作流（只在父对话里生效）」。
- 子对话、子任务、工作流节点一律没有启动工作流的工具，提示词里也不再列「可用工作流」。
  - `start_plan` 去掉。
  - 执行角色去掉 `mode` 参数，永远在对话里直接做。
- 用户手动启动（工作流页「在项目里运行」、父对话输入框里选工作流）也走同一个入口，挂在某个父对话下。见第 7 条。

### 3. 跑在「工作流子对话」里

`start_workflow` 在父对话下新建一个子对话，任务上记 `flow`（用哪个工作流、这次的要求、种类）。

**工作流子对话复用子对话已有的全部机制：**

- 独立分支 / 共用目录认领（`files`）。
- 8 个对话状态（`convState`）。
- 父计划里的等待（`kind: 'child'`）。
- 右栏查看。
- 暂停 / 继续（0042）。
- 卡住检测（0036）。
- 生命周期诊断（0040）。

**面板怎么跑它：**

- **直接按流程图跑。** 不先让执行角色读一遍再决定用不用。节点就是这个子对话计划里的步骤：计划第一步是「工作流『名字』」，节点是它的子步骤，和现在 `bindRun` 的做法一样。
- **流程图跑完后的收尾：**
  - `readonly`（代码评审这类一个文件都不写的剧本）：最终结果交回父对话，子对话完成。
  - `change`（改代码的）：面板把运行结果交给这个子对话的执行角色，由它收尾，顺序是评审（只看 diff，带交接单）→ 完整测试 / 编译 → `submit_merge`。这和普通子对话是同一条路。工作流里照旧不放评审、完整验收和提交节点，`CHILD_RULES` 的分工不变，只改「由谁启动」这一句。
- **一个工作流子对话只属于一个工作流。** 同一件事要再跑一遍（例如方案被否、要从头来），父对话用 `start_workflow` 带 `again: <工作流子对话 id>`。在同一个分支上起这个工作流的第 2 次运行，前一次的改动保留。

### 4. 父对话什么时候启动工作流

判定规则只写在一处：新文件 shared/workflow-pick.ts，生成「可用工作流」目录和判定说明。主理的角色设定、`agent-catalog.md` 都引用它，不再各写一份。判定顺序：

1. **用户点名了**（消息里写了工作流名字，或者在输入框里选了）：直接用，不再判断。
2. **需求命中某个工作流的「适用场景」**：用它。同时命中几个时选最具体的，例如「数据与配置迁移」优先于「通用项目」。
3. **下面这些一律不起工作流：** 问答和分析、排查和 Bug 定位、一两个文件的小改动、要边做边和用户商量的、一次性调研。它们按主理现有的分诊表处理：就地做、派子任务或交给子对话。
4. **拿不准就交给子对话（执行角色）**，不起工作流。起错一个工作流比少起一个更贵：节点全跑一遍，还多一层收尾。

为此工作流加三个字段，目录按它们列给父对话：

- `when`：适用场景，一两句话；内置工作流必填。
- `notFor`：明确不适用的情况。
- `kind`：`change` 或 `readonly`。决定开不开独立分支、跑完要不要合回。

启动时 `route`（分诊卡）写清「为什么用这个工作流」，用户在父对话里能看到判断依据。

内置工作流的适用场景：

| 工作流               | `kind`   | 什么时候用（`when`）                        | 不用（`notFor`）                     |
| -------------------- | -------- | ------------------------------------------- | ------------------------------------ |
| 通用项目             | change   | 正式的功能开发：跨模块、要先确认方案再动手  | 小改动、Bug、问答                    |
| UE 项目              | change   | UE 项目里同上                               | 同上                                 |
| 功能开发（OpenSpec） | change   | 用户要求按规范走，或项目用 OpenSpec 管需求  | 没有规范要求的日常功能               |
| 数据与配置迁移       | change   | 改 schema、数据格式、配置结构，要兼容旧数据 | 只加一个可选字段                     |
| Bug 修复             | change   | **只在用户点名时用**                        | 其余 Bug：交子对话按「逐层定位」做   |
| 架构设计             | change   | 要出候选方案、做取舍、写 ADR                | 已经定了方案的实现                   |
| 代码评审             | readonly | 用户要求评审一段改动                        | 子对话收尾前的评审（执行角色自己派） |
| 依赖升级与安全       | change   | 升级依赖、查漏洞和许可                      | 只升一个包的补丁版本                 |
| 发布与回滚           | change   | 准备发版：定范围、验产物、写说明和回滚方案  | 打 tag、推送、发布（父对话做）       |
| Blender 建模与动画   | change   | 建模、动画、导出 UE                         | —                                    |

`readonly` 只给一个文件都不写的剧本：架构设计要写 ADR、发布与回滚要写发布说明，都会落盘，所以记作 `change`，照样开分支、合回。

### 5. 暂停、继续、终止、失败（接 0042）

| 情况                                   | 工作流子对话                                                    | 父计划里的等待                                   | 继续时                                                                                                  |
| -------------------------------------- | --------------------------------------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| 父对话停、面板重启、卡住重开、用量上限 | 运行暂停。在跑的节点和子任务一样记暂停（`pauseUnit`），会话保留 | 保持等待中                                       | 递归拉起时，运行从没做完的节点接着跑：同一次运行、原会话 `--resume`，不重新起                           |
| 用户单独停                             | 暂停                                                            | 保持等待中                                       | 不自动拉起；父对话的续接说明里点名，问用户                                                              |
| 节点失败，或验收超过轮数               | 运行停在这个节点（「需要你处理」），向父对话发一封带提问的信    | 保持等待中，不算失败：事情没结束，只是要人拿主意 | 父对话 `send_to_conversation` 写意见：这个节点带着意见重跑，通过后接着往下走。或者 `stop_workflow` 终止 |
| 父对话 `stop_workflow`、归档、删除     | 终止（`cancelUnit`）：没跑的节点跳过，这次运行改了哪些文件交回  | 收成失败                                         | 不拉起；父对话决定另起还是放弃                                                                          |
| 收尾阶段（执行角色在做）               | 和普通子对话完全一样                                            | 同 0042                                          | 同 0042                                                                                                 |

`resumeNote` 里「用 start_plan 重新启动那一步」这句去掉：运行由面板接着跑，不靠模型重起。

### 6. 父对话和工作流子对话之间的消息

- **`send_to_conversation` 发给工作流子对话：**
  - 运行中：交给当前在跑的节点。这和用户在运行面板里补充要求是同一条路，按 CLI 的能力插话或留给下一个节点。
  - 运行停在某个节点上：意见交给那个节点重跑。
  - 运行结束、在收尾：交给执行角色。
- **工作流子对话不能开子对话、不能起工作流。** 节点照旧能派子任务（`spawn_agents`）。
- **进度上报按 0034 分清「信」和「状态」：**
  - 节点开始、完成只更新状态。父对话的子对话面板、`list_conversations` 里看得到「3/5 实现」，不发信。
  - 运行完成、停在节点上要人拿主意、收尾完成，才发信。

### 7. 界面

- **子对话栏和侧栏：** 工作流子对话和普通子对话排在一起，标题旁标「工作流 · 名字」，进度写「3/5 实现」。图标和状态还是 `convState` → `childIcon` 那一处判定，不另加一套。
- **右栏查看：** 点开就在右栏打开，和子对话是同一个视口、同一套页签切换。头部有「输出 / 流程图」切换：
  - 输出：按节点铺开每个节点的消息、思考和工具行（现在的 `RunFlow`），下面接着收尾那段对话。
  - 流程图：流程图画布（`TaskFlow` 改成按运行画），节点上标状态、轮次和结论，点节点在下面看它的输出。
  - 切到哪一页记在本机。父对话里点工作流卡片时默认打开流程图。
- **父对话里的入口：** 「工作流」卡片（`RunCard`）和计划里的工作流步骤，点了都在右栏打开那个工作流子对话。
- **收成一处：** 去掉中间的运行页签和 `RunDialog` 窗口，看运行一律在右栏。老数据里子对话自己跑过的运行，照旧在那个子对话里就地打开（`RunView` 只读保留）。
- **工作流页：** 编辑器不变。「在项目里运行」改成：
  1. 选项目，再选父对话（默认新建一个）。
  2. 面板在这个父对话下直接起工作流子对话，不经过父对话的模型。
  3. 跳到父对话，并在右栏打开它。

### 8. 老数据和兼容

- `mode: 'workflow'` 的老任务照旧能看、能继续跑完，不再新建。
- `NextWorkflows` 推荐去掉：它只认老的「默认」工作流，新建入口已经收到第 7 条。
- 子对话里 `start_plan` 跑到一半的运行：升级后继续时按第 5 条接着跑完这一次。这是最后一次兼容，之后子对话不再有 `start_plan`。
- 执行角色的 `mode`：旧取值「总是按工作流」读成「自动」，参数本身从角色上去掉。
- 用户自定义角色开了 `canPlan`、又被用在子对话里：子对话不给工具，提示词也不写。
- 内置工作流：`CHILD_RULES` 第一句改成「这个工作流由父对话启动，在工作流子对话里跑」，并补上 `when` / `notFor` / `kind`。改前那一版按惯例登记进 `LEGACY_WORKFLOWS`。

### 放弃的方案

- **父对话自己同步跑工作流（现在顶层 `start_plan` 那样）：** 放弃。父对话会被一次运行占住，不能回用户、不能管别的子对话；改代码的节点会直接改父对话的目录，和子对话的独立分支冲突。
- **节点直接挂进父对话的计划，每个节点各开一个子对话：** 放弃。节点之间的上下文（上一步的输出是下一步的输入）、验收轮次、同一个分支上的连续改动都会断开。
- **保留子对话里的 `start_plan`，只让父对话「点名」：** 放弃。这就是现在的做法，决定权还在子对话的模型手里。
- **工作流自己带评审、完整测试、合回节点，不交给执行角色收尾：** 放弃。合回、评审门禁、父对话代跑的测试步骤要再做一套，和子对话那套分叉。

## 与现有实现的关系

- `startPlan` 的主体（快照、`ensureTaskRun`、`planTask`、`bindRun`、`runFlow`、终止开关）原样搬给工作流子对话的第一轮用。区别是它跑在子对话自己的任务上，不再嵌在某个对话的 CLI 轮次后面。
- `spawnChild` 加一个分支：带 `flow` 时，第一轮由引擎按流程图跑，不调用执行角色；跑完再按 `kind` 决定交执行角色收尾，还是直接交回。
- `childHolds` 里的 `workflow` 一项保留，口径不变：运行没跑完，子对话就不算完成。
- 0042 的 `pauseUnit` / `cancelUnit`、`rearmKidWait`、递归 `resumeKids` 都直接用。补的只是「运行暂停后继续时接着跑」这一段：老 `mode: 'workflow'` 任务里的 `runWorkflow` 已经能从没做完的节点接着跑，复用它。

## 运行时

1. 父对话调用 `start_workflow`。面板做三件事：建工作流子对话（独立分支或认领文件）；父计划那一步挂成等待中；子对话面板里出现一行「工作流 · 名字」。
2. 子对话的第一轮：引擎按流程图跑节点。节点状态实时推给父对话的子对话面板，父对话不被叫醒。
3. 跑完：
   - `readonly`：结果作为信交回父对话，子对话完成，父计划那一步结算。
   - `change`：结果交给执行角色收尾。它 `submit_merge` 后，父对话照常 `finish_child`，合回后结算。
4. 停下 / 继续 / 失败按第 5 条走。

## 分期

1. **第 1 期：引擎和工具。**
   - 内容：`start_workflow` / `stop_workflow`；工作流子对话；收尾交执行角色；暂停后继续时接着跑；子对话去掉 `start_plan`；workflow-pick.ts；工作流的三个新字段；主理、执行、`CHILD_RULES` 改写。
   - 出口：单测覆盖判定目录、工具权限、暂停 / 继续 / 失败的结算。端到端跑通两条：「父对话起工作流 → 节点跑完 → 执行角色收尾合回 → 父对话被叫醒」；「停父对话 → 继续 → 运行从没做完的节点接着跑」。

## 风险与代价

- **每次起工作流多一个子对话。** 多一条任务记录；独立分支模式下还多一个 worktree。换来的是状态、收尾、暂停继续只有一套。
- **判定靠父对话的模型执行。** 兜底有三层：目录里写清 `when` / `notFor`；分诊卡记下理由，用户看得到；用户能在输入框直接选工作流。
- **`change` 工作流跑完多一轮执行角色的 CLI 调用。** 这一轮现在就有（子对话 `start_plan` 后照样要收尾），只是换了位置。
- **两套逻辑并存一段时间。** 老 `mode: 'workflow'` 任务和新的工作流子对话会并存，直到老数据自然淘汰。

和正文不一样的几处（实现时按更省的一条路走）：

- **只读工作流也经执行角色交付**：`readonly` 跑完同样交给执行角色，只是交代「不用评审、不用测试，整理成总结后按收尾规则交付」。不另做一条「直接交回父对话」的路，子对话的收尾、状态和父计划的结算只有一套。
- **节点失败按子对话失败交回**：父计划那一步按子对话失败结算（0042 的口径不变）；父对话 `send_to_conversation` 交回意见时，失败的节点带着意见重跑、接着往下走，等待照常重新挂上。
- **「在项目里运行」经父对话的模型**：新建对话时必须带第一条消息，它本身就会开一轮；所以让这一轮按「用户点名了工作流」去启动，而不是面板绕过父对话再开一次。项目默认角色启动不了工作流时，弹窗里先说清会直接在对话里做。
- **中间的运行页签和 `RunDialog` 留给老数据**：新的运行都在工作流子对话里、从右栏看；升级前父对话自己跑过的运行，照旧在中间页签和弹窗里看（也有「输出 / 流程图」切换）。
