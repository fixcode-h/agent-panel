# ADR 0006：后台命令由对话监管到真正结束

状态：已接受 · 2026-10-24

## 背景

用户 2026-10-24 反馈了三件连在一起的事：

- 子对话用 `run_background` 装 Playwright 浏览器，对话里那一行显示「运行命令 … 完成 0.09s」，像是跑完了；对话说「本轮先停在这里」就结束了。用户要的是：放到后台的命令在界面上一直转圈，显示真实用时和结果，对话等结果回来，不能「交出去就算完成」。
- 下载明明完成了，对话却一直没收到结果，模型自己在前台 `sleep 15` 轮询。
- 所有后台命令都要这样；跑得久的要主动让对话检查，避免命令卡死没人管。

## 事实核对

| 位置（改动前）                                | 现状                                                                                                                                      |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `server/exec/parsers.ts` `genericTool`        | 只认裸名字的面板工具；`panel_run_background` 这类带前缀的名字被 `/run/` 匹配成 CLI 自己的命令（kind `run`），界面认不出是后台命令，不转圈 |
| `web/src/components/tasks/ToolRow.tsx`        | 认出来的后台命令会转圈，但时间停在调用返回的那一刻；跑完后这一行还是「已放到后台」，看不到结果                                            |
| `server/background.ts`                        | 只有完成时推结果；没有「多久没输出」「跑了多久」的监视；超时固定两小时；对话停不掉单独一条                                                |
| `server/tasks.ts` 后台结果的推送              | `sendToChild` 的返回值没看，推送失败只 `log.warn`，结果可能悄悄丢                                                                         |
| `shared/task.ts` `taskBusy`、`task-unread.ts` | 不看后台命令：这一轮说完、命令还在跑时，侧栏显示成做完了、还标「完成未读」                                                                |
| `shared/clis.ts` Claude Code                  | 自带的 `Bash run_in_background`、超时自动转后台、`Monitor` 都开着，那些命令面板看不见                                                     |

## 决策

### 一、后台命令仍然马上返回，对话停在「等结果」，不阻塞这一轮

`run_background` 不改成阻塞调用：阻塞期间用户的消息要等命令跑完才处理（`engine.ts` 的提示一直这么说），Codex 这类 CLI 的 MCP 调用还有超时。
「对话等结果」用 ADR 0005 已有的 `waiting` 状态表达：这一轮说完了，但对话在等会推回来的结果。界面上做到看得见：

- 发起命令的那一行一直转圈、按命令真正开始跑的时间走表；排队时写「排队中」。
- 侧栏把还有后台命令的对话算成在跑（`taskBusy` 看 `jobs`），不标「完成未读」。
- 命令置终态（成功、失败、被停止、超时）时，面板把那一行换成真实用时、结果和输出结尾（`settleJobTool`）；`request_build` 的几条编译结果依次接在那一行后面。

没选：把调用改成阻塞到命令结束。用户的消息会被卡住，和「不要在前台干等」的规则冲突。

### 二、面板盯着每条命令直到真正结束

`createBackground` 对每条在跑的命令：

- 记 `lastOutputAt`（stdout、stderr 都算，进度多写在 stderr）。10 分钟没有任何输出 → 提醒对话一次「可能卡住了」，附最后的输出，有了新输出再重新计。
- 跑满 15 分钟提醒对话看一眼进度，之后 30、60、120 分钟……间隔翻倍：一直在刷输出的死循环、重试不停的下载靠这个认出来，正常的长编译不会被反复打扰。
- 限时 `timeout_minutes`（默认 120，最多 480），到点停掉并按失败推回。
- 新工具 `stop_background`：对话确认卡住时停掉一条；`check_background` 带上已跑多久、多久没输出。

提醒和结果走同一个出口 `pushJobNote`：子对话按 `sendToChild`，顶层对话正在跑就实时送达、空闲就开新一轮。推送失败等 3 秒重试一次，再失败就记进对话、`holdForNextTurn`，并写日志，不悄悄丢。

没选：卡住了面板自动停掉重跑。是不是卡住要看命令（解压大文件就是很久没输出），由对话判断。

### 三、所有长命令都走面板

- 带服务名前缀的面板工具名先认出来再按名字猜类型（`panelToolName`），旧数据里被记成「运行命令」的后台命令按面板的回复认回来。
- Claude Code 设 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` 并禁用 `Monitor`：CLI 自己的后台命令不受面板监管，进程被回收结果就没了。
- 面板退出前停掉还在跑的后台命令，把那一行收口成「面板退出时还没跑完，已停止」，重启后不会一直挂着「已放到后台」。

## 运行时

- `BgJob` 新增 `createdAt`、`lastOutputAt`、`stalled`、`timeoutMs`、`nextCheckMs`；记录仍只在内存里。
- `createBackground` 的 deps：`onSettle`（置终态）、`onNotice`（提醒）、`stallMs` / `checkFirstMs` / `now`（测试用）。

## 风险与代价

- 每次提醒会唤醒对话、多花一轮 token：间隔翻倍，同一段沉默只提醒一次。
- 面板重启后后台命令仍然丢失（记录不落盘），只做到收口说明，不续跑。
- 改工具行是改历史消息：只改输出、用时、失败标记，靠 `messageStamp` 里的输出指纹推到界面。
