# ADR 0043：工作报告写成人写的日报——条目能挂单子链接，报告能再次生成、旧的原样留着

状态：已接受 · 2026-11-03

- 影响范围：`shared/summary.ts`（分项、拼报告、提示词）、`shared/builtin/agents.ts`（「每日工作总结」角色的写法）、`shared/lesson-draft.ts`、`server/summary.ts`、`web/src/pages/SummaryPage.tsx`、`web/src/components/summary/`、`web/src/lib/summary-page.ts`、`web/src/lib/demo-summary.ts`
- 取代：无。沿用工作总结「先提炼分项、逐项采纳、按固定格式拼报告」的两步流程

## 背景

用户 2026-11-03 对工作总结报告提了几点：

1. 待确认（提炼出来、还没生成报告）时，每条需求或 Bug 能附一个 Bug 单 / 需求单的链接，链接直接写进报告。
2. 生成过的报告能再次生成，之前生成的那份原样留着。
3. 报告只写必要的信息，就是正常的每日工作报告；不写版本管理的操作（提交、推送、合并、cherry-pick 这些）。
4. 人味重一点、去掉 AI 味，别让人一看就是 AI 写的。需求简单说下怎么做的；Bug 说是什么问题、怎么解决的，没解决就不写解决部分。

## 事实核对

| 位置                                                 | 现状                                                                                                                               |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `shared/summary.ts` 的 `SummaryEntry`                | 分项字段：`kind`、`project`、`title`、`content`（需求）、`cause` / `fix`（Bug），没有链接                                          |
| `shared/summary.ts` 的 `renderReport`                | 固定模板：`## 一、需求` / `## 二、Bug` 两节，条目是 `1. **标题**`，下面缩进 `内容：` / `原因：` / `修复：`；某节没有条目写「暂无」 |
| `server/summary.ts` 的 `POST /summary`               | 只收采纳的分项，按 `renderReport` 拼正文存成新报告；`PUT /summary/:id` 只改正文                                                    |
| `server/summary.ts` 的提炼任务（`jobs`）             | 内存里留一小时；页面按 job id 轮询，取分项                                                                                         |
| `web/src/lib/summary-page.ts`                        | 页面状态（来源、日期、job id、已采纳的分项 id）存在本机                                                                            |
| `shared/builtin/agents.ts` 的 `worklog`              | 写法规则：标题、内容、原因、修复各有字数和要求；要求「全文不用第一人称」「用『支持…』『修复…』这种陈述」                           |
| `shared/lesson-draft.ts` 的 `lessonDraftsFromReport` | 从报告正文按节名和 `修复：` / `原因：` 前缀解析 Bug 条目，生成教训草稿                                                             |

## 决策

**报告的正文由面板按一份朴素的模板拼，内容的「人味」靠提炼时的写法规则；链接和再次生成都落在「分项」这一层。**

1. **分项加 `link`**：待确认列表里每条可以填单子链接（网址或单号，可选）。采纳后随分项交给生成接口，写进报告，也存进报告的 `items`。
2. **再次生成 = 从报告开一次新的待确认**：报告页「再次生成」把这份报告的分项（连同链接）重新放回待确认列表，全部默认采纳。用户可以改链接、取消采纳、或者重新提炼这段时间，确认后生成一份**新的**报告，记 `basedOn` 指回原报告。原报告不改、不删，树里照旧在原来的位置。
3. **模板去掉 AI 腔**：
   - 标题写成「11月3日工作日报」，按周写「第45周工作周报（11月3日-11月9日）」；
   - 两节叫「需求」「问题」，没有条目的节整节不写（不写「暂无」）；
   - 每条一段话：`1. 标题。说明`，不加粗、不写「内容：/原因：/修复：」这类标签；Bug 是「问题 + 怎么解决的」连成一段，没解决只写问题；
   - 有单子就在下一行写 `单子：<链接>`。
4. **写法规则改成人写日报的口吻**（`worklog` 角色）：短句、具体、像同事之间写的；列出一批 AI 常用词（「实现了」「优化了」「提升了…体验」「确保」「从而」「进一步」「此外」「有效」「显著」「赋能」、破折号、冒号列点）不许用；需求一两句说怎么做的；Bug 一两句说问题、一两句说怎么解决，没解决 `fix` 留空；版本管理操作不算条目、也不写进任何条目。
5. **拼报告时再做一次轻量清理**（`plainText`）：去掉加粗和反引号、破折号换成逗号、压掉多余空白。只做确定无害的替换，不改写句子。

候选方案：

- **报告正文整篇交给 CLI 写**：放弃。每次结果不一样、链接可能被改写或漏掉，再次生成也没法保证条目一致；分项已经是 CLI 写的，模板只负责摆放更稳。
- **再次生成直接覆盖原报告**：放弃。用户明确要求「之前生成的就固定在那」。
- **只在报告里编辑链接**：放弃。用户要求在待确认时附加；报告正文本来就能手动编辑，不再单独做一套链接编辑。

## 操作清单 / 契约

| 项                       | 内容                                                                                      |
| ------------------------ | ----------------------------------------------------------------------------------------- |
| `SummaryEntry.link`      | 字符串，最长 300 字，默认空；网址或单号                                                   |
| `SummaryReport.basedOn`  | 字符串，默认空；再次生成时记原报告 id                                                     |
| `POST /summary/:id/redo` | 用这份报告的分项开一次提炼任务（状态直接是完成），返回 job；页面按普通 job 显示待确认列表 |
| `POST /summary`          | 照旧只收采纳的分项（现在带 `link`）；可带 `basedOn`                                       |
| 页面状态 `links`         | 待确认时填的链接（分项 id → 链接），存在本机，确认生成时合进分项                          |

报告样例（按天）：

```
# 11月3日工作日报

## 需求

1. 工作总结能按周生成。日期那里加了按天和按周的切换，按周时取周一到周日，报告标题跟着改成周报。
   单子：https://example.com/browse/REQ-12

## 问题

1. 停下父对话再继续，子对话做完了父对话还一直等。子对话被一起停下时，计划里等它的那一步被当成了失败，后面结果交回来对不上。改成停下只算暂停，继续时把这一步恢复成等待中。
   单子：BUG-345
2. 状态诊断日志偶尔不贴到最新。日志刷新时滚动位置被重置了，还在查是哪次渲染引起的。
```

## 与现有实现的关系

- 提炼、采纳、确认的两步流程不变；`renderReport` 换模板，`parseExtract` 多收一个空的 `link`（CLI 不写链接）。
- 老报告不迁移：正文是生成时拼好的，原样显示；对老报告点「再次生成」会按新模板出一份新的。
- 教训草稿优先按报告的 `items` 取 Bug 条目（问题 + 解决），没有 `items` 的老报告照旧解析正文；正文解析也认新的「## 问题」节名。

## 运行时

- 待确认：页面把链接存在本机状态里，确认时随分项提交；刷新页面不丢。
- 再次生成：`POST /summary/:id/redo` 在服务端的提炼任务表里登记一个已完成的任务（带原报告的范围、来源、项目、分项），页面切到提炼面板、按 job id 读出分项、全部预先采纳、链接预先填好。
- 生成：服务端用新模板拼正文，存成新报告；`basedOn` 指回原报告，报告头写「由这份报告再次生成」加原报告的生成时间。

## 分期

一次做完。

## 风险与代价

- 写法规则只能约束，CLI 偶尔还会写出 AI 腔：报告正文能直接编辑，`plainText` 兜住最明显的几种符号。
- 「问题」节名替换了「Bug」：教训草稿的正文解析同时认新旧节名，老报告照旧能提炼。

## 开放问题

无。
