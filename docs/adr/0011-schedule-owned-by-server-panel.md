# ADR 0011：定时计划由面板服务端自己驱动，错过的计划不补跑

状态：已接受 · 2026-10-26

## 背景

用户 2026-10-26 要求加「计划面板」：左侧导航新增「计划」，可以新建计划并指定一个时间，到点由面板自己启动一个对话去执行，例如每天 19:00 跑一次「总结今日工作」。

用户没有细说实现方式，只要求「到点自动启动一个对话，行为和手动新建任务一致」。需要先定两件以后不好改的事：定时由谁驱动（面板进程 / 系统计划任务），以及面板没开着时错过的计划怎么办（补跑 / 不补跑）。

## 事实核对（改动前）

| 位置                                    | 现状                                                                                         |
| --------------------------------------- | -------------------------------------------------------------------------------------------- |
| `server/tasks.ts` 的 `POST /tasks`      | 建对话的全部逻辑写在路由里，校验、建独立分支、拷附件、启动执行混在一起，只有 HTTP 这一个入口 |
| `server/store.ts` 的 `DATA_FILES`       | 用户数据是数据目录下的 JSON，配置文件走 `config/` 前缀                                       |
| `server/data.ts` 的 `PATHS`             | 「配置」类覆盖 `config/` 整个目录，导出、导入、占用统计都按「类」走（这一类不可清理）        |
| `server/index.ts` 的启动与 `shutdown()` | 已有内存采样这类定时器：启动时开始、退出时停掉，`unref()` 不挡进程退出                       |
| 面板形态                                | 本机网页控制台，服务端只监听 `127.0.0.1`，用户不一定会一直开着                               |

## 决策

一、**定时由面板服务端进程自己轮询，不借助系统计划任务。**

- 服务进程在跑时按固定间隔（`SCHEDULE_TICK_MS`，30 秒）检查一次，启动后先检查一次再进间隔；定时器 `unref()`，退出时在 `shutdown()` 里停掉。
- 到点判定、执行后怎么往后推，全在 `shared/schedule.ts` 里做成纯函数，前端显示下次执行时间用同一套，界面和服务端不会各算一套。
- 启动对话复用 `server/tasks.ts` 里抽出来的 `createTask` + `startChat`，和页面上 `POST /tasks` 完全同一条链路，不另造执行流程。
- 没选**系统计划任务 / cron / launchd**：三个平台三套写法，还要处理打包后的路径和「任务计划看不到 Node 环境」这类问题；用户要的是「面板自己到点干一件事」，装一个每 30 秒醒一次、只用 `curl` 调本机接口的外部任务，代价比收益大。以后真要在面板没开时也能跑，再单开一条 ADR。

二、**面板没开着时错过的计划不补跑。**

- 超过宽限时间（`SCHEDULE_MISS_MS`，60 秒）才被发现的计划算错过：只记下错过的那一次时间，每天的把时间推到下一次，单次的标成已跳过；列表里显示「错过 …（面板没开着，不补跑）」。
- 启动失败（项目被删、角色不存在）同样不自动重试：原因记进计划显示给用户，时间照样往后推，否则每轮询一次就重试一次、一直刷同一条错误。
- 没选**补跑**：用户打开面板时突然冒出一串对话，比漏掉一次更吓人；「每天一次」的总结补跑几遍也没有意义。要给用户补跑的能力，用列表里的「立即执行」，由用户自己点。

## 操作清单 / 契约

| 项         | 内容                                                                                                                                                                 |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 数据文件   | 数据目录的 `config/schedules.json`，登记在 `server/store.ts` 的 `DATA_FILES`，随「数据」页的「配置」类一起统计、导出、导入（这一类不可清理）                         |
| schema     | `shared/schedule.ts` 的 `ScheduleInput` / `Schedule`：名称、提示词、项目、角色、`once` / `daily`、下次执行时间、启用、状态、上次执行时间和对话、错过的一次、上次错误 |
| 接口       | `GET/POST /schedules`、`PUT/DELETE /schedules/:id`、`POST /schedules/:id/run`（立即执行，不改排期）                                                                  |
| 启动对话   | `startChat(NewTaskInput)`：项目为空是聊天模式，角色为空跟随默认 CLI，失败抛原因给计划记下来                                                                          |
| 时间口径   | 一律存 ISO 字符串；界面按本机时区显示和编辑（`toLocalInput` / `fromLocalInput`）                                                                                     |
| 进程启动时 | 启动后先检查一次再进轮询间隔，上一次进程期间到点的计划在这一次被标成错过                                                                                             |

## 风险与代价

- **面板不在跑就没有定时**：这是选型认下的代价，界面文案写清楚「面板进程在跑时才会触发」。
- **机器休眠、进程被挂起超过 60 秒会漏跑**：记进 `missedAt` 给用户看，不静默吞掉。
- **轮询重叠会把同一条计划启动两次**：用「上一轮没做完就不重入」的标记挡住，启动一条计划期间不再开新的检查。
- **用户改时间会让已执行 / 已跳过的计划回到待执行**：改时间就是重新排期，之前的错过和错误记录一起清掉。

## 开放问题

- 是否需要「每周 / 每月」或工作日规则：现在只有 `once` 和 `daily`，倾向等有真实需求再加枚举值，不提前做 cron 表达式。
- 错过的那一次要不要提供「补跑一次」按钮：倾向加在列表里由用户主动点，定下来之前先只有「立即执行」。
