# ADR 0031：用例总数不设上限，只拦本次净新增，出包时报数，定期批量清理

状态：已接受 · 2026-10-29

## 背景

[ADR 0024](./0024-test-output-retry-budget.md) 第 4 条给各层用例定了硬上限（纯函数层 1510、集成层 740），只降不升：超了就要在同一提交里合并或删掉等量旧用例，或者在提交说明写「测试预算:」段。

上线两天，集成层就停在 740～742。上限已经顶满，之后的提交都要补一段说明，哪怕这次一条用例都没加：

- 交付契约那次（ADR 0030）加了 2 条，写了说明，之后总数一直超 2 条；
- 下一个提交把 2 条旧用例合成 1 条，净减 1 条，因为改了用例名被算成「新增」，又被拦下。

用户 2026-10-29 认为太容易满，同意改成：本地和推 dev 时只拦本次新增；总数不设上限，出包时报数；重复和过时的用例定期一批清掉，代替每次一换一。

## 事实核对

| 位置                                           | 改动前                                                                                                                                                       |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `scripts/lib/test-budget.mjs`                  | `BUDGET_BASELINE` / `TEST_BUDGET` 各层上限、`raisedBudgets`（只降不升）、`overBudgets`、`UNIT_CASE_LIMIT`、`mergedChainMessages`（沿合并链找子提交的预算段） |
| `scripts/test-budget.mjs`                      | `--check` 静态计数超上限就要预算段；`--tap` 用实测总数按两层合计上限再判一次；「本次新增」只数新增的 `test(` 行，不扣删掉的                                  |
| `.github/workflows/ci.yml`                     | `test` job：`npm run lint`（含 `--check`）和单测后的 `--tap` 复核                                                                                            |
| `.github/workflows/release.yml`                | 出包前不报用例数                                                                                                                                             |
| 「测试验收」角色（`shared/builtin/agents.ts`） | `task` 有跑验收 / 设计用例 / 补测试三档，没有清理用例的做法                                                                                                  |

## 决策

**各层用例总数不设上限。lint 只拦本次净新增（新增减去删掉，大于 0 时要预算段写理由）；CI 的 tap 复核只报数；出包时把各层用例数和上一个正式版对比写进运行摘要；「测试验收」加「清理用例」，按 ADR 0024 引用的淘汰标准一次列一批候选，用户确认后再删。**

1. `--check`：本次改动指工作区（有测试目录的未提交改动时，提交说明用 `--message` 传），否则指 HEAD 这一个提交。从 `git diff -U0` 取新增和删掉的用例行（单测的 `test(` / `it(`，e2e 分片的 `step(`），净新增 = 新增 − 删掉。改名（删一加一）、合并（删二加一）、删除都放行。合并提交不判：新增用例在被合进来的提交上已经判过，合并提交的 diff 会把对方分支的改动全算进来。
2. `--tap`：报实测总数和静态计数的差，不拦。差得多说明有循环生成的用例，静态口径要跟着改。
3. `--report [--since <标签|auto>]`：报各层计数；给了 `--since` 就按 git 里那个版本的文件逐项对比（`auto` 取 HEAD 祖先里最新的正式版标签，和 `scripts/release-notes.mjs` 同一口径）。出包流程在计算版本号前跑一次，结果写进 `$GITHUB_STEP_SUMMARY`。
4. 「测试验收」`task=清理用例`：第一步只读，列候选表（文件:行、用例名、类别、证据、处置），每条必须属于三类之一：被测能力已删、被更强的用例完全覆盖、长期不稳定且修复代价高于价值；用户报过的 Bug 回归、数据丢失与不可逆路径、凭据与安全边界的用例不列。然后用提问工具问用户，停下。第二步只删、合并用户确认的几条，不改产品代码。主理在用户要清理用例时派它，确认结果用 `resume` 交回同一个子任务。

没选的方案：

- **把上限抬高一档**：几天后又会顶满，问题只是推后；而且 ADR 0024 的「只降不升」本身就是这次要改的东西。
- **保留上限，只修「改名算新增」**：能解决这一次误拦，但总数已经贴着上限，下一个真加用例的提交照样要找旧用例来抵，仍然是用户说的「太容易满」。
- **出包时超过上次发版一定比例就失败**：出包阶段失败代价最大（检查都过了、包没出），而且用例增长多半是正常的功能增长；报出来让人看见就够了。
- **在 CI 里也判合并提交**：PR 的 merge ref、dev 上面板生成的合并提交都是合并，判它就得沿合并链找子提交的预算段（原来的 `mergedChainMessages` 走了四轮评审才勉强对），收益只是多兜住「没在本地跑 lint 就推」的情况。
- **新建一个「测试清理」角色**：清理是「测试与验收」能力块里的一档，和设计用例、补测试一样做成 `task` 的选项。

## 操作清单 / 契约

| 命令                                                      | 谁用                     | 失败条件                                                |
| --------------------------------------------------------- | ------------------------ | ------------------------------------------------------- |
| `node scripts/test-budget.mjs --check [--message <文件>]` | `npm run lint`、本地预检 | 本次净新增 > 0 且提交说明没有非空的「测试预算:」段      |
| `node scripts/test-budget.mjs --tap <报告>`               | CI `test` job            | 只在报告不存在或没有 `# tests N` 时失败                 |
| `node scripts/test-budget.mjs --report --since auto`      | 出包流程                 | 只在 `--since` 指的版本不存在时失败（浅克隆看不到标签） |

## 与现有实现的关系

- 替代 ADR 0024 第 4 条（用例预算棘轮）；0024 的其余各条（只输出失败、失败只重跑失败的、继承环境）不变。
- 改动：`scripts/lib/test-budget.mjs`（去掉上限、基线、合并链；加 `diffCases`、`newCaseVerdict`、`countDelta`）、`scripts/test-budget.mjs`（三种模式）、`scripts/lib/test-layers.mjs`（`isUnitTestPath`，导出 `E2E_SHARD_DIR`）、`.github/workflows/release.yml`（报数一步）、`.github/workflows/ci.yml`（注释）、「测试验收」角色设定和主理的一句派单规则。
- 文档：`docs/modules/testing/README.md`、`docs/agent-test-steps.md`、`docs/agent-catalog.md`。

## 运行时

`--check` 和 `--report` 都只读源码和 git 对象，不跑测试，秒级。`--report --since` 用 `git ls-tree` / `git show` 读历史版本，不切工作区；出包 job 的 checkout 已是 `fetch-depth: 0`。

## 分期

一次做完。

## 风险与代价

- 总数会涨。认下来：涨多少在每次出包的摘要里看得见，清理改成定期一批做，比每个提交被迫找一条旧用例来抵更容易做对。
- 只判非合并提交：没在本地跑 lint 就直接以合并提交推上来的新用例不会被拦。AGENTS.md 要求提交前跑 `npm run lint`，面板的子对话也是先在自己的提交上跑检查再合回。
- 同一提交里删一条无关用例、加一条新用例，净新增为 0 会放行：和原来的「一换一」要求一致，删除本身要符合淘汰标准，由评审看提交说明里的理由。

## 开放问题

- **清理的节奏**：倾向每次大版本（次版本号提升）前跑一次「清理用例」；定下来之前由用户按需触发。
