# ADR 0009：评审只出意见，由执行角色逐条核实处置，门禁不再只认「通过」

状态：已接受 · 2026-10-24

## 背景

`b027ca9` 把「评审」升为必备角色并接进子对话收尾：子对话 `submit_merge` 之前必须派评审，最近一次评审写「验收结论：通过」才放行。用户 2026-10-24 反馈：收尾阶段评审发现问题 → 改 → 再评审 → 又发现问题，反复循环，问到底是评审乱来还是写代码的 CLI 不严谨，并定下一条硬要求：**评审的结果不能直接当真，当前对话要自己分析是不是真问题、有没有必要修，不能评审给什么就修什么。**

用户同时贴了一份 AI 对一次失败记录的分析：8 次评审全部「不通过」、执行改了 7 轮，三个小修复 1h22m 没交付；报告的结论是「不是评审太挑，每次都是真问题；根因是口径没先定、评审没有收敛规则、执行逐条打补丁」，附 10 条代码问题和三处提示词修改建议。这份报告本身也按同一条原则处理：逐条对代码核实，见下面「报告逐条核实」。

## 事实核对（改动前）

| 位置                                                     | 现状                                                                                                                                |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `shared/review-gate.ts` 的 `reviewGate`                  | 最近一次评审结论是 `fail` 就拒绝：「按 🛑 逐条改完，再派一次评审复看，通过之后才调用 submit_merge」。唯一的放行条件是评审写「通过」 |
| `shared/builtin/agents.ts` 执行角色「收尾前评审」第 4 条 | 「有 🛑：先改完，再新加一条评审步骤复看……**不要自己把 🛑 判成不重要，也不要跳过复看**」                                             |
| 同上，评审角色                                           | 「有 🛑 时必须写不通过」；🛑 的门槛只有「必须改」三个字，没说复看只看增量，也没说范围外、极端数据怎么算                             |
| `shared/engine.ts` 的 `spawn` / `runHelper`              | 每次 `spawn_agents` 新建一个子任务、一个新会话（`sessionKey: step.id`）：复看的评审从零开始，重读模块文档、重读全量 diff            |
| 同上 `runHelper`                                         | `step.output = clip(text, MAX_OUTPUT)`，4000 字之后直接截掉，没像节点那样走 `storeOutput` 存文件                                    |

三条叠在一起就是循环：评审是唯一裁判（门禁只认它的「通过」），执行角色被明令禁止驳回，每次复看是一个没有上下文的新评审、看的是越改越大的全量 diff，🛑 又没有门槛——每一轮都能从新角度找出新的 🛑，而按规则只能继续改。

## 决策

**结论：主要是结构问题，不是哪一方单独的错。** 评审找到的多数是真问题（报告的核实也支持这一点），执行逐条打补丁、口径没先定也确实不严谨；但让循环停不下来的是规则本身：裁判权只在评审手里、执行不许判断、复看没有收敛条件。改结构：

1. **评审只出意见，采不采纳由执行角色核实后定。** 门禁放行条件改成：最近一次评审「通过」，**或者**执行角色对它的每条 🛑 都写了处置。处置走 `submit_merge` 的新参数 `review_triage`：

   | 字段       | 内容                                                                                                                            |
   | ---------- | ------------------------------------------------------------------------------------------------------------------------------- |
   | `id`       | 评审的编号 `R1`、`R2`…；评审没编号时写意见原话摘要                                                                              |
   | `decision` | `fix` 核实是真问题、在范围里、已改并验证；`reject` 核实不成立；`defer` 真问题但范围外 / 只在构造的极端数据上成立 / 代价大于收益 |
   | `reason`   | 怎么核实的（读了哪段代码、跑了什么）和理由；短于 8 个字当没写                                                                   |

   门禁检查每个 🛑 编号都有处置（编号从评审第二行「必须改：R1、R2」和正文带 🛑 的行里读，开头那行在输出被截断时也读得到）。处置原样写进给父对话的收尾请求和交接摘要：合并就是验收（[ADR 0005](./0005-conversation-states.md)），驳回得没道理的由父对话打回。

2. **评审的 🛑 有门槛**：只给需求明确要求、用户能看到或能复现的问题（自相矛盾、崩溃、数据丢失、回归、改坏契约）；范围外的历史问题、只在构造数据上成立的边界、措辞偏好写成 💭；需求没写清的验收标准单列「需要先定的口径」，不当成代码缺陷。每条 🛑 要有执行能独立核实的依据。
3. **复看收敛**：复看接着上一次评审的会话（`spawn_agents` 的 `resume`，见下），只给增量 diff 和上一轮每条的处置，评审只确认修复对不对、增量有没有新问题、reject / defer 的理由站不站得住；同一处最多复看 2 轮；同一模块同类问题被退回两次就回到定口径，或交父对话定方向。小改动有用例覆盖时可以不复看。
4. **先定口径**：统计口径、数据模型、跨模块契约类的改动，动手前先写口径，评审按口径评。

候选方案：

- **只改提示词、门禁不动**（报告的建议）：给评审加门槛、给执行加「复看 2 轮后上报父对话」。没选：门禁仍然只认「通过」，执行到第 3 轮除了上报没有出路，用户要求的「当前对话自己判断」落不了地；而且提示词约束不了门禁。
- **复看次数到上限后自动放行**：没选。放行的依据变成「审累了」，不是「每条都看过」；没处置的 🛑 会悄悄进父对话的分支。
- **让父对话裁决每条意见**：没选。父对话只统筹、不读代码（[builtin 教训](../lessons/builtin.md)），核实成本应该落在改代码的那一方；父对话只看处置理由，站不住再打回。

### 评审子任务复用会话

`spawn_agents` 每项加 `resume`（之前某个子任务的 id）：新子任务记下 `TaskStep.session`，执行时 `sessionKey` 用它，接着那个 CLI 会话跑，上一轮读过的模块文档、代码和意见都在上下文里。限制：被接的必须是同一个父节点派过的、已经结束的、同一个角色的；同一批里不能两个都接同一个会话（同一会话同一时间只能跑一轮）。旧数据 `session` 为空，按自己的 id 起会话，行为不变。

### 文档落地

评审第 5 步对照模块文档：改动让文档过期、或该有模块文档却没有，单列「文档要更新」（文件、小节、应改成什么、代码依据）。执行角色在评审前把文档更新列进计划派「文档」，没有模块文档的把这次读明白的职责、入口、关键文件交给「文档」补上——下次评审和排查先读文档就能定位，这是提速的主要来源；评审列的「文档要更新」同样先核对再交，「文档」角色落盘前再对照代码核一遍。

## 报告逐条核实

| 报告的条目                                       | 核实                                                                                                                                                    | 处置                                                                      |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 子 Agent 输出截到 4000 字                        | 属实：`runHelper` 只 `clip`                                                                                                                             | 改：走 `storeOutput` 存文件                                               |
| 返工只按节点 rounds 算                           | 部分过时：`86e03b7` 已按验收 / 重跑 / 收尾驳回分类；评审、测试验收子任务的「不通过」确实没算                                                            | 改：加 `reworkBy.sub`「子任务验收不通过」                                 |
| 对话模式主 Agent 没有节点行                      | 属实，但是报告的展示偏好，不影响正确性；子任务各自有行，合计减一下就是主 Agent                                                                          | 不改                                                                      |
| 后台命令退出码非 0 记成失败的工具调用            | 不成立：这是约定口径（`failedToolsOf` 注释「命令非零退出……都会标上 failed」），前台命令非 0 也这么算；后台测试失败标红正是要让对话看到                  | 不改                                                                      |
| 父对话转发的消息记成用户消息                     | 属实：统计和导出里 `role === 'user'` 没排除带 `peer` 的消息（[ADR 0008](./0008-peer-messages.md) 之后有了来源标记）                                     | 改：不算用户消息，过程里写「父对话（…）发来」                             |
| 停止时运行中的评审停在 running                   | 部分属实：`runHelper` 停止后标 `pending`，但没标 `interrupted`，报告分不清「被停了」和「没开始」                                                        | 改：标 `interrupted`                                                      |
| `spawn_agents` 的 title 必填                     | 属实：引擎早就会取 instructions 第一行兜底，只是工具 schema 把它写成 required                                                                           | 改：只要求 instructions；`instructionsFile` 不做（JSON 转义是模型的问题） |
| 子对话占用被 min 夹（90m 报成 50m）              | 不成立：报告里的口径是「跨度 = 执行 + 子对话占用 + 空闲」，子对话占用只算父没在执行的那部分，50m 正是这个口径下的上限；精确值要父的执行窗口，记录里没有 | 不改                                                                      |
| 重启落盘不结算 idleWaitMs                        | 「跨度随查看时间涨」不成立：`idleWaitDuration` 只给 running 的任务算到 now。但重启分支确实没把 `idleWaitAt` 结掉，和 `waitMs` 不对称                    | 改：重启时一起结算                                                        |
| 用例只造已结束的记录                             | 方向对，是写用例的做法，不是一处代码缺陷                                                                                                                | 不改（新用例按真实形态造）                                                |
| 提示词：执行「禁止用 python / sed 改文件」       | 理由是「不进改文件统计」，是统计的问题不是正确性问题；在 Windows 上编辑工具也不总可用                                                                   | 不采纳                                                                    |
| 提示词：「通用约束」加「同类问题退回两次回根因」 | 方向对，但它只和收尾评审有关；写进执行角色的收尾一节，不改「通用约束」（改它要登记旧指纹升级已装副本）                                                  | 改在执行角色里                                                            |

## 与现有实现的关系

- `shared/review-gate.ts`：`reviewGate` 加第四个参数 `triage`，新增 `blockingIds`、`triageText`、`triageInput`。
- `shared/verdict.ts`：`parseVerdict` 和「首行优先」的 `leadVerdict` 从 `engine.ts` 挪出来（`engine.ts` 仍导出 `parseVerdict`），评审门禁和执行报告不用为一个函数引整个引擎。
- `server/orch-mcp.ts`：`submit_merge` 加 `review_triage`，`spawn_agents` 加 `resume`、`title` 改选填。
- `server/tasks.ts`：`submitMerge` 收处置、交给门禁，写进收尾请求和交接摘要（`shared/handoff.ts` 的「评审意见的处置」）。
- 角色设定：执行、评审、文档三个必备角色，启动时直接同步，不用登记旧指纹。

## 运行时

处置只在 `submit_merge` 那一次传入，不落成单独状态：门禁当场核对，结果进 `tk.handoff` 和发给父对话的消息。父对话打回后子对话再请求收尾时重新写。

## 分期

一次做完。

## 风险与代价

- 执行角色可能为了合回去把 🛑 全写成 reject / defer。防线：理由必须写怎么核实的，处置原样交给父对话验收；复看时评审要看 reject / defer 的理由站不站得住，站不住重新列成 🛑。
- 评审不按「必须改：R1…」编号时只能按条数兜底：写了不通过就至少要有一条处置。

## 开放问题

- 报告建议的「对话模式给主 Agent 单独一行」：倾向等用户在报告里实际要看成本分布时再做。
