# ADR 0045：Bug 先交诊断报告，确认了方案再改

状态：已接受（2026-11-03 用户确认并实施；和最初提议不同的地方见「实施记录」） · 2026-11-03

- 影响范围：`shared/builtin/agents.ts`（`BUG_METHOD`、`BUG_REPORT_TEXT`、主理的「Bug 怎么交」、执行）、`server/orch-mcp.ts`（新工具 `submit_diagnosis`）、`server/exec/panel-requests.ts`（诊断确认请求）、`shared/task-request.ts`、`shared/schema.ts`（`Task.diagnoses`）、`shared/review-gate.ts`（收尾核对改动范围）、`web/src/components/tasks/ReviewDialog.tsx`、`RequestCard.tsx`、`ChildRequestBar.tsx`、`Messages.tsx`
- 取代：无。补全 `BUG_METHOD` 第 5 步「根因成立 → 先写失败测试，再修」：在「根因成立」和「修」之间加一道确认

## 背景

用户 2026-11-03 提的问题：

1. Agent 分析 Bug 一顿操作之后就开始改，改完还是错的，反复返工。
2. 最要紧的是避免乱改。
3. 父对话开着「提问」时，Bug 分析完应该先问用户确认，确认了再改。
4. 分析结果要是一份报告，能点开弹窗看；交互参照工作流里审查设计方案的弹窗，用户可以在上面标出疑问，让它再查、再确认。

## 现状：Bug 现在怎么走

| 位置                                                  | 现状                                                                                                                                                                                                                                                                                                                                     |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 主理的「Bug 怎么交」（`shared/builtin/agents.ts`）    | 父对话只把 Bug 定位到模块，按现象卡写派单交给子对话；子对话交回后按「排查报告」核对调用栈、证据链、验证结果，缺了退回                                                                                                                                                                                                                    |
| `BUG_METHOD`（同文件）                                | 子对话（执行）的方法：钉住现象 → 模块文档 → 模块代码 → 调用栈 → 日志 → 证据链三环齐全 → **先写失败测试，再修** → 验证 → 回写文档；有「排查记录」（已确认 / 已排除 / 待验证）和「修了三次不对就停下报告」                                                                                                                                 |
| `BUG_REPORT_TEXT`（同文件）                           | 排查报告 11 节（现象、复现、范围、时间线、调用栈、证据链、根因、修复、验证、回归、文档），**改完之后**才交                                                                                                                                                                                                                               |
| 子对话的提问                                          | 子对话自己的「提问」开着就直接问用户，关着交给父对话答；父对话的「提问」开着时，要用户拍板的再问用户（`shared/child-ask.ts`）。没有哪一条规定 Bug 修之前要问                                                                                                                                                                             |
| 工作流节点的「完成后等我确认」（`NodeHooks.confirm`） | 节点做完发 `kind: 'confirm'` 的请求（`server/exec/real-turn.ts` 的 `confirm`），输入框上方出现「需要你确认 · 查看结果」，点开 `ReviewDialog`：左边按 Markdown 渲染结果，选中文字可以标注，右栏列出标注；「修改」把标注整理成意见退回返工（`web/src/lib/review-feedback.ts`），「确认」往下走。只有工作流节点能发，对话（含子对话）发不了 |
| 收尾的评审门禁（`shared/review-gate.ts`）             | 评审通过或每条高、中级意见有处置才放行；不核对改动是不是超出了修复方案的范围                                                                                                                                                                                                                                                             |

### 问题出在哪

1. **诊断和修复之间没有闸门**：`BUG_METHOD` 第 5 步把「根因成立」和「先写失败测试再修」写在同一句里，模型分析完就直接动手。根因判断错了，后面的改动全是错的，还要撤。
2. **报告是事后的**：排查报告在改完之后才交，用户和父对话只能核对「已经改了的东西」，拦不住乱改。
3. **确认只能靠文字提问**：对话里没有像工作流节点那样能审阅、能标注的确认入口；一问一答的文字提问装不下调用栈和证据链，用户也没法逐处提疑问。
4. **疑问没有闭环**：用户对某一处有疑问，只能整段回一句；Agent 不知道哪几条要补证据，往往整套重来。
5. **修复范围没人核对**：方案说改 A，实际顺手改了 B、C，收尾时没有任何检查会提出来。
6. **修失败了就在上一次的修法上叠**：规则里写了「修复没生效记进已排除、回到证据链」，但没有机制让它回到诊断，常见的是连着改三次。

## 决策

**Bug 分两段：先交「诊断报告」（含修复方案），确认后才能改；确认之后按方案改，收尾时核对实际改动有没有超出方案。确认由谁做跟父对话的「提问」开关走：开着问用户，关着由父对话按清单审。**

### 1. 新的一步：诊断报告（`submit_diagnosis`）

子对话（执行）查到根因、修之前，调用面板工具 `submit_diagnosis` 交一份诊断报告。工具调用停在那里，等确认结果回来才返回，所以等的时候它动不了文件。报告是结构化的，面板按固定格式渲染：

| 小节       | 写什么                                                                         |
| ---------- | ------------------------------------------------------------------------------ |
| 现象       | 期望 vs 实际、触发步骤、频率、是否回归（沿用现象卡）                           |
| 复现       | 命令 / 测试 / 操作和本轮的真实输出；复现不了写试过什么                         |
| 位置       | 模块、哪一层；调用栈一跳一行（`path:line 函数`）                               |
| 证据链     | 每一环：现象 ← 日志原文或测试输出 ← 代码 `path:line` 的条件或赋值              |
| 根因       | 一两句；标「已证实」或「假设，用 X 确认」                                      |
| 已排除     | 排除过的方向和依据（沿用排查记录）                                             |
| 修复方案   | 要改的文件和每处怎么改（一两句）；为什么这是根因而不是症状；不改的（顺带发现） |
| 影响和风险 | 会影响哪些调用方、旧数据、别的功能                                             |
| 验证计划   | 哪条测试改前失败、改后通过；还要跑哪些测试；没法自动化的手工步骤               |

查不出根因时也交这份报告：根因写「未找到」，修复方案换成「下一步要加哪些日志、要用户提供什么」。这就是现在规则里「停下来报告」那一步，有了统一的格式。

### 2. 谁来确认：总是用户

诊断报告一律交给用户确认，不跟「提问」开关走，父对话也不代为确认（用户 2026-11-03 定的）。审阅弹窗只从子对话里交报告的那一行工具调用打开（见实施记录的调整）。用户的决定原样交回子对话。

### 3. 确认之前不能改，确认之后按方案改

- **交了报告这一轮就结束**：`submit_diagnosis` 记下报告，回「结束这一轮，确认之前不要改任何文件」。用户可能隔很久才看，所以不让 CLI 卡在工具调用里等（会撞上 CLI 的工具超时）；等确认期间对话算执行中（父对话那边照样转圈），面板不推它接着做、也不当成做完。用户确认或提了意见，页面把结果作为一条消息发给子对话，它从这里接着做。
- **交报告之前就改了的**：面板在交报告时拍一次改动快照，确认前如果工作区多了改动（例如模型先改再交），报告上标出「交报告前已改动：…」，审阅时一眼能看见。
- **收尾核对改动范围**：合回（`submit_merge`）前，面板拿实际改动的文件对照已确认方案里的文件列表；测试、文档、翻译不算超出。有超出的直接不放行：不需要的改回去，确实要改就交新一版诊断报告写明为什么，等用户确认。
- **修失败了回到诊断**：按方案改完验证不过，不在上一次的修法上叠。子对话交新一版诊断报告，把这次的修法和失败证据写进「已排除」，再走一遍确认。规则写进 `BUG_METHOD`；面板这边只认最新一版确认过的方案，收尾核对也按它。

### 4. 界面：诊断报告的审阅弹窗

在现有 `ReviewDialog`（工作流节点的确认弹窗）上扩展，不另做一套：

- **入口**：
  - 子对话里交报告的那一行工具调用：那一版等确认时一直转圈，写「等你查看报告」，行尾按钮「查看报告」；确认之后按钮还在，弹窗只读，随时能回看。
  - 父对话页不单独放入口：子对话照常转圈，点开子对话就看到那一行。
- **弹窗布局**（照现在的审阅弹窗）：
  - 头部：报告标题、子对话名；有多版时用分段切换「第 1 版 / 第 2 版 …」。
  - 左边：按上面的小节渲染报告。和上一版比改过的小节左边一道竖线，标「这版改了」。
  - 右栏：标注列表。选中文字点「标注」，每条标注选种类：**疑问**（这里有问题，要它查清楚、补证据）或**改方案**（要换修法、缩小 / 扩大范围）。第 2 版起，上一轮的每条疑问下面显示 Agent 的回答和补的证据，没回答的标红。
  - 底部：整体意见输入框；两个按钮：
    - 「有疑问，再查」：有标注或整体意见才能点。标注按「原文 + 种类 + 意见」交回，Agent 只针对这几条去查，查完交新一版。
    - 「确认方案，开始修」：主按钮。
- **作废**：有了新一版，旧版自动标「已作废」，弹窗里还能切回去看。

### 5. 疑问的闭环：只查被问到的

- 交回的疑问逐条带编号。`submit_diagnosis` 的新一版要逐条写回答：查了什么、结论、补的证据或改了哪一节。面板按编号把回答对到弹窗右栏对应的标注下面。
- 规则写明：只回答被问到的几条，其余小节不重写；被问到的改了才标「这版改了」。用户看第 2 版只看改过的地方。
- 没回答的疑问不许直接交新一版：工具报错，列出还没回答的编号。

### 6. 规则文字怎么改

- `BUG_METHOD`：第 5 步拆成两步——「证据链齐了 → 交诊断报告，等确认」「确认后先写失败测试，再按方案修」。修失败回到诊断。只改方案里的文件。
- `BUG_REPORT_TEXT`：最终的排查报告沿用，第 8 节「修复」改成「按已确认的第 N 版方案改了什么；超出方案的文件和原因」。
- 主理「Bug 怎么交」：
  - 派 Bug 时在 `create_conversation` 写 `kind: "bug"`，面板据此给子对话开诊断闸门。不写就是普通任务，不强制，避免小改动也要交报告。
  - 父对话「提问」关着时，加一段「诊断核对清单」，按它确认或退回。

### 放弃的方案

- **只改提示词，让它分析完先问一句**：放弃。现在的问题就是规则写了，模型照样直接改；没有闸门，什么都拦不住。
- **用普通的 ask_user 文字提问来确认**：放弃。调用栈、证据链放不进一问一答，也没法逐处标疑问。
- **诊断做成单独的子任务，修复另开子对话**：放弃。诊断时读过的代码和建立的上下文到修复时全丢，交接还会走样；同一个子对话、同一个会话里先诊断后修最省。
- **工作流节点做诊断（Bug 修复工作流加确认节点）**：放弃。ADR 0044 已经去掉「Bug 修复」工作流：Bug 的定位是边查边定，不适合固定节点；闸门放在子对话里更贴合。
- **确认前锁住写文件的权限**：做不到可靠。各 CLI 的权限模型不一样，有的还开着跳过确认。工具调用卡住，加上交报告前后的改动快照，已经够用。

## 操作清单 / 契约

| 项                                                 | 内容                                                                                                                                                                                                                                                                    |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `submit_diagnosis`（Bug 子对话，`kind: bug` 时有） | 字段按第 1 条的小节；`answers`（第 2 版起，逐条对上一轮疑问的回答）；返回：确认 →「方案已确认（第 N 版）」，有疑问 → 编号的疑问清单                                                                                                                                     |
| `create_conversation` / `send_to_conversation`     | 多一个可选的 `kind: "bug"`                                                                                                                                                                                                                                              |
| `Task.diagnoses`                                   | 每版一条：`version`、`at`、各小节、`files`（方案里要改的文件）、`status`（`pending` / `questioned` / `approved` / `superseded`）、`notes`（`{ quote, kind: 'question' \| 'change', comment }[]`）、`answers`、`by`（`user` / `parent`）、`before`（交报告前的改动快照） |
| `TaskRequest`                                      | `kind: 'confirm'`、`purpose: 'diagnosis'`、`version`                                                                                                                                                                                                                    |
| 收尾门禁                                           | 实际改动 − 方案文件（测试、文档、翻译除外）→ 每个都要处置，规则写在 `review-gate.ts` 旁边                                                                                                                                                                               |
| 确认人                                             | 父对话 `askUser` 开 → 用户；关 → 父对话（核对清单），拿不准的转问用户                                                                                                                                                                                                   |

## 与现有实现的关系

- 审阅弹窗、标注、退回意见的格式（`ReviewDialog`、`reviewFeedback`）直接复用，加上标注种类、多版切换、回答对位。
- 请求的发起、等待、作废沿用 `panelRequest`。停下再继续时，请求按现有规则作废、重新确认（ADR 0042）。
- 子对话请求冒到父对话页沿用 `ChildRequestBar`。
- 排查方法（`BUG_METHOD` 的定位顺序、证据链、排查记录）不变，诊断报告就是把它在动手之前交出来。

## 分期

1. **第 1 期：闸门和数据**。
   - 内容：`submit_diagnosis`、`Task.diagnoses`、确认人按「提问」开关路由、交报告前后的改动快照、收尾时核对改动范围；`BUG_METHOD`、`BUG_REPORT_TEXT`、主理和执行的规则；`kind: bug`。
   - 出口：
     - 单测覆盖路由、疑问编号必须全部回答、超出方案的文件进门禁。

2. **第 2 期：界面**。
   - 内容：子对话和父对话页的入口、对话流里的报告卡、弹窗的标注种类、多版切换、回答对位、「这版改了」标记。
   - 出口：界面检查截图，亮暗两套主题和窄窗口。
3. **第 3 期：文档和教训**。
   - 内容：模块文档、`agent-catalog.md` 的「Bug 怎么分工」。

## 风险与代价

- **多一次等待**：「提问」开着时每个 Bug 都要等用户看一次报告。这是用户要的取舍；小改动不标 `kind: bug` 就不受影响。
- **父对话代审可能放水**：清单只能约束；证据不全时工具会退回（根因没标已证实、方案里没有文件、没有验证计划都不收）。
- **模型可能先改再交报告**：拦不住，但交报告时的改动快照会把它摆出来，收尾的范围核对也会拦。

## 实施记录

用户 2026-11-03 确认：

1. **确认人**：不跟「提问」开关走，总是由用户确认，父对话不代为确认。
2. **范围**：只有父对话派来的 Bug（`create_conversation` 写 `kind: "bug"`）走诊断报告；评审、测试里发现的问题子对话直接修。
3. **标注种类**：由实现决定。定为三种：疑问（要它查清）、改方案（换修法、改范围）、补充信息（用户知道的事实，下一版用上，不用逐条回答）。

实现（一次做完）：

- **逻辑**：都在 `shared/bug-diagnosis.ts`，包括交报告、校验、渲染、用户的决定、交回的话、收尾核对。数据结构在 `shared/bug-diagnosis-schema.ts`，挂在 `Task.bug`、`Task.diagnoses` 上。
- **工具**：`submit_diagnosis` 的定义和调用在 `server/diagnosis-tool.ts`，只有 `task.bug` 的子对话有。决定接口是 `POST /tasks/:id/diagnosis/:version`（`server/tasks/diagnosis-routes.ts`）。收尾核对在 `server/tasks/merge.ts` 的 `submitMerge`。
- **等确认的状态**：不挂成等你处理的请求，只看最新一版报告的状态（`shared/task.ts` 的 `diagnosisPending`）。`ConvFacts.diagnosis` 让对话算执行中；`childWait` 写「等你查看诊断报告第 N 版」；自驱、收尾提醒按「在等用户」不推；完成判定和等确认的请求一样拦着。
- **2026-11-03 用户纠正**：第一版（1efc3a9）把诊断报告挂成「等你处理」的请求，子对话不转圈，父对话页还多一条「查看报告」。用户要求：等报告期间子对话仍是运行中、在父对话里照样转圈；「查看报告」只放在子对话里转圈的那一行工具调用上。已按此改，教训记在 `docs/lessons/state.md`。
- **审阅弹窗**：`ReviewDialog` 加了标注种类、多版切换（旧版只读）和只读模式；诊断报告的包装在 `web/src/components/tasks/DiagnosisDialog.tsx`。「回答上一版的意见」作为报告的第一节显示在正文里，没有挪到右栏每条标注下面：正文里按编号对得上，右栏留给这次的新标注。
- **规则**：`BUG_METHOD` 第 5 步写了交报告、等确认、修失败回到诊断、只改方案里的文件；主理的「Bug 怎么交」写了 `kind: "bug"`，且不代为确认。
- **入口补到父对话页**（2026-11-04，用户报找不到入口）：只放在子对话工具行上时，用户在父对话页上只看到「等你查看诊断报告第 N 版」、点不开。现在父对话页「正在运行」里这个子对话的那一行、子对话列表里它的那一项都有「查看报告」（`ChildReport.tsx`，点了取子对话的报告直接打开审阅弹窗）；每一版交上来时自动弹一次审阅弹窗，关掉后不再弹（浏览器里按子对话和版本记，父对话页和子对话页共用）。仍不在父对话页另起一行、不挂请求。
