# ADR 0046：Bug 分析重构：一套方法、一份档案、按证据选最优修法

状态：已接受（2026-11-03 用户确认：开放问题都按倾向定；用户报的 Bug 和 Agent 自己发现的 Bug 分两条路，见第 0 条） · 2026-11-03

- 影响范围：`shared/builtin/agents.ts`（`BUG_METHOD`、`BUG_REPORT_TEXT`、`LOG_TIMELINE_TEXT`、主理的「Bug 怎么交」、执行、开发、分析、评审、测试验收、文档）、`skills/coding/systematic-debugging/SKILL.md`、`shared/bug-diagnosis-schema.ts`、`shared/bug-diagnosis.ts`、`server/diagnosis-tool.ts`、`shared/diagnosis.ts`（分析窗口的结论块）、`web/src/components/tasks/DiagnosisDialog.tsx`、`web/src/components/tasks/ReviewDialog.tsx`、`web/src/lib/analysis-report.ts`
- 取代：不取代 [0045](./0045-bug-diagnosis-confirm.md)。0045 定的「先交诊断报告、用户确认了方案再改、收尾核对改动范围」原样保留；本文扩充报告里装什么、报告之前怎么查、报告之后怎么修和收口

## 背景

用户 2026-11-03 的要求：

1. 好好分析现在找 Bug 的能力和流程，整理成设计文档，再看怎么优化，可以重构 debug 的架构。
2. 分析 Bug 要有完善的流程和步骤：确定**时间线**、**功能模块**、**调用堆栈**、**造成问题的原因**；有版本管理的，列出**具体是谁那边的问题**（哪次改动、谁改的）。目标是又准又全地找出 Bug。
3. 修复要**全面**、**不引入新 Bug**、**修改面合适**。「修改面最小」「修复全面」「最合适」三者**没有固定优先级**，要比较几种修法，找出最优的那个。
4. 先写文档，用户确认后再改代码。

### 做得好的，保留

- **先现象后代码、先代码后日志**：现象卡、复现优先、日志先找到打印位置再用。用户反馈过的「翻日志看到像的就下结论」已经被这条拦住。
- **证据链三环**、「假设：……，用 X 确认」的写法、不猜着改。
- **日志时间段和状态流转时间线**：已经是比较完整的「现象时间线」做法。
- **找到就停、控制深度**：防止一路挖到底层。
- **排查记录三栏**：防止重复返工。
- **0045 的确认关**：用户确认方案之前不改代码；改动不超出方案。

### 问题出在哪

1. **方法写了三份，口径会漂。** `BUG_METHOD`、systematic-debugging、分析角色各写一份定位顺序和证据链。三份的编号、措辞、细节不一样（技能里还有英文的 Phase 1–4 和中文的「逐层」两套步骤）。改一处常漏另外两处；模型读到两套编号时会挑省事的那套。
2. **三套结论结构互不相通。** 排查报告 11 节是纯文字；诊断报告（0045）是一组扁平字段；分析窗口的 `diagnosis` 块又是另一套字段。分析窗口查清的问题转给子对话修时，子对话要从头再查一遍；子对话交回时主理要从文字里逐节找。
3. **只有「日志时间线」，没有「变更时间线」。** 现在只提到 `git log -p -n 10 -- <模块目录>` 和 `git bisect`。没有逐行追溯（blame / annotate），没有 P4、SVN 的对应做法，也没要求把「这行是哪次改动引入的」写成结论。用户要的「是谁那边的问题」目前没有落点。依赖升级、配置、数据、环境的变化也不在任何时间线里。
4. **准，但不够「全」。** 证据链三环证明了一个原因，但不要求这个原因能**解释全部现象**：为什么是偶发的、为什么只在某个环境出、为什么以前没出。也不要求把其他可能的原因（鉴别诊断）列出来、写清怎么排除的。结果是找到一个说得通的原因就下结论，漏掉同时存在的第二个原因。
5. **修法只有一个，而且默认偏向「最小」。** 现在的规则是「只改根因所在的那一处，不顺手重构」，诊断报告里 `fix` 只有一个方案。没有影响面分析（调用方、旧数据、并发时序、平台差异），也不比较修法。用户要的是在全面、修改面、风险、契合之间权衡出最优，而不是固定选最小。
6. **防新 Bug 靠「同模块搜一遍」。** 回归只要求「复现用例改前失败、改后通过」，没有「影响面每一项对应一个验证」。评审不拿确认过的诊断报告对照，只看通用清单。
7. **阶段看不见，排查记录会丢。** 阶段只写在提示词里，面板不知道子对话查到了哪一步。排查记录三栏写在回复或计划里，交新一版诊断报告时没有带上，换一轮对话就要重新翻。
8. **所有 Bug 一样重。** 堆栈直接指到一行的笔误，和偶发的并发问题走同一套要求：前者被迫写一堆「无」，后者又没有更强的要求（复现率统计、bisect、多假设并行）。实际效果是模型凭感觉省略。
9. **Bug 记录靠重新整理。** 文档角色从对话里摘内容写 `bugs/<id>.md`，信息容易漏；而这些信息在诊断报告里本来就有结构。

## 决策

一句话：**一套方法（单一来源生成提示词和技能）、一份 Bug 档案（从分析到归档都用它）、八个阶段（每个阶段有产出和关卡）、三个级别（按难度定要求），修法要列候选、按证据选最优。** 0045 的确认流程不变，放在第 6 阶段。

### 0. 两条路：用户报的 Bug 走完整流程，Agent 自己发现的走简易版

用户 2026-11-03 确认方案时加的要求：只有**用户报的、要查原因的 Bug** 用这一整套；Agent 自己写代码、自测、跑测试、评审时发现的问题用简易版，不交报告给用户确认。

| 路       | 什么时候                                                                                                                                           | 怎么走                                                                                                                                                                          |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 完整流程 | 用户报的 Bug：主理派的 `kind: "bug"` 子对话；用户在分析窗口（AI 排查、报错交给 AI）里让查的问题                                                    | 下面第 1–9 条：八个阶段、三个级别、版本归因、候选方案对比、Bug 档案、用户确认（分析窗口只读，不用确认）、Bug 记录                                                               |
| 简易版   | 其余所有：子对话改代码时自己跑测试失败、评审或测试验收报出的问题、工作流里开发节点的「修 Bug」、测试验收 `onFail=自己修`、Agent 自己发现的任何问题 | 现象（失败输出原文）→ 定位（调用栈到出错点）→ 根因（证据链三环）→ 修（写一句为什么这样修；影响面只看调用方和同类写法）→ 验证（改前失败、改后通过 + 相关测试）→ 交接摘要里写一段 |

简易版**省掉**的部分，以及为什么能省：

- **用户确认、诊断报告、Bug 档案、草稿工具、计划预置**：问题是 Agent 在自己的工作里发现的，修它本来就是这次任务的一部分；评审和收尾核对已经兜着。
- **版本归因**：自己改出来的问题，引入点就是这次改动，看自己的 diff 就够；只有确认**不是**这次改动引入的（改动前就失败），才写一句「历史遗留 / 外部依赖」和依据，交接摘要里列成顺带发现。
- **变更时间线、级别、鉴别诊断**：失败的测试或评审意见已经给了确定的现场，不用从头建时间线。
- **候选方案对比**：默认省掉。只有修法会动接口、数据格式或别的模块时，才写两三句比较，放进交接摘要。
- **Bug 记录**：照现有规则不写（只记用户报的 Bug），值得长期记住的写项目教训。

简易版**不省**的：不猜着改、症状修复的那几种不算修、三次修不好停下来报告、`[排查-…]` 临时日志清掉、同类写法搜一遍。

两条路的方法放在同一个方法数据文件里（第 7 条），简易版是完整流程里标了「简易版也要」的那几步，不另写一份。

**怎么判定走哪条路**（用户 2026-11-03 定）：

- **`/bug <现象>`（新的内置命令）：强制走完整流程。** 不用主理判断。
  - 在项目里的父对话里发：主理按完整流程派 `kind: "bug"` 子对话，级别初判照常给。
  - 直接在某个子对话里发：面板把这个子对话标成用户报的 Bug（`Task.bug`），它就有了交诊断报告的工具，按完整流程查，确认之前不改。
  - 在不能开子对话、也不是子对话的会话里发（例如 Chat 页）：就地按完整流程查到「修复设计」，在回复里给出诊断报告，结束这一轮，等用户回复同意再改。
- **不写 `/bug`、只是描述了一个 Bug：主理照样判断。** 看出是用户报的、要查原因的 Bug，就按完整流程（现在 0045 的做法）；拿不准就问用户。（2026-11-07 起改按「提问」开关：开着先问用户、关着默认直接修，见 ADR 0057）
- **`/fix <现象>`（已有的内置命令）：明确走简易版**，不交报告确认。命令的展开文字按简易版改写。

### 1. 八个阶段

| 阶段            | 要回答的问题                                   | 产出（写进档案）                                                                           | 过关条件                                                                        |
| --------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| S1 立案         | 到底哪里不对？能不能稳定复现？                 | 现象卡（期望、实际、触发、频率、环境和版本、从什么时候开始）、复现方式和本轮输出、复现率   | 现象卡每项有值或写「未知」；能复现的有本轮输出；偶发的有触发条件和频率          |
| S2 定位         | 在哪个模块、哪条调用路径上出的错？             | 模块和层、调用栈（结构化：每跳 path:line、函数、这一跳做了什么）、排除的层                 | 调用栈每一跳都读过；有报错堆栈的每一帧都对上                                    |
| S3 时间线       | 什么时候、按什么顺序坏的？那段时间里变了什么？ | 现象时间线（事件、状态流转）+ 变更时间线（代码提交、依赖、配置、数据、环境），两条线对齐   | 标出「最后一个正常」和「第一个异常」；变更时间线至少覆盖「从以前好过到现在」    |
| S4 归因         | 为什么坏？是哪次改动引入的？还有别的可能吗？   | 根因（证据链三环）、引入点（版本归因）、一致性检查、鉴别诊断（排除的假设和依据）、把握程度 | 根因能解释现象卡里的每一条；引入点有来源（blame / bisect / 差异法），没有写原因 |
| S5 修复设计     | 怎么修最好？会不会弄坏别的？                   | 影响面清单、候选方案（通常两个以上）、对比、选定和理由、验证计划                           | 每个影响面条目有对应的验证；选定理由写清为什么不选别的                          |
| S6 确认         | 用户同意这个方案吗？                           | 诊断报告第 N 版（0045）                                                                    | 用户确认（父对话派来的 Bug）                                                    |
| S7 修复与验证   | 按方案修好了吗？别的地方还好吗？               | 修复记录、复现用例改前失败 / 改后通过、影响面逐项验证结果、偶发的多次运行统计              | 改动不超出方案；影响面每项有「命令 + 本轮输出」                                 |
| S8 防复发与归档 | 下次怎么更快找到、怎么不再犯？                 | 回归测试、同类写法搜索结果、模块文档补充、Bug 记录草稿、教训（需要时）                     | 回归测试在改动里；临时日志已清                                                  |

- **阶段可以回退。** S4 推不通回 S2 或 S3；S7 验证不过不在这次修法上叠改，回 S4 并把失败修法写进「已排除」，交新一版报告（0045 已有的规则）。
- **找到就停照旧。** S2 的「逐层往下、三层就停下报告」不变；S4 的「全面」指根因要解释全部现象，不是往更底层挖。

### 2. 三个级别

| 级别 | 典型情况                                                                   | 要求的差别                                                                                                                                            |
| ---- | -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 快速 | 有报错堆栈直接指到出错行、必现、根因读代码就能确定、改一个文件             | S3 可以只写一行变更时间线（出错行的 blame 结果）；S5 可以只有一个方案，但要写一句为什么没有别的合理修法；其余照常。父对话派来的 Bug 仍然要用户确认    |
| 标准 | 默认                                                                       | 八个阶段全做；候选方案至少两个                                                                                                                        |
| 深入 | 偶发、并发和时序、跨模块、回归但找不到引入点、改了三次不对、只在某些环境出 | S3 必须有状态流转时间线（涉及状态的）和完整变更时间线；S4 必须做二分或差异法定位引入点、鉴别诊断至少两个假设；S7 偶发问题按原频率估算运行次数并写统计 |

- 级别由主理派单时给一个初判（看现象卡就能判断大半），子对话查的过程中可以**升级**并写明原因，**不能悄悄降级**（要降级写在档案里，用户审阅时能看到）。
- 面板的关卡按级别查必填项（见第 8 条）。

### 3. 版本归因：是谁那边的问题

S4 必须给出「引入点」。做法按工作区类型：

| 步骤                         | Git                                                                                                 | P4                                                                           | SVN                                      | 没有版本管理                                         |
| ---------------------------- | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------- | ---------------------------------------------------- |
| 出错的几行最后是谁改的       | `git blame -w -C -L <起>,<止> -- <文件>`（`-w -C` 跳过空白和搬移）                                  | `p4 annotate -c -i <文件>`                                                   | `svn blame -r <起>:<止> <文件>`          | 文件修改时间、依赖版本、用户描述                     |
| 这段代码的演变               | `git log -L <起>,<止>:<文件>`、`git log -S '<关键串>'`                                              | `p4 filelog <文件>`、`p4 describe -du <CL>`                                  | `svn log -v <文件>`、`svn diff -c <rev>` | —                                                    |
| 那次改动是不是「引入」       | 读那次 diff；或把复现用例在它的前一版上跑（在独立 worktree 里，`git show <rev>:<path>` 只读取文件） | `p4 print <文件>@<CL-1>` 只读对比                                            | `svn cat -r <rev-1> <文件>` 只读对比     | —                                                    |
| 找不到具体行（回归但没头绪） | `git bisect run <复现命令>`（在独立 worktree 里跑，不碰用户的工作区）                               | 按 changelist 列表手工二分，每次 `p4 print` 出那一版的相关文件到临时目录对比 | 按 rev 手工二分，`svn cat` 到临时目录    | 差异法：一好一坏的环境逐项对比版本、配置、数据、系统 |

- **只读。** P4 不 sync、不 revert，SVN 不 update，Git 不在用户的工作区里 checkout（这些已经是 project-vcs 的硬规则）。要跑旧版本就开独立 worktree 或把文件取到临时目录。
- **判断「引入」而不是「最后改过」。** blame 只说明最后谁动过这几行；要看那次改动之前是不是就有问题。格式化、搬移文件的提交要跳过（Git 读仓库里的 `.git-blame-ignore-revs`，有的话用 `--ignore-revs-file`）。
- **责任类别**（档案里必填一个）：

| 类别     | 意思                                                                   |
| -------- | ---------------------------------------------------------------------- |
| 本次改动 | 当前分支或这个对话里还没合进去的改动引入的                             |
| 近期变更 | 最近的某次提交 / CL / rev 引入的（写出是哪次、谁、何时）               |
| 历史遗留 | 一直就有，只是这次的输入或用法才触发                                   |
| 外部依赖 | 第三方库、上游服务、CLI 本身的问题（写版本和出处）                     |
| 环境配置 | 本机环境、配置文件、权限、系统差异                                     |
| 数据     | 存量数据、旧格式、脏数据触发                                           |
| 用户操作 | 按设计就是这样，操作或预期不对（这时结论是「不是 Bug」或「要改提示」） |
| 未确定   | 查不到，写清试过什么、还缺什么                                         |

- **措辞对事不对人。** 作者名、提交号、时间都取自版本记录原文，不加评价；界面上和文档里写「引入于 <提交> 《标题》（作者，日期）」。是否显示作者名见开放问题 1。
- **为什么值得做：** 引入那次改动的 diff 往往直接说明了修法（漏改的调用方、改错的条件、该一起改的另一处）；同一次改动还可能在别处埋了同类问题，S8 的同类搜索直接从那次 diff 开始搜。

### 4. 修法：比较候选方案，选最优，不默认选最小

S5 按这个顺序做：

1. **影响面分析。** 列出要改的地方会碰到什么，每条写「怎么受影响、用什么验证」：
   - 调用方：谁调用了要改的函数或读了要改的字段，几处（用搜索结果，不估）。
   - 数据和契约：持久化格式、旧数据、接口形状、默认值、配置项。
   - 时序和并发：异步顺序、重入、取消、超时。
   - 平台和变体：不同 CLI、操作系统、Git / P4 / SVN、浏览器、语言。
   - 界面和文案：状态分支（空、加载、报错、超长）、多语言。
   - 同类现场：同一个原因在别处的其他表现（从引入那次 diff 和同类写法搜索来）。
2. **列候选方案。** 至少两个**有实质区别**的修法（快速级别可以一个，写明为什么没有别的）。常见的几组对照：
   - 在源头修 / 在边界上校验；
   - 只修这一处 / 修掉这一类写法（所有同类现场）；
   - 回退引入的那次改动 / 往前修；
   - 修实现 / 修契约（改接口或数据格式，带迁移）。
3. **逐个评估。** 每个方案写这几项，用证据说话：

| 维度   | 写什么                                                                  |
| ------ | ----------------------------------------------------------------------- |
| 修得全 | 能解释的现象、同类现场里修掉了哪些、漏了哪些                            |
| 修改面 | 改哪些文件、大概几处、动不动契约和数据格式                              |
| 风险   | 可能引入的新问题从哪来（影响面清单里哪几条），怎么防                    |
| 契合   | 合不合现有的架构、模块边界、项目约定（ADR、硬规则、模块文档里写的做法） |
| 可验证 | 能不能写出改前失败、改后通过的测试；影响面的各条能不能逐项验证          |

4. **选定并写理由。** 没有固定优先级，但有两条底线：**修的是根因**（症状修复的那几种照旧不算修）、**复现用例改后通过**。在满足底线的方案里按上表权衡，写清「选 A 因为……；不选 B 因为……」。常见的取舍提示写进方法里，例如：同类现场是同一个根因时，只修一处就是没修全；动契约能一次修掉一类问题但要迁移旧数据时，把迁移成本写进风险让用户判断；修改面差不多时选更容易验证的。
5. **验证计划。** 复现用例 + 影响面每一条对应的验证（测试名或命令或手测步骤）。S7 按它逐条给结果。

用户在审阅弹窗里可以看到方案对比表，也可以直接选另一个方案（见第 6 条和开放问题 2）。

### 5. Bug 档案：一份结构贯穿始终

把诊断报告（0045）、排查报告 11 节、分析窗口的 `diagnosis` 块合成一份 **Bug 档案**。档案按阶段分块，每一块都可以单独填：

| 块       | 内容                                                                                                                                                                                                                                                      | 来自现在的                                    |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| 基本     | 级别（快速 / 标准 / 深入）和升降级理由、模块、层                                                                                                                                                                                                          | 新增                                          |
| 现象     | 期望、实际、触发、频率、环境和版本、从什么时候开始；复现方式、本轮输出、复现率                                                                                                                                                                            | 诊断报告 symptom / repro、排查报告 1–2 节     |
| 调用栈   | 一跳一行：path、line、函数、这一跳做了什么；排除的层和依据                                                                                                                                                                                                | location（一句话）、排查报告 3、5 节          |
| 时间线   | 每条：时间、来源（path:line / 进程 / 提交）、类别（事件 / 状态 / 变更）、内容、关键值、是否异常                                                                                                                                                           | 排查报告 4 节（文字）                         |
| 归因     | 根因（标题、细节、是否已证实）、证据（沿用分析窗口的 problem / reference / repro / context 四类）、引入点（类别、提交 / CL / rev、作者、时间、标题、怎么确定的、把握）、一致性检查（现象卡每条 → 怎么解释）、假设表（已证实 / 已排除 / 待验证，各自依据） | rootCause、evidence、excluded、分析窗口的证据 |
| 修复设计 | 影响面清单（条目、怎么受影响、怎么验证）、候选方案（改哪里、文件、五个维度）、选定方案和理由、验证计划                                                                                                                                                    | fix、files、risk、verify                      |
| 确认     | 版本、状态、用户标注、整体意见、回答上一版（0045 原样）                                                                                                                                                                                                   | 0045                                          |
| 结果     | 改了什么、复现用例改前改后、影响面逐项验证结果、多次运行统计、回归测试、同类搜索、文档和教训                                                                                                                                                              | 排查报告 8–11 节                              |

- **排查报告不再单独写。** 交回给父对话的报告由档案生成（现在的 `diagnosisMarkdown` 扩展），子对话只需补「结果」一块。主理按档案核对，不再从文字里逐节找。
- **分析窗口用同一份档案。** 分析角色只读，填到「修复设计」为止（候选方案写成建议）。分析窗口右栏按档案画；加一个「交给子对话修」的入口，把档案原样带到 `kind: "bug"` 的子对话里，子对话从 S5（或用户要求时从 S2 复核）开始，不从头查。
- **Bug 记录有草稿。** 修完验证后，面板从档案生成 `bugs/<id>.md` 的草稿（元数据头 + 现象、根因、引入点、修复、防线），交给文档角色审改，不再靠它从对话里摘。
- **旧数据兼容。** 档案的字段都可选，0045 已经存下的诊断报告照常显示；分析窗口旧的 `diagnosis` 块继续能读。

### 6. 档案在面板里：草稿、提交、审阅

- **草稿工具（新）。** 子对话查的过程中用它往档案里记东西（补一条时间线、加一个假设、把假设标成已排除、写影响面），按块合并，不用一次写完。作用：排查记录跨轮次不丢，交新一版报告时自动带上；面板能看到查到了哪个阶段。工具名暂定 `update_bug_case`（见开放问题 3）。
- **提交还是 `submit_diagnosis`。** 把当前草稿冻结成第 N 版，按级别查必填（第 8 条），缺什么直接退回说清；其余行为和 0045 一样（结束这一轮、用户确认之前不改文件）。
- **计划预置。** `kind: "bug"` 的子对话开出来时，计划预置成八个阶段（快速级别合并成五个：立案、定位归因、修复设计、确认、修复收尾），子对话照常更新状态。父对话的子对话栏能看出它在第几步。
- **审阅弹窗按块画。** 在 0045 的弹窗上加：时间线表（异常行标红，变更行带提交号）、调用栈、归因卡（引入点、类别、把握）、假设表、方案对比表（选定的那列高亮）。用户可以在方案对比表上点「改用这个方案」，作为一条「改方案」意见退回（不直接改档案，子对话按它交新一版）。

### 8. 面板强制的关卡

| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

### 9. 角色分工

| 角色           | 做什么                                                                                                         |
| -------------- | -------------------------------------------------------------------------------------------------------------- |
| 主理           | 不变：只定模块、写现象卡、派 `kind: "bug"`；新增给出级别初判、用户贴来的日志和版本信息原样带上；按档案核对交回 |
| 执行           | `kind: "bug"` 的子对话：S1–S8 全流程，草稿随查随记，S6 交报告；其余子对话里自己发现的问题：简易版              |
| 开发（修 Bug） | 简易版（工作流里的修 Bug 节点修的是流程里发现的问题，不是用户报的）                                            |
| 分析           | 只读，S1–S5（方案写成建议），产出档案；可以一键交给子对话修                                                    |
| 评审           | 拿已确认的档案对照：改动是不是选定的方案、影响面每条有没有验证、同类现场处理了没有；对不上的报出来             |
| 测试验收       | 跑影响面对应的回归；`onFail=自己修` 时走简易版                                                                 |
| 文档           | 从档案草稿审改 Bug 记录和模块文档                                                                              |

评审、测试里自己发现的问题直接修、不走确认、不写 Bug 记录，按第 0 条的简易版查和修。

### 放弃的方案

- **恢复「Bug 修复」工作流，用流程图跑八个阶段。** 阶段之间要按证据回退（S4 推不通回 S2），流程图的固定节点做不好；而且 0044 刚把这个工作流去掉。阶段放在子对话的计划里更灵活。
- **面板自己跑 blame、bisect。** 要跨 Git / P4 / SVN，还要能跑复现用例，交给 Agent 更合适；面板只规定结论字段和只读的边界。
- **给候选方案打分、自动选分最高的。** 用户明确说没有固定优先级；打分会让模型凑数。改成写证据和理由，让用户在审阅时判断。
- **每个阶段都让用户确认。** 太重，用户会疲劳。确认只在 S6 一次（0045），其余阶段靠档案透明（用户随时能看）。
- **只改提示词，不改结构。** 便宜，但问题 2、7、9（结构不通、记录丢失、Bug 记录靠重摘）都解决不了。

3. **第 3 期：打通两头。** 分析窗口改用档案并能「交给子对话修」；评审对照档案；Bug 记录草稿。出口：从分析窗口转成修复、修完生成 Bug 记录草稿，端到端测试覆盖一遍。

## 风险与代价

- **提示词变长、费 token。** 提示词只放阶段、关卡和底线，细节放技能；快速级别要求少。会比现在长一些，认下。
- **模型填表凑数。** 关卡只能查结构。防法：每条结论都要带出处（path:line、命令和输出、提交号），出处空的条目面板直接退回；内容靠用户确认和评审对照。
- **归因误判。** blame 只说明最后改动的人，格式化和搬移会误导。防法：`-w -C`、读仓库的 ignore-revs、要求用「前一版跑复现用例」或读 diff 确认是「引入」，把握程度如实写。
- **作者信息敏感。** 只显示版本记录原文，不加评价；可以在设置里关掉作者显示（见开放问题 1）。
- **流程变重。** 有三个级别缓解；用户确认仍然只有一次。
- **和 0045 的数据兼容。** 字段都可选，旧版本照常显示；提交检查只对新提交的版本生效。

## 实施记录

- **第 1 期（2026-11-03）**：方法放在新文件 `shared/builtin/bug-method.ts`：`BUG_FULL_TEXT`（完整流程）、`BUG_SIMPLE_TEXT`（简易版）、`BUG_ANALYSIS_TEXT`（分析角色）、`BUG_REPORT_TEXT`（按八个阶段排的 12 节排查报告）、`LOG_TIMELINE_TEXT`、`bugCommandPrompt`、`debugSkillMd`。`agents.ts` 原来的 `BUG_METHOD` 去掉。`/bug` 加进内置命令，`/fix` 的展开改成简易版。systematic-debugging 的 SKILL.md 由 `scripts/gen-debug-skill.mjs` 生成，三份附录改写成中文。诊断报告的字段暂时不变，新内容按 S6 写的对应关系装进现有字段（例如时间线进 evidence、候选方案比较进 fix、影响面进 risk）。

- **第 2 期（2026-11-03）**：诊断报告扩成 Bug 档案（`shared/bug-diagnosis-schema.ts` 的 `BugCaseFields`：级别、调用栈、时间线、引入点、一致性、假设、影响面、候选方案、选定、下一步），任务上多一份草稿 `Task.bugCase`。新工具 `update_bug_case`（`server/diagnosis-tool.ts`）随查随记、返回所在阶段和还缺什么；`submit_diagnosis` 把草稿合上这次交的内容冻结成一版，按级别查必填。收尾核对（`diagnosisGate`）多了两条：`result` 里要有回归测试、影响面逐条有验证记录；`submitMerge` 还拦改动里留着的 `[排查-` 临时日志。审阅弹窗按档案画时间线表、引入点、候选方案，没选的方案有「改用方案 X」按钮（加一条「改方案」意见退回）。设置里加「诊断报告显示作者」（默认开）。父对话的子对话行写「Bug · 阶段」。

- **第 3 期（2026-11-03）**：分析窗口的结论块（`shared/diagnosis.ts`）多了调用栈、时间线、引入点三块，旧块照读；结论页画出「引入点」「时间线」卡片，被分析的是一个对话时多一个「按完整流程修」，把查到的原样带上、以 `/bug` 发回那个对话。派评审时，面板把用户确认过的那一版的要点（选定方案、方案里的文件、影响面、验证计划）附进评审的提示词（`approvedBrief`）。用户报的 Bug 请父对话收尾时，收尾请求里带上 Bug 记录的草稿（`bugRecordDraft`），父对话派「文档」时原样附上。

和正文不一样的几处：

- **完整流程不进角色设定。** 执行、开发的角色设定只带简易版；完整流程由面板在 `kind: "bug"` 子对话的新会话第一轮注入，或者随 `/bug` 的展开一起给（`server/exec/bug-prompt.ts`）。这样平时的对话不用背着几千字，用户报的 Bug 又一定拿得到全文。
- **技能和方法一致靠单测核对。** 没放进 `scripts/rules-check.mjs`：生成要跑 TypeScript 和 Prettier，放在 `shared/builtin/bug-method.test.ts` 里比对，手改技能文件单测会失败。
- **子对话里中途发 `/bug`。** 正在回复时拒绝（这一轮换不了工具，等这一轮结束或先停止再发）。空闲、进程还挂着等下一句时，标记以后交付这条消息会发现「和现在的选择对不上」（runner 的 `stillCurrent` 多比一项 `bug`），按现有逻辑结束旧进程、重开新一轮，新一轮就有 `submit_diagnosis`。
- **保活进程里收到的 `/bug` 也由面板展开。** 别的 `/命令` 在保活时原样交给 CLI；`/bug` 不行，原样交给 Claude Code 会被当成它自己的同名命令。
- **计划不预置，阶段从档案推算。** 子对话的计划由它自己用 set_plan 管，面板预置八步会和它的计划互相覆盖；改成按草稿和报告推算查到哪一步（`bugStage`），父对话的子对话行上写「Bug · 阶段」，效果一样，不碰它的计划。
- **分析窗口不直接开 Bug 子对话。** 「按完整流程修」走 `/bug`：发回被分析的对话，由它按在哪（父对话、子对话、别的会话）去派单或就地查，分析窗口查到的写进这条消息，不另做一条「把档案原样塞进新子对话」的路；子对话从这段已查到的内容接着核对，不从头查。

## 已定的问题
