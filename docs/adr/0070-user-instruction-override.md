# ADR 0070：用户的指令优先，门禁拦下用户要求的操作时请用户放行一次

状态：已接受 · 2026-11-19

## 背景

用户 2026-11-19 定下长期原则：**用户的指令优先级最高**。和门禁冲突时可以弹窗让用户确认，用户确认后就直接执行，不能被门禁挡住。

排查时面板和插件里会拦 Agent 的地方有三十来处，几乎都是「硬拒绝 + 让 Agent 换个做法 / 让用户自己去改设置 / 让用户自己执行」。用户在对话里明确要求时，Agent 只有两条路：放弃，或者换个写法绕过去——两条都不对。能让用户说了算的出口只有推送授权卡（`ask_push`）、插件确认卡（`ctx.confirm`），以及评审门禁的 `review_override`，而后者是 Agent 自报 `by: "user"`、不经用户确认。

## 事实核对

| 位置                                           | 现状                                                                                                                        |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `server/hooks/dispatch.ts` `hookOptions`       | 工具前的内置守卫按顺序问，第一个拒绝的说了算；命令行工具、后台命令（`guardCommand`）、插件改文件工具（`guardEdit`）三个入口 |
| `server/hooks/guards.ts`                       | 推送授权、Bug 先诊断、危险命令、长命令、测试步骤归属、凭据、独立分支越界等守卫，返回交给模型的原因                          |
| `server/hooks/dispatch.ts` `beforeEnd`         | 「没做完不收尾」「改完没验证」和用户的收尾钩子                                                                              |
| `server/tasks/merge/submit.ts`                 | `submit_merge` 调 `reviewGate`，`review_override.by` 由调用方自报                                                           |
| `server/exec/panel-requests.ts` `panelRequest` | 面板自己发起、等用户点的请求卡（`ask_push` 用的就是它）                                                                     |
| `server/exec/no-push.ts`                       | 「不推送」项目和子对话独立分支用 git 配置兜底拦推送                                                                         |

## 决策

**一个门禁无关的放行通道：门禁拦下时面板记下拦了什么，Agent 用 `request_override` 请用户在卡片上确认，用户同意后同一个门禁在这个对话里放行一次。**

1. 放行只认用户在卡片上亲手点的。Agent 说「用户同意了」不算（ADR 0041、0049：不按模型回复的文字判断）。
2. 卡片上的「被拦下的操作」和「门禁的原因」取面板记下的，不取 Agent 自报的；Agent 只转述用户的要求，卡片上标明是 Agent 说的。
3. 范围只到这一次：用掉就没，10 分钟没用作废。要长期放开的仍然去设置里关守卫或改项目设置。
4. 拦截说明统一附一句：用户明确要求的就调 `request_override`，没要求过的照门禁说的做，不要自己判断「问题不大」，也不要换写法绕开。
5. 只给用户能直接对话的对话本身（顶层对话、子对话），子任务和工作流节点被拦就照门禁做或交回。

候选方案：

- **每个门禁在设置里加「冲突时：问我 / 拦 / 放行」、放行记录页、「以后都放行」**：没选。清单里一大半门禁管的是「怎么做」（临时文件放哪、先读再改、长命令放后台），用户的要求换种做法照样能达成，很少真冲突；用户 2026-11-19 同意按精简版做。
- **在守卫里直接弹卡、等用户点完再回答钩子**：没选。钩子是 CLI 同步等的，有超时；卡片可能等很久。放行请求做成独立的工具调用，钩子照常马上回答。
- **按命令原文 / 文件路径精确匹配放行**：没选。Agent 重试时常会微调命令（加 `cd`、换引号），精确匹配会让放行落空；门禁级的一次性放行加有效期已经足够窄，卡片上显示的是面板记下的真实操作。

## 操作清单 / 契约

| 项       | 内容                                                                                                                                                   |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 工具     | `request_override`，参数 `gate`（拦截说明里给的名字）、`reason`（用户原话或怎么要求的），都必填；收在 `more_tools` 里，拦截说明点名                    |
| 门禁名   | 内置钩子用钩子 id（`danger-guard`、`push-guard`、`keep-going`、`verify-before-end`、`push-lessons`……）；用户钩子 `hook:<名字>`；评审门禁 `review-gate` |
| 卡片     | `TaskRequest.kind = 'tool'`、`purpose = 'override'`，允许 / 拒绝；图标和普通权限请求区分                                                               |
| 返回     | 同意：「重试刚才的操作，放行一次」，推送另附去掉 git 兜底的写法；拒绝：用户的话 + 「按门禁说的做」                                                     |
| 评审门禁 | `review_override.by = "user"` 要先有 `review-gate` 的放行；`by = "parent"` 照旧（父对话对合并负责）                                                    |

## 与现有实现的关系

- `shared/hooks/override.ts`：工具名、门禁名、附在拦截原因后的提示、放行后的补充说明。
- `server/hooks/overrides.ts`：拦下记录和放行登记（内存），`gateDeny` 是各门禁的统一入口，`overrideRequest` 弹卡。
- `server/hooks/dispatch.ts`：三个工具前入口共用 `firstDeny`；用户钩子、升级成拦截的教训、收尾门禁都经 `gateDeny`。
- `server/panel-tools/request-override.ts`：面板工具注册表条目，用法说明里写总则「用户的指令优先级最高」。
- `shared/host/override.ts`：`OrchOverride` / `OverrideHost`。
- 推送授权卡 `ask_push` 不变：「问一次」的项目照旧先问推送授权；「不推送」的项目用户要求推时走放行。
- [ADR 0022](./0022-review-gate-override.md) 的放行记录（谁、什么时候、为什么）保留，`by: "user"` 改为必须经卡片确认。

## 运行时

守卫拒绝 → `gateDeny` 查放行：有就用掉、这个守卫当没拦，接着问下一个；没有就记下 `{门禁, 操作, 原因}` 并返回原因 + 提示。Agent 调 `request_override` → 找这个对话里该门禁最近一次拦下的记录（没有就报错让它别乱请求）→ `panelRequest` 弹卡 → 用户同意记放行。服务重启放行全部作废（CLI 进程也不在了）。

## 分期

一次做完面板这边；插件里的同类门禁（UE「权限与设置」的只读档）用插件自己的确认卡改成「确认后放行一次」，随插件版本发。

## 风险与代价

- Agent 可能在用户没要求时请求放行：卡片由用户点，拒绝就不放；卡片上写明「Agent 说你要求的」，用户能看出它在转述什么。
- 危险命令（递归删目录、强推）确认后也会执行：这是用户定的原则，卡片显示完整命令。
- 门禁级放行可能被同一门禁的另一次操作用掉：有效期 10 分钟、只一次，代价可接受。

## 开放问题

- 被拦的那一行要不要直接给用户「放行这次」按钮（不用等 Agent 请求）？倾向要，先不做，看用户用起来是否需要。
