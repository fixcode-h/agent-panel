# ADR 0053：工作流是父对话名下的一次独立运行，不再是子对话，去掉主 Agent

状态：已接受（2026-11-05 用户看过设计稿后定 D1–D7，四期都已实施） · 2026-11-05

- 替代 [ADR 0044](./0044-workflow-started-by-parent.md) 的「每次启动挂成一个工作流子对话」；「只由父对话启动」和挑工作流的判定规则保留
- 设计稿：[docs/openspec/changes/workflow-runs/design.md](../openspec/changes/workflow-runs/design.md)

## 背景

ADR 0044 把工作流做成父对话下的「工作流子对话」：第一轮由引擎按流程图跑，跑完交给执行角色收尾。用下来几处别扭（设计稿第 1 节）：

- 子对话那一整套（8 个对话状态、自驱、收尾规则、`submit_merge`）都作用到工作流上，流程图跑完还要再起一个执行角色的会话收尾，状态一会儿是流程图的、一会儿是对话的；
- 节点等确认时，确认卡挂在子对话里，父对话那一行行尾的按钮和子对话自己的方案确认抢位置；
- 改需求只能「再跑一次」（`again`），没有「退回某个节点重做」，也没有「之后的节点都要知道」的补充；
- 主 Agent（`@main`）早就不调度了（`dispatches()` 恒为 false），但引擎、编排工具、提示词里还留着整套代码。

## 事实核对

| 位置                                                         | 现状（改之前）                                          |
| ------------------------------------------------------------ | ------------------------------------------------------- |
| `flow-child.ts`、`flow-child-run.ts`（已删）                 | 工作流子对话：哪一段流程图、进度、交给执行角色的话      |
| `server/tasks/run.ts` 的 `spawnChild`（带 `flow`）           | `start_workflow` 开子对话；`again` 改流程图状态再跑一次 |
| `shared/engine.ts` 的 `startPlan` / `run` / `closeRun`       | 对话里起运行、常驻编排器起停运行                        |
| `shared/flow.ts` 的 `dispatches()`                           | 恒返回 false，`@main` 不再生成                          |
| `shared/dispatch.ts`、`server/submit-tools.ts` 的 `dispatch` | 主 Agent 交决定的提示词和工具，走不到                   |

## 决策

工作流运行是一个 `mode: 'workflow'`、带 `Task.flowRun` 的任务（`shared/tasks/flow-schema.ts`），`flowRun.owner` 记它属于哪个父对话，**没有** `parentTaskId`：子对话那套不作用到它身上，状态只看 `flowRun.phase`。

用户定的七条（设计稿第 8 节）：

| 编号 | 决定                                                                                                     |
| ---- | -------------------------------------------------------------------------------------------------------- |
| D1   | 主 Agent 彻底去掉；`mainAgentId` 保留为「默认执行角色」（节点没指定角色时用它，老数据照读）              |
| D2   | 收尾是运行的固定阶段：改代码的运行末尾接「收尾」节点，验收流程是「评审 → 测试」，不通过交回修，最多 3 轮 |
| D3   | 父对话输入框上方单独一行「工作流栏」，只列名下没结束的运行；父对话的 AI 用 `list_workflows` 看           |
| D4   | 父对话停了，名下在跑的运行一起暂停；父对话继续时接着跑；运行自己有暂停、重启                             |
| D5   | 节点确认在工作流栏上做（查看结果 / 追问 / 交给父对话）；子对话行尾的按钮留给子对话自己的方案确认         |
| D6   | 同一节点修改轮次有上限（工作流上可设，默认 3），超过也继续，只在运行结尾提示                             |
| D7   | 老的工作流子对话、老的工作流任务不做兼容，但打开不崩：照常能看，继续时报一句不能再执行                   |

放弃的做法：

- **保留工作流子对话、只把确认挪到父对话**：状态还是两套，收尾还要再起执行角色的会话，问题的根子没动。
- **收尾单独写一套阶段机（评审、测试、修复各一个阶段）**：节点的验收回路（`engine.ts` 的 `review`）已经是「做 → 验收 → 不通过带意见重做 → 最多 N 轮」，收尾接成一个带验收流程的节点就复用了它，进度、停下续跑、流程图显示都不用另写。
- **运行跑完自动合回**：合不合回、合不回时怎么办是父对话的判断（父对话目录里可能有同一文件的改动），面板只报原因。

## 操作清单 / 契约

父对话的面板工具（`server/workflow-tools.ts`，只给能启动工作流的父对话）：

| 工具               | 参数                                           | 做什么                                                     |
| ------------------ | ---------------------------------------------- | ---------------------------------------------------------- |
| `start_workflow`   | `workflow`、`input`、`title`、`files`、`step`  | 起一次运行，挂到父对话计划的一步上（等待 kind `workflow`） |
| `list_workflows`   | —                                              | 名下运行的一行摘要（`runLine`）                            |
| `message_workflow` | `id`、`text`、`to`（current / later / 节点名） | 交给正在跑的节点，或记成运行级说明                         |
| `revise_workflow`  | `id`、`node`、`text`                           | 退回到某个节点重做，意见记进决定记录                       |
| `answer_workflow`  | `id`、`decision`（confirm / revise）、`text`   | 用户交给父对话决定时代答确认；运行停着时记下、继续时直接用 |
| `stop_workflow`    | `id`、`reason`                                 | 终止，改过的文件留在分支上                                 |
| `finish_workflow`  | `id`、`action`（merge / discard）              | 待合回时合回父对话的目录（先补提交），或放弃并删分支       |

运行给父对话写信（面板消息 kind `workflow`）只在：节点失败或流程停在不通过的结论上（等决定）、待合回、完成、被用户终止；同一阶段只写一次（`flowRun.told`）。

## 与现有实现的关系

- 纯函数（进度、决定记录、退回、判定规则）在 `shared/flow-run.ts`；运行的一轮在 `shared/flow-run-turn.ts`；收尾的接线在 `shared/flow-run-wrap.ts`；父对话侧的工具胶水在 `shared/flow-run-orch.ts`。
- 服务端宿主 `server/tasks/flow-runs.ts`：建运行（改代码的开独立分支）、补充、退回、代答、终止、合回、回信、随父对话暂停 / 继续；`GET /tasks?owner=<父对话>` 列名下运行，运行不进对话列表。
- 引擎去掉主 Agent：`startPlan`、`run`、`closeRun`、`ask_main`、`dispatch` 工具和 `shared/dispatch.ts` 的调度提示都删了（`stripDispatch` 留着显示老消息）；`dispatch`、`mainTier` 字段从工作流 schema 里删掉。
- 直接经接口建的 `mode: 'workflow'` 任务（端到端测试、脚本、演示）是没有父对话的独立运行，跑完直接完成。

## 运行时

- 确认：节点等确认前把结果和 `awaitConfirm` 落盘；停下再继续时直接回到确认，不重跑节点。追问（`RequestAnswer.ask`）只回答、不改结果、不计轮次。确认、修改、追问、补充都记进 `flowRun.decisions`，之后每个节点的提示都带「这次运行里已经定下的事」。
- 暂停：`pausedBy` 记是谁停的（父对话 / 用户 / 面板重启）；父对话继续时只拉起随它停的和面板重启停的。

## 分期

四期都已做完：1 运行本身和父对话的工具；2 固定收尾；3 工作流栏和确认；4 去掉主 Agent 的残留、修改轮次可设、文档。

## 风险与代价

- 改代码的运行每次多一个 git worktree，合回或放弃时删；父对话目录里同一文件有没提交的改动时合不回，原因交给父对话（e2e 覆盖）。
- 老的工作流任务不能再继续执行，只能看；要再做一次从父对话起。

## 开放问题

- 运行里直接发消息（右栏打开运行时的输入框）现在按「交给正在跑的节点」处理；要不要改成只读、统一从父对话交，看用起来的反馈再定。
