### P2 · 轻微

- [ ] **Claude 重试耗尽后，「正在重试」警告不会收口**
  - **现象**：期望重试结束时把警告收成「已恢复」或失败。实际网关持续报错时 `api_retry` 每来一次插一条 warn 卡片，只有后续收到 `stream_event` / `assistant`（`retry_ok`）才收口；若 Claude Code 重试耗尽、以失败退出，`retrying` 一直不清零，最后一条「模型请求失败，N 秒后第 x/y 次重试」会一直挂成未恢复的警告，和下方的失败原因并存，看起来像还在重试。
  - **位置**：`server/exec/parsers.ts:334`–`:354` 只发 `retry`，任何失败路径都不发 `retry_failed`；`server/exec/runner.ts:1704`–`:1708` 只在 `retry_ok` 调 `settleRetryNotes`；`server/exec/recovery.ts:144`–`:156` 没有别的收口路径。对比：specParser（Codex/Pi）有 `retry_failed` 分支（`parsers.ts:875`、`:891-901`），Claude 这条缺。
  - **触发 / 复现**：Claude Code 连续收到 5xx / 529 直到放弃（提交 `8d6c5486` 新增的行为）。
  - **已有记录**：无。

- [ ] **没有声明 `inputExcludesCache` 的 CLI，未命中量恰好等于缓存量时少算输入**
  - **现象**：期望输入 token 按含缓存口径统计。实际 `specParser` 在 CLI 没声明口径时用 `rawIn < cache` 判断「是否不含缓存」；当未命中数与缓存数恰好相等（如各 50）时条件为 false，不补缓存，input 少算一半。注释自己也写了「只靠猜不行」。
  - **位置**：`server/exec/parsers.ts:840`–`:849`。
  - **触发 / 复现**：只影响没在 CLI 定义里写明 `inputExcludesCache` 的 CLI，且某次请求未命中量等于缓存量。
  - **已有记录**：与教训 `lmvj4a96okasa`（token 口径统一按含缓存）相关，但没有 Bug 记录。

## 二、可优化点

### 高优先级

- [ ] **多个核心文件已顶到 `file-caps` 上限，新增功能前必须先拆分**
  - **问题**：几个核心文件只剩个位数行数余量，任何一点新增都会先撞上文件行数上限。
  - **依据**：`scripts/file-caps.json:16`（`shared/engine.ts` 上限 4750）、`:8`（`server/exec/runner.ts` 2900）、`:19`（`shared/schema.ts` 2850）、`:28`（`web/src/components/tasks/TaskView.tsx` 2800）、`:29`（`web/src/lib/demo-backend.ts` 4900），与实测行数——`shared/engine.ts` 4747 行 / 上限 4750（剩 3 行）；`server/exec/runner.ts` 2899 / 2900（剩 1 行）；`web/src/components/tasks/TaskView.tsx` 2799 / 2800（剩 1 行）；`shared/schema.ts` 2841 / 2850（剩 9 行）；`web/src/lib/demo-backend.ts` 4849 / 4900（剩 51 行）。
  - **影响**：任何一点新增都会让 `npm run lint` 失败，开发者只能先做无关重构，改动被迫混在一起。
  - **建议**：先拆 `engine.ts`（提示词组装 / 计划推进 / 工具实现三块）、`runner.ts`（参数拼装 / 流式解析 / 生命周期）、`TaskView.tsx`（右栏、子对话栏、消息区抽成组件 + hook），拆分后再加功能。

- [ ] **`EngineHost` 是 269 行的上帝接口，引擎与宿主强耦合**
  - **问题**：`EngineHost` 一个接口承载全部宿主能力，所有实现和测试桩都依赖它。
  - **依据**：`shared/engine.ts:594` 起 `export interface EngineHost`，`awk` 计数 269 行；`shared/chat-prompt.ts:9`、`shared/cherry-pick.ts:1`、`shared/helper-summary.ts:8`、`shared/push-auth.ts:9`、`shared/fix-route.ts:1` 等 10+ 模块都 `import type { EngineHost }`。
  - **影响**：改引擎宿主的任何能力，所有实现和测试桩都要跟着改；新增能力只能继续往这个大接口里塞，且它所在文件已顶格。
  - **建议**：按能力拆成 `EngineExec` / `EnginePlan` / `EngineUsage` / `EngineIo` 等小接口，`EngineHost` 只做组合；类型定义移出 `engine.ts`，顺带解掉下面第 9 条的类型循环。

- [ ] **核心执行引擎缺直接单测，回归只能靠 e2e**
  - **问题**：`engine.ts` 和 `runner.ts` 两个核心文件没有同名单测，引擎调度、计划推进、子对话生命周期这类高风险改动缺少快速回归手段。
  - **依据**：`shared/engine.ts` 4747 行（入口 `runEngineTurn` 在 `shared/engine.ts:4532`），没有同名的 `engine.test.ts`（`git ls-files 'shared/engine*.test.ts'` 只有 `engine-budget.test.ts`）；`server/exec/runner.ts` 2899 行（`runAgent` 在 `server/exec/runner.ts:906`）无同名测试，只有 `server/exec/` 下 23 个局部测试（parsers、rpc、worktree 等）；`web/src` 约 284 个 tsx，只有 54 个 `.test.ts`。
  - **影响**：引擎调度、计划推进、子对话生命周期这类高风险改动只能靠 e2e（慢，且 Windows 上要进 WSL），出问题时定位成本高。
  - **建议**：把 `runEngineTurn` 拆出可注入宿主的纯逻辑后补「节点调度 / 验收退回 / 计划收口」三类单测；`runner.ts` 按「参数拼装」「事件转换」抽出纯函数再补测，不必整体测。

- [ ] **演示后端是正式后端的手抄副本，缺契约保护**
  - **问题**：演示版在浏览器里自己实现了一整套接口，字段只能靠人工与正式后端对齐，没有运行时或测试层面的契约校验。
  - **依据**：`web/src/lib/demo-backend.ts` 4849 行、`web/src/lib/demo-design.ts` 1950 行，各自在 `request` 里拦截并返回模拟响应（`web/src/lib/api.ts:168` 动态 import）；项目教训 `lmvknaj45x05u` 已记录「演示版后端的响应字段要和正式后端一致，加判定前先补 demo 后端」。
  - **影响**：正式后端加字段 / 改状态码后，演示版静默与正式版不一致，线上演示给用户看到错误行为；两份实现共约 6800 行，维护成本高。
  - **建议**：用 `shared/schema.ts` 的 zod schema 对演示响应做运行时校验，或补一组契约测试（同一组 fixture 同时喂给正式 handler 和 demo handler 比较结构），并优先收敛高频接口（tasks、children、settings）。

### 中优先级

- [ ] **前端轮询逻辑重复实现，缺统一 hook；页面隐藏时仍在请求**
  - **问题**：多个组件各自实现同一套轮询，隐藏暂停、请求串行、失败退避没有统一处理。
  - **依据**：三段几乎相同的状态轮询——`web/src/components/settings/LocalImageSection.tsx:32`（`useLocalImage`）、`web/src/components/settings/ReadAloudSection.tsx:20`（`useTtsStatus`）、`web/src/components/settings/SpeechSection.tsx:19`（`useSpeechStatus`），都是「运行中 1s / 否则 6s」，且无 `document.hidden` 判断；`web/src/components/chat/AskToggle.tsx:197` 每 1.2 秒轮询，挂在 AssistDialog、DesignChat、DesignProjectDialog、StyleLibrary、ProjectDocs 等多处（`git grep '<ScopeRequests'`），同样无隐藏判断。对比：`web/src/components/design/DesignChat.tsx:94` 自己写了 `!document.hidden && load()`，`web/src/components/tasks/JobDialog.tsx:49` 自己写了链式 setTimeout。
  - **影响**：后台标签页仍持续请求；慢网时可能叠加请求；新增轮询很容易漏掉隐藏 / 串行处理。
  - **建议**：抽 `usePolling(fn, { active, interval, pauseWhenHidden, chain })`，先迁移上述 4 处和 `web/src/components/comfy/ComfyQueuePanel.tsx:25`、`web/src/components/comfy/ComfyWeb.tsx:51`。

- [ ] **CLI 输出解析层用 `any`，外部结构变化会静默丢事件**
  - **问题**：解析器入口不做结构校验，CLI 输出字段改名时不会报错，只会少解析出事件。
  - **依据**：`server/exec/parsers.ts:135` `export type Parser = (obj: any) => CliEvent[]`；该文件 `as any` / `: any` 共 22 处，全仓 262 处；例如 `claudeTool(name, input: any, cwd)`（`:221`）、`toolLookup(input: any)`（`:285`）、`claudeLimits(info: any)`（`:520`）。
  - **影响**：CLI 升级后输出字段改名时，解析器不报错、只是少解析出事件，用户看到的是「没有输出 / 没有用量」，排查要翻日志。
  - **建议**：zod 已是依赖，对关键 envelope（`type`、用量、工具名）加 `safeParse`，失败记一条 warn 并带上原始片段；解析器内部可继续用宽松类型，但入口做一次校验。

- [ ] **前端大量 `.catch(() => {})` 把用户可见的失败吞掉**
  - **问题**：读取类请求失败时界面停在旧值或毫无反应，用户无法判断是网络、后端还是数据问题。
  - **依据**（以轮询 / 读取为例）：`web/src/components/chat/AskToggle.tsx:195` 提问轮询失败无提示，用户不知道「有新提问」的更新已停止；`web/src/components/settings/LocalImageSection.tsx:40`、`web/src/components/settings/SpeechSection.tsx:30`、`web/src/components/settings/ReadAloudSection.tsx:29` 状态拉取失败时界面停在旧值；`web/src/components/design/DesignChat.tsx:90`、`:112`，`web/src/components/comfy/ComfyQueuePanel.tsx:23` 同类。反例：`web/src/lib/api.ts:155` 的 `failure` 只 `throw`，不负责提示，所以调用方一写空 catch 用户就完全看不到错误。
  - **影响**：设置页 / 设计页出现「点了没反应」时，用户无法判断原因。
  - **建议**：区分「清理类请求可忽略」与「读取类失败」——后者把错误交给 `toast` 或就地显示一行状态；可在 `api.ts` 增加 `request(...).catch` 的统一提示开关，避免每处重写。

- [ ] **存在 10 个无引用的导出（死代码）**
  - **问题**：脚本扫描加 `git grep -w` 复核后，有 10 个导出只有定义行命中、没有调用方。
  - **依据**：`server/task-log.ts:28 taskLogPath`；`server/tasks/child-messages.ts:34 setLetterGapMs`；`server/app-actions/registry.ts:96 ActionRegistry`；`shared/summary-card.ts:231 summaryCardHint`；`shared/anim.ts:549 PresetName`；`shared/i18n.ts:15 LangSetting`；`shared/inline-edit.ts:17 InlineEditState`；`shared/library.ts:68 LibraryRenameRequest`；`web/src/lib/connection.ts:18 isOffline`；`web/src/lib/demo-backend.ts:2699 __schemas`。（`latestRun`、`removeFromCart` 只出现在文档字符串示例里，属于误报，不计入。）
  - **影响**：低到中，但无引用的类型 / 函数会误导后续维护者以为还有调用方，也占着已顶格文件的行数。
  - **建议**：删除前确认不是对外 API 或测试钩子；`setLetterGapMs` 如果只给测试用，改成测试内的注入点。

### 低优先级

- [ ] **`shared/engine.ts` 与 `shared/engine-budget.ts` 存在类型循环**
  - **问题**：两个模块互相引用，依赖图出现环。
  - **依据**：`shared/engine.ts:113` `import { budgetLimit, overBudget } from './engine-budget.ts'`；`shared/engine-budget.ts:2` `import type { EngineHost } from './engine.ts'`。
  - **影响**：当前是 `import type`，编译后擦除，无运行时报错；但会让依赖图出现环，配合上面第 2 条拆分时容易踩坑。
  - **建议**：随第 2 条把 `EngineHost` 移到独立文件，环自然消失。

- [ ] **子对话列表每 4 秒做两次完整 `JSON.stringify` 比较**
  - **问题**：列表刷新时用整份 JSON 序列化结果判断有没有变化。
  - **依据**：`web/src/components/tasks/TaskView.tsx:380` 的 `sameJson` 用 `JSON.stringify(cur) === JSON.stringify(next)`；调用在列表刷新处（同文件 `:1017` 附近 `setChildren((cur) => sameJson(cur, list))`）。
  - **影响**：子对话多时每次轮询都要序列化两份列表。实测子对话通常个位数，影响有限，列为低。
  - **建议**：比较 `updatedAt` / `status` / `childrenWorking` 组成的轻量 key，或让服务端返回版本号。

- [ ] **`web/src/lib/api.ts` 1155 行，所有接口与类型集中在一处**
  - **问题**：接口层按单文件组织，职责已经接近文件行数上限。
  - **依据**：`wc -l web/src/lib/api.ts` = 1155；顶部 60 行全是 `@shared/*` 的 type import（`web/src/lib/api.ts:1`–`:60`）。
  - **影响**：低，但已接近默认上限 1200，继续加接口会触发 `file-caps`。
  - **建议**：按域拆成 `api/tasks.ts`、`api/settings.ts`、`api/design.ts` 等，保留一个 `api` 聚合对象，调用方不变。

- [ ] **运行日志逐条同步写盘**
  - **问题**：每条日志都同步 append 到文件，高频事件路径上会阻塞事件循环。
  - **依据**：`server/log.ts:13` 引入 `appendFileSync`，`write()`（`:98-108`）每条日志同步 append；调用点较多（`server/index.ts` 25 处、`server/exec/runner.ts` 24 处、`server/exec/worktree.ts` 21 处）。
  - **影响**：低。同步写保证崩溃 / 强杀前日志完整，是有意权衡；但在高频事件路径上会增加事件循环阻塞。
  - **建议**：保持同步语义的前提下，把高频 DEBUG 合并成缓冲、按时间 / 大小批量 flush；ERROR / WARN 仍立即写。改前先确认日志是排查主力，不要为了性能丢日志。

## 四、方法与局限

- 两路调研都是只读静态分析：只读代码和文档，没有改文件，也没有跑测试或界面检查。
- 没有做运行时性能剖析（CPU profile、渲染耗时），性能相关结论均来自代码结构，不是实测数据。
- 没有覆盖 `extension/`、`skills/` 两个模块，本轮排查聚焦 `shared/`、`server/`、`web/`。
- 没有检查依赖版本过时情况和 `npm audit` 的实际结果（CI 已跑 `npm audit --omit=dev`）。
- 已有 60 条已修复 Bug 记录只核对了状态列，没有逐条回到代码确认修复是否仍在。
- 行号均基于提交 `718b39c3`；本次核对时四个「状态不明」记录中 `helper-stuck-no-output.md` 实际位于 `docs/modules/server/bugs/`（调研原文写作 `server-exec`），文档按真实路径登记。
