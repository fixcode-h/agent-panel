## 1. 现状：对话输出是怎么来的

```
CLI 进程 (-p --output-format json / RPC)          面板服务端                         页面
  stdout 一行一个 JSON 事件  ──►  server/exec/parsers.ts、rpc/*  ──►  TaskMessage[]  ──SSE──►  Messages.tsx / ToolRow.tsx
                                   归一成 text / thinking / tools    （存盘、liteMessages 截短）    气泡 + 卡片
```

要点：

- 每家 CLI 都是**非交互模式**跑的（`shared/clis/commandcode.json` 里是 `-p --output-format json` + JSON-RPC 的 `turn/start`），
  面板从来没拿到过 CLI 的终端界面（TUI），拿到的是结构化事件。
- 事件被归一成 `TaskMessage`（`shared/schema.ts`）：`text`、`thinking`、`tools: ToolUse[]`（`kind` / `label` / `input` / `output` / `exitCode` / `running` / `ms`）、
  `alert`、`peer`、`panel`、`ask`、`turnChanges` 等。**这份数据已经足够画出终端样式**——终端里每一行要的信息（动作名、对象、输出、diff、耗时、退出码）都在。
- 前端渲染集中在 `web/src/components/tasks/Messages.tsx`（`Msgs` / `AgentMessage` / `ChatReply` / `FoldedRun`）和 `web/src/components/tasks/ToolRow.tsx`（`ToolRow` / `DiffView`），
  工具的显示名、对象由 `web/src/lib/tasks.ts` 的 `toolView` / `panelTool` 算，折叠和总结判定在 `web/src/lib/fold.ts`。

## 2. 目标 / 非目标

目标：

- G1 一个对话可以在「对话」和「控制台」两种显示之间随时切换，执行中也能切，切换不重载、不丢滚动位置。
- G2 控制台模式看起来像 CLI 在终端里的输出：等宽字体、紧凑行距、一行一个动作，工具输出缩进挂在下面，diff 红绿，状态行在底部。
- G3 面板特有的东西（提问、子对话、收尾建议、警告、改动文件、撤回菜单）在控制台模式下都还能看、能点，不能因为换皮丢功能。
- G4 历史对话、演示模式、导出都不用迁移数据。

非目标：

- 不在网页里跑真正的终端 / 交互式 CLI（见第 3 节）。
- 不 1:1 复刻某个 CLI 的界面（颜色、Logo、品牌元素），只借鉴终端输出通用的排版。

## 3. 三条路线和取舍（可行性结论）

| 路线                       | 做法                                                                               | 能否「随时互切」                                                                                         | 主要问题                                                                                                                                                                                                                                                                                                                                                                                                                     | 结论                           |
| -------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| **A 同数据换渲染**         | 前端新写一套「控制台」渲染器，读同一份 `TaskMessage[]`                             | 能，纯前端状态，瞬时切换                                                                                 | 是「仿」终端，不是 CLI 原样输出；CLI 新版本改了 TUI 外观不会自动跟上                                                                                                                                                                                                                                                                                                                                                         | **推荐**，工作量中等，风险低   |
| B 真终端（PTY + xterm.js） | 服务端用 node-pty 起交互式 `cmdc` / `claude`，字节流经 WebSocket 推给页面 xterm.js | **基本不能**：一个 CLI 进程只能跑一种协议，切换 = 杀掉进程、换协议重开会话；终端输出也没法反推回对话气泡 | ① 面板的结构化能力全部依赖 JSON 事件：用量 / 上下文细分、提问卡片、子对话派发、警告分类、撤回分叉、自动续跑，在 TUI 字节流里都拿不到；② node-pty 是原生模块，破坏「解压只要 Node 22+」的出包方式（`scripts/package.mjs` 打单文件 `server.mjs`），Windows 要 ConPTY；③ TUI 依赖窗口宽度重绘，历史记录无法从存盘数据回放；④ 输入框和 TUI 自己的输入抢键盘；⑤ 每家 CLI 的 TUI 交互（确认框、菜单）都不同，违背「按 CLI 定义走」 | 不作为本需求的方案             |
| C 原样显示 stdout          | 把 CLI 打出的 JSON 行直接贴出来                                                    | 能                                                                                                       | 是 JSON，不是人看的终端输出，没有可读性                                                                                                                                                                                                                                                                                                                                                                                      | 不做（排查时已有生命周期诊断） |

**可行性结论：好做，走 A。** 数据层已经齐了，后端零改动；主要工作量在前端写一套紧凑的渲染器，并把提问卡片这类交互件做成控制台风格。
路线 B 只有在「要在网页里接管 CLI 的原生交互界面」时才值得，那是另一个需求（可以作为「在终端里打开此会话」的外链功能，见 D5），不适合做成和对话模式来回切的显示方式。

## 4. 推荐方案：同一份数据，两套渲染

```
                        ┌─ ChatTranscript（现有 Msgs / ChatReply / ToolRow，原样保留）
TaskMessage[] ─► 共用视图逻辑 ─┤
  （SSE、lite、outputCut） toolView / fold / linkPaths   └─ ConsoleTranscript（新增，web/src/components/console/）
                                                    ConsoleLine / ConsoleTool / ConsoleBox / ConsolePrompt
```

- **不重构现有对话渲染**：控制台渲染器是平行的一套组件，挂在 `TaskView.tsx` 选择用哪个 transcript 的那一处。降低回归风险，现有的界面检查截图不受影响。
- **共用的视图逻辑必须复用，不另写**：`toolView` / `panelTool`（工具显示名）、`fold.ts` 的 `summaryStart`（哪段是总结）、`file-path.ts` 的 `linkPaths`（路径可点）、
  `ToolRow.tsx` 的 `parseDiff`、`useFullOutput`（`outputCut` 时取全文，规则见 lessons/memory「发给页面的对话是轻量版」）、`useStickToBottom`（贴底跟随）。
  需要时把这些从组件文件里提到 `web/src/lib/`，两套渲染器都从那里取。
- **交互件复用逻辑、换外壳**：提问卡片（`QuestionPanel`）、子对话行、收尾建议、`AlertRow`、改动文件卡片在控制台里画成框线块（见第 5 节），点击行为、接口调用不变。
- **输入框**：沿用 `TaskComposer` / `ChatComposer`，只加一个 `variant="console"` 换外观（`>` 提示符、等宽、无圆角），附件、斜杠菜单、语音、插话逻辑不动。
- **演示模式**：演示数据本来就是 `TaskMessage`，不用改，在线演示直接能切。

## 5. 控制台模式的视觉规范

参考 Command Code、Claude Code 这类终端 Agent 的通用排版（实施前先截几张 Command Code 真实输出做对照）：

```
> 帮我把设置弹窗的闪动修一下                                    ← 用户输入：灰底整行，前缀 >

✻ 思考了 4s                                                      ← 思考：暗色，默认收起，点开看全文

⏺ 先看一下弹窗是怎么定位的。                                      ← AI 正文：⏺ 前缀，Markdown 按终端风渲染

⏺ Read(web/src/components/ui/dialog.tsx)                          ← 工具行：动作名(对象)
  ⎿  读取了 212 行                                                 ← 结果摘要，⎿ 缩进；点开看全文

⏺ Update(web/src/components/ui/dialog.tsx)
  ⎿  +3 -1
       41 -    const pos = initial
       41 +    const pos = useLayoutEffect(...)                       ← diff：红绿行，带行号

⏺ Bash(npm run typecheck)
  ⎿  exit 1 · 8.2s                                                 ← 失败：红色，带退出码
     error TS2322: ...                                             ← 输出最多显示 N 行，「… 还有 120 行（点开）」

╭─ 子对话「执行 · 修复弹窗」 ── 进行中 ────────────────╮          ← 面板特有内容：框线块，整块可点
│ 已改 2 个文件，正在跑测试                            │
╰──────────────────────────────────────────────────────╯

✶ 正在执行… (32s · ↓ 1.8k tokens · Esc 停止)                      ← 底部状态行：转圈字符 + 耗时 + 速度
```

- 字体：等宽字体走外观设置（新增一项「控制台字体」，默认 `ui-monospace, SFMono-Regular, Menlo, Consolas`），中文回落到已有的中文字体设置，避免中英文不等宽时排版错位。
- 颜色：全部用现有主题 token（`text-success` / `text-danger` / `text-muted` 等），浅色、深色主题都要好看；**不做固定黑底**，「终端黑底」作为可选的配色（D3）。
- 符号：`⏺ ⎿ ✻ ✶ ╭╮╰╯` 等在 Windows 默认字体下要确认能显示，缺字时回落到 `●`、`└`、`*`、`+-`。
- 行距、内边距明显比对话模式紧凑；宽度占满对话区，不再限制气泡最大宽度。
- 所有文案照规则走 `t('中文原文')`，符号不翻译。

## 6. 消息 → 控制台行的映射

| `TaskMessage` / `ToolUse`                          | 控制台里画成                                                                |
| -------------------------------------------------- | --------------------------------------------------------------------------- |
| `role: 'user'`（含附件、`delivery`）               | `> 原文`，附件画成 `[图片 a.png]` 这样的标记，可点开；插话写 `↳ 插进当前轮` |
| `thinking` / `thinkingMs`                          | `✻ 思考了 Ns`，点开                                                         |
| `text`（AI 正文）                                  | `⏺ ` + 终端风 Markdown（标题加粗、列表、代码块灰底，不用大字号）            |
| `tools[]` kind=read / search / web / skill / other | `⏺ 动作(对象)` + `⎿ 摘要`                                                   |
| `tools[]` kind=edit                                | `⏺ Update(路径)` + `⎿ +a -b` + diff（`parseDiff`）                          |
| `tools[]` kind=run                                 | `⏺ Bash(命令)` + `⎿ exit / 耗时` + 输出尾部 N 行；`running` 时实时滚        |
| `tools[]` kind=agent / compact                     | 子任务、压缩：`⏺ Task(…)`、`✻ 已压缩上下文 120k → 18k`                      |
| `alert`                                            | 黄 / 红色前缀行 `⚠ 网络中断，正在重试`，点开看 `detail`                     |
| `panel`、`peer`、`child`、`ask`、`summaryCards`    | 框线块（`ConsoleBox`），行为同对话模式                                      |
| `turnChanges`                                      | 一轮末尾 `⎿ 已更改 3 个文件 +40 -12  [查看] [撤销]`                         |
| `role: 'system'`（状态说明、错误）                 | 暗色 / 红色的一行，不居中                                                   |
| 用户消息的「⋯」菜单（撤回、分叉、复制）            | 行尾常显一个小「⋯」（遵守 lessons/messages「时间和操作一直显示」）          |

折叠：对话模式里「一轮做完后把过程折叠成 n 段说明」在控制台模式默认**不折叠**（终端就是全量滚动），但总结判定仍用 `summaryStart`，
长对话靠「每个工具输出只显示前 N 行」控制高度。是否也提供折叠见 D2。

## 7. 切换：入口、记忆、滚动位置

- **入口**：对话顶部标题栏右侧一个两态切换（图标 `MessageSquare` / `Terminal`，悬停提示「对话 / 控制台」）；快捷键 `Ctrl+Shift+``；命令面板（`app_actions`）里加一项「切换控制台模式」，Agent 也能调用。
- **记忆**（D1，推荐方案）：
  - 设置 → 外观里加「对话默认显示方式：对话 / 控制台」，存 `Settings.appearance`（新增字段，有默认值，旧数据不用迁移）。
  - 某个对话里手动切过就记住这个对话自己的选择，存浏览器 `localStorage`（只是这台浏览器的偏好，不进任务数据、不同步）。
- **滚动位置**：切换前记下视口顶部那条消息的 id，切换后用 `web/src/lib/message-anchor.ts` 滚回同一条；贴底跟随状态原样保留。
- **执行中切换**：两套渲染器读同一份实时数据，切换不影响正在流式输出的那一轮，也不碰 CLI 进程。

## 8. 实施分期与工作量

| 期  | 内容                                                                                                                                 | 估计   |
| --- | ------------------------------------------------------------------------------------------------------------------------------------ | ------ |
| P1  | 抽出共用视图逻辑；`ConsoleTranscript` 只读渲染（用户行、正文、思考、工具、diff、警告、状态行）；顶部切换 + 记忆 + 滚动锚点；英文翻译 | 3–4 天 |
| P2  | 框线块：子对话、提问 / 收尾建议、接收消息、改动文件与撤销；输入框 `variant="console"`；外观设置（字体、默认模式、终端配色）          | 2–3 天 |
| P3  | 界面检查分片（两种模式各截图、切换前后滚动位置不变、浅深色）、单测（消息 → 行的映射）、演示页验证；视需要扩展到工作流节点详情        | 1–2 天 |

后端、CLI 定义、数据格式都不改。风险最大的是 P2 的交互件——数量多、各自状态复杂，要逐个对照对话模式的行为。

## 9. 待定项（需要用户拍板）

- **D1 切换记在哪**：推荐「全局默认 + 每个对话记住自己的选择（本机浏览器）」；备选是只有全局一个开关（更简单，但不能某个对话单独切）。
- **D2 控制台模式要不要折叠**：推荐默认全量展开、工具输出限行；备选是沿用对话模式的「做完折叠成 n 段说明」。
- **D3 配色**：推荐跟随当前主题；另给一个「终端黑底」可选配色。还是控制台模式一律黑底？
- **D4 范围**：第一期只做任务 / 对话页；工作流节点详情、设计页 AI 对话、子对话预览面板放第二期？
- **D5 真终端**：是否要另做一个「在本机终端里打开这个会话」的按钮（调起系统终端执行 `cmdc --resume <会话>`），满足偶尔要用 CLI 原生交互的场景。它和本需求独立，不影响 A 方案。

## 10. 风险与验证

- 两套渲染器的行为漂移：新增消息类型时容易只改了一边。对策：消息 → 行的分派写成一个穷尽 `switch`（漏了类型检查报错），并在 `docs/lessons/` 记一条「新增消息类型两种模式都要画」，能做成检查就加进 `scripts/rules-check.mjs`。
- 长对话性能：控制台模式默认不折叠，DOM 会比对话模式多。对策：工具输出限行 + 沿用 `outputCut` 按需取全文；P3 用 600 条以上的对话实测，卡了再考虑分段渲染。
- 等宽排版下的中英文混排、超长路径和命令换行：界面检查专门截一张中英混排、超长命令的图。
- 验证：`npm run typecheck && npm run lint && npm run test:affected`，`npx vite build --mode demo` 后跑新增的界面检查分片。
