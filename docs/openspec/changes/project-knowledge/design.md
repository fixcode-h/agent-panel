## 2. 问题：为什么说「什么都往里塞」

1. **「教训」和「经验」混在一起。** `RECORD_HINT` 的第二种情况「你发现自己用的办法不对、绕了弯路才换成对的」，本质是「怎么做最快」，不是「这么做会错」。它和被纠正的规则用同一个工具、同一种格式、同样立即生效，还同样进每个新会话的提示词。
2. **入口没有门槛。** 消息菜单和诊断报告能把任何一段话记成教训。Bug 根因本该进 Bug 记录（`docs/modules/<模块>/bugs/`），现在可能同时进了两处，两边各改各的。
3. **越塞越贵。** 没写 `paths` 的条目每个新会话都带全文，攒多了就从 3000 字预算里挤掉真正要紧的那几条；标题列表最多 60 条，又是一两千字。条目越杂，每条被用上的概率越低，花的 token 却一样。
4. **Git 项目的教训目录和项目自己的 `docs/lessons/` 撞了。** 面板写 `<项目>/docs/lessons/<id>.md`，而像本仓库这样自己就有 `docs/lessons/ui.md` 这类分片的项目，面板把每个分片都当成「格式不对的教训文件」，每次保存都报一长串错（`server/project-lessons.ts` 的 `readLessonsDir` 只跳过 `README.md`）；「文档」角色又往同一个目录的分片里追加另一种格式的教训。两套东西挤在一个目录里。
5. **只进不出。** 没有记录哪条被用过、用过几次。AI 评审只能凭内容猜「是不是过期了」，没法说「这条 90 天里一次都没被查到」。
6. **项目的「门道」没有地方放。** 用户说的那种「表格相关的直接去某个目录找，不用每次搜全项目」，现在只能靠模块文档（要「文档」专门分析一遍才有）或塞进教训（又回到问题 1）。

## 3. 范围界定：教训、经验、模块文档、Bug 记录各管什么

一句话区分：**教训防错，经验提速，模块文档讲结构，Bug 记录讲一次故障。**

| 类别      | 回答的问题                       | 例子                                                                | 谁来记                             | 怎么交给 Agent                      | 放在哪                                 |
| --------- | -------------------------------- | ------------------------------------------------------------------- | ---------------------------------- | ----------------------------------- | -------------------------------------- |
| **教训**  | 「这么做会错，要那样做」         | 改协议字段必须同时改 `shared/` 和 `server/` 两份校验                | 被纠正、返工、回归之后才记         | 少量必读的推进提示词；其余按文件查  | `<文档根>/agent-knowledge/lessons/`    |
| **经验**  | 「做 X 最快的路是 Y」            | 表格相关的代码在 `Source/Game/Table/`，配置在 `Content/DataTables/` | 对话完成后面板自动学，用户也能手记 | **只按需搜索**，不预加载            | `<文档根>/agent-knowledge/experience/` |
| 模块文档  | 「这个模块是什么、源码在哪」     | `docs/modules/server/README.md`                                     | 「文档」角色                       | 协调器先读 `MODULE-MAP`（ADR 0048） | `<文档根>/modules/`                    |
| Bug 记录  | 「这次故障为什么发生、怎么修的」 | `bugs/restart-lost-conversations.md`                                | 用户报的 Bug 修完后                | 排查时按模块读                      | `<文档根>/modules/<模块>/bugs/`        |
| Chat 记忆 | 「这个用户喜欢什么」             | 「回复用中文」                                                      | Chat 里的 `remember`               | Chat 对话提示词                     | 数据目录 `chat-memory.json`            |
| 不记      | 一次性的事件经过、本次的进度     | 「今天改了三个文件」                                                | —                                  | —                                   | —                                      |

### 3.1 教训的准入标准（四条都满足才算教训）

1. **有证据**：用户纠正过、自己返工过，或者修的是之前改出来的问题（回归）。记的时候要选是哪一种（`evidence` 字段）。
2. **是规则**：标题写「该怎么做」，不是「发生了什么」。
3. **能复用**：换个文件、换个需求还适用，具体事件只进「起因」。
4. **代码和文档里看不出来**：读一下代码或模块文档就能知道的，不记。

不满足的去向：「绕了弯路才找到」→ 经验；Bug 根因 → Bug 记录（要防复发，再从 Bug 记录里提一条带 `evidence: 回归` 的教训）；结构说明 → 模块文档。

### 3.2 经验的准入标准

1. **省事是可度量的**：这次对话实际先走了弯路（搜了很多次、读了很多不相关的文件、命令试了几次才成），或者用户明确说「记住这个」。
2. **可验证**：带路径的，路径现在必须存在；带命令的，这次对话里它真的跑成功过。
3. **能复用**：下次同类请求能直接用上，不只是这一次的某个文件。

### 3.3 判定写在一处

这套判定只写在一处（实现时落在 shared/experience.ts 的 EXPERIENCE_SCOPE，教训那半在 shared/lessons.ts 的 RECORD_HINT）：`record_lesson` / `record_experience` 的工具说明、记录弹窗的提示文字、「文档」角色设定都引用这里导出的短句，满足 `scripts/rules-check.mjs` 第 20 条「同一句不许出现在两个文件里」。

## 4. 教训重构

结论：**要重构，但只动边界和用法，不推倒格式。** 一条一个文件、标记格式、写入队列、旧文件迁移都保留（ADR 0052 刚做完，没必要再换）。

### 4.1 目录换成专用的 `agent-knowledge/`

```
<文档根>/agent-knowledge/
  README.md          这个目录是什么、可以手改、格式说明（面板维护）
  lessons/<id>.md    教训，一条一个文件（格式不变）
  experience/<id>.md 经验，一条一个文件（第 5 节）
```

- 解决问题 4：不再和项目自己的 `docs/lessons/` 抢目录，面板也不会把项目的分片当成坏文件。
- 位置规则不变：Git / 无版本管理的文档根是 `<项目>/docs`；P4 / SVN 文档根在项目外时用共用文档根（ADR 0052），各分支共用。
- 迁移：读取时同时看旧位置 `<文档根>/lessons/`，**只认带 `<!-- lesson -->` 标记的文件**，不带标记的（项目自己的分片）直接忽略、不报错。下一次保存时把认出来的搬进新目录、删掉旧文件；旧目录里还剩项目自己的文件就不动目录。
- 「文档」角色收到「教训」派单时写面板的 `agent-knowledge/lessons/`；项目说明文件（AGENTS.md / CLAUDE.md）里明确规定了自己的教训目录的，按项目的规定走，面板不接管。

### 4.2 收紧入口

| 入口                 | 改成                                                                                                                                              |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `record_lesson`      | 必填 `evidence`（用户纠正 / 返工 / 回归）和 `cause`；`RECORD_HINT` 去掉「绕了弯路」那种情况，改成一句「找路、试命令的心得用 `record_experience`」 |
| 消息「⋯ → 记成…」    | 弹窗顶部选「教训 / 经验」，各带一行准入标准；默认选中按消息内容猜，用户可改                                                                       |
| 诊断报告「记成教训」 | 改成「写进 Bug 记录」（默认）和「另提一条防复发教训」（带 `evidence: 回归`、起因自动填 Bug id）                                                   |
| 工作报告候选教训     | 不变（本来就只进草稿区）                                                                                                                          |

### 4.3 生效分级：不是每条记下来就进提示词

教训加一个 `status`：`active`（生效）/ `candidate`（候选）/ `disabled`（停用，即原来的 `enabled: false`）。

| 来源                                     | 记下后的状态 | 为什么                                           |
| ---------------------------------------- | ------------ | ------------------------------------------------ |
| 用户手动加、用户在弹窗里确认的           | 生效         | 用户自己的话                                     |
| Agent 记的、`evidence` 是「用户纠正」    | 生效         | 用户当场纠正过，下一个对话就该照做               |
| Agent 记的、`evidence` 是「返工 / 回归」 | 候选         | Agent 自己的判断，先能被查到，但不推进每个提示词 |

候选的条目 `project_lessons` 照样能查到（排在生效的后面、标「候选」），只是不进新会话开头的提示词。用户在界面上点「确认」转成生效；被查到并且这次对话照着做了（改的文件在它的 `paths` 里、没有再被纠正）累计 3 次，面板自动转成生效，界面上标「自动确认」。

### 4.4 提示词瘦身

| 项                       | 现在                          | 改成                                                                                          |
| ------------------------ | ----------------------------- | --------------------------------------------------------------------------------------------- |
| 没写 `paths` 的全文预算  | 3000 字（没工具 6000）        | 1500 字（没工具 4000），只算 `active`                                                         |
| 标题列表                 | 最多 60 条，全部条目          | 只列没写 `paths`、超出预算的 `active` 条目，最多 15 条；写了 `paths` 的只报个数和查法         |
| 记教训说明 `RECORD_HINT` | 约 600 字，每个能记的会话都带 | 收成两行；详细的写进 `record_lesson` 的工具说明（它本来就在 `DEFERRED_TOOLS` 里，用到才展开） |

按 `paths` 生效的教训本来就靠 `project_lessons` 按文件取，不用在开头列标题。续接会话照旧只发变了的段落（ADR 0027）。

### 4.5 用了才留：命中统计

每次 `project_lessons` / `project_knowledge` 返回某条的全文，面板记一次命中。**统计存在数据目录**（`projects/knowledge-stats/<项目 id>.json`），不写进 `agent-knowledge/` 的文件里：每查一次就改项目里的文件，会在用户仓库里制造无意义的改动。

AI 评审拿到命中数据：90 天没被命中过、或者被命中后对话里又被纠正的条目，优先提「停用 / 改写」。

## 5. 经验：是什么、长什么样

### 5.1 五种经验

| 种类（`kind`）    | 说的是                    | 例子                                                                                       |
| ----------------- | ------------------------- | ------------------------------------------------------------------------------------------ |
| `locate` 找位置   | 某类东西在哪个目录 / 文件 | 表格（DataTable）相关：代码 `Source/Game/Table/`，配置 `Content/DataTables/`，不用搜全项目 |
| `vocab` 叫法对照  | 用户的说法和代码里的名字  | 「表格」「配表」= `UDataTable` / `FTableRowBase`；「背包」= `Inventory`                    |
| `command` 命令    | 怎么编译、跑测试、看日志  | 只编译游戏模块：`Build.bat GameEditor Win64 Development -Module=Game`                      |
| `verify` 验证方法 | 怎么确认改对了            | 改了表格结构后先跑 `Tools/TableCheck.py`，编辑器里看不出错                                 |
| `flow` 做法       | 某类改动的固定步骤        | 加一个新表：建 `FXxxRow` → 在 `TableRegistry.cpp` 注册 → 加 csv → 跑检查                   |

`vocab` 是专门为「搜什么词」准备的：用户说「表格」，代码里根本没有这两个字，Agent 只能乱搜。叫法对照让下一次直接搜 `DataTable`。

### 5.2 文件格式

和教训一样一条一个文件、起止标记加字段，人能直接读、能手改：

```markdown
<!-- experience -->

id: e7k2m9x
kind: locate
status: confirmed
keywords: ["表格", "配表", "DataTable", "csv"]
paths: ["Source/Game/Table/**", "Content/DataTables/"]
branch: Main
source: auto
taskIds: ["t_abc", "t_def"]
createdAt: 2026-11-05T07:10:00Z
updatedAt: 2026-11-08T02:30:00Z
title: |
表格相关的代码和配置在哪
body: |
代码在 Source/Game/Table/（每张表一个 FXxxRow，注册在 TableRegistry.cpp），
数据在 Content/DataTables/\*.csv。改表格先看这两处，不用全项目搜。

<!-- /experience -->
```

- `keywords` 是检索的主要依据，包含用户的说法和代码里的叫法。
- `status`：`candidate`（自动学到、还没被证实）/ `confirmed`（被用上证实过或用户确认）/ `stale`（路径不在了，等更新）。
- `branch`：P4 / SVN 共用文档根时记下学到它的分支（同 ADR 0052 的模块文档）。
- 正文不超过 600 字：经验是指路牌，不是文档。

## 6. 经验怎么学：对话完成后，先机械筛、再小模型提炼

原则：**多数对话一个 token 都不花；值得学的才调一次低档模型；模型只写字，判断都由面板做。**

```
对话完成 ─▶ ① 机械摘要（0 token） ─▶ ② 闸门（0 token）─不值得─▶ 结束（多数对话停在这）
                                         │值得
                                         ▼
                              ③ 低档模型提炼一次（约 3k 输入）
                                         │
                                         ▼
                              ④ 面板校验（0 token）─▶ 写成「候选」经验，对话里出一行提示
```

### 6.1 什么时候学

- **触发**：对话（含子对话）进入「已完成」（`shared/task.ts` 的 `convState` 为 `done`）之后，后台排队，不挡用户。子对话在合回完成时学，因为找路的过程大多发生在子对话里。
- **手动**：对话菜单「从这次对话学经验」，跳过第 ② 步的闸门（但仍做第 ④ 步校验）。
- **不学**：Chat 模式（没有项目）；分析 / 评审类只读对话的第 ② 步闸门更严（只学 `vocab` / `locate`）；项目设置里关掉了「自动学经验」。
- **排队**：同一项目同时只跑一个提炼；每个项目每天最多 N 次（默认 0 即不限，设置里改）；超了就只做到第 ②步，把「待提炼」挂在经验页，用户想要再点。

### 6.2 ① 机械摘要：只看工具调用

面板已经把每次工具调用按 `ToolUse.kind`（`read` / `edit` / `run` / `search` …）归一化存在 `TaskMessage.tools` 里，各 CLI 都一样，不用按 CLI 名字写分支。摘要从这里算：

| 字段             | 怎么算                                                                            |
| ---------------- | --------------------------------------------------------------------------------- |
| `searches`       | 所有 `search` 调用的搜索词和范围                                                  |
| `landing`        | 最后真正改过（`edit`）或读了之后马上去改的文件，取它们共同的 1～2 个目录          |
| `detour`         | 第一次进入 `landing` 目录之前的搜索 + 读取次数，和读过但不在 `landing` 里的文件数 |
| `commands`       | `run` 调用里同一个目的试了几次：失败（`failed` / 非零 `exitCode`）之后成功的那条  |
| `usedExperience` | 这次查过哪些经验、之后是不是直接落到了它的 `paths`                                |
| `request`        | 用户第一条消息的前 300 字（只用来提炼关键词，不判断状态）                         |

**不读模型的回复文字**，符合「不按模型回复的文字判断状态」（ADR 0041、0049）。

### 6.3 ② 闸门：值不值得花这次提炼

满足任一条才往下走，否则结束：

1. **绕路明显**：`detour` ≥ 8 次，且 `landing` 集中（这次改动 ≥ 70% 在 ≤ 2 个目录里）。
2. **命令试错**：同一个目的的命令失败 ≥ 2 次后成功。
3. **用过的经验不对**：查到了某条经验，但最后落在它的 `paths` 之外，或它的路径已经不存在 → 进第 ③ 步做「更新」而不是新加。

再排除：已有经验的 `paths` 已经覆盖 `landing`、`keywords` 也和这次的搜索词重合的，直接给那条记一次「证实」（第 6.5 节），不提炼。

阈值写在 shared/experience-gate.ts（新增），有单测；用户能在项目设置里调「学得勤一点 / 少一点」三档，对应不同阈值。

### 6.4 ③ 低档模型提炼一次

- 用设置里「低」档的模型，走现有的一次性调用（`server/exec/invoke.ts` 的 `invokeCli`，和 AI 辅助生成配置同一条路），**不开对话、不挂工具、不读项目**。
- 输入（约 3k token 上限）：第 ① 步的摘要、`landing` 目录往下两级的目录树（截到 80 行）、和这次路径或关键词有重合的已有经验（只给标题、关键词、路径）。
- 输出：一个 JSON 代码块，0～2 条，每条是 `add` / `update <id>` 加上 `kind`、`title`、`keywords`、`paths`、`body`。说明里写明：没有值得记的就输出空数组。
- 失败（调不起来、超时、输出不是 JSON）照实显示在对话里的那一行和经验页上，不悄悄重试。

### 6.5 ④ 面板校验，然后写入

1. `paths` 逐条查是否存在（不存在的去掉；全去掉了就丢弃这条）。
2. 和已有经验按「路径重合 + 关键词重合」判重：重合高的改成 `update`。
3. 字段长度、条数上限（每项目 300 条）校验。
4. 写成 `candidate`，对话末尾加一行面板消息（第 8.2 节）。

**怎么从候选变成确认**（都不花 token）：

- 下次被查到、且那次对话直接落到它的 `paths`（`detour` < 3），记一次「证实」；证实 2 次自动转 `confirmed`。
- 用户在经验页或对话里那一行点「对」。
- 被查到时路径已不在 → 转 `stale`，不再出现在搜索结果前面，等下一次第 ② 步第 3 条触发更新。

## 7. 经验怎么用：按需搜索，不预加载

### 7.1 不把经验放进提示词，只放一句话

项目有经验时，新会话开头只多一行（约 60 字）：

> 这个项目有 23 条经验（找位置、叫法对照、命令）。要在全项目搜索之前，先用 `project_knowledge` 按关键词查。

没有经验时这一行也不出。

### 7.2 一个检索工具：`project_knowledge`

把现在的 `project_lessons` 扩成 `project_knowledge`（旧名照样能调，`server/orch-mcp.ts` 里当别名处理），一份工具说明比两份省：

| 参数    | 作用                                                               |
| ------- | ------------------------------------------------------------------ |
| `query` | 关键词：对经验的 `keywords` / 标题 / 路径和教训的全文做匹配        |
| `files` | 要改的文件：返回管这些文件的教训（现在的行为）和路径覆盖它们的经验 |
| `kind`  | `lesson` / `experience` / 不填（都要）                             |

返回：经验最多 3 条全文（1500 字预算），教训按现在的规则（8000 字预算），其余列标题。确认过的排前面，候选的标「候选」，`stale` 的不给全文。

### 7.3 面板替 Agent 先查一次（0 token 的预检）

光靠 Agent 自己记得查不可靠。面板在两个地方先用本地匹配查一遍，**只在命中时**附上最多 2 条的标题和路径（≤ 300 字）：

- 新对话的第一条用户消息；
- 协调器派单（`create_conversation` / `spawn_agents`）的需求原文：子对话开头直接带上「可能相关的经验」，这正是最需要它的地方（ADR 0048 的协调器先读模块文档，经验是它的补充）。

匹配是本地的关键词包含加简单的分词（中文按 2 字切），不调模型。没命中就什么都不加。

### 7.4 和模块文档的关系

- 模块文档是权威的结构说明，经验是学来的捷径。两者说法冲突时以模块文档为准，经验转 `stale`。
- `locate` / `vocab` 类经验确认后被证实 ≥ 5 次的，经验页提示「并入模块文档」：派「文档」把关键词和路径补进对应模块 README 的元数据头，然后经验标「已并入」，不再单独出现在搜索结果里。这样常用的门道最终沉淀进模块文档，经验库自己保持小。
- ADR 0048 定过「不建文件索引、不加查询工具」。这里的经验是学来的少量条目，不是全项目的结构索引，但确实加了查询能力，所以列为待定项 D3。

## 11. 分期、风险和验证

### 分期

| 期  | 内容                                                                       |
| --- | -------------------------------------------------------------------------- |
| P1  | 教训重构：目录迁移、`evidence` / `status`、入口收紧、提示词瘦身、命中统计  |
| P2  | 经验的存储、界面（经验页、记录弹窗）、`project_knowledge` 检索、手动记经验 |
| P3  | 自动学习：机械摘要、闸门、低档模型提炼、校验、对话末尾那一行、学习设置     |
| P4  | 预检（新对话 / 派单时附上相关经验）、候选自动确认和过期检测、并入模块文档  |

P1 单独就能解决「什么都往里塞」；P2 以后才有新能力。每期都能单独上线。

### 风险

- **学错了**：小模型可能把偶然的路径当成规律。靠三道防线：闸门只在绕路明显时才学；路径必须存在；默认是候选、被实际用上证实才转确认。
- **经验过期**：重构挪了目录后经验指错路。检索时顺手查路径存在（本地文件判断），不在了转 `stale`；第 6.3 节第 3 条会触发更新。
- **token 花在学习上**：多数对话停在第 ② 步。设置里显示当天的提炼次数和 token，有每日上限。
- **P4 共用文档根**：A 分支学到的路径在 B 分支可能不存在。检索时按当前分支判断路径，不在的标「来自 X 分支」、排到后面。
- **Git 项目里多出未跟踪文件**：经验一条一个新文件，不会和合并冲突；面板不自动提交，经验页显示「N 条还没提交」。

### 验证

- 单测：闸门的阈值和摘要（造几组工具调用序列：绕路的、直达的、命令试错的）；检索排序和预算；旧目录迁移只认带标记的文件；`record_lesson` 缺 `evidence` 时报错。
- e2e（`scripts/fake-cli`）：一个对话搜了十几次才落到某目录 → 完成后出「学到 1 条经验」；下一个同类请求开头带上了这条经验、直接落到目录 → 经验转确认。
- 量 token：拿真实项目对比改前改后新会话开头「项目教训」一段的字数（`TaskTurn.sources` 已经在记）。
