# Design：缩短一轮对话的耗时（模型调用提速）

> 状态：用户选定了 2.2 的测速和首包显示、2.3、3.1、3.2、4.1、4.2、4.3，已实现（PR fixcode-h/agent-panel#201）；实测对比和剩下的待确认项见 [results.md](results.md)。
> 规划约定：**不加反引号**的路径是实施时才创建的文件；加反引号的是现有文件。现状按 2026-11-04 的 `dev` 核对。
> 数据来源：用户提供的两份导出——① 对话「修复 Pi models.json 写入校验」（Claude Code + `deepseek-v4.1-flash`，经中转，强度 high，Windows）；
> ② 对话「修复 claude 原生包下载失败」的状态诊断（Command Code + `deepseek/deepseek-v4.1-flash`，新对话）。

## 1. 一轮的时间花在哪

导出 ① 的第一轮：从第一条回复到最后一条共 **427 秒**，58 步模型请求、76 次工具调用、输出 41k token（含思考）。

| 部分                   | 耗时      | 占比 | 怎么算的                                                                |
| ---------------------- | --------- | ---- | ----------------------------------------------------------------------- |
| 模型思考               | 约 181 秒 | 42%  | 各条回复 `thinkingMs` 之和；单次最长 30.6 秒，10 秒以上的有 7 次        |
| 等模型第一个字（首包） | 约 160 秒 | 37%  | 57 个「工具做完 → 下一段开始」的间隔扣掉工具和思考：中位 2.8 秒 × 57 次 |
| 工具执行               | 约 40 秒  | 9%   | 各工具 `ms` 之和；其中约 17 秒是面板钩子的进程开销（第 4.1 节）         |
| 模型写正文和工具入参   | 约 46 秒  | 11%  | 余下部分；大段 Edit 时单步可达 20 秒以上                                |

导出 ② 的请求轨迹（状态诊断里的「模型请求开始 → 模型开始输出」）：新对话、上下文很小，首包仍然是
**第 1 次 5.1 秒，之后 1.96–2.40 秒，非常稳定**。说明首包里大部分是**链路的固定延迟**，和上下文大小关系不大。

结论：**思考和首包占了快八成**，面板自身开销不到 5%。要明显变快，主要靠「少想、少等、少几步」，面板优化是锦上添花。

## 2. 模型侧（收益最大）

### 2.1 思考强度：占 42%

- 现状：导出 ① 的角色「执行」用 `@high` 档，`deepseek-v4.1-flash` + 强度 high。读文件、跑测试这类机械步骤也在长时间思考（00:55:21 读完几个文件后想了 30.6 秒）。
- 可做的：
  1. **配置层（不改代码）**：把「执行」这类动手的角色换成中档强度，或把高档的强度降一级；只在方案设计、评审这类角色上用高强度。对 DeepSeek 这种思考很长的模型效果最明显。
  2. **功能层（要改代码，需决定）**：按阶段换强度——分析 / 设计阶段用高，计划里的「实施、跑测试」步骤用低。面板已经有计划步骤（`shared/plan.ts`），但 Claude Code 的强度绑在进程启动参数上，换强度要重开进程（`server/exec/runner.ts` 的 `stillCurrent` 会重开），重开又会丢缓存，**收益要实测**，不建议先做。
- 预估：降一档可省 30–60% 的思考时间，即整轮 **15–25%**。代价是复杂问题的质量，要看任务类型。

### 2.2 首包延迟：每步约 2–3 秒

- 现状：导出 ① 走 Claude Code → 中转网关 → DeepSeek；导出 ② 走 Command Code 自己的服务 → DeepSeek。两条链路首包都在 2 秒以上，且与上下文大小基本无关，推测是**多一跳中转（可能出境再回来）**加模型排队。
- 可做的：
  1. **配置层**：同一模型换直连的 API（DeepSeek 官方或国内节点），用 curl 测首包对比（`time_starttransfer`）。如果直连只要零点几秒，每轮能省 57 × 2 秒 ≈ **近 2 分钟**。
  2. **功能层：在 API 设置里加「测速」**——对选中的接口发一个最小的流式请求，显示首包时间和输出速度；多条链路时用户能直接挑快的。数据只在本机。
  3. **功能层：把首包时间放进会话栏**——`server/exec/cli-trace.ts` 已经在日志里记了每次请求的 `waitedMs`，但只写日志、不汇总。汇总成「本轮平均首包 / 最长首包」显示在会话栏，用户才看得出是链路慢还是模型慢。这也是验证其他优化有没有效果的前提，**建议最先做**。

### 2.3 少几步：每少一步省一次首包

- 现状：58 步、76 次工具，平均每步 1.3 个工具。前期调研阶段一步只读一两个文件，下一步再读下一批。
- 可做的：在通用约束（`shared/builtin/` 里的内置角色）里加一句「调研时把已经知道要看的文件、要跑的只读命令一次并行发出，不要一个一个来」。Claude Code、Command Code 都支持一次回复里并行调多个工具。
- 预估：调研阶段步数减少 20–30%，按每步 2.8 秒首包计，每轮省 **15–30 秒**。几乎没有代价，只改提示词，要按 `docs/agent-catalog.md` 的规则改。

### 2.4 第一个请求冷启动：5 秒

- 现状：导出 ② 第一个正式请求 5.1 秒，后面 2 秒：连接刚建立、系统提示词和工具定义还没进模型服务的缓存。
- 面板已有「预热」（`server/tasks/conversation-routes.ts` 的 `prewarmChat`）：打开对话时提前用 `--resume` 起好 CLI 进程，但**不发模型请求**，所以首包的冷启动没省掉。
- 可做的（需决定）：预热时可选发一个极小的请求暖连接和缓存。代价是每次打开对话都要付一次缓存写入的 token，**默认关、作为设置项**比较合适；收益约 3 秒 / 次新开或重开。

## 3. 上下文与缓存

### 3.1 中途开独立分支：进程换目录，缓存全丢

- 现状（导出 ①）：第一轮调研完，调 `begin_edit` 开独立分支（**9.7 秒**），之后在新目录里重开 CLI 进程。
  新进程的第一条回复在 11 秒后才出来，随后模型又把要改的文件**在新目录里重读了一遍**。
- 原因：系统提示词里带工作目录等环境信息，目录一变，模型服务的缓存前缀就对不上，约 19 万 token 的上下文要整段重新处理；路径变了，模型也不信任之前读到的内容。
- 可做的（需决定，涉及 ADR 0023 的就地改动流程）：
  1. **能预判要改代码时，先开分支再调研**：父对话分诊时已经判断「要改文件」，派子对话时直接在分支目录里开工，调研和修改在同一个目录、同一份缓存里完成。
  2. 提示词层：要求「确定要动手后立即 `begin_edit`，再读要改的文件」，减少重读。
- 预估：每次开分支省 10–20 秒外加一次整段上下文的重新处理（按 token 计费的接口还省钱）。

### 3.2 独立分支的依赖复制

- 现状：每个独立目录复制一份 `node_modules`（`server/exec/worktree.ts`，用户 2026-11-02 决定，见 `docs/lessons/worktree.md`），大项目实测 12–20 秒，这是 `begin_edit` 慢的主要原因。
- 可做的（不推翻「每个目录一份」的决定）：
  1. **提前复制**：对话开始或分诊判定要改代码时，后台就开始准备分支目录和依赖，等真正 `begin_edit` 时已经好了。
  2. **备用目录池**：始终在后台留一个依赖已复制好的空分支目录，用掉一个补一个。
  3. Windows 上如果项目在 Dev Drive（ReFS），可以用块克隆代替逐个复制，几乎瞬间完成；不是 Dev Drive 时照旧复制。需要实测 Node 在 Windows 上 `copyFile` 的 `COPYFILE_FICLONE` 是否生效。

### 3.3 面板注入的提示词

- 导出 ① 第一轮 `sources`：规则 8,969、设定 16,187 token，工具结果 120,032 字符。前两项只在第一次请求时完整处理，之后走缓存，**影响小，不建议优先做**。
- 工具结果偏大：大文件整段读进来。可以在通用约束里提醒「大文件先 grep 定位，再按行读」，收益有限。

## 4. 面板自身的开销

### 4.1 Claude Code 的工具钩子：每次调工具多起两个 node 进程

- 现状：`shared/clis/claude.json` 给 Claude Code 装了 PreToolUse、PostToolUse，**没有按工具过滤**。每次调工具（包括 Read、Grep）都要新起两次 `node agent-panel-hook.mjs`，各发一次 HTTP 回面板。
  默认就会装：内置的工具前规则（只读角色拒绝改文件、子对话不能改分支外的文件……）和默认开着的「计划没跟上提醒」（`shared/hook-builtins.ts` 的 `plan-pace`，工具后）。
- 数据：Read 最快 229 ms、中位 262 ms；Edit 中位 245 ms。Claude Code 自己读文件只要几毫秒，这 0.2 秒多基本是钩子。76 次 × 约 0.22 秒 ≈ **17 秒 / 轮（4%）**。
- 可做的：
  1. **按需生成 matcher**：Claude Code 的钩子配置支持 `matcher`（按工具名匹配）。按这一轮实际启用的钩子关心哪些工具类别（`shared/hooks.ts` 的 `toolNames` 对照表）算出 matcher：内置的工具前规则和 `plan-pace` 只关心改文件、跑命令，Read / Grep / Glob 就不触发。用户自己配了「任意工具」的钩子时照旧全装。
  2. **PostToolUse 同理**：只在有钩子用到工具后事件、且只对相关工具装。
  3. 更彻底的做法是把转发脚本换成常驻进程或 Claude Code 支持的 HTTP 类型钩子（如果当前版本支持，需要先确认版本和 `minVersion`），每次只剩一次本机 HTTP。
- Command Code、Pi 的钩子写在进程内的扩展里（`shared/hook-mod.ts`），是本机 fetch，**没有这个问题**。

### 4.2 结束前钩子没拦住，多了一轮提醒

- 现状（导出 ①）：01:01:11 模型说完一段就结束了这一轮，01:01:25 面板发了「【面板】你的计划才做了 4/8……」提醒，又开了一轮。按 ADR 0049 的设计，这种情况应该由结束前钩子（Stop）在同一轮里拦住，不用另起一轮。
- 多一轮的代价：一次额外的首包 + 14 秒左右的间隔。
- 需要查：这次为什么没走钩子（版本低于 `minVersion`？这一轮没挂编排工具？钩子超时放行？）。日志里会有「结束前钩子：…」一行，要对话的 `.log` 才能确认。**是否是 bug 待日志确认**。

### 4.3 Claude Code 的辅助请求（待实测）

- Claude Code 除了主请求，还会发一些辅助的小模型请求（例如生成标题、判断 Bash 命令前缀）。经第三方网关时，这些请求可能映射到主模型、或失败后重试，和主请求抢时间。
- 导出 ① 里 Bash 的最短耗时（323 ms）比 Read（229 ms）多约 100 ms，可能就是这一类开销，但证据不足。
- 可做的：先抓一次 Claude Code 的请求轨迹确认有没有这类请求；有的话评估设置 Claude Code 关闭非必要请求的环境变量（变量名以所装版本的文档为准），写进 CLI 定义的 `env`。

## 5. 不建议做的

- **为了省时间关掉面板钩子**：省下的 4% 不值得丢掉只读保护、分支越界保护。用 matcher 缩小范围就够了。
- **为了提速在一轮中途换强度或模型**：要重开进程，缓存全丢，大概率更慢。
- **把工具结果截短再交给模型**：省 token 不省时间（缓存命中后处理成本很低），还会让模型反复重读。

## 6. 建议的顺序

| 优先 | 项                                             | 改什么            | 预估收益（以导出 ① 为例）        | 风险 / 需决定              |
| ---- | ---------------------------------------------- | ----------------- | -------------------------------- | -------------------------- |
| 1    | 2.2-3 会话栏显示首包时间（观测）               | 代码，小          | 不直接提速，后面所有优化靠它验证 | 无                         |
| 2    | 2.1-1 动手类角色降一档强度                     | 配置              | 15–25%                           | 复杂任务质量，需用户判断   |
| 3    | 2.2-1 换直连 / 更快的链路                      | 配置              | 每步省 1–2 秒，约 1–2 分钟 / 轮  | 取决于可用的接口           |
| 4    | 2.3 提示词要求并行读文件                       | 内置角色提示词    | 15–30 秒 / 轮                    | 小                         |
| 5    | 4.1 钩子按工具过滤                             | 代码，中          | 约 4%，17 秒 / 轮                | 用户钩子匹配范围要算对     |
| 6    | 4.2 查清结束前钩子为什么没拦住                 | 先查日志          | 每次少一轮（约 15 秒）           | 先确认是不是 bug           |
| 7    | 3.1 先开分支再调研 / 3.2 依赖提前复制          | 代码 + 流程，较大 | 每次开分支 10–30 秒              | 涉及 ADR 0023 流程，需决定 |
| 8    | 2.2-2 API 测速、2.4 预热时暖缓存、4.3 辅助请求 | 代码，中          | 视链路而定                       | 2.4 有 token 成本          |

第 1、4、5 项改动小、风险低，可以先做；第 2、3 项是配置，用户自己就能试；第 6 项要先看日志；第 7、8 项需要先定方案。
