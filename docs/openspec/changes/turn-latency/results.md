# 对话提速：实测对比与剩下的问题（待确认）

> 状态：`design.md` 里用户选定的几项已经实现（提交 f3b92b6 起，PR fixcode-h/agent-panel#201）。本文是改动前后的真实对比，
> 以及还剩下、需要用户拍板的时间问题。现状按 2026-11-04 的 `dev` 核对。

## 1. 怎么测的

- 环境：云端 Linux 容器；面板用临时数据目录起一份；Claude Code 2.1.318；模型 `deepseek-v4.1-flash`，强度 high。
- 接口：用户给的中转站，Anthropic 协议（Claude Code 只支持这一种）。中间加了一个本机记录代理，记下每个请求从发出到第一个字节的时间。这样量出来的首包不依赖面板自己的计时。
- 任务：被测项目固定在提交 382461f。提示词固定为同一条只读调研：「调查面板给 Claude Code 装工具钩子的完整链路……只读代码，不要修改任何文件」。
- 改动前、改动后各跑一次。模型每次走的步数不一样，中转站的响应速度也随时段变化，所以只有和面板改动直接相关的指标能一对一比较，其余的看趋势。

## 2. 结果

| 指标                           | 改动前                   | 改动后             | 说明                                                                                     |
| ------------------------------ | ------------------------ | ------------------ | ---------------------------------------------------------------------------------------- |
| 整轮用时                       | 800 秒                   | 372 秒             | 含模型随机性和接口波动，不全是改动的功劳（见下）                                         |
| 模型请求次数                   | 35                       | 25                 | 每步平均调工具数两次都是 1.8，少的 10 次主要是模型这次少走了几步                         |
| 工具调用                       | 63 次，合计 16.5 秒      | 45 次，合计 3.8 秒 |                                                                                          |
| 单次 Bash 中位 / 最快          | 243 / 199 ms             | 77 / 57 ms         | **钩子改成直接请求面板**，每次省约 0.17 秒                                               |
| 单次 Read                      | 约 230 ms（导出 ① 实测） | 30 ms              | **钩子按工具过滤**，读文件不再跑钩子（另跑的一轮小任务里测到）                           |
| 首包（代理量）中位 / 合计      | 20.3 秒 / 593 秒         | 8.9 秒 / 240 秒    | **接口这边的波动**：两次的请求内容和大小相近（81→438 KB 和 81→407 KB），面板没改请求本身 |
| 首包（面板记录）中位           | 0.24 秒                  | 9.1 秒             | 面板以前算错了：从模型回出第一段才开始算。改后和代理量的一致                             |
| 思考合计                       | 49 秒                    | 72 秒              | 模型随机                                                                                 |
| 一轮结束后多开的「面板提醒」轮 | 0                        | 0                  | 结束前钩子都在同一轮里拦住、接着做                                                       |

能确定算在这次改动上的：

- **工具开销降到原来的约四分之一。** Bash 每次省约 0.17 秒，读文件每次省约 0.2 秒。按导出 ① 的 76 次工具调用算，一轮省 13–15 秒。Windows 上起 node 进程更慢，省得应该更多；这一点是推测，没在 Windows 上实测。
- **首包计时变准了。** 会话栏「模型响应」和状态诊断里的数，现在和真实等待一致。以前显示零点几秒，实际要等 5–20 秒。

不能算在这次改动上的：

- **首包从 20 秒降到 9 秒。** 这是中转站在两个时段的响应速度不同。同一份 3.7 万 token 的请求单独测，前后也在 12–16 秒之间浮动。
- **整轮用时减半。** 主要来自上面的首包波动，加上模型这次少走了 10 步。

只在单测里验证、这次基准没覆盖到的（基准任务只读，不改代码、不开分支）：

- 开独立分支用备用依赖副本；
- `create_conversation` 带 `edits` 时开工前就开好分支；
- 预热的进程也装钩子。

## 3. 4.3 Claude Code 的辅助请求

- 按面板默认的权限（「自动接受改文件」）跑了一轮小任务，代理记下的所有请求里，这一轮中间 Claude Code 自己没有发任何辅助请求（标题生成、命令前缀判断这类）。
- 唯一一个不带工具的请求，是面板在这一轮**结束后**自动起标题：约 1 秒，不在对话的等待时间里。
- 结论：不需要改 Claude Code 的环境变量。

## 4. 这次顺手修掉的

- **钩子拦住后接着做的那次请求，首包只记了零点几秒。** 「交出去」的时刻没记上，现在钩子拦住时补记一笔（`server/hooks/dispatch.ts`）。
- **预热起的进程没有任何钩子。** 开独立分支后在新目录重开也是预热，所以那之后的轮次连只读保护、分支越界保护都不生效。不只是「多一轮提醒」的问题，见 PR 说明。

## 5. 剩下的时间问题（待确认）

按对整轮用时的影响从大到小排：

### D1 中转站的 Anthropic 协议首包慢：占整轮用时的 65–74%

实测数据（同一中转站、同一模型、约 3.7 万 token 的输入）：

| 协议                             | 小请求首个内容 | 大请求首个内容                 |
| -------------------------------- | -------------- | ------------------------------ |
| OpenAI（`/v1/chat/completions`） | 0.8–1.4 秒     | 1.7–2.8 秒                     |
| Anthropic（`/v1/messages`）      | 1.1–1.5 秒     | 13–16 秒（基准里一度到 20 秒） |

开不开思考都一样，命中缓存（5.5 万 token）也一样。Claude Code 只能走 Anthropic 协议，所以每步都要多等 10 秒以上。面板代码改不了这一点，可选的做法：

- **a（推荐，不用改代码）：** 用这个中转站时，让 Command Code 或 Pi 走 OpenAI 协议。在 Agent 设置里选这个 API 的 OpenAI 协议即可。设置 › API 的「测速」可以先对比。
- **b：** 把大请求慢的现象反馈给中转站：同一模型两种协议差出 5–10 倍，像是 Anthropic 协议那一路在做格式转换或排队。
- **c（不推荐先做）：** 面板自己做一层 Anthropic→OpenAI 的本地转换代理，让 Claude Code 也走 OpenAI 端点。思考、工具调用、缓存的格式都要转，出错面大，要单独评估。

### D2 每一步都重发整段上下文，首包跟着上下文变长

请求体从 81 KB 涨到 438 KB。在慢的那条路上，首包也跟着从 7 秒涨到 20 秒（基准的前几步：7.1 → 6.2 → 3.6 → 11.0 → 12.2 → 12.7 → 17.0 秒）。

- **可选：** 把自动压缩的门槛从 70% 调低（Claude Code 的上下文窗口按 20 万算）；或者让父对话更早把大任务拆给子对话。代价是压缩本身要花一次请求，还会丢细节。要不要调、调到多少，需要决定。

### D3 思考强度

这次基准里思考占 10–20%；用户的导出 ① 里占 42%（单次最长 30 秒）。

- **可选：** 「执行」这类动手的角色默认用中档，或者高档的强度降一级。这是质量和速度的取舍，需要用户定。

### D4 新开对话的第一次请求冷启动

导出 ② 的第一个请求等了 5.1 秒，之后约 2 秒。

- **可选：** 预热时发一个极小的请求，把连接和缓存暖起来。每次打开对话都要多付一次缓存写入的 token，建议做成默认关闭的设置项。要不要做需要决定。

### D5 Codex 的钩子（已做，2026-11-05）

用户确认后改成通用做法，按顺序选：

1. CLI 支持 HTTP 钩子：直接请求面板（Claude Code 2.1.318 起）。
2. 不支持、本机有 curl：调转发脚本的命令自动换成 curl 直接 POST 到面板（Codex、老版本 Claude Code）。
3. 都没有：照旧用 node 转发脚本。

Codex 0.166 实测：每次钩子 11–17 ms，原来 81–134 ms；拒绝照常生效。Codex 自带的 `mcp_tool` 钩子不把工具名和参数交给面板，守卫没法判断，所以不用它。Pi、Command Code 的钩子本来就在 CLI 进程里直接请求面板，不用改。Windows 上用系统自带的 `curl.exe`，没实测。

### D6 本机测试环境

本地 e2e 的 `browser` 分片和界面检查起不来：本机 Playwright 的浏览器版本对不上，是容器环境的问题，不是代码问题，CI 上照常跑。

## 6. 复现

基准脚本不进仓库（它要带密钥）。做法是：

1. 用临时数据目录起面板；
2. 设置里加一个指向本机记录代理的 API，代理再转发到中转站；
3. 新建项目和对话，跑同一条提示词；
4. 结束后读对话日志里的「模型开始输出 waitedMs」和代理的记录。
