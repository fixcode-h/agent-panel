# 协调器与「文档优先」：角色架构重新设计（设计稿）

状态：草案，待用户确认 · 2026-11-03 · 不含代码改动

## 0. 一页结论

1. **主理改名「协调器」**（key 仍是 `orchestrator`，不迁移数据），定位收窄为「入口 + 定位 + 路由 + 汇总 + 对外动作」：只读文档和目录，不读实现、不排查、不出方案。
2. **先分析、再查文档**：协调器不是一收到消息就查。先判断这条消息要不要定位（闲聊、问面板用法、回答子对话的提问都不用），要的话先从用户原话里提炼关键词（模块名、类名、术语、点名的路径、报错里的文件名和日志类别），再用这些关键词调 `find_module`。
3. **大项目不靠 `/initDocs`，也不靠 rg 扫全仓**：面板在本机建一份**结构索引**（缓存，不进仓库）。模块骨架直接从构建清单读（UE 的 `*.uproject` / `*.uplugin` / `Build.cs`，Node workspaces 等），不用 AI；文件路径表从版本控制拿（`git ls-files` 等），之后只做增量；UE 项目另在后台扫头文件里的声明，建一张类名表。定位分三级：模块文档 → 结构索引 → 只在候选模块目录里搜，没有全仓搜索这一步。`/initDocs` 降为可选命令，只负责给模块补一句话职责（§5）。
   **Bug 记录只落用户报的**：`bugs/<id>.md → bugs.md` 的做法不变；能不能写由面板按 Bug 的来源判断，评审、测试、自测发现的问题没有入口写成 Bug 记录（§7.1）。
4. **文档优先**：协调器要开子对话时，在 `create_conversation` 里写 `modules`。目标模块只有索引、还没模块文档时，**面板**先派「文档」建简要模块文档，建完再启动子对话，并把文档路径附进派单。这一步靠面板执行，不靠协调器记得。
5. **存储用 Markdown，不用 SQL**：每个模块一个 `modules/<模块>/README.md`，开头的元数据头是唯一来源；`MODULE-MAP.md` 改成生成物（和现在的 `bugs.md` 同一套做法）；面板在内存里缓存索引，供 `find_module` 查询，随时可以重建。
6. **模块删了，文档跟着删**：面板在合回、`find_module`、`/initDocs` 三个时机检查 `source_paths` 还在不在；源码全没了就交「文档」删目录、重新生成地图。改名 / 移动走更新，不走删除。
7. **去掉重复的规则**：同一条规则现在散在角色设定、面板提示词、技能里，最多的写了 7–9 处，已经出现互相矛盾（见 §2.3-B）。按「面板管必须、角色管职责、技能管做法」三层，每条规则只留一个出处。协调器的设定预计从约 5800 字压到 2000 字以内。
8. **模块文档只有「文档」一个出口**：调研、子任务不再自己写模块文档，只交结论。

## 1. 背景与要求

用户 2026-11-03 提出：

- 主理改名为协调器。
- 协调器分析用户消息时，先从文档里找对应的模块。
- 要有一个 `initDocs` 命令初始化项目文档：只是**极简**的初始化，把模块找出来，简单描述模块做什么、代码在哪，不细看代码，方便以后快速定位。
- 模块还没有模块文档时，协调器先派子任务建模块文档，建完再创建子对话交给它。
- 模块删除时，对应文档也要删除。
- 模块文档不要太细。
- 评估存储形式（SQL 数据库、Markdown 或其他）。
- 评估父对话 / 子对话角色设计是否合理、流程是否贯通、定义分散多处会不会互相偏移；列出可优化、缺少、可删除、繁杂多余的步骤；重新设计角色架构、划定能力范围、和技能结合起来。
- 先出设计文档，不改代码。

同日补充：

- Bug 记录（`bugs/<id>.md → bugs.md`）只落用户报的，Agent 自己评审发现的不落。
- `find_module` 不是一收到消息就调：先分析出要查哪些关键词再调。
- UE 这类大项目 `initDocs` 不好用，要别的方案；不要靠 rg 强制遍历，太耗时间。

### 2.2 现在一条消息怎么走

```
用户消息 → 主理：理解（「只收集到模块为止」，自己决定读不读 MODULE-MAP）
        → 澄清 → 分诊表 → create_conversation / send / spawn / 就地改 / 自己答
子对话（执行）：复述 → 实现计划 → [自己读 MODULE-MAP + 模块 README] → 改 → 快速检查
        → 派评审 → 处置 → 完整测试 → 收尾前「判断要不要派文档」→ submit_merge
父对话：finish_child → 汇总
```

| 子对话的完成标准           | 通用约束两节、执行「版本管理」、engine「子对话的完成标准」（4）                                                                                                                                     | engine 写了「和角色设定里写的不一样时以这里为准」——说明已经知道会不一样      |

根因：没有约定「哪类规则写在哪一层」。面板机制（工具返回什么、门禁拦什么）写进了角色设定；角色职责写进了面板提示词；做法细则（找 Bug、写代码、评审循环）抄进了角色设定，又在技能里写了一份。

#### C. 繁杂、冗长

- 主理设定约 5800 字（17.5 KB），每轮常驻；engine 还在后面追加约 2000 字的「你的定位」和隔离方式说明。
- 执行设定本体约 4400 字，加上嵌入的 `IMPL_PLAN_TEXT`、`CODING_TEXT`、`BUG_METHOD`、`LOG_TIMELINE_TEXT`、`SELF_CHECK_TEXT`，总量超过一万字；而 ADR 0023 的原则是「高级角色挂载基本角色，不要把能力的做法抄进它的设定」——执行恰好把「开发」的做法整段抄了进来，`developer` 角色里又有一份。
- 主理挂了 `analyst`（方案设计）为「澄清和分诊时就地用」，方案设计会往实现细节里挖，和「只收集到模块为止」方向相反。
- 大方案派单前有两道关：「大改动先确认」（问用户）+ 挂载 `reviewer`「大方案派单前独立复核」。
- 主理和执行两处都写了「测试验收·设计用例 / 清理用例」的用法和参数。
- 「派单的粒度」里让模型自己写 `tier: "low"`：这是面板能按角色默认档位决定的事。
- 执行接单「先复述」和「实现计划」的第一节「目标与验收」内容重复。

#### D. 命名容易混

`analyzer`「分析」/ `analyst`「方案设计」key 只差两个字母；`helper`「子任务」/ `explorer`「调研」都是只读调研、都能回写文档；`worker`「执行」/ `developer`「开发」都写代码。主理改名协调器是个机会，顺带把这几处讲清楚（见 §8）。

## 3. 设计原则：三层，每条规则只有一个出处

| 层                                         | 管什么                                                         | 例子                                                                                   | 不放什么               |
| ------------------------------------------ | -------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ---------------------- |
| **面板**（工具、工具返回、门禁、自动步骤） | 必须照做、能用程序判断的：调用顺序、前置条件、状态流转、生成物 | 评审门禁、收尾步骤、`find_module`、文档优先、模块删除检测、send 的返回值自带下一步说明 | 「你是谁、该怎么想」   |
| **角色设定**                               | 我是谁、管哪段、交给谁、交付什么、不做什么                     | 协调器的分诊表、执行的收尾顺序（只列步骤名）                                           | 工具用法细节、做法细则 |
| **技能**                                   | 某类工作的具体做法，按需加载                                   | 找 Bug 的方法、写代码规范、模块文档的格式                                              | 角色边界、面板机制     |

约束：

1. 同一条规则只在一层写全文，别处最多一行指针（「按 project-documentation 的『模块文档』」）。
2. 能写成面板判断的，删掉对应提示词（`docs/lessons/plan.md`「必须照做的规则交给面板执行」）。
3. 加一条检查：`scripts/rules-check.mjs` 对内置角色设定、`engine.ts` 提示词、`skills/` 做长句去重，同一句（≥ 30 字）出现两次以上报错（白名单登记例外）。

## 4. 模块文档：存储和格式

### 4.1 选型

| 方案                                                | 优点                                                                                                           | 缺点                                                                                                                                                                                                  | 结论                 |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| SQLite / SQL 数据库                                 | 查询方便、并发写安全                                                                                           | Agent 只能通过工具读，用户直接用 Claude Code / Codex 打开项目时看不到；不能 git diff、评审、合并；P4 / SVN 项目外的文档根也要另存；要做 schema 迁移；放在数据目录就和项目代码脱节，换台机器文档就没了 | 不用                 |
| 单个 JSON 索引文件                                  | 机器好读                                                                                                       | 人读不了；并行改同一个文件必冲突；描述写在 JSON 里不好维护                                                                                                                                            | 不用                 |
| Markdown（现状：手写地图 + 模块 README）            | 人和 Agent 都能读；跟代码走版本控制                                                                            | 地图手写，并行冲突；状态靠模型维护，已漂移                                                                                                                                                            | 保留形式，改维护方式 |
| **Markdown 为准 + 地图生成 + 面板内存索引**（推荐） | 保留 Markdown 的全部好处；每个模块一个文件，并行不冲突；地图是生成物；面板解析出索引供工具查询，确定、省 token | 要写一个解析 / 生成器（面板里，不依赖项目脚本）                                                                                                                                                       | **采用**             |

要点：真相只有一份，就是各模块 README 的元数据头；`MODULE-MAP.md` 和面板的内存索引都从它生成，坏了随时重建。这和 `bugs/<id>.md → bugs.md` 是同一个做法，项目里已经验证过。

### 4.2 两级文档、三个状态

| 状态         | 谁产生                                                                          | 内容                                        | 协调器怎么看                                                       |
| ------------ | ------------------------------------------------------------------------------- | ------------------------------------------- | ------------------------------------------------------------------ |
| `indexed`    | `/initDocs`（可选）                                                             | 只有元数据头 + 一句话职责（约 8 行）        | 能定位，但「没有模块文档」：开子对话前要先建                       |
| `documented` | 「文档」建模块文档                                                              | 元数据头 + 固定几节（见 4.3），上限约 80 行 | 有文档，直接派                                                     |
| `stale`      | 面板检测（源码在 `verified_commit` 之后改动很多）或任何角色发现文档和代码对不上 | 内容保留                                    | 当作有文档，但派单里附一句「文档可能过期」；子对话收尾时交文档刷新 |

还有一种情况不是状态：模块只在结构索引（§5.3）里、还没有 README。协调器把它当成和 `indexed` 一样——能定位，开子对话前要先建文档。大项目的大多数模块一直停在这里，这是正常的。

去掉的：`inferred`、`analyzed`、`confirmed`、`verified`（合并成 `documented`，没人会真的去「人工确认」，留着只会漂移）；`retired`（模块没了就删，不留墓碑，迁移线索写进接手模块的 README）。

### 4.3 格式

元数据头沿用现在 Bug 详情的写法（标题之后、第一个 `## ` 之前的列表行），不引入 YAML，脚本只读这一块：

```md
# web：React 前端

- 状态：documented
- 职责：项目、任务、工作流、角色等页面，流程图画布和对话输出
- 源码：`web/`
- 入口：`web/src/main.tsx`、`web/src/App.tsx`
- 关键词：页面、侧栏、对话页、流程图、设置
- 依赖：shared
- 更新：2026-11-03 · a1b2c3d
```

`documented` 的正文只有这几节，每节写不出内容就不写：

| 节                | 写什么                             | 上限  |
| ----------------- | ---------------------------------- | ----- |
| 做什么 / 不做什么 | 职责边界，和相邻模块的分界         | 5 行  |
| 关键文件          | 路径 + 一句话，按「先读哪个」排    | 10 条 |
| 对外接口与数据流  | 别的模块怎么调它、数据从哪来到哪去 | 8 行  |
| 改这里要注意      | 易错点、隐含约束                   | 8 条  |
| 怎么验证          | 相关测试命令 / 用例位置            | 5 行  |

不写：实现细节、逐函数说明、变更历史（历史在 git 和 ADR 里）。现在 `web` 那样拆成十个子页面的做法不再推荐；已有的子页面保留，不强制迁移。

### 4.4 `MODULE-MAP.md` 改成生成物

- 面板（`server/`）带一个生成器：扫 `DOC_ROOT/modules/*/README.md` 的元数据头，按模块名排序写出地图表（模块、源码、职责、入口、状态、文档链接），文件头写「生成物，不要手改」。
- 地图上方保留一段手写区（依赖方向、「不容易发现位置的改动」这类跨模块说明），生成器只重写标记之间的表格。
- 本仓库的 `scripts/rules-check.mjs` 第 7 条改成调用同一个生成器的 `--check`，和 `docs:bugs` 一样。
- 冲突处理：以任意一边为准重新生成，不手工合表。

### 4.5 面板工具

工具给协调器和执行用（orch-mcp），背后是 §5 的三级定位：

| 工具               | 参数                                                                                                                                              | 返回                                                                                                                                                            |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `find_module`      | `keywords`（协调器提炼的关键词，必填，1–10 个）、`paths`（用户点名的路径，可选）、`errorText`（报错原文，可选，面板从里面抽路径、类名、日志类别） | 候选模块（最多 5 个，按匹配度排）：名字、职责、源码、文档状态、文档路径、**匹配理由**（命中了哪一级、哪个关键词）、最相关的几个文件；`missing` 表示源码已经不在 |
| `search_in_module` | `module`、`pattern`、可选 `glob`                                                                                                                  | 只在这个模块的源码目录里搜，带排除清单和超时（默认 10 秒）；超时返回已搜到的部分并写明                                                                          |
| `list_modules`     | —                                                                                                                                                 | 全部模块，一行一个（看全貌时用，平时不用）                                                                                                                      |

不提供全仓搜索工具。通用约束「搜索范围」那一大段改成一句：「先 `find_module`，再 `search_in_module`；不要在项目根跑 rg / grep / find。」

## 5. 定位：大项目不靠 `/initDocs`，也不扫全仓

### 5.1 为什么 `/initDocs` 在大项目不好用

- UE 项目的 `Source/` 和 `Plugins/` 里少则几十个、多则上百个 C++ 模块，加上 Lua 脚本目录，文件动辄十几万；`Content/` 里的资源能有上百 GB。划「3–15 个模块」太粗，定位不到；划细了，AI 要看的目录树本身就很长，跑一次贵、跑完也会过时。
- rg / grep 全仓：一次几十秒到几分钟，而且每个子对话、每个子任务都会重新扫一遍，时间和 token 都花在重复劳动上。
- 大项目里真正会被改到的只是一小部分模块，给全部模块一次性写文档，大半用不上。

所以大项目的思路反过来：**结构信息由面板用程序拿，不用 AI；文档只给用到的模块建。**

### 5.2 三级定位

| 级            | 是什么                                         | 来源                                | 成本                   | 命中什么                                         |
| ------------- | ---------------------------------------------- | ----------------------------------- | ---------------------- | ------------------------------------------------ |
| L1 模块文档   | 模块 README 的元数据（职责、关键词、源码路径） | §4                                  | 内存查找               | 业务术语、功能名（「背包」「登录」「技能冷却」） |
| L2 结构索引   | 模块骨架 + 文件路径表 + 声明表（可选）         | 面板本机缓存，见 5.3                | 内存查找，建索引在后台 | 类名、文件名、模块名、日志类别、路径片段         |
| L3 模块内搜索 | `search_in_module`                             | 只在 L1 / L2 给出的候选模块目录里搜 | 秒级，有超时           | 报错原文、字符串常量这类只在文件内容里有的       |

按顺序查，前一级命中就不往下走。L3 只在候选模块的目录里跑，没有全仓搜索这一级。

### 5.3 结构索引（L2）怎么建

**模块骨架：直接读构建清单，不用 AI、不读源码**

| 项目类型  | 读什么                                                                                                                                                              | 得到                                                            |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| UE        | `*.uproject` 和各 `*.uplugin` 的 `Modules[]`（JSON）；每个模块的 `<模块>.Build.cs` 只读依赖那几行（`PublicDependencyModuleNames` / `PrivateDependencyModuleNames`） | 模块名、类型（Runtime / Editor…）、所属插件、源码目录、依赖关系 |
| UE Lua    | 项目配置的 Lua 根目录下的一级功能目录                                                                                                                               | 按功能目录划的模块                                              |
| Node / TS | `package.json` 的 `workspaces`、`pnpm-workspace.yaml`；单包项目用一级目录                                                                                           | 包和目录                                                        |
| 其他      | `Cargo.toml` workspace、`go.work`、`.sln` 里的 `.csproj`、CMake 的 `add_subdirectory`                                                                               | 同上                                                            |

这些文件就是项目对「模块」最权威的定义，读出来是确定的，几十毫秒。UE 项目默认只把项目自己的模块（`Source/` 和项目插件）当成「项目模块」；引擎、第三方和市场插件只登记路径，能查到但不建文档。

**文件路径表：从版本控制拿，之后只做增量**

- Git：`git ls-files`（读 git 的索引，不走磁盘，十几万个文件 1 秒左右）；之后按上次记下的 HEAD 跑 `git diff --name-status` 加 `git status` 增量更新。
- P4：首次 `p4 have`（只列本机已同步的文件）；之后用文件监听增量。
- SVN / 没有版本控制：首次按搜索排除清单在后台遍历一次（跳过 `Binaries`、`Intermediate`、`Saved`、`DerivedDataCache`、`Content` 等）；之后用文件监听（Windows、macOS 支持递归监听）加 mtime 增量。
- 只存路径。按路径段和文件名建倒排，驼峰拆词：`UInventoryComponent.h` 可以用「inventory」「component」查到。

**声明表（可选，UE 项目默认开）**

- 后台低优先级只扫头文件里的声明行：UE 的 `UCLASS` / `USTRUCT` / `UENUM` / `UINTERFACE` 后面的类型名、`DECLARE_LOG_CATEGORY_EXTERN` / `DEFINE_LOG_CATEGORY` 的日志类别；TS 的 `export class / function / const`。按 mtime 增量，不读实现。
- 日志类别很关键：UE 的报错日志都带 `LogXxx:`，查声明表就能直接对到定义它的模块，不用拿报错原文去搜。

**存在哪**

结构索引是缓存，不是文档：放在数据目录（`~/.agent-panel/index/<项目 id>/`），按模块分片的 JSON，启动时读进内存。删了能重建，不进仓库，也不在 P4 / SVN 里纳管。§4.1 不用数据库，说的是文档；这里是本机缓存，以后要换成 SQLite（Node 自带的 `node:sqlite` 稳定以后）也只是换存储，不影响别的部分。

**路径对到模块**：用最长前缀匹配到骨架里的模块目录（UE 按 `Build.cs` 所在的目录）。

### 5.4 什么时候建、谁来建

- 打开项目时面板在后台建（或增量更新）结构索引，界面角落显示进度；建好之前 `find_module` 只查 L1，结果里写明「结构索引还在建」。
- 模块文档**按需建**：只有协调器要把某个模块交给子对话、而它还没有模块文档时才建（§6.2）。没碰过的模块永远不用花钱。
- `/initDocs` 降为可选：在 L2 骨架上给项目模块批量补一句话职责（低档模型，只看模块名、依赖和目录名，不读源码），写成 `indexed` 的元数据头。中小项目想一次看到全貌时用；UE 大项目不需要先跑它。
- 「AI 初始化项目」里的文档部分改成：建结构索引 + 可选跑一次 `/initDocs`，不再给每个模块写长篇 README。

### 5.5 越用越准

- 子对话合回时，面板知道这次协调器用了哪些关键词、改动实际落在哪些模块（来自 diff）。收尾清单里列出「关键词 → 模块」的对应，「文档」刷新模块文档时顺手把用得上的关键词补进「关键词」一行（每个模块最多 20 个）。下次同类问题在 L1 就能命中。
- L1 没命中、靠 L2 / L3 找到的，同样补。

### 5.6 大模块再细一层：区域，不再拆文档

UE 的一个模块里可能有几百个文件。模块 README 的「关键文件」一节允许写成「区域」：`Private/Inventory/` 一行一句话，最多 15 行。不为区域单独建文档；协调器派单时 `modules` 写模块，`files` 写区域目录。

## 6. 协调器：新的处理流程

### 6.1 流程

```
用户消息
  │
  ├─ 1 理解：一句话复述；看现有子对话，判断是不是某个子对话的后续
  │          不需要定位的到这里就直接去分诊：闲聊、讨论、问面板怎么用、回答子对话的提问、
  │          某个子对话的后续（它自己有上下文）
  ├─ 2 提炼关键词（写在回复里，也记进 route.keywords，分诊卡上能看到）：
  │          用户点名的模块 / 路径 / 类名；业务术语（中英文各一份，如「背包 / inventory」）；
  │          报错原文里的文件路径、类名、日志类别（LogXxx）；截图、日志附件里的同类信息
  │          提炼不出关键词、消息太含糊 → 先澄清，不拿整句话去查
  ├─ 3 定位：find_module(keywords, paths, errorText) → 候选模块 + 匹配理由 + 文档状态
  │          候选不止一个 → 按匹配理由选，选不出来就问；都没命中 → 换一组关键词再查一次，
  │          还没命中就按目录判断，派单里写「索引未收录」
  ├─ 4 澄清：只在会做出不同交付物、缺验收标准、不可逆时问
  ├─ 5 分诊（命中即停）
  │     后续 → send_to_conversation
  │     问答 → 读模块文档 + 少量文件，自己答
  │     微改动 → 就地改（护栏不变）
  │     只读调研 / 文档 → spawn_agents
  │     要改代码 → create_conversation(modules=[…], keywords=[…])
  │                 └─ 面板：模块还没有模块文档 → 先派「文档·建模块文档」→ 完成后启动子对话
  ├─ 6 派发后本轮结束，等推回
  └─ 7 汇总：按证据转述；合回结果里带「模块已删除 / 文档要刷新」时派「文档」
```

提炼关键词是协调器自己的判断，不由面板替它做：面板没法理解「技能冷却不对」指的是哪套系统；但面板会在 `find_module` 返回里写清命中了哪一级、哪个词，提炼得不好时协调器能看出来再换一组。

### 6.2 文档优先由面板执行

`create_conversation` 新增 `modules`（模块名数组，项目有索引时必填）。面板拿到后：

1. 查索引：全部 `documented` / `stale` → 直接启动子对话，派单里自动附「模块文档：`docs/modules/<模块>/README.md`」，子对话不用再自己查地图。
2. 有还没有模块文档的（结构索引里有、没有 README，或只有 `indexed` 元数据头）→ 子对话先建好、状态「等文档」，面板同时派「文档」（`task=建模块文档`，每个模块一个子任务，并行），全部回来后再启动子对话；派单里附新文档路径。协调器这一轮照常结束，不用自己回来接力。
3. 同一个模块正在建文档时，后来的子对话排在同一个子任务后面，不重复建。
4. 建文档失败：子对话照样启动，派单里写「模块文档没建成：<原因>」，错误显示给用户（不悄悄重试，符合 AGENTS.md）。
5. 不在索引里的模块名：拒绝并返回候选（`find_module` 的结果），让协调器改正或明确写 `modules: []` 加理由。
6. 「文档」建模块文档时，派单里自动带上结构索引里这个模块的骨架（依赖、文件列表前 200 条、声明表里的类型名）和这次的关键词：它从入口和这些关键词相关的文件读起，按 §4.3 的上限写，不把整个模块读完。

项目参数（协调器的参数）`docsFirst`：`开子对话前`（默认）/ `总是`（`spawn_agents` 调研类也先建）/ `关闭`。Bug 和功能都走同一条，不区分。

为什么放面板：协调器设定里写「先派文档、等回来再建子对话」需要它跨两轮记住，正是 `docs/lessons/plan.md` 里「对话能不能走完不靠模型自觉」那类问题。

### 6.3 新的分诊表（替代现有那张）

| 情况                                                       | 去向                                                             |
| ---------------------------------------------------------- | ---------------------------------------------------------------- |
| 某个子对话的后续（追加要求、返工、验收没过、它提问的答案） | `send_to_conversation` 交回原子对话                              |
| 问答、解释、查一个事实                                     | 读模块文档和少量文件，自己答                                     |
| 改什么、改成什么已经清楚的微小改动                         | 就地微改动                                                       |
| 只读：跨模块调研、几个方向比较、核实结论                   | `spawn_agents`（调研 / 方案设计 / 评审）                         |
| 只写文档                                                   | `spawn_agents` 派「文档」，几份一次派完                          |
| 要改代码（功能、Bug、重构、迁移，或要按固定剧本做的）      | `create_conversation`，写 `modules`；要用工作流时 message 里点名 |
| 几件互不相关的交付                                         | 拆开并行（参数 `split`）；改的文件重叠就合成一个                 |
| 推送、PR、合并主干、发布                                   | 按「授权情况」自己做                                             |

派单正文的五个小节（目标 / 交付物与验收 / 范围 / 已知 / 假设）保留；Bug 派单的现象卡保留，压成一段。

### 6.4 协调器设定里删掉 / 移走的

| 现在的节                                         | 处理                                                                                                                 |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| 「交回子对话之后怎么确认它接到了」（约 900 字）  | 删。`send_to_conversation` 的返回文本自己写清「已送到，本轮结束，等推回」/「排队中，不用重发」/「失败：原因 + 建议」 |
| 「派单的粒度」里的 `tier: low` 和 token 说明     | 删 `tier` 一条（面板按被派角色的默认档位走）；token 说明压成一句                                                     |
| 「Bug 怎么交」后半段核对排查报告的细则           | 压成一句「按排查报告的『调用栈 / 证据链 / 验证』三项核对，缺了交回」；排查报告的格式归 systematic-debugging 技能     |
| 「守住一致·测试」里设计用例 / 清理用例的参数写法 | 只留在「测试验收」角色自己的设定里；协调器只写一句什么时候派                                                         |
| 「守住一致·文档」「Bug 记录只记用户报的」        | 删，归「文档」角色和 project-documentation                                                                           |
| 「提交和推送」「子对话的完成条件」               | 删，归通用约束「安全边界」一处                                                                                       |
| 「怎么回复用户」                                 | 保留，缩短                                                                                                           |
| 挂载 `analyst` 就地用                            | 改成只能派出（架构级方案），不在分诊时就地用                                                                         |
| 挂载 `reviewer`「大方案派单前复核」              | 删；大方案只保留「先给用户确认」一道                                                                                 |

engine 那边：内置协调器时，「你的定位」只留就地微改动的护栏数字和分支说明；「几个子对话都合进来之后…新建一个子对话去跑完整的测试」删掉（合回后的测试由面板自动跑，用户点名要整体回归时派「测试验收」，只留这一种说法）。

## 7. 模块删除与过期

| 时机                         | 面板做什么                                                                                                                                                                                                                             |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 子对话 `submit_merge` 合回后 | 按这次 diff 里删除 / 重命名的路径对照索引：某模块的 `源码` 全部消失且没有对应的重命名 → 合并结果里写「模块 X 的源码已删除」；有重命名 → 写「模块 X 的源码移到了 Y」。协调器看到后派「文档」（`task=清理`）删目录或改路径，重新生成地图 |
| `find_module`                | 命中的模块源码不存在时标 `missing`，协调器顺手派「文档·清理」                                                                                                                                                                          |
| `/initDocs` 增量运行         | 列出「将删除」，用户确认后删                                                                                                                                                                                                           |
| 子对话合回、改动落在某模块里 | 改动行数超过阈值（例如 200 行）或改了入口文件 → 把该模块标成 `stale`，合并结果提示「文档可能要刷新」；协调器决定要不要派文档（默认在执行收尾时已经顺带交过就不再派）                                                                   |

删除走「文档」角色而不是面板直接删：需要判断「是真删了还是并进别的模块」，迁移线索要写进接手模块。面板只负责发现和提示，确定的部分（地图重新生成）由面板做。

执行（子对话）收尾时的文档同步保持现有做法（`docsync` 挂成 `parent`，转交父对话创建），但触发由「自己判断」改成面板在收尾清单里列出「这次改到的模块：x、y；文档状态：…」，执行照着决定派不派。

结构索引（§5.3）也参与判断：构建清单里模块没了（`.uproject` / `.uplugin` 的 `Modules[]` 去掉了、`Build.cs` 删了、workspace 去掉了），比「目录还在不在」更准，UE 项目以它为准。

### 7.1 Bug 记录：只落用户报的

做法不变：一个 Bug 一个 `modules/<模块>/bugs/<bug-id>.md`，`bugs.md` 由它生成，不手改。变的是「能不能写」由面板按来源判断，不再靠八处提示词提醒。

| 环节                                                         | 怎么做                                                                                                                                                                                                |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 标来源                                                       | 协调器派 Bug 时，`create_conversation` 的 `route` 写 `kind: "bug"`，面板自动记下触发它的那条**用户消息** id。只有这样建出来的子对话（以及之后 `send_to_conversation` 交回它的续作）算「用户报的 Bug」 |
| 收尾清单                                                     | 只有「用户报的 Bug」子对话，合回时收尾清单里才出现「写 Bug 记录」一项，并带上用户原话、排查报告的根因 / 修复 / 回归测试                                                                               |
| 写入                                                         | 「文档」写 Bug 记录要用 `task=Bug 记录` 并带 `bugFrom`（子对话 id）；面板核对这个子对话的来源，不是用户报的就拒绝，并返回「这不是用户报的 Bug，写进交接摘要」                                         |
| 其他问题去哪                                                 | 评审意见、测试失败、自测、AI 排查时顺带发现的问题：写进交接摘要的「顺带发现」；值得长期记住的写进项目教训。它们没有通道进 `bugs/`                                                                     |
| 兜底                                                         | 「文档」这一轮结束时，面板看 diff：新增了 `bugs/*.md` 却没有对应的 `bugFrom`，在对话里显示一条警告给用户（不悄悄删，符合「错误一律显示给用户」）                                                      |

### 8.2 各位置的边界（一句话版，写进各自设定开头）

- **协调器**：我只读文档和目录，判断交给谁；要读代码才能回答的，交出去。

### 8.3 工作流和文档节点

## 17. 附：子对话请求收尾后父对话不动（用户 2026-11-03 报）

### 现象

子对话「面板提醒次数做成设置项（默认 6）」调用 `submit_merge` 后显示「待收尾」。父对话收到了【收尾请求】，也开了一轮：跑了 4 条命令，回复「改动核对通过……现在合回。」，然后这一轮就结束了，**没有调用 `finish_child`**。之后父对话一直停着，状态诊断报 `child-idle-parent-waiting`（计划还在等子对话，它们已经不在跑了，父对话却没被叫醒）。

### 根因：父子互相等，判定里没有人负责推

| 一方   | 它在等什么                                                                                                                            | 面板怎么看                                                                                                                                 |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 子对话 | `wrapRequest.state = 'requested'`，等父对话 `finish_child`                                                                            | `planStalled` 第 2 行：请求过收尾就不推（`shared/task.ts` 的 `planStalled`）——对，它确实在等别人                                           |
| 父对话 | 计划里等这个子对话的那一步是 `waiting`（`reportChild` 对「待收尾」只把那一步继续挂着等，`server/tasks/children.ts` 的 `reportChild`） | `planStalled` 看到计划里有 `waiting` 的步骤就返回 false，日志记 `step-waiting`，`nudgePlan` 不推（`server/tasks/drive.ts` 的 `nudgePlan`） |

父对话那一步写着「等子对话」，可子对话这时等的正是父对话自己：这个等待实际上是父对话自己要做的事（调 `finish_child` 或退回），被当成「在等别人」跳过了。和已修过的 `child-stuck-before-merge`（子对话说「现在收尾」没调 `submit_merge`）是同一类问题，发生在父对话这一边，当时只给子对话加了 `nudgeMerge`，父对话这边没有对应的兜底。

触发条件是模型提前结束回合：说了「现在合回」，这一轮却没有工具调用。CLI 照常报这一轮结束，面板按「在等子对话」处理，于是没人再动。

状态诊断（`shared/lifecycle.ts`）其实已经认出来了，但它只负责显示，没有接到任何恢复动作上。

另一条要排除的路径：收尾请求没送到父对话（`wakeTask` 交不出去，退回收件箱）。截图里父对话已经收到请求并回了话，不是这一条；诊断文件里父对话的「计划推进」日志应该是 `action: none, reason: step-waiting`，可以用它确认。

### 修法（等确认后做）

1. **判定改一处（`shared/task.ts`）**：新增 `waitsOnSelf(tk, kids)`：计划里在等的子对话已经是「待收尾」（`wrapRequest.state === 'requested'`）时，这个等待算父对话自己的事。`planStalled` 的「有在等的步骤」改成只认真在等别人的步骤。判定只有这一个出处，状态诊断、会话栏「状态」、推进逻辑都用它。
2. **父对话一轮结束时推一次（`server/tasks/drive.ts`）**：按上面的判定，父对话这一轮结束、有子对话待收尾、这一轮里没对它调用过 `finish_child` / `send_to_conversation`，就推一条：「子对话「X」在等你收尾：核对通过就调用 `finish_child`（id …），要补的用 `send_to_conversation` 交回。直接调用工具，不用先说明。」次数和计划推进共用 `nudgeMax`（刚做成设置项的那个）。
3. **推满了还不动，交给用户**：父对话里写一行警告，子对话行上「待收尾」旁边给一个「合回」按钮，由用户直接触发同一个 `finish_child`（错误照常显示给用户）。
4. **状态诊断分开说**：子对话是「待收尾」时不再报 `child-idle-parent-waiting`，改报 `wrapup-unhandled`：「子对话已请求收尾 N 分钟，父对话这一轮结束时没有合回，也没有退回」，并写明面板推过几次。
5. **兜底定时检查**：父对话空闲、有待收尾的子对话超过几分钟没处理（比如收尾请求进了收件箱、没开成新一轮），按第 2 条再推一次；同一个请求只推一次。
