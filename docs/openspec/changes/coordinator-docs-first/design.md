# 协调器与「文档优先」：角色架构重新设计（设计稿）

状态：草案，待用户确认 · 2026-11-03 · 不含代码改动

## 0. 一页结论

1. **主理改名「协调器」**（key 仍是 `orchestrator`，不迁移数据）：定位收窄为「入口 + 定位 + 路由 + 汇总 + 对外动作」。协调器只读模块文档和目录，不读实现、不排查、不出方案。
2. **先分析、再查文档**：收到消息后先判断要不要定位，要的话先从用户原话里提炼关键词，再去文档根的 `modules/` 下找有没有对应模块的文档。有就读，没有就是「这个模块还没分析过」。不建文件索引，不加新的查询工具，也不用 rg 扫全仓。
3. **模块文档按需建，不一次性全建**：没有 `/initDocs`。某个模块第一次要交给子对话时，如果还没有模块文档，先派一个「模块分析」子任务读这个模块、写出简要模块文档，写完再开子对话。以后的对话都先读这份文档，所以一个模块只在第一次花时间；没用到的模块永远不建。
4. **模块文档要简要**：一个模块一份 `modules/<模块>/README.md`，开头是几行元数据，正文最多约 80 行。`MODULE-MAP.md` 改成从这些元数据生成，里面只列建过文档的模块。存储用 Markdown，不用数据库。
5. **模块删了，文档跟着删**：子对话合回时，面板按模块文档里写的源码路径检查，路径全没了就交「文档」删目录、重新生成地图。
6. **Bug 记录只落用户报的**：`bugs/<id>.md → bugs.md` 的做法不变；能不能写由面板按 Bug 的来源判断，评审、测试、自测发现的问题没有入口写成 Bug 记录。
7. **去掉重复的规则**：同一条规则现在分散在角色设定、面板提示词和技能里，最多的写了 9 处，已经出现互相矛盾（§2.3-B）。按「面板管必须、角色管职责、技能管做法」分三层，每条规则只留一个出处。协调器的设定从约 5800 字压到 2000 字以内。
8. **附**：子对话请求收尾后父对话不动的根因和修法（§13）。

## 1. 背景与要求

用户 2026-11-03 提出：

- 主理改名为协调器；协调器分析用户消息时，先从文档里找对应的模块。
- 模块还没有模块文档时，先派子任务建模块文档，建完再创建子对话；模块删了，文档也删；模块文档不要太细。
- 评估存储形式（SQL 数据库、Markdown 或其他）。
- 评估父 / 子对话角色设计是否合理、流程是否贯通、定义分散多处会不会偏移；列出可优化、缺少、可删除、繁杂多余的步骤；重新划定角色能力范围，和技能结合。
- 先出设计文档，不改代码。

同日补充、调整：

- Bug 记录只落用户报的，Agent 自己评审发现的不落。
- 不是一收到消息就去查文档，先分析出要找哪些关键词再查。
- 不做文件索引、查询工具和 `/initDocs`：查文档就到模块文档目录下看有没有；分析子任务把分析过的模块写成文档，之后的对话优先查它；不给所有模块都建文档。
- 子对话请求收尾后父对话不动，一起分析原因。

## 2. 现状核对

### 2.1 角色和位置

| 位置             | 默认角色                                                    | 层                    | 主要设定所在                          |
| ---------------- | ----------------------------------------------------------- | --------------------- | ------------------------------------- |
| 项目对话（父）   | `orchestrator` 主理                                         | 高级                  | `shared/builtin/agents.ts` 341–502 行 |
| 子对话           | `worker` 执行                                               | 高级                  | `shared/builtin/agents.ts` 503–614 行 |
| 子任务（不点名） | `helper` 子任务                                             | 基本，只能派出        | `shared/builtin/agents.ts` 700–728 行 |
| 文档             | `docsync` 文档                                              | 基本，`runIn: parent` | `shared/builtin/agents.ts` 615–698 行 |
| AI 分析          | `analyzer` 分析                                             | 高级                  | `shared/builtin/agents.ts` 730–773 行 |
| 其他基本角色     | 调研、方案设计、评审、测试验收、版本控制、界面走查、本地化… | 基本                  | 同文件                                |

每轮注入父对话的不只是角色设定，`shared/engine.ts` 的 `conversationPrompt`（约 4067-4300 行）还会拼上「你的定位」「子对话各自在独立分支里改 / 共用一个目录」「现有子对话」等几段；内置主理只跳过「这条消息怎么处理」「分派前只收集到模块为止」两节（`ownDispatch`）。

### 2.2 现在一条消息怎么走

```
用户消息 → 主理：理解（「只收集到模块为止」，自己决定读不读 MODULE-MAP）
        → 澄清 → 分诊表 → create_conversation / send / spawn / 就地改 / 自己答
子对话（执行）：复述 → 实现计划 → [自己读 MODULE-MAP + 模块 README] → 改 → 快速检查
        → 派评审 → 处置 → 完整测试 → 收尾前「判断要不要派文档」→ submit_merge
父对话：finish_child → 汇总
```

#### B. 同一条规则定义在多处，已经互相偏移

| 推送 / 对外操作归谁        | 通用约束「安全边界」、主理两节、执行「版本管理」、engine「执行目录」「你的定位」、版本控制角色、project-vcs（7）                                                                                    | `docs/lessons/builtin.md` 已记过一次因此打架                                 |
| 子对话的完成标准           | 通用约束两节、执行「版本管理」、engine「子对话的完成标准」（4）                                                                                                                                     | engine 写了「和角色设定里写的不一样时以这里为准」——说明已经知道会不一样      |

根因：没有约定「哪类规则写在哪一层」。面板机制（工具返回什么、门禁拦什么）写进了角色设定；角色职责写进了面板提示词；做法细则（找 Bug、写代码、评审循环）抄进了角色设定，又在技能里写了一份。

#### C. 繁杂、冗长

- 主理设定约 5800 字（17.5 KB），每轮常驻；engine 还在后面追加约 2000 字的「你的定位」和隔离方式说明。
- 执行设定本体约 4400 字，加上嵌入的 `IMPL_PLAN_TEXT`、`CODING_TEXT`、`BUG_METHOD`、`LOG_TIMELINE_TEXT`、`SELF_CHECK_TEXT`，总量超过一万字；而 ADR 0023 的原则是「高级角色挂载基本角色，不要把能力的做法抄进它的设定」——执行恰好把「开发」的做法整段抄了进来，`developer` 角色里又有一份。
- 主理挂了 `analyst`（方案设计）为「澄清和分诊时就地用」，方案设计会往实现细节里挖，和「只收集到模块为止」方向相反。
- 大方案派单前有两道关：「大改动先确认」（问用户）+ 挂载 `reviewer`「大方案派单前独立复核」。
- 主理和执行两处都写了「测试验收·设计用例 / 清理用例」的用法和参数。
- 「派单的粒度」里让模型自己写 `tier: "low"`：这是面板能按角色默认档位决定的事。
- 执行接单「先复述」和「实现计划」的第一节「目标与验收」内容重复。

#### D. 命名容易混

`analyzer`「分析」/ `analyst`「方案设计」key 只差两个字母；`helper`「子任务」/ `explorer`「调研」都是只读调研、都能回写文档；`worker`「执行」/ `developer`「开发」都写代码。主理改名协调器是个机会，顺带把这几处讲清楚（见 §8）。

## 3. 设计原则：三层，每条规则只有一个出处

| 层                                         | 管什么                                                         | 例子                                                                              | 不放什么               |
| ------------------------------------------ | -------------------------------------------------------------- | --------------------------------------------------------------------------------- | ---------------------- |
| **面板**（工具、工具返回、门禁、自动步骤） | 必须照做、能用程序判断的：调用顺序、前置条件、状态流转、生成物 | 评审门禁、收尾步骤、先建文档再开子对话、模块删除检测、send 的返回值自带下一步说明 | 「你是谁、该怎么想」   |
| **角色设定**                               | 我是谁、管哪段、交给谁、交付什么、不做什么                     | 协调器的分诊表、执行的收尾顺序（只列步骤名）                                      | 工具用法细节、做法细则 |
| **技能**                                   | 某类工作的具体做法，按需加载                                   | 找 Bug 的方法、写代码规范、模块文档的格式                                         | 角色边界、面板机制     |

约束：

1. 同一条规则只在一层写全文，别处最多一行指针（「按 project-documentation 的『模块文档』」）。
2. 能写成面板判断的，删掉对应提示词（`docs/lessons/plan.md`「必须照做的规则交给面板执行」）。
3. 加一条检查：`scripts/rules-check.mjs` 对内置角色设定、`engine.ts` 提示词、`skills/` 做长句去重，同一句（≥ 30 字）出现两次以上报错（白名单登记例外）。

## 4. 模块文档：存储和格式

### 4.1 选型

| 方案                                             | 优点                                                                                                          | 缺点                                                                                                                                                            | 结论     |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| SQLite / SQL 数据库                              | 查询方便、并发写安全                                                                                          | Agent 要通过工具才能读，用户直接用 Claude Code / Codex 打开项目时看不到；不能 git diff、评审、合并；放在数据目录就和项目代码脱节，换台机器就没了；要维护 schema | 不用     |
| 单个 JSON 文件                                   | 机器好读                                                                                                      | 人读不了；并行改同一个文件必冲突                                                                                                                                | 不用     |
| **Markdown，一个模块一个文件，地图生成**（推荐） | 人和各家 CLI 直接能读；跟代码走版本控制；每个模块一个文件，几个子对话并行写不冲突；地图是生成物，不用手工维护 | 要写一个小生成器                                                                                                                                                | **采用** |

`MODULE-MAP.md` 现在是手写的大表，几个子对话同时收尾时都往里加行、改行，会冲突（`bugs.md` 以前也是这个问题，已经改成生成）。改成同一个做法：各模块 README 的元数据头是唯一来源，地图从它生成。

### 4.2 状态：只有两个

| 状态         | 含义                                                                               | 协调器怎么用                                                               |
| ------------ | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 没有文件     | 这个模块还没分析过                                                                 | 要交给子对话时先建文档                                                     |
| `documented` | 分析过，有简要文档                                                                 | 直接读、直接派                                                             |
| `stale`      | 代码变了不少、文档可能过期（面板在合回时标，或者任何角色发现文档和代码对不上时标） | 照样读，派单里写一句「文档可能过期」；这次的子对话收尾时顺带交「文档」刷新 |

去掉 `inferred`、`analyzed`、`confirmed`、`verified`、`retired`：没人会去「人工确认」，状态多了只会漂移（§2.3 A4）；模块没了就删，不留墓碑。

### 4.3 格式

元数据头沿用 Bug 详情的写法（标题之后、第一个 `## ` 之前的列表行），生成器只读这一块：

```md
# web：React 前端

- 状态：documented
- 职责：项目、任务、工作流、角色等页面，流程图画布和对话输出
- 源码：`web/`
- 入口：`web/src/main.tsx`、`web/src/App.tsx`
- 关键词：页面、侧栏、对话页、流程图、设置
- 依赖：shared
- 更新：2026-11-03 · a1b2c3d
```

正文只有这几节，写不出内容的节就不写，总共约 80 行以内：

| 节                | 写什么                                                                            | 上限  |
| ----------------- | --------------------------------------------------------------------------------- | ----- |
| 做什么 / 不做什么 | 职责边界，和相邻模块怎么分                                                        | 5 行  |
| 关键文件          | 路径 + 一句话，按「先读哪个」排；大模块写成区域（`Private/Inventory/`），一行一个 | 15 条 |
| 对外接口与数据流  | 别的模块怎么调它、数据从哪来到哪去                                                | 8 行  |
| 改这里要注意      | 易错点、隐含约束                                                                  | 8 条  |
| 怎么验证          | 相关测试命令 / 用例位置                                                           | 5 行  |

不写：实现细节、逐函数说明、变更历史（历史在 git 和 ADR 里）。

### 4.4 `MODULE-MAP.md` 改成生成物

- 生成器扫 `DOC_ROOT/modules/*/README.md` 的元数据头，按模块名排序写出表格（模块、职责、源码、关键词、状态、文档链接），表格上下标「生成物，不要手改」。
- 表格以外的手写段落（依赖方向、「不容易发现位置的改动」）保留，生成器只重写标记之间的表格。
- 生成器放在面板里（`server/`，解析放 `shared/`），用户的项目不需要自带脚本；「文档」写完模块文档后由面板重新生成。本仓库的 `scripts/rules-check.mjs` 第 7 条改成调同一个生成器的检查，和 `docs:bugs` 一样。
- 冲突了就重新生成一次，不手工合表。
- 地图里只有建过文档的模块，所以就算是 UE 这样的大项目，地图也只有用到过的那些行，读一遍很快。

## 5. 协调器：新的处理流程

### 5.1 流程

```
用户消息
  │
  ├─ 1 理解：一句话复述；看现有子对话，判断是不是某个子对话的后续
  │          不需要定位的直接去分诊：闲聊、讨论、问面板怎么用、回答子对话的提问、
  │          某个子对话的后续（它自己有上下文）
  ├─ 2 提炼关键词：用户点名的模块 / 路径 / 类名；业务术语（中英文各一份，如「背包 / inventory」）；
  │          报错原文里的文件路径、类名、日志类别；附件里的同类信息
  │          提炼不出来、消息太含糊 → 先澄清，不拿整句话去找
  ├─ 3 查文档：读 MODULE-MAP.md（只列建过文档的模块），按模块名、职责、关键词对上
  │          对上了 → 读那个模块的 README
  │          对不上 → 这个模块还没分析过：看一、二级目录（ls，不 rg），按目录判断它在哪
  ├─ 4 澄清：只在会做出不同交付物、缺验收标准、不可逆时问
  ├─ 5 分诊（命中即停，见 5.3）
  │     要改代码 → create_conversation(modules=[…])
  │                 └─ 面板：有模块还没有文档 → 先派「模块分析」→ 写完再启动子对话
  ├─ 6 派发后本轮结束，等推回
  └─ 7 汇总：按证据转述；合回结果里提示「模块源码已删除 / 文档要刷新」时派「文档」
```

查文档就是读文件，不加新工具：地图是生成物、一模块一行，`modules/<模块>/README.md` 在固定位置。关键词写进分诊记录（`route.keywords`），分诊卡上能看到协调器是按什么去找的。

### 5.2 先建文档再开子对话：由面板保证

`create_conversation` 加一个参数 `modules`（这次涉及的模块名；模块还没文档时写目录名）。面板拿到后：

1. 每个模块看 `DOC_ROOT/modules/<模块>/README.md` 在不在（就是一次文件检查）。都在 → 直接启动子对话，派单里自动附上这些文档的路径，子对话不用再自己找。
2. 有不在的 → 子对话先建好、状态显示「等文档」，面板同时给每个缺文档的模块派一个「模块分析」子任务（「文档」角色，`task=模块分析`，几个模块并行）。全部写完再启动子对话，派单里附上新文档的路径。协调器这一轮照常结束，不用自己回来接着办。
3. 同一个模块已经在分析了，后来的子对话排在它后面，不重复分析。
4. 分析失败：子对话照样启动，派单里写「模块文档没建成：<原因>」，错误显示给用户（不悄悄重试）。

协调器的参数 `docsFirst`：`开子对话前`（默认）/ `关闭`。

为什么由面板做：「先派分析、等回来再开子对话」要跨两轮，靠协调器记得容易断，和 `docs/lessons/plan.md` 里「对话能不能走完不靠模型自觉」是同一类问题。

### 5.3 「模块分析」子任务做什么

- 输入：模块名或目录、协调器提炼的关键词、用户原话（帮它判断先看哪部分）。
- 做法：从入口和构建文件读起（UE 是模块的 `Build.cs` 和 `Public/` 头文件，Node 是 `package.json` 和入口文件），只顺着关键词相关的部分往下读，不把整个模块读完。
- 写什么：按 §4.3 的格式和上限写 `modules/<模块>/README.md`，面板重新生成地图。
- 交回：文档路径，加几句这次关键词相关的发现（直接写进子对话的派单）。
- 其他只读分析（调研、AI 分析、子对话排查时）读明白了一个还没有文档的模块：在结果里写「建议补模块文档」和读到的要点，协调器交「文档」按要点写，不重新分析一遍。

## 6. 模块删除和文档过期

| 时机                                   | 面板做什么                                                                                                                                                                                                                |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 子对话合回后                           | 对照这次改动涉及的模块文档里的「源码」路径：全部不存在了且没有对应的重命名 → 合并结果里写「模块 X 的源码已删除」；有重命名 → 写「模块 X 的源码移到了 Y」。协调器派「文档」（`task=清理`）删目录或改路径，面板重新生成地图 |
| 协调器读到一份文档、发现源码路径不在了 | 顺手派「文档·清理」                                                                                                                                                                                                       |
| 子对话合回、改动落在有文档的模块里     | 改了入口文件或改动很大（例如超过 200 行）→ 把它标成 `stale`，合并结果提示「文档可能要刷新」；执行收尾已经交过文档同步的不再提示                                                                                           |

删除交给「文档」判断：要分清「真删了」和「并进别的模块 / 改名」，迁移线索写进接手的模块。面板只负责发现和提示，重新生成地图由面板做。

执行收尾时的文档同步沿用现有做法（「文档」挂成 `parent`，转交父对话派），只是改成面板在收尾清单里列出「这次改到的、有文档的模块：x、y」，执行照着决定要不要派。

### 6.1 Bug 记录：只落用户报的

做法不变：一个 Bug 一个 `modules/<模块>/bugs/<bug-id>.md`，`bugs.md` 由它生成，不手改。变的是「能不能写」由面板按来源判断，不靠八处提示词提醒。

| 环节                                                 | 怎么做                                                                                                                                                       |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 标来源                                               | 协调器派 Bug 时，`create_conversation` 的 `route` 写 `kind: "bug"`，面板记下触发它的**用户消息**。只有这样建的子对话（和之后交回它的续作）算「用户报的 Bug」 |
| 收尾清单                                             | 只有「用户报的 Bug」子对话合回时，收尾清单里才有「写 Bug 记录」，并带上用户原话和排查报告的根因 / 修复 / 回归测试                                            |
| 写入                                                 | 「文档」写 Bug 记录要用 `task=Bug 记录`，带上 `bugFrom`（子对话 id）；面板核对来源，不是用户报的就拒绝，并告诉它「写进交接摘要」                             |
| 其他问题去哪                                         | 评审意见、测试失败、自测、AI 排查时顺带发现的：写进交接摘要的「顺带发现」，值得长期记住的写进项目教训；它们没有入口进 `bugs/`                                |
| 兜底                                                 | 「文档」这一轮结束时面板看改动：新增了 `bugs/*.md` 却没有对应的 `bugFrom`，在对话里显示警告给用户（不悄悄删）                                                |
| 用户随口说「这里有个 Bug」、协调器就地答完没开子对话 | 不写：Bug 记录要有分析、修复、验证的结果                                                                                                                     |

规则正文只留在 project-documentation 一处，角色设定里的 8 处删掉。

### 7.2 各位置的边界（一句话版，写进各自设定开头）

- **协调器**：我只读模块文档和目录，判断交给谁；要读代码才能回答的，交出去。
- **执行**：我只负责这一件交付，做到合回父对话所在的分支为止。

### 7.3 工作流里的文档节点

改代码的内置工作流最后一个节点都是「文档」，执行收尾时又会判断要不要派「文档」，同一次改动可能写两遍。改成：走工作流时以工作流里的文档节点为准，执行收尾不再另派（面板按这次计划里有没有做完的「文档」节点决定收尾清单里列不列文档同步）。

## 13. 附：子对话请求收尾后父对话不动（用户 2026-11-03 报）

### 现象

子对话「面板提醒次数做成设置项（默认 6）」调用 `submit_merge` 后显示「待收尾」。父对话收到了【收尾请求】，也开了一轮：跑了 4 条命令，回复「改动核对通过……现在合回。」，然后这一轮就结束了，**没有调用 `finish_child`**。之后父对话一直停着，状态诊断报 `child-idle-parent-waiting`（计划还在等子对话，它们已经不在跑了，父对话却没被叫醒）。

### 根因：父子互相等，判定里没有人负责推

| 一方   | 它在等什么                                                                                                                            | 面板怎么看                                                                                                                                 |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 子对话 | `wrapRequest.state = 'requested'`，等父对话 `finish_child`                                                                            | `planStalled` 第 2 行：请求过收尾就不推（`shared/task.ts` 的 `planStalled`）——对，它确实在等别人                                           |
| 父对话 | 计划里等这个子对话的那一步是 `waiting`（`reportChild` 对「待收尾」只把那一步继续挂着等，`server/tasks/children.ts` 的 `reportChild`） | `planStalled` 看到计划里有 `waiting` 的步骤就返回 false，日志记 `step-waiting`，`nudgePlan` 不推（`server/tasks/drive.ts` 的 `nudgePlan`） |

父对话那一步写着「等子对话」，可子对话这时等的正是父对话自己：这个等待实际上是父对话自己要做的事（调 `finish_child` 或退回），被当成「在等别人」跳过了。和已修过的 `child-stuck-before-merge`（子对话说「现在收尾」没调 `submit_merge`）是同一类问题，发生在父对话这一边，当时只给子对话加了 `nudgeMerge`，父对话这边没有对应的兜底。

触发条件是模型提前结束回合：说了「现在合回」，这一轮却没有工具调用。CLI 照常报这一轮结束，面板按「在等子对话」处理，于是没人再动。

状态诊断（`shared/lifecycle.ts`）其实已经认出来了，但它只负责显示，没有接到任何恢复动作上。

另一条要排除的路径：收尾请求没送到父对话（`wakeTask` 交不出去，退回收件箱）。截图里父对话已经收到请求并回了话，不是这一条；诊断文件里父对话的「计划推进」日志应该是 `action: none, reason: step-waiting`，可以用它确认。

### 修法（等确认后做）

1. **判定改一处（`shared/task.ts`）**：新增 `waitsOnSelf(tk, kids)`：计划里在等的子对话已经是「待收尾」（`wrapRequest.state === 'requested'`）时，这个等待算父对话自己的事。`planStalled` 的「有在等的步骤」改成只认真在等别人的步骤。判定只有这一个出处，状态诊断、会话栏「状态」、推进逻辑都用它。
2. **父对话一轮结束时推一次（`server/tasks/drive.ts`）**：按上面的判定，父对话这一轮结束、有子对话待收尾、这一轮里没对它调用过 `finish_child` / `send_to_conversation`，就推一条：「子对话「X」在等你收尾：核对通过就调用 `finish_child`（id …），要补的用 `send_to_conversation` 交回。直接调用工具，不用先说明。」次数和计划推进共用 `nudgeMax`（刚做成设置项的那个）。
3. **推满了还不动，交给用户**：父对话里写一行警告，子对话行上「待收尾」旁边给一个「合回」按钮，由用户直接触发同一个 `finish_child`（错误照常显示给用户）。
4. **状态诊断分开说**：子对话是「待收尾」时不再报 `child-idle-parent-waiting`，改报 `wrapup-unhandled`：「子对话已请求收尾 N 分钟，父对话这一轮结束时没有合回，也没有退回」，并写明面板推过几次。
5. **兜底定时检查**：父对话空闲、有待收尾的子对话超过几分钟没处理（比如收尾请求进了收件箱、没开成新一轮），按第 2 条再推一次；同一个请求只推一次。
