# 协调器与「文档优先」：角色架构重新设计（设计稿）

状态：草案，待用户确认 · 2026-11-03 · 不含代码改动

## 0. 一页结论

1. **主理改名「协调器」**（key 仍是 `orchestrator`，不迁移数据），定位收窄为「入口 + 定位 + 路由 + 汇总 + 对外动作」：只读文档和目录，不读实现、不排查、不出方案。
2. **每条消息的第一步是查模块文档**：面板提供 `find_module` 工具，按关键词 / 路径 / 报错原文查模块索引，返回命中的模块、源码路径、文档状态。不靠协调器自己翻 `MODULE-MAP.md`。
3. **新增 `/initDocs` 命令**：面板先确定性地扫目录和构建清单，AI 只负责「划模块 + 一句话职责」，产出极简的模块索引（每个模块一个几行的 README 元数据头），不读源码正文。可以重复跑，增量更新，消失的模块自动清掉。
4. **文档优先**：协调器要开子对话时，在 `create_conversation` 里写 `modules`。目标模块只有索引、还没模块文档时，**面板**先派「文档」建简要模块文档，建完再启动子对话，并把文档路径附进派单。这一步靠面板执行，不靠协调器记得。
5. **存储用 Markdown，不用 SQL**：每个模块一个 `modules/<模块>/README.md`，开头的元数据头是唯一来源；`MODULE-MAP.md` 改成生成物（和现在的 `bugs.md` 同一套做法）；面板在内存里缓存索引，供 `find_module` 查询，随时可以重建。
6. **模块删了，文档跟着删**：面板在合回、`find_module`、`/initDocs` 三个时机检查 `source_paths` 还在不在；源码全没了就交「文档」删目录、重新生成地图。改名 / 移动走更新，不走删除。
7. **去掉重复的规则**：同一条规则现在散在角色设定、面板提示词、技能里，最多的写了 7–9 处，已经出现互相矛盾（见 §2.3-B）。按「面板管必须、角色管职责、技能管做法」三层，每条规则只留一个出处。协调器的设定预计从约 5800 字压到 2000 字以内。
8. **模块文档只有「文档」一个出口**：调研、子任务不再自己写模块文档，只交结论。

## 1. 背景与要求

用户 2026-11-03 提出：

- 主理改名为协调器。
- 协调器分析用户消息时，先从文档里找对应的模块。
- 要有一个 `initDocs` 命令初始化项目文档：只是**极简**的初始化，把模块找出来，简单描述模块做什么、代码在哪，不细看代码，方便以后快速定位。
- 模块还没有模块文档时，协调器先派子任务建模块文档，建完再创建子对话交给它。
- 模块删除时，对应文档也要删除。
- 模块文档不要太细。
- 评估存储形式（SQL 数据库、Markdown 或其他）。
- 评估父对话 / 子对话角色设计是否合理、流程是否贯通、定义分散多处会不会互相偏移；列出可优化、缺少、可删除、繁杂多余的步骤；重新设计角色架构、划定能力范围、和技能结合起来。
- 先出设计文档，不改代码。

## 2. 现状核对

### 2.1 角色和位置

| 位置             | 默认角色                                                    | 层                    | 主要设定所在                       |
| ---------------- | ----------------------------------------------------------- | --------------------- | ---------------------------------- |
| 项目对话（父）   | `orchestrator` 主理                                         | 高级                  | `shared/builtin/agents.ts:341-502` |
| 子对话           | `worker` 执行                                               | 高级                  | `shared/builtin/agents.ts:503-614` |
| 子任务（不点名） | `helper` 子任务                                             | 基本，只能派出        | `shared/builtin/agents.ts:700-728` |
| 文档             | `docsync` 文档                                              | 基本，`runIn: parent` | `shared/builtin/agents.ts:615-698` |
| AI 分析          | `analyzer` 分析                                             | 高级                  | `shared/builtin/agents.ts:730-773` |
| 其他基本角色     | 调研、方案设计、评审、测试验收、版本控制、界面走查、本地化… | 基本                  | 同文件                             |

每轮注入父对话的不只是角色设定，`shared/engine.ts` 的 `conversationPrompt`（约 4067-4300 行）还会拼上「你的定位」「子对话各自在独立分支里改 / 共用一个目录」「现有子对话」等几段；内置主理只跳过「这条消息怎么处理」「分派前只收集到模块为止」两节（`ownDispatch`）。

### 2.2 现在一条消息怎么走

```
用户消息 → 主理：理解（「只收集到模块为止」，自己决定读不读 MODULE-MAP）
        → 澄清 → 分诊表 → create_conversation / send / spawn / 就地改 / 自己答
子对话（执行）：复述 → 实现计划 → [自己读 MODULE-MAP + 模块 README] → 改 → 快速检查
        → 派评审 → 处置 → 完整测试 → 收尾前「判断要不要派文档」→ submit_merge
父对话：finish_child → 汇总
```

### 2.3 问题

#### A. 流程断点：文档不在主流程里

| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |

| A5  | 「AI 初始化项目」（项目设置，`shared/project-init.ts`）、内置 `/init`（`shared/commands.ts`）、技能的「初始化」一节，三个入口做的事有重叠又不完全一样；都会写 AGENTS.md，只有技能那份会给每个模块建 `inferred` README，内容很多，和「极简」的要求相反 | 同左                                                                                                     |

#### B. 同一条规则定义在多处，已经互相偏移

| 规则                       | 出现位置（数）                                                                                                                                                                                      | 已发现的矛盾                                                                 |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 子对话合回后整体验证由谁做 | 主理挂载 `tester`「合并后的父对话测试由面板自动跑；只在用户点名要整体回归时派它」；主理「守住一致·测试」「派测试验收去跑」；`engine.ts:4211`「需要整体验证时**新建一个子对话**去跑完整的测试」（3） | 三种说法：面板自动跑 / 派测试验收子任务 / 新开子对话                         |
| 子 Agent 失败了怎么办      | 通用约束 `agents.ts:311`「**自己接手**（或缩小范围重做一次）」；主理「交回原子对话，不要新建」；engine「交回原来那个子对话 / resume」（3）                                                          | 通用约束让父对话自己接手，等于让协调器自己动手改代码，和「父对话不动手」矛盾 |

| 模块文档的状态值           | 技能（5 种）、`MODULE-MAP.md` 实际值、rules-check（3）                                                                                                                                              | 见 A4                                                                        |
| Bug 记录只记用户报的       | 主理、执行、docsync、project-documentation、systematic-debugging、openspec 技能、工作流定义、AGENTS.md（8）                                                                                         | 暂无矛盾，但每改一次口径要改 8 处                                            |
| 推送 / 对外操作归谁        | 通用约束「安全边界」、主理两节、执行「版本管理」、engine「执行目录」「你的定位」、版本控制角色、project-vcs（7）                                                                                    | `docs/lessons/builtin.md` 已记过一次因此打架                                 |
| 子对话的完成标准           | 通用约束两节、执行「版本管理」、engine「子对话的完成标准」（4）                                                                                                                                     | engine 写了「和角色设定里写的不一样时以这里为准」——说明已经知道会不一样      |

根因：没有约定「哪类规则写在哪一层」。面板机制（工具返回什么、门禁拦什么）写进了角色设定；角色职责写进了面板提示词；做法细则（找 Bug、写代码、评审循环）抄进了角色设定，又在技能里写了一份。

#### C. 繁杂、冗长

- 主理设定约 5800 字（17.5 KB），每轮常驻；engine 还在后面追加约 2000 字的「你的定位」和隔离方式说明。
- 执行设定本体约 4400 字，加上嵌入的 `IMPL_PLAN_TEXT`、`CODING_TEXT`、`BUG_METHOD`、`LOG_TIMELINE_TEXT`、`SELF_CHECK_TEXT`，总量超过一万字；而 ADR 0023 的原则是「高级角色挂载基本角色，不要把能力的做法抄进它的设定」——执行恰好把「开发」的做法整段抄了进来，`developer` 角色里又有一份。
- 主理挂了 `analyst`（方案设计）为「澄清和分诊时就地用」，方案设计会往实现细节里挖，和「只收集到模块为止」方向相反。
- 大方案派单前有两道关：「大改动先确认」（问用户）+ 挂载 `reviewer`「大方案派单前独立复核」。
- 主理和执行两处都写了「测试验收·设计用例 / 清理用例」的用法和参数。
- 「派单的粒度」里让模型自己写 `tier: "low"`：这是面板能按角色默认档位决定的事。
- 执行接单「先复述」和「实现计划」的第一节「目标与验收」内容重复。

#### D. 命名容易混

`analyzer`「分析」/ `analyst`「方案设计」key 只差两个字母；`helper`「子任务」/ `explorer`「调研」都是只读调研、都能回写文档；`worker`「执行」/ `developer`「开发」都写代码。主理改名协调器是个机会，顺带把这几处讲清楚（见 §8）。

## 3. 设计原则：三层，每条规则只有一个出处

| 层                                         | 管什么                                                         | 例子                                                                                   | 不放什么               |
| ------------------------------------------ | -------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ---------------------- |
| **面板**（工具、工具返回、门禁、自动步骤） | 必须照做、能用程序判断的：调用顺序、前置条件、状态流转、生成物 | 评审门禁、收尾步骤、`find_module`、文档优先、模块删除检测、send 的返回值自带下一步说明 | 「你是谁、该怎么想」   |
| **角色设定**                               | 我是谁、管哪段、交给谁、交付什么、不做什么                     | 协调器的分诊表、执行的收尾顺序（只列步骤名）                                           | 工具用法细节、做法细则 |
| **技能**                                   | 某类工作的具体做法，按需加载                                   | 找 Bug 的方法、写代码规范、模块文档的格式                                              | 角色边界、面板机制     |

约束：

1. 同一条规则只在一层写全文，别处最多一行指针（「按 project-documentation 的『模块文档』」）。
2. 能写成面板判断的，删掉对应提示词（`docs/lessons/plan.md`「必须照做的规则交给面板执行」）。
3. 加一条检查：`scripts/rules-check.mjs` 对内置角色设定、`engine.ts` 提示词、`skills/` 做长句去重，同一句（≥ 30 字）出现两次以上报错（白名单登记例外）。

## 4. 模块文档：存储和格式

### 4.1 选型

| 方案                                                | 优点                                                                                                           | 缺点                                                                                                                                                                                                  | 结论                 |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| SQLite / SQL 数据库                                 | 查询方便、并发写安全                                                                                           | Agent 只能通过工具读，用户直接用 Claude Code / Codex 打开项目时看不到；不能 git diff、评审、合并；P4 / SVN 项目外的文档根也要另存；要做 schema 迁移；放在数据目录就和项目代码脱节，换台机器文档就没了 | 不用                 |
| 单个 JSON 索引文件                                  | 机器好读                                                                                                       | 人读不了；并行改同一个文件必冲突；描述写在 JSON 里不好维护                                                                                                                                            | 不用                 |
| Markdown（现状：手写地图 + 模块 README）            | 人和 Agent 都能读；跟代码走版本控制                                                                            | 地图手写，并行冲突；状态靠模型维护，已漂移                                                                                                                                                            | 保留形式，改维护方式 |
| **Markdown 为准 + 地图生成 + 面板内存索引**（推荐） | 保留 Markdown 的全部好处；每个模块一个文件，并行不冲突；地图是生成物；面板解析出索引供工具查询，确定、省 token | 要写一个解析 / 生成器（面板里，不依赖项目脚本）                                                                                                                                                       | **采用**             |

要点：真相只有一份，就是各模块 README 的元数据头；`MODULE-MAP.md` 和面板的内存索引都从它生成，坏了随时重建。这和 `bugs/<id>.md → bugs.md` 是同一个做法，项目里已经验证过。

### 4.2 两级文档、三个状态

| 状态         | 谁产生                                                                          | 内容                                        | 协调器怎么看                                                       |
| ------------ | ------------------------------------------------------------------------------- | ------------------------------------------- | ------------------------------------------------------------------ |
| `indexed`    | `/initDocs`                                                                     | 只有元数据头 + 一句话职责（约 8 行）        | 能定位，但「没有模块文档」：开子对话前要先建                       |
| `documented` | 「文档」建模块文档                                                              | 元数据头 + 固定几节（见 4.3），上限约 80 行 | 有文档，直接派                                                     |
| `stale`      | 面板检测（源码在 `verified_commit` 之后改动很多）或任何角色发现文档和代码对不上 | 内容保留                                    | 当作有文档，但派单里附一句「文档可能过期」；子对话收尾时交文档刷新 |

去掉的：`inferred`、`analyzed`、`confirmed`、`verified`（合并成 `documented`，没人会真的去「人工确认」，留着只会漂移）；`retired`（模块没了就删，不留墓碑，迁移线索写进接手模块的 README）。

### 4.3 格式

元数据头沿用现在 Bug 详情的写法（标题之后、第一个 `## ` 之前的列表行），不引入 YAML，脚本只读这一块：

```md
# web：React 前端

- 状态：documented
- 职责：项目、任务、工作流、角色等页面，流程图画布和对话输出
- 源码：`web/`
- 入口：`web/src/main.tsx`、`web/src/App.tsx`
- 关键词：页面、侧栏、对话页、流程图、设置
- 依赖：shared
- 更新：2026-11-03 · a1b2c3d
```

`documented` 的正文只有这几节，每节写不出内容就不写：

| 节                | 写什么                             | 上限  |
| ----------------- | ---------------------------------- | ----- |
| 做什么 / 不做什么 | 职责边界，和相邻模块的分界         | 5 行  |
| 关键文件          | 路径 + 一句话，按「先读哪个」排    | 10 条 |
| 对外接口与数据流  | 别的模块怎么调它、数据从哪来到哪去 | 8 行  |
| 改这里要注意      | 易错点、隐含约束                   | 8 条  |
| 怎么验证          | 相关测试命令 / 用例位置            | 5 行  |

不写：实现细节、逐函数说明、变更历史（历史在 git 和 ADR 里）。现在 `web` 那样拆成十个子页面的做法不再推荐；已有的子页面保留，不强制迁移。

### 4.4 `MODULE-MAP.md` 改成生成物

- 面板（`server/`）带一个生成器：扫 `DOC_ROOT/modules/*/README.md` 的元数据头，按模块名排序写出地图表（模块、源码、职责、入口、状态、文档链接），文件头写「生成物，不要手改」。
- 地图上方保留一段手写区（依赖方向、「不容易发现位置的改动」这类跨模块说明），生成器只重写标记之间的表格。
- 本仓库的 `scripts/rules-check.mjs` 第 7 条改成调用同一个生成器的 `--check`，和 `docs:bugs` 一样。
- 冲突处理：以任意一边为准重新生成，不手工合表。

### 4.5 面板索引和工具

面板按项目缓存索引（文件变了就重读），提供给协调器和执行（orch-mcp）：

| 工具           | 参数                                          | 返回                                                                                                                                                    |
| -------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `find_module`  | `query`（关键词 / 报错原文）、`paths`（可选） | 命中的模块（按匹配度）：名字、职责、源码、入口、状态、文档路径、`missing`（源码路径已不存在）；没有索引时返回「项目还没有模块索引，可以运行 /initDocs」 |
| `list_modules` | —                                             | 全部模块一行一个（给协调器看全貌时用，平时不用）                                                                                                        |

匹配只做程序能做的：路径前缀、关键词、职责里的词、报错原文里出现的文件路径。拿不准时返回多个候选，由协调器判断。

## 5. `/initDocs`

### 5.1 做什么

极简初始化：**找出模块，一句话说清做什么，写清代码在哪**。不读源码正文、不分析实现、不写 AGENTS.md（那是 `/init` 和「AI 初始化项目」的事）。

### 5.2 怎么做

1. **面板先扫（确定性，不花 token）**：一、二级目录树（按项目的搜索排除清单跳过生成物）、构建清单（package.json 的 workspaces、Cargo / go.mod、`*.uproject`、`Build.cs`、`*.sln`、CMakeLists）、每个目录的文件数和主要扩展名、已有的模块索引。
2. **派「文档」（`task=初始化索引`，低档模型）**：输入就是上面的扫描结果，加上可以读的顶层 README。按 project-documentation「模块怎么划」划 3–15 个模块，每个只写名字、源码路径、入口、一句话职责、关键词；只允许读目录列表和清单文件的开头，不读源码。产出结构化 JSON（面板工具 `submit_module_index`）。
3. **面板写盘**：每个新模块建 `modules/<模块>/README.md`（`indexed`，只有元数据头）；已有的模块不覆盖，只补缺的元数据行；重新生成 `MODULE-MAP.md`。
4. **增量**：重复跑时，已有模块保持原样；新出现的目录加成新模块；源码已全部不存在的模块列成「将删除」，在结果里给用户确认后删（首次和日常清理都走这条）。
5. **结果**：对话里一张小表（新增 / 保留 / 删除 / 待确认），不刷屏。

### 5.3 入口和触发

- 输入框 `/initDocs`（`shared/commands.ts` 的内置命令，`action: 'initDocs'`，由面板执行，不展开成普通要求）。
- 项目设置「AI 初始化项目」里，文档部分改为调用同一流程（它写 AGENTS.md、推荐设置的部分不变），不再给每个模块写长篇 `inferred` README。
- 协调器调 `find_module` 发现项目没有索引时：自动跑一次 `/initDocs`（便宜、只建索引），在回复里告诉用户。是否改成「先问用户」见 §16 Q2。
- 技能 project-documentation 的「初始化」一节改成指向这个命令，自己不再写一套步骤。

## 6. 协调器：新的处理流程

### 6.1 流程

```
用户消息
  │
  ├─ 1 理解：一句话复述；看现有子对话，判断是不是某个子对话的后续
  ├─ 2 定位：find_module（关键词 / 报错原文 / 用户点名的路径）→ 模块 + 文档状态
  │          没有索引 → 自动 /initDocs；命中不了 → 按目录判断，派单里写「索引未收录」
  ├─ 3 澄清：只在会做出不同交付物、缺验收标准、不可逆时问
  ├─ 4 分诊（命中即停）
  │     后续 → send_to_conversation
  │     问答 → 读模块文档 + 少量文件，自己答
  │     微改动 → 就地改（护栏不变）
  │     只读调研 / 文档 → spawn_agents
  │     要改代码 → create_conversation(modules=[…])
  │                 └─ 面板：有模块是 indexed → 先派「文档·建模块文档」→ 完成后启动子对话
  ├─ 5 派发后本轮结束，等推回
  └─ 6 汇总：按证据转述；合回结果里带「模块已删除 / 文档要刷新」时派「文档」
```

### 6.2 文档优先由面板执行

`create_conversation` 新增 `modules`（模块名数组，项目有索引时必填）。面板拿到后：

1. 查索引：全部 `documented` / `stale` → 直接启动子对话，派单里自动附「模块文档：`docs/modules/x/README.md`」，子对话不用再自己查地图。
2. 有 `indexed` 的 → 子对话先建好、状态「等文档」，面板同时派「文档」（`task=建模块文档`，每个模块一个子任务，并行），全部回来后再启动子对话；派单里附新文档路径。协调器这一轮照常结束，不用自己回来接力。
3. 同一个模块正在建文档时，后来的子对话排在同一个子任务后面，不重复建。
4. 建文档失败：子对话照样启动，派单里写「模块文档没建成：<原因>」，错误显示给用户（不悄悄重试，符合 AGENTS.md）。
5. 不在索引里的模块名：拒绝并返回候选（`find_module` 的结果），让协调器改正或明确写 `modules: []` 加理由。

项目参数（协调器的参数）`docsFirst`：`开子对话前`（默认）/ `总是`（`spawn_agents` 调研类也先建）/ `关闭`。Bug 和功能都走同一条，不区分。

为什么放面板：协调器设定里写「先派文档、等回来再建子对话」需要它跨两轮记住，正是 `docs/lessons/plan.md` 里「对话能不能走完不靠模型自觉」那类问题。

### 6.3 新的分诊表（替代现有那张）

| 情况                                                       | 去向                                                             |
| ---------------------------------------------------------- | ---------------------------------------------------------------- |
| 某个子对话的后续（追加要求、返工、验收没过、它提问的答案） | `send_to_conversation` 交回原子对话                              |
| 问答、解释、查一个事实                                     | 读模块文档和少量文件，自己答                                     |
| 改什么、改成什么已经清楚的微小改动                         | 就地微改动                                                       |
| 只读：跨模块调研、几个方向比较、核实结论                   | `spawn_agents`（调研 / 方案设计 / 评审）                         |
| 只写文档                                                   | `spawn_agents` 派「文档」，几份一次派完                          |
| 要改代码（功能、Bug、重构、迁移，或要按固定剧本做的）      | `create_conversation`，写 `modules`；要用工作流时 message 里点名 |
| 几件互不相关的交付                                         | 拆开并行（参数 `split`）；改的文件重叠就合成一个                 |
| 推送、PR、合并主干、发布                                   | 按「授权情况」自己做                                             |

派单正文的五个小节（目标 / 交付物与验收 / 范围 / 已知 / 假设）保留；Bug 派单的现象卡保留，压成一段。

### 6.4 协调器设定里删掉 / 移走的

| 现在的节                                         | 处理                                                                                                                 |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| 「交回子对话之后怎么确认它接到了」（约 900 字）  | 删。`send_to_conversation` 的返回文本自己写清「已送到，本轮结束，等推回」/「排队中，不用重发」/「失败：原因 + 建议」 |
| 「派单的粒度」里的 `tier: low` 和 token 说明     | 删 `tier` 一条（面板按被派角色的默认档位走）；token 说明压成一句                                                     |
| 「Bug 怎么交」后半段核对排查报告的细则           | 压成一句「按排查报告的『调用栈 / 证据链 / 验证』三项核对，缺了交回」；排查报告的格式归 systematic-debugging 技能     |
| 「守住一致·测试」里设计用例 / 清理用例的参数写法 | 只留在「测试验收」角色自己的设定里；协调器只写一句什么时候派                                                         |
| 「守住一致·文档」「Bug 记录只记用户报的」        | 删，归「文档」角色和 project-documentation                                                                           |
| 「提交和推送」「子对话的完成条件」               | 删，归通用约束「安全边界」一处                                                                                       |
| 「怎么回复用户」                                 | 保留，缩短                                                                                                           |
| 挂载 `analyst` 就地用                            | 改成只能派出（架构级方案），不在分诊时就地用                                                                         |
| 挂载 `reviewer`「大方案派单前复核」              | 删；大方案只保留「先给用户确认」一道                                                                                 |

engine 那边：内置协调器时，「你的定位」只留就地微改动的护栏数字和分支说明；「几个子对话都合进来之后…新建一个子对话去跑完整的测试」删掉（合回后的测试由面板自动跑，用户点名要整体回归时派「测试验收」，只留这一种说法）。

## 7. 模块删除与过期

| 时机                         | 面板做什么                                                                                                                                                                                                                             |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 子对话 `submit_merge` 合回后 | 按这次 diff 里删除 / 重命名的路径对照索引：某模块的 `源码` 全部消失且没有对应的重命名 → 合并结果里写「模块 X 的源码已删除」；有重命名 → 写「模块 X 的源码移到了 Y」。协调器看到后派「文档」（`task=清理`）删目录或改路径，重新生成地图 |
| `find_module`                | 命中的模块源码不存在时标 `missing`，协调器顺手派「文档·清理」                                                                                                                                                                          |
| `/initDocs` 增量运行         | 列出「将删除」，用户确认后删                                                                                                                                                                                                           |
| 子对话合回、改动落在某模块里 | 改动行数超过阈值（例如 200 行）或改了入口文件 → 把该模块标成 `stale`，合并结果提示「文档可能要刷新」；协调器决定要不要派文档（默认在执行收尾时已经顺带交过就不再派）                                                                   |

删除走「文档」角色而不是面板直接删：需要判断「是真删了还是并进别的模块」，迁移线索要写进接手模块。面板只负责发现和提示，确定的部分（地图重新生成）由面板做。

执行（子对话）收尾时的文档同步保持现有做法（`docsync` 挂成 `parent`，转交父对话创建），但触发由「自己判断」改成面板在收尾清单里列出「这次改到的模块：x、y；文档状态：…」，执行照着决定派不派。

### 8.2 各位置的边界（一句话版，写进各自设定开头）

- **协调器**：我只读文档和目录，判断交给谁；要读代码才能回答的，交出去。
- **执行**：我只负责这一件交付，做到合回父对话所在的分支为止。
- **子任务类（文档 / 调研 / 评审 / 测试验收 / 子任务）**：一个回合做完，结果交回给派我的一方，不问用户。

### 8.3 工作流和文档节点

改代码的内置工作流最后一个节点都是「文档」，执行收尾时又会判断要不要派「文档」，同一次改动可能写两遍。改成：走工作流时以工作流里的文档节点为准，执行收尾不再另派（面板按「这次计划里有没有完成的 docsync 节点」决定收尾清单里是否列文档同步）。

## 13. 兼容与迁移

- 旧模块 README：元数据头的 `status: inferred/analyzed/confirmed/verified` 读成 `documented`，`retired` 读成「待清理」；英文字段名（`status`、`source_paths`、`entry`、`analyzed_at`）和新的中文字段名都认，写回时统一成新格式。
- 旧的手写 `MODULE-MAP.md`：第一次生成时，表里有、模块目录里没有的行，按表格内容补建 `indexed` README（不丢信息）；表格上方和下方的手写段落原样保留进手写区。
- 没有 `modules/` 的项目：`find_module` 提示可以 `/initDocs`，不报错；`docsFirst` 在没有索引时不拦。
- P4 / SVN 项目文档根在项目外：生成器和索引按面板给的文档根读写，不做 P4 操作（沿用现有规则）。

## 15. 风险

| 风险                                               | 应对                                                                                                          |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 文档优先让第一次开子对话变慢（多一次子任务冷启动） | 只在 `indexed` 时建，建一次以后都复用；多模块并行建；`docsFirst=关闭` 可一键回到现状                          |
| `find_module` 匹配不准，协调器被带偏               | 返回多个候选和匹配理由；命中不了按目录判断；索引只是起点，执行仍以代码为准                                    |
| 模块划分不合理（太粗 / 太细）                      | `/initDocs` 限 3–15 个；用户可以直接改 README 元数据头再跑生成；协调器发现划分不对时派「文档」调整            |
| 设定瘦身后模型漏做以前写在提示词里的事             | 有门禁的已在面板；去掉的每一条在 PR 里列出「现在由谁保证」；按 AGENTS.md 跑 `test:affected` 和 e2e 子对话用例 |
| 改动面大，子对话并行实现时冲突                     | 按 §14 分期串行做，P0 先合                                                                                    |
