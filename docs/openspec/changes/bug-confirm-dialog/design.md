# Bug 确认弹窗：按「取证 → 根因 → 方案」走，能补日志、能接着探讨（设计稿）

相关：[ADR 0045](../../../adr/0045-bug-diagnosis-confirm.md)（先交诊断报告、确认了再改）、[ADR 0046](../../../adr/0046-bug-analysis-pipeline.md)（一套方法、一份档案）、`shared/bug-diagnosis.ts`、`shared/bug-diagnosis-schema.ts`、`server/diagnosis-tool.ts`、`server/hooks/guards.ts`（`bugDeny`）、`web/src/components/tasks/DiagnosisDialog.tsx`、`ReviewDialog.tsx`、`shared/builtin/bug-method.ts`

## 0. 一页结论（按用户 2026-11-05 的要求）

用户的原话：确认弹窗没有补充日志的按钮，计划里要列出日志怎么补；标了疑问之后应该是「继续探讨、出下一版」，而不是只有确认。要更接近真实的修 Bug 过程。

1. **弹窗分两种报告，按阶段换按钮**。根因还没证实时交的是「取证计划」，主按钮是「同意加日志」；根因证实了交的是「修复方案」，主按钮才是「确认方案，开始修」。现在两种都叫「确认方案，开始修」，加日志也得点它。
2. **补日志写成结构化的「日志计划」**：每一处写文件和行、打什么值、用来区分哪个假设；再写复现步骤、日志落在哪、要贴回哪几行。弹窗里单独一块显示，对话计划里同步出「加日志 → 等你复现 → 分析日志」三步。
3. **加了日志之后有「等你复现」这一步**：弹窗换成复现步骤 + 贴日志的框，按「交日志，继续分析」它接着查，出下一版。Agent 自己能复现的就自己跑，不用等用户。
4. **标了疑问，主按钮就变成「继续分析，出第 N+1 版」**。确认按钮退成次要，还有没处理的疑问时点它会先提醒。侧栏改成按版本串起来的讨论：每条疑问下面挂下一版的回答，用户可以接着追问。
5. **修复方案上也能「先加日志证实」**：用户觉得证据不够时一键退回成取证计划，不用自己写一大段疑问。
6. **报告顶部加一张结论卡**：根因（已证实 / 假设）、选定方案、要改的文件、下一步要你做什么。二十来节的详情放下面，默认收起次要小节。

顺带修两个现有问题（见 §1.3）：确认时写的标注会被丢掉；同意加日志时 Agent 收到的却是「先写失败测试再按方案改」。

## 1. 现在的弹窗怎么走

### 1.1 流程

```
子对话查 Bug（update_bug_case 随查随记）
  └─ submit_diagnosis 交第 N 版 → status: pending，这一轮结束，改文件被 bugDeny 拦住
        └─ 用户打开弹窗（交报告那一行工具调用上的「查看报告」）
              ├─ 确认方案，开始修 → approved，发「先写失败测试，再按方案改，只改 files 里的文件」
              ├─ 有疑问，再查（要先标注）→ questioned，发逐条意见，让它交第 N+1 版
              └─ 取消修复 → cancelled，计划收口，不发话
```

- 标注种类三种：疑问、改方案、补充信息；候选方案里没选的会出「改用方案 X」的快捷标注。
- 根因没证实（`confirmed: false`）也走同一个弹窗：`rootCause` 写「未找到」，`next` 写一段话说要加哪些日志，`files` 写要加日志的文件。

### 1.2 和真实修 Bug 过程对不上的地方

真实的过程是一个循环：复现 → 定位 → 提假设 → **加日志 / 写用例取证 → 复现拿结果 → 排除或证实** → 根因成立 → 比较修法 → 修 → 验证。弹窗只覆盖了最后「确认修法」这一个口子。

| 缺口                   | 现在                                                       | 后果                                                                                                                 |
| ---------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 取证没有自己的入口     | 根因没证实时只能点「确认方案，开始修」才能加日志           | 用户不知道点了是让它修还是让它加日志；方法里写的「加临时日志、告诉用户怎么复现、停下等用户」，在面板里没有对应的状态 |
| 日志计划是一段自由文字 | `next` 一个字符串                                          | 加在哪、打什么、为了区分哪个假设、怎么复现、贴回什么，常常写不全，用户没法逐条看                                     |
| 没有「等你复现」       | 加完日志后对话就停着，用户贴日志是一条普通消息             | 面板不知道它在等日志；用户贴了日志后 Agent 可能直接在「已确认」状态下接着改，跳过了下一版报告                        |
| 疑问只能「再查」       | 有标注时「确认」仍是主按钮，「有疑问，再查」是次要的灰按钮 | 用户以为没有「继续探讨」的路；一不小心点了确认                                                                       |
| 讨论不连续             | 侧栏每版清空，上一版的回答埋在下一版正文最上面一节         | 看不出哪条问题回答了、还要不要追问，像是重新提交而不是对话                                                           |
| 方案上不能要求取证     | 只能写一条疑问「证据不够」                                 | 用户要自己描述要什么证据                                                                                             |
| 结论埋在长文里         | Markdown 二十来节平铺                                      | 决策要看的根因、选定方案、文件、风险要往下翻                                                                         |

### 1.3 现有的两个小问题（这次一起修）

1. **确认时的标注被丢掉**：`decideDiagnosis` 确认时把 notes 记进了报告，但 `diagnosisFeedback` 确认那一支只带了整体意见，标注没有发给 Agent。用户带着「补充信息」点确认，Agent 收不到。
2. **加日志收到的话不对**：根因没证实的那版被确认后，Agent 收到的是「先写改前失败的测试，再按方案改」，和「加临时日志」不是一回事。

## 2. 新流程

### 2.1 阶段

弹窗顶部一条阶段条，标出现在在哪一步、取证到第几轮：

```
立案 → 定位 → 取证（第 k 轮） → 根因 → 方案 → 修复 → 验证
```

阶段沿用 `bugStage` 的推算，补上「取证」：报告 `confirmed: false` 且有日志计划时就是取证。

### 2.2 状态机

```
                 ┌────────────── 继续分析（带疑问）──────────────┐
                 ▼                                               │
  submit_diagnosis ──► 等确认（pending）─────────────────────────┤
        ▲               │ 取证计划                │ 修复方案      │
        │               ├─ 同意加日志 ──► 加日志（logging）       │
        │               │                  │ ready_for_repro     │
        │               │                  ▼                     │
        │               │             等复现（awaiting）          │
        │               │                  │ 交日志 / 复现不了    │
        │               │                  ▼                     │
        └───────────────┴──── 它分析日志，交下一版 ◄──────────────┘
                        ├─ 我来贴日志（不让它改文件，直接给日志）──► 它分析，交下一版
                        ├─ 先加日志证实（修复方案上）──► 它补日志计划，交下一版
                        ├─ 确认方案，开始修 ──► 修复（approved）──► 收尾核对
                        └─ 取消修复 ──► cancelled
```

Agent 自己能复现（跑测试、跑命令）时，日志计划里标 `selfRun: true`：同意加日志后它加完日志自己跑，跳过「等复现」，直接分析出下一版。

### 2.3 每种状态下弹窗的按钮

| 状态                         | 主按钮                                        | 次按钮                                | 说明                                                 |
| ---------------------------- | --------------------------------------------- | ------------------------------------- | ---------------------------------------------------- |
| 等确认 · 取证计划，没标注    | 同意加日志                                    | 我来贴日志、取消修复                  | 只放行日志计划里的文件，只许加带 `[排查-` 前缀的日志 |
| 等确认 · 修复方案，没标注    | 确认方案，开始修                              | 先加日志证实、取消修复                | 现在的「确认」                                       |
| 等确认 · 有疑问 / 改方案标注 | 继续分析，出第 N+1 版                         | 确认（会提醒「还有 k 条疑问没处理」） | 现在的「有疑问，再查」改名升为主按钮                 |
| 等确认 · 只有补充信息标注    | 确认并带上补充信息 / 同意加日志并带上补充信息 | 继续分析                              | 补充信息不用回答，可以直接带着确认                   |
| 加日志中                     | —                                             | 只读，显示「它在加日志」              | 对话里照常看它改                                     |
| 等复现                       | 交日志，继续分析                              | 复现不了、取消修复                    | 弹窗换成复现步骤 + 贴日志框 + 附文件                 |
| 修复中 / 已处理 / 旧版本     | —                                             | 只读                                  | 和现在一样                                           |

### 2.4 「继续探讨」怎么更像讨论

- 侧栏分两个标签：「本版标注」（现在的标注）和「讨论」（按版本串起来）。讨论里每条意见下挂下一版的回答，标出「已回答 / 改了哪一节」，用户可以对回答点「追问」，直接变成本版的一条新标注，引用上一条。
- 新一版正文里改过的小节标「本版改动」，切版本时可以只看改动。
- 新一版还是一份完整报告（档案不变），只是展示上把它当成一轮回复。

## 3. 数据和工具（只列要改什么，不写实现）

### 3.1 档案里加结构化的日志计划

`BugCaseFields` 加：

```ts
logPlan: z.array(z.object({
  id: str(20),            // L1、L2
  file: str(500),         // 相对项目根
  line: z.coerce.number().int().positive().optional(),
  fn: str(300),
  print: str(1000),       // 打什么：分支条件、关键变量、旧值 → 新值
  hypothesis: str(300),   // 用来区分哪个假设（对上 hypotheses 的序号）
})),
repro: {                  // 怎么复现（和现有 repro 文字并存）
  steps: z.array(str(500)),
  selfRun: z.boolean(),   // Agent 自己能跑：同意后它加完日志自己复现
},
collect: {                // 日志怎么拿回来
  where: str(500),        // 日志文件 / 控制台 / 浏览器 DevTools
  filter: str(300),       // 例如 grep "[排查-拖线]"
  expect: str(1000),      // 每种结果说明什么：看到 A 是假设 1，看到 B 是假设 2
},
```

`diagnosisProblem`：`confirmed: false` 时要求 `logPlan` 至少一条、每条写了 `print` 和 `hypothesis`，`collect.expect` 不能空（用户贴回来之前就知道每种结果意味着什么）。`next` 保留作补充说明。

### 3.2 决定和状态

- `Diagnosis.status` 加 `logging`（同意加日志）和 `awaiting`（日志加好了，等用户复现）。
- `DiagnosisDecision` 从 `approve / cancel` 改成 `action: 'fix' | 'log' | 'discuss' | 'evidence' | 'supply' | 'cancel'`，加 `logs: string`（用户贴的日志或附件路径）。`evidence` 是修复方案上的「先加日志证实」，`supply` 是「我来贴日志」和等复现时的「交日志」。
- 标注种类加一种「要证据」：Agent 下一版要么补上证据，要么把它放进日志计划。

### 3.3 新的面板工具 `ready_for_repro`

加完日志后调用：写本轮实际加的位置（对上 logPlan 的 id）和最终的复现步骤。面板把状态改成 `awaiting`，这一轮结束，交报告那一行显示「等你复现」。`selfRun` 的不用调。

### 3.4 拦截和收尾

- `bugDeny`：`logging` 状态只放行日志计划里的文件；`awaiting` 状态不放行。
- `diagnosisGate` 已经会拦留着的 `[排查-` 临时日志，不变。
- `diagnosisFeedback`：按 action 分别写交给 Agent 的话；`fix` 那一支带上全部标注（修 §1.3 第 1 条）；`log` 那一支说「只加日志计划里的日志、统一前缀、不改逻辑；能自己跑的自己跑，不能的调 `ready_for_repro`」（修第 2 条）。

### 3.5 对话里的计划

日志计划存在时，面板替它在计划里补三步：「加日志（L1–L3）」「等你复现」「分析日志」，状态跟着 `logging / awaiting` 走。这就是用户说的「计划里要列出日志怎么补」。

## 4. 弹窗 UI

示例见 [Bug 确认弹窗示例](https://claude.ai/artifact/So4QWtswQoSqT4eodVL57e)（三个状态可切换：取证计划、等你复现、修复方案带疑问；示例里的文件和日志是虚构的）。要点：

- 头部：标题 + 第几版 + 阶段条。
- 正文顶部结论卡：根因（标「假设」或「已证实」）、下一步要你做什么、要改 / 要加日志的文件。
- 取证计划时，结论卡下面是「日志计划」表（位置、打什么、区分哪个假设）和「每种结果说明什么」，再下面是假设表和完整报告。
- 等复现时，正文换成复现步骤清单 + 日志粘贴框 + 附文件；右栏显示这一轮要贴回的过滤条件。
- 侧栏：「本版标注 / 讨论」两个标签；没标注时主按钮按阶段，有标注时主按钮变「继续分析，出第 N+1 版」。

## 5. 开放问题

1. 「我来贴日志」要不要也要求先有日志计划？倾向不要求：用户手上已有日志时直接贴，Agent 拿去分析。
2. `logging` 状态要不要检查加的内容只是日志（例如 diff 里只多了带 `[排查-` 的行）？倾向先只按文件拦，收尾时由现有的临时日志检查兜住；内容检查容易误伤。
3. 取证轮数要不要上限？倾向不设硬上限，第 3 轮起在阶段条上标黄，提示考虑换思路或让用户介入（和方法里「三次停」一致）。
