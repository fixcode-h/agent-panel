## 1. 现状：工作流和子对话是怎么缠在一起的

按 ADR 0044，父对话调用 `start_workflow` 时，在自己下面开一个「工作流子对话」，在任务上记一个 `flow` 字段（`shared/task-flow-schema.ts`）。之后：

| 环节           | 现在谁做                                                                                                                             | 代码位置                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| 承载运行       | 一个完整的子对话：有执行角色、CLI 会话、消息流、独立分支、认领、8 个对话状态                                                         | `server/tasks/run.ts` 的 `spawnChild`；`flow-child.ts`                               |
| 跑节点         | 子对话的第一轮由引擎按流程图跑                                                                                                       | `flow-child-run.ts` → `shared/engine.ts` 的 `startPlan` / `runFlow`                  |
| 节点之间的判断 | 流程图里的「主 Agent」：常驻在 `@main` 步骤上的一个 CLI 会话，每个子节点做完都要评估一次，还负责选路和最后整理结果                   | `shared/engine.ts` 的 `openMain` / `mainEvaluates` / `mainTurn`                      |
| 收尾           | 流程图跑完后，同一个子对话的执行角色接手：评审 → 完整测试 → `submit_merge`                                                           | `flowHandoffPrompt`                                                                  |
| 方案确认       | 节点设了「完成后等用户确认」时，在工作流子对话里挂一条 `kind: 'confirm'` 的请求；父对话只在子对话那一行行尾放一个「查看结果」按钮    | `server/exec/real-turn.ts` 的 `confirm`；`web/src/components/tasks/ChildConfirm.tsx` |
| 停止和继续     | 跟着子对话走 0042 那套：暂停、递归拉起、`resumeKids`                                                                                 | `shared/resume-kids.ts`、`shared/run-stops.ts`                                       |
| 显示           | 子对话栏里和普通子对话排在一起，标一个流程图标和「工作流 · 名字 n/m」；右栏打开后有「输出 / 流程图」切换，下面接着执行角色的收尾对话 | `web/src/components/tasks/ChildrenBar.tsx`、`child-line.ts`、`RunCard.tsx`           |

这些事实决定了下面的判断：

- **内置工作流默认都开着主 Agent。** `WorkflowFields.dispatch` 的注释写「没写等于打开」，内置工作流都没写。所以每个子 Agent 节点做完，都要多一次主 Agent 的模型调用。按上次的实测，这个接口上一次调用光等首包就要 9–20 秒。
- **一个工作流至少同时挂着三类 CLI 会话：** 各节点的会话、主 Agent 的常驻会话、收尾的执行角色会话。
- **子对话的规则都会作用到工作流子对话上：** 自驱推进、结束前自检、空闲询问、卡住重开、收尾规则……以后改子对话的任何一条，都要回头确认工作流会不会受影响。这就是你说的「混在一起」。

## 2. 问题 1：工作流子对话、主 Agent 还有没有必要

工作流现在套了三层「管理者」，逐层看：

### 2.1 工作流子对话（承载层）：作为「对话」不必要，作为「容器」需要

运行确实需要一个地方放东西：流程图快照、各节点的状态和会话、运行记录、独立分支、待确认请求、改动快照。但这些都不需要它是一个「对话」：

- **执行角色那个 CLI 会话：** 流程图跑完之前一直不用；跑完以后只做收尾，而收尾的大部分动作是面板本来就会做的（见 2.3）。
- **消息流：** 运行的输出本来就按节点存（`task.steps` + 各节点的消息），执行角色的消息流和节点输出混在一起反而难读。
- **对话状态、自驱、空闲询问、卡住重开：** 这些是为「模型自己推进的对话」设计的。工作流由面板按图推进，节点卡住有节点级的超时和重试，不需要对话级的这一套。

**结论：** 换成一个独立的「工作流运行」记录，不再是 Task 的子对话。见第 3 节。

### 2.2 主 Agent（调度层）：默认去掉，保留成可选的高级用法

主 Agent 现在管四件事，各有更便宜的替代：

| 主 Agent 现在做的                    | 替代                                                                                                          |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| 评估子节点做得好不好，决定通过或退回 | 节点的「验收流程」（`hooks.review`）本来就在做；评估规则写在验收节点里，比写在一个什么都管的主 Agent 里更清楚 |
| 条件连线选路（通过 / 不通过）        | 由出边前面那个节点用 `submit_verdict` 交结论（已有工具），面板按结论走线，不读回复文字                        |
| 委派另一个工作流                     | 流程图里的「调用流程」节点（`kind: 'flow'`）静态写好；运行中不再临时起别的工作流                              |
| 跑完整理最终结果                     | 加一个可选的「总结」节点，或者由面板拼各节点的结论（不调模型）                                                |

收益：

- 每个子节点省一次模型调用，也就省一次首包等待。
- 少一个常驻 CLI 会话，也少一类「主 Agent 和验收意见打架」的情况。代码里已经专门写了「有验收或确认的节点主 Agent 不再评估」来避免打架。

保留的场景：用户自己的工作流确实需要「做完看情况决定下一步走哪」的动态调度时，在编辑器里打开「动态调度」开关，行为和现在一样。**内置工作流全部关掉**（D1）。

### 2.3 执行角色收尾（收尾层）：改成运行的固定收尾阶段，不再开一个 Agent 会话

现在 `change` 类工作流跑完，执行角色做「评审 → 完整测试 → 合回」。拆开看：

| 收尾动作               | 需要模型吗 | 新设计里谁做                                                                                                |
| ---------------------- | ---------- | ----------------------------------------------------------------------------------------------------------- |
| 评审                   | 要         | 运行自带的「评审」阶段，派一个评审节点（和现在执行角色派的评审是同一个内置角色、同一份 diff）               |
| 完整测试和编译         | 不要       | 面板按项目的测试步骤直接跑（`agent-test-steps.md` 那套，后台命令）                                          |
| 评审或测试没过，就地修 | 要         | 运行自带的「修复」阶段：一个修复节点带着评审意见和测试输出修，修完回到评审 / 测试，最多 N 轮                |
| 交给父对话合回         | 不要       | 运行进入「待合回」，发一封信给父对话；父对话用 `finish_workflow` 合回或放弃，合回走现有的 `integrateBranch` |

这样一个工作流从头到尾只有节点会话。收尾阶段在流程图上画成固定的尾巴（评审 → 测试 → 修复回路 → 待合回），用户看得见每一步。`readonly` 类没有收尾阶段，跑完直接把结果交回父对话。

## 3. 新设计：工作流运行（Run）是一种独立的执行单元

### 3.1 父对话名下的三种执行单元

|                    | 子任务（`spawn_agents`） | 子对话（`create_conversation`） | 工作流运行（`start_workflow`）  |
| ------------------ | ------------------------ | ------------------------------- | ------------------------------- |
| 是什么             | 一次性的小活             | 一个由模型自己推进的对话        | 按流程图由面板推进的流水线      |
| 有没有自己的对话   | 没有                     | 有                              | **没有**（只有节点的会话）      |
| 谁推进             | 子 Agent 自己            | 执行角色（自驱、计划）          | 面板（状态机）                  |
| 状态               | 子任务状态               | 8 个对话状态（0005 / 0042）     | 运行自己的状态机（3.3）         |
| 收尾               | 自动交回                 | 执行角色收尾 → 父对话合回       | 运行的固定收尾阶段 → 父对话合回 |
| 改了会不会互相影响 | —                        | 只影响子对话                    | 只影响工作流                    |

### 3.2 共用的是「零件」，不是「对话」

这些零件现在已经是独立模块，工作流运行直接用。用的是它们的接口，不是子对话本身：

| 零件                                                 | 现有位置                                               | 工作流运行怎么用                               |
| ---------------------------------------------------- | ------------------------------------------------------ | ---------------------------------------------- |
| 跑一个节点（拼提示、起 CLI、续会话、解析输出、钩子） | `server/exec/runner.ts`、`shared/engine.ts` 的节点部分 | 原样用                                         |
| 流程图推进（节点、连线、子流程、验收轮次、确认）     | `shared/engine.ts` 的 `runFlow` 一带                   | 原样用，去掉对 `host.task` 是对话的假设（3.5） |
| 独立分支、依赖副本、合回                             | `server/exec/worktree.ts`、`worktree-integrate.ts`     | 原样用，分支挂在运行上                         |
| 预算、用量、首包                                     | `shared/budget.ts`、`AgentUsage`                       | 按运行记                                       |
| 暂停、终止的原语                                     | `shared/run-stops.ts`                                  | 原样用                                         |
| 生命周期诊断                                         | `shared/lifecycle.ts`                                  | 加一类「运行」节点                             |

### 3.3 运行的状态机

```
排队 ─► 准备（开分支、拷依赖） ─► 执行节点 ⇄ 等确认
                                    │
                                    ├─► 节点失败（等决定）
                                    ▼
                            收尾：评审 ─► 测试 ─► 修复 ↺（最多 N 轮）
                                    ▼
                      待合回（change）／ 已完成（readonly）
                                    ▼
                              已合回 ／ 已放弃

任意阶段 ─► 暂停（可继续）       任意阶段 ─► 已终止
```

- 每个状态都落盘，带着「停在哪个节点、哪个子阶段」：节点执行中、验收中、等确认、评审中、测试中、修复中。继续时按这个子阶段接着走（第 8.2 节）。
- 只有三种情况会叫醒父对话：等决定（节点失败、修复轮次用完）、待合回 / 已完成、已终止。其余状态变化只推给界面，不发信（沿用 0034「信和状态分开」）。

### 3.4 存在哪里

- **新记录类型** WorkflowRun，存成 `tasks/runs/<运行 id>.json`：工作流快照、输入、种类、状态、子阶段、节点步骤、各节点会话、分支、待确认、用量、事件日志。
- 它属于某个父对话（`ownerTaskId`）。父对话的任务上只记它名下运行的 id 列表，和子对话一样按 id 关联，不把运行的数据塞进父对话的任务文件。
- 日志沿用每个单元一份的做法，写进 `tasks/runs/<运行 id>.log`。

### 3.5 引擎要改的地方

`runFlow` 现在通过 `EngineHost.task` 读写一个 Task。拆的方法是加一层「运行宿主」（RunHost）：

- **对外提供引擎要的那几样：** steps、sessions、runs、usage、requests、changed、runAgent、confirm、reviewDiff。
- **数据落在 WorkflowRun 上**，不落在 Task 上。
- **只是挪地方，节点推进的逻辑不变。** 对话那一侧的 `runConversationTurn` 不再碰流程图：`startPlan` 和 `flow-child-run.ts` 从对话里搬出去。

## 4. 问题 2：父对话和工作流怎么通讯

原则：**父对话下指令，运行回事件；父对话的上下文里只放结论和指针，不放节点的全文。**

### 4.1 父对话 → 运行（面板工具）

| 工具               | 作用                                                                                                                                                                                |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `start_workflow`   | 开一次运行。参数沿用：`workflow`、`input`、`files`、`step`、`route`，返回运行 id。去掉 `again`，改用 `revise_workflow`                                                              |
| `list_workflows`   | 名下运行的一行摘要：名字、状态、子阶段、当前节点、n/m、等什么。也可以并进 `list_conversations`，见 D3                                                                               |
| `message_workflow` | 给运行补充要求。`to` 取三种之一：`current`（交给正在跑的节点，能插话就插话，不能就留给它下一轮）、`later`（记成运行级说明，之后所有节点都带上）、`node`（指定节点，它下次跑时带上） |
| `revise_workflow`  | 调整方案：从某个节点带着意见重跑，它之后的节点标成「过期」重跑（第 8.3 节）                                                                                                         |
| `answer_workflow`  | 替用户回答确认或决定。只在用户点了「交给父对话决定」时可用，和现在子对话提问的委托是同一个口径                                                                                      |
| `stop_workflow`    | 终止。没跑的节点不跑，已有改动列清单交回                                                                                                                                            |
| `finish_workflow`  | 待合回时：`merge`（合回父对话所在的分支，走现有的合回和编译排队）或 `discard`（删分支）                                                                                             |

### 4.2 运行 → 父对话（信）

- 信的格式固定：`{运行 id, 类型, 节点, 一句话结论, 全文指针}`。类型只有四种：等决定、待合回、已完成、已终止。
- 父对话收到的是「工作流『通用项目』待合回：改了 12 个文件，评审通过、测试 5/5 通过，详情见 <指针>」，不是节点的全文。
- 父对话计划里的等待加一类 `kind: 'run'`，和等子对话一样挂、一样结算。

### 4.3 父对话每一轮看到的现状

提示词里「名下的工作流」一节，每个运行一行，例如：

- 「工作流『通用项目』第 1 次运行：3/6，等用户确认『方案』」
- 「工作流『代码评审』：已完成，结论见 <指针>」

父对话不用轮询，也不会因为节点开始、结束被叫醒。

## 5. 问题 3：工作流的能力范围，什么时候用、什么时候不用

### 5.1 能力边界

| 工作流能做                                                      | 工作流不能做                                                               |
| --------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 按流程图跑节点（每个节点一个角色、档位、参数）                  | 开子对话、起别的工作流（流程图里静态的「调用流程」节点除外）               |
| 节点里派子任务（`spawn_agents`）并行查资料、核实                | 推送、合并主干、发布、P4 submit 这类对外操作（交回父对话做）               |
| 验收回路、条件连线、子流程、等用户确认                          | 运行中改流程图本身（改了只影响下一次运行）                                 |
| `change` 类在自己的独立分支里改代码；收尾阶段评审、跑测试、修复 | 直接改父对话的目录                                                         |
| 运行级说明、节点级补充要求                                      | 和用户自由对话。用户的话通过父对话或运行面板交进来，交给哪个节点有明确去处 |

### 5.2 什么时候用：三个条件同时满足

1. **步骤事先定得下来**：做什么、按什么顺序，不取决于上一步查到了什么。
2. **有不能跳的门禁或留痕**：先确认方案再动手、迁移和回滚成对写、每批升级都验证、要出 ADR。
3. **会重复做**：同一类事在这个项目里会做很多次，值得固定成剧本。

### 5.3 什么时候不用

- **边查边定的事：** Bug 定位、排查、调研。下一步取决于上一步，拆成固定节点会丢线索。
- **一问一答、分析、一两个文件的小改动：** 起一次运行的固定开销（开分支、节点提示、收尾）比事情本身大。
- **要和用户来回商量的：** 需求还没定，先在父对话里聊清楚，再决定交子对话还是起工作流。
- **对外操作：** 推送、发布由父对话按授权做。

### 5.4 判定规则仍然只写在一处

规则就是 `flow-child.ts` 的 `WORKFLOW_PICK_RULES`，挪进 shared/workflow-run/pick.ts。内容按 5.2、5.3 改写：用户点名了就用，拿不准就交给子对话。

## 6. 问题 4：方案确认在父对话里怎么显示、怎么交互

### 6.1 放在哪：父对话的对话流里一张「工作流卡片」

- 卡片插在启动它的那条回复后面，跟着运行实时更新。
- 不再只是子对话栏行尾的一个小按钮。

```
╭─ 工作流 · 通用项目  第 1 次运行 ─────────────── 3/6 · 等你确认 ─╮
│ ✓ 需求分析   ✓ 方案设计   ⏸ 确认方案   ○ 实现   ○ 文档   ○ 收尾 │
│                                                                    │
│ 方案要点（节点「方案设计」的结论，前 6 行）                         │
│  • 新增 WorkflowRun 记录，存在 tasks/runs/                          │
│  • …                                                               │
│                                                                    │
│ [查看完整方案]  [确认，继续]  [提出修改…]  [追问…]  [交给父对话决定] │
╰────────────────────────────────────────────────────────────────────╯
```

### 6.2 交互

| 操作           | 结果                                                                                                          |
| -------------- | ------------------------------------------------------------------------------------------------------------- |
| 查看完整方案   | 右栏打开这次运行，定位到这个节点，用现有的审阅视图看全文、能做标注（`ReviewDialog` 的能力搬进右栏，不再弹窗） |
| 确认，继续     | 卡片里这一步变成「✓ 已确认 · 时间」，运行往下走                                                               |
| 提出修改…      | 卡片里展开输入框。写意见后这个节点带着意见重做，做完再来确认。卡片上记「第 2 版」，能对比两版                 |
| 追问…          | 只问问题、不算退回：节点回答后仍停在等确认。不计入修改轮次                                                    |
| 交给父对话决定 | 父对话的 AI 拿到 `answer_workflow`，按它的判断确认或提修改；卡片写明「已交给父对话」                          |

### 6.3 卡片被滚上去时

- 输入框上方只出现一条「工作流『通用项目』等你确认」，点了滚回卡片。
- 同一时间只出现一条；几个运行都在等时，写「2 个工作流等你确认」。
- 不另弹窗、不挡输入（沿用「执行中不挡用户」的规则）。

### 6.4 确认的去向

- 确认的结论和意见记进运行的「决定记录」，后面每个节点的提示里都带上这份记录（见 8.3）。
- 父对话的上下文里只留一行：「用户确认了『方案』」或「用户要求修改『方案』：……」。

## 8. 问题 6、7、8：运行中发消息、父对话停止与重启、方案调整

### 8.1 问题 6：运行中能不能发消息？能，但要说清发给谁

运行没有自己的对话，所以没有「和工作流聊天」这回事。消息有明确的去处：

| 从哪发                                             | 发给谁       | 怎么处理                                                                     |
| -------------------------------------------------- | ------------ | ---------------------------------------------------------------------------- |
| 运行面板（右栏）底部的输入框，默认「交给当前节点」 | 正在跑的节点 | CLI 支持插话就插进这一轮，不支持就留到它下一轮。节点输出里画成「你补充：……」 |
| 同一个输入框，切到「之后的节点都要知道」           | 运行级说明   | 之后每个节点的提示都带上，记进决定记录                                       |
| 等确认时在卡片上写                                 | 等确认的节点 | 就是「提出修改」或「追问」（6.2）                                            |
| 父对话里对 AI 说「让工作流……」                     | 父对话的 AI  | AI 用 `message_workflow`，`to` 按意思选                                      |

**不能发的：**

- 运行已终止、已合回：输入框灰掉，提示「运行已结束，要再做一次请从父对话发起」。
- 收尾阶段的「测试」子阶段：没有模型在跑。消息记成运行级说明，交给下一个修复或评审节点。

### 8.2 问题 7：父对话停止、重启时运行怎么办

**父对话停止：**

| 怎么停的                       | 运行怎么办                                                 | 理由                                                      |
| ------------------------------ | ---------------------------------------------------------- | --------------------------------------------------------- |
| 父对话这一轮结束、停在等下一句 | 照跑                                                       | 运行不依赖父对话的 CLI，跑完发信，信会叫醒父对话          |
| 用户点父对话的「停止」         | **默认照跑**；停止按钮旁边多一个「连同工作流一起停」（D4） | 用户多半只是想停当前那个 AI，不想把排了半天的流水线也停掉 |
| 关闭面板、面板重启             | 暂停，面板起来后自动从断点接着跑                           | 进程没了，只能暂停；状态都落盘了                          |
| 用量上限到了                   | 暂停，等用户                                               | 和子对话一样                                              |
| 删除或归档父对话               | 终止，分支保留到回收期                                     | 没有人接收结果了                                          |

**父对话重新启动：**

- 父对话的续接说明里列出名下每个运行的一行现状。
- 不会因为父对话重启而重启运行：在跑的继续跑，停着的继续停着，等用户或父对话决定。

**运行在各个阶段被暂停后，继续时从哪里接着：**

| 停在哪           | 继续时                                                         | 和现在比                                                                                                    |
| ---------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 排队 / 准备分支  | 从头准备；分支已经开了就复用                                   | 一样                                                                                                        |
| 节点执行中       | 续同一个会话，提示「上次做到一半，检查后接着做」               | 一样                                                                                                        |
| 节点验收中       | 只重跑验收，不重做节点                                         | **改**：现在会连节点一起续                                                                                  |
| **等确认**       | **直接回到等确认**：结果原样还在，卡片原样出现，**不重跑节点** | **改**：现在停在等确认时节点被记成「做到一半」（`interrupted`），继续时要让模型再跑一轮才重新确认，白跑一轮 |
| 收尾：评审中     | 重新评审（评审没有副作用）                                     | 新                                                                                                          |
| 收尾：测试中     | 重跑测试                                                       | 新                                                                                                          |
| 收尾：修复中     | 续修复节点的会话                                               | 新                                                                                                          |
| 待合回           | 没有要继续的，等父对话 `finish_workflow`                       | 新                                                                                                          |
| 节点失败、等决定 | 不自动继续，等决定                                             | 一样                                                                                                        |

### 8.3 问题 8：方案调整、继续分析

**三种调整，按影响范围从小到大：**

| 用户想要                         | 操作                        | 运行怎么做                                                           |
| -------------------------------- | --------------------------- | -------------------------------------------------------------------- |
| 只是问清楚，不改方案             | 追问                        | 节点回答，仍停在等确认，不算一轮修改                                 |
| 方案要改，但还是这一步的事       | 提出修改                    | 这个节点带着意见在同一个会话里重做，出第 2 版，再确认                |
| 要退回更早的步骤（需求本身变了） | 「退回到…」选一个更早的节点 | 从那个节点带着意见重跑，它之后已经跑过的节点标成「过期」，按顺序重跑 |

**几条规则：**

- **决定记录：** 每次确认、修改、退回，都把结论和意见记进运行的决定记录，后面节点的提示里都带上。这样第 2 版方案之后的「实现」节点知道哪些是用户明确要求的。
- **版本对比：** 方案有第 2 版以后，卡片和右栏都能「对比上一版」，只看改了哪几段。
- **轮次上限：** 同一个节点修改超过 N 轮（默认 3），卡片提示「改了 3 轮还没定，建议在父对话里先把需求聊清楚」，同时给「交给父对话决定」。不会自动终止。
- **实现之后再改方案：** 实现已经开始、甚至在收尾了，用户回头改方案，按「退回到『方案设计』」处理：实现、文档、收尾都标过期，分支上的改动保留，重跑的实现节点在已有改动上调整，不从零开始。

## 9. 数据、接口和迁移

### 9.1 数据

- WorkflowRun：
  - 标识和来源：`id`、`ownerTaskId`、`projectId`、`workflow`（快照）、`input`、`kind`。
  - 状态：`status`、`phase`（子阶段）、`steps`、`sessions`、`requests`（等确认、等决定）。
  - 产出和记录：`decisions`（决定记录）、`notes`（运行级说明）、`worktree`、`usage`、`events`、`createdAt` / `endedAt`。
- 父对话的 Task 加 `runIds: string[]`；计划等待加 `kind: 'run'`。
- 去掉 `Task.flow`；`flow-child.ts`、`flow-child-run.ts` 拆进 shared/workflow-run/。

### 9.2 接口

- 面板工具：第 4.1 节的七个。
- HTTP 接口：
  - 读：`GET /runs/:id`。
  - 写：`POST /runs/:id/{message,confirm,revise,stop,finish}`。
  - 推送沿用对话的 SSE，事件带运行 id。
- 演示模式：`web/src/lib/demo-*.ts` 加运行的模拟数据。

### 9.3 迁移

- **已经完成的工作流子对话：** 照旧作为子对话只读打开。数据不搬，界面认得 `flow` 字段，用新的运行视图只读显示。
- **跑到一半的工作流子对话：** 升级后继续时，按老路径（工作流子对话）跑完这一次。之后新起的都是运行。
- **`mode: 'workflow'` 的更老任务：** 照 ADR 0044 的口径只读。
- **内置工作流：**
  - 关掉主 Agent 调度（D1）。
  - 要靠主 Agent 选路的条件连线，改成由前一个节点 `submit_verdict` 交结论。
  - 改前那一版按惯例登记进 `LEGACY_WORKFLOWS`。

- **D2 收尾谁做：** 收尾做成运行的固定阶段，评审节点 + 面板跑测试 + 修复回路（推荐）；还是保留「流程图跑完交给一个执行角色收尾」？

## 11. 分期、风险和验证

### 分期

1. **第 1 期：运行记录和引擎。**
   - 内容：WorkflowRun 存储、RunHost、状态机、子阶段落盘和断点续跑（含「等确认原样恢复」）、七个面板工具、信和计划等待。
   - 先只支持 `readonly` 类和没有收尾的跑法。
2. **第 2 期：收尾阶段。**
   - 内容：评审节点、面板跑测试、修复回路、待合回、`finish_workflow` 接现有合回。
   - `change` 类切到新路径。
3. **第 3 期：界面。**
   - 内容：工作流卡片和确认交互、子对话栏分组、右栏运行视图（输出 / 流程图，节点用时和首包）、版本对比、退回到某节点。
   - 老的三处查看收成一处。
4. **第 4 期：内置工作流和文档。**
   - 内容：关掉主 Agent（D1）、条件连线改 `submit_verdict`、新 ADR 取代 0044 的对应部分、`agent-catalog.md`、模块文档。

### 风险

- **引擎的 `host.task` 假设到处都是：** 加 RunHost 时要把 `runFlow` 用到的 Task 字段列全；先用单测锁住现有运行的行为再挪。
- **两套路径并存：** 升级前跑到一半的工作流子对话要按老路径跑完，老代码要留一段时间。
- **收尾从模型改成固定阶段后，少了「执行角色看情况补一刀」的灵活性：** 修复回路给足上下文（评审意见、测试输出、决定记录），轮次用完交回父对话决定，不硬撑。
- **父对话停止默认不停运行（D4）：** 要在界面上说清楚，不然用户以为全停了。

### 验证

- **单测：** 状态机每个子阶段的暂停和继续；等确认原样恢复、不重跑节点；退回到某节点后过期标记；信只在四类事件发。
- **端到端：** 用假 CLI 跑三条：
  - 父对话起运行 → 确认 → 收尾 → 待合回 → `finish_workflow` 合回；
  - 停在等确认时重启面板 → 原样回到等确认；
  - 实现后退回方案 → 实现重跑。
- **界面检查：** 工作流卡片的各个状态、亮暗两套主题、右栏运行视图。
