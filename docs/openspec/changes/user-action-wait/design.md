## 0. 一页结论

用户 2026-11-05 的原话：提问系统有点乱来，什么都走提问；像截图里那样等用户跑一次 PIE，应该像后台命令一样转圈表示在等，用户跑完回来点确认或者发日志，就结束等待往下走。不能用提问框，属于滥用。

1. **提问框只用来让用户拿主意**。判断只看一条：回答是「选哪个 / 是什么」用提问，回答是「做完了 / 这是结果」用等你操作。
2. **新增面板工具 `request_user_action`**。Agent 写清步骤、为什么要做、要交回什么、跳过时它怎么办，然后像交出后台命令一样结束这一轮，不占着进程。
3. **界面全部复用现有的位置和组件**，不新开地方：
   - 面板贴在发起它的那个对话的输入框上面，和提问面板同一个位置、同一套底色。可以收起，收起后就是一行转圈。
   - **输入框就是交回框**。贴日志、拖文件、写结果，发送就算交回。文件按路径交，和诊断报告弹窗一样。面板上只留「完成了，没有要交回的」「做不了…」「跳过」三个按钮。
   - 父对话里不单独出卡片（用户 2026-11-05 在示例上批注定的）：子对话那一行显示「等你操作」，后面加一个「去操作」按钮；输入框上方的子对话栏也不加胶囊。左栏有角标，会话栏的「状态」也会写。
4. **子对话发起的等你操作直接交给用户**，不管「提问」开关开没开。协调器不代答，也不改写成提问；父对话卡片上不放「交父对话决定」。
5. **Bug 对话不用等你操作**。复现贴日志、交验证结果，评审弹窗（诊断报告弹窗）里都已经有了，不另外加一套。等你操作只复用它的 `BugCollect` 字段形状。

## 1. 现在的问题

截图里，子对话缺一个「ID=106 的路牌蓝图路径」，这东西只有用户能拿到。协调器用 `ask_user` 问用户「你方便用哪种方式提供」，给了三个选项：补跑 PIE、在编辑器里选中路牌、不提供先出报告。

- **选项不是决定，是操作**。点了「补跑 PIE」，提问就结束了，可事情才刚开始。之后用户贴回来的日志只是一条普通消息，面板不知道它回答的是哪件事。
- **没有「在等」的状态**。点完选项，子对话只能停下来，看起来像结束了或卡住了，总览里看不出在等用户做什么、等了多久。
- **拿数据的方法不该让用户挑**。前两个选项是拿同一份数据的两种办法，Agent 应该自己选一个推荐的写成步骤，另一个放进「也可以这样」。
- **「不提供」是退路**，应该由 Agent 事先写好，用户点「跳过」就按它走。
- **协调器转述会失真**：「要贴回什么」「过滤条件」这些细节容易丢。

现有「停下来找用户」的通道，以及缺的那一个：

| 通道                           | 适合                                                       | 现状                   |
| ------------------------------ | ---------------------------------------------------------- | ---------------------- |
| `ask_user` / 原生提问          | 让用户拿主意                                               | 被拿来让用户去做事     |
| `suggest_next_step`            | 这一轮做完了，给下一步建议                                 | —                      |
| `end_turn`（`blocked`）        | 卡住了，又说不出具体步骤                                   | —                      |
| 评审弹窗（诊断报告、节点结果） | 各自流程里的确认；Bug 对话的复现贴日志、交验证结果也在这里 | 已上线，不在这次范围里 |
| **缺**                         | **用户要离开对话做一件事，再交回来**                       | 全挤进了提问           |

## 2. 能力边界：Agent 怎么判断

按顺序问自己，命中就停：

1. **我自己能做吗？** 能跑的命令、能读的文件、能跑的测试、能启动的程序，自己做。
2. **这一轮做完了，要给下一步建议？** 用 `suggest_next_step`。
3. **要用户在几种做法里拍板？** 偏好、范围、取舍、不可逆或对外操作的授权，用户不用离开对话就能答 → **提问**。
4. **要用户离开对话去做一件事，做完能交回结果？** 在本机、编辑器、浏览器、设备上操作；复现一次；登录、授权；给一个只在用户手里的文件、截图、日志、配置值 → **等你操作**。Bug 对话要用户复现、交验证结果时，走评审弹窗，不用它。
5. **做不下去，也说不出要用户做什么？** → `end_turn`（`blocked`）。

容易混的几种：

| 情况                                            | 用                   |
| ----------------------------------------------- | -------------------- |
| 「跑一次 PIE，把 `OnCreated hit` 那几行发回来」 | 等你操作             |
| 「用 PIE 抓日志，还是在编辑器里看路径？」       | 等你操作（一主一备） |
| 「要不要先加日志再修？」                        | 提问                 |
| 「装一下 SDK，装好告诉我」                      | 等你操作（只要确认） |
| 「我改好了，你在设备上看看效果对不对」          | 等你操作             |
| 「这个改动会删掉旧存档，确定吗？」              | 提问                 |
| 提问的某个选项写着「你去……然后发给我」          | 等你操作             |

- **一次只挂一件**：同一个对话最多一个未完成的等你操作。几件有先后关系的事，写成同一个请求的几步。
- **等的时候能干别的**：不依赖结果的事先做完再结束这一轮，和交出后台命令一样。

## 3. 工具

### 3.1 `request_user_action`

```ts
{
  title: string,        // 一句话要用户做什么：「跑一次 PIE，抓路牌的 Actor 路径」
  why: string,          // 拿到之后用来干什么
  collect: BugCollect & // 复用 shared/bug/diagnosis-schema.ts 的形状：steps / where / filter / expect
    { kind: 'confirm' | 'result' },  // confirm 只要确认做完；result 要交回东西（文字、日志、文件都走输入框）
  alternative?: { title: string, steps: string[] },   // 最多一个「也可以这样」
  fallback: string,     // 必填：用户点「跳过」时它怎么继续
}
```

- `collect.steps` 是 1 到 8 步，每步一个动作；`where` 写日志或结果在哪；`filter` 写过滤条件；`expect` 写看到什么说明什么。字段含义和评审弹窗里复现步骤的写法一样，界面可以共用渲染步骤的那一块。
- `fallback` 必填。这样用户才敢点「跳过」，也避免用户不做就永远卡着。
- 没有超时，等了多久显示在界面上。
- 返回给 Agent 的话：「已登记，等用户操作。不依赖结果的事可以先做完；做完就结束这一轮，不用调用 end_turn。用户交回时面板会作为新消息推给你。」
- 拒绝的情况：已有一个未完成的；这是 Bug 对话，要用户复现或交验证结果（让它走评审弹窗）；子任务、工作流节点、Chat 页没有这个工具。

### 3.2 和其他工具的关系

- **`end_turn`**：发起之后结束这一轮不用调 `end_turn`，结束前钩子在「在等别人」那一档放行（和提问、后台命令、子对话同一档）。`blocked` 留给说不出具体步骤的卡住。
- **计划**：`PlanWait.kind` 加 `user`。步骤挂上这个等待后显示「等你操作」，交回时按 `waitPlans` 一样收口。
- **`wait_user_message`**（对话页开着时停在进程里等下一句）：等你操作期间照常可以停在这里。用户在输入框发送交回时，这条消息直接作为工具结果交回去，省一次 `--resume`；进程已经退了，就走 `wakeConv` 开新一轮。两条路都是现成的。

## 4. 状态和数据

```ts
Task.userActions?: {
  id: string; title: string; why: string
  collect: BugCollect & { kind: 'confirm' | 'result' }
  alternative?: { title: string; steps: string[] }
  fallback: string
  status: 'waiting' | 'done' | 'returned' | 'cannot' | 'skipped' | 'cancelled'
  reply?: { text: string; files: string[]; at: string }   // 交回的文字和文件路径
  at: string; endedAt?: string
}[]
```

只留最近 20 条。字段名不叫 `awaitingUser`：这个名字已经被「CLI 停在等下一句」占了（`server/tasks/keepalive.ts`）。

- **`convState`**：有 `waiting` 的等你操作就归到 `needs`（等你处理），和提问、待确认请求同一组。行上的说法是「等你操作」，不是「等你回复」。
- **`childNeeds`**：子对话的等你操作也算进父对话，父对话一样显示「等你处理」。
- **状态说明**（`shared/tasks/diagnosis.ts`）：写「在等你操作：{title}，已等 12 分钟」，下面一行写退路。

推给 Agent 的话（不翻译），走后台命令结果推回的同一条路（`wakeConv`；子对话走 `sendToChild`，`panel: 'action'`）：

| 用户的操作           | 推给 Agent                                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------- |
| 输入框发送（交回）   | 【面板】用户完成了「{title}」并交回了下面的内容（消息原文照常显示在对话里）。按 why 接着做。 |
| 完成了，没有要交回的 | 【面板】用户完成了「{title}」，没有要交回的内容。接着做。                                    |
| 做不了（写原因）     | 【面板】用户做不了「{title}」：{原因}。换个办法，或者按退路「{fallback}」继续。              |
| 跳过                 | 【面板】用户跳过了「{title}」。按你写的退路继续：{fallback}。                                |

只看用户按了什么、发没发送，不看贴的内容像不像日志（不按文字判断状态）。

## 5. 子对话、协调器和几种边角情况

### 5.1 子对话发起

```
子对话 request_user_action
  ├─ 子对话：输入框上面出现等你操作面板（F），输入框边框变成提醒色，带「交回给：…」标签（G）
  ├─ 父对话：子对话那一行显示「等你操作」，后面加「去操作」按钮（B）；子对话栏不加胶囊
  ├─ 左栏：两个对话的角标都是「等你操作」（A）
  └─ 协调器的 AI：收件箱一条只读通知
用户在子对话里交回（父对话卡片上点「去操作」，右栏打开子对话）
  └─ 推给子对话开新一轮；父对话卡片收成一行「你已交回」（场景 3）
```

- **不看「提问」开关**。提问开关管的是拿主意的事交给谁。等你操作是 AI 做不了的事，谁都代答不了，所以一律交给用户。「提问」关着时也能发起，工具说明里加一句：先确认真的只有用户能做，`fallback` 要能让它不等也走得下去。
- **协调器不代答，也不转述**。协调器提示词里「子对话的提问和收尾建议怎么答」那一节加一条：子对话要用户做事时会自己发起等你操作，直接到用户，你不用转成提问；收到的子对话提问如果其实是要用户去做事，就用 `send_to_conversation` 让它改用 `request_user_action`。
- **父对话不单独出卡片**，只在子对话那一行后面加「去操作」，点了在右栏打开子对话；不放「交父对话决定」。交回只在子对话的输入框里进行，交回的文件和日志都属于子对话，只放在一处，两边不会对不上。

### 5.2 对话自己发起（含协调器）

和子对话里那块一样：面板在自己的输入框上面，没有父对话卡片。场景 2 画的是收起的样子，会话栏「状态」里写着在等什么。

### 5.3 边角情况（第一版漏掉的）

| 情况                         | 怎么处理                                                                                                   |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 用户只想聊别的，不是交回     | 点掉输入框上的「交回给：…」标签再发送，就是普通消息，等你操作还挂着                                        |
| 对话被停止、删除、进回收站   | 未完成的等你操作标成 `cancelled`，记录行写「已撤掉：对话被停止了」；恢复对话不自动挂回                     |
| Agent 发起了新的等你操作     | 旧的那个自动 `cancelled`（「一次只挂一件」，所以一般不会发生）                                             |
| 定时任务触发、没人看着的对话 | 照常挂起等人，不自动跳过（不悄悄替用户决定）；左栏和总览照常提醒                                           |
| 系统通知                     | 现在的浏览器通知只发「任务已完成 / 失败了」（`web/src/lib/notify.ts`）。加一种「等你操作」，开关沿用同一个 |
| 归档、已解决的子对话         | `convState` 已经会把收起的对话收敛成已完成；有等你操作的不能收起，和有提问时一样                           |
| Bug 子对话                   | 复现贴日志、交验证结果都在评审弹窗里，不发起等你操作；和诊断无关的操作（例如装个工具）才用它               |

### 5.4 子任务和工作流节点

不给这个工具。子任务缺东西就写进结果交回，由派它的对话来发起；工作流节点按现有的人工节点走。

## 7. 提示词要改的地方

- `ask_user` 的工具说明：只用来让用户拿主意；要用户离开对话去做事的用 `request_user_action`，不要把「去做…再发回来」写成选项。
- `childAskPrompt`（`shared/children/ask.ts`）：开着那一支补「要用户动手做事的用 request_user_action，它直接交给用户」；关着那一支补「自己确实做不了、要用户动手的，仍然可以用 request_user_action，写好退路」。
- 协调器提示词（`shared/builtin/agents.ts`）：第 3 条澄清和「子对话的提问和收尾建议怎么答」，按 §5.1 加。
- `BACKGROUND_WAIT_RULE` / `TURN_PROGRESS_RULES`（`shared/turn-rules.ts`）、`end_turn` 的说明：「在等后台命令、子对话、子任务」加上「等你操作」；能写出步骤的不用 `blocked`。

改完要搜测试里断言原句的地方（`server/engine-steps.test.ts`、`server/orch-mcp.test.ts`、`shared/children/ask.test.ts`）。

## 8. 开放问题

1. **自动检测日志**：面板跑在本机，能盯着 `collect.where` 写的日志文件，出现匹配 `filter` 的新行就提示「检测到 3 行新日志」。倾向以后再做，先把手动交回做稳。
2. **几个对话等同一件事**：比如两个子对话都要跑一次 PIE。倾向先靠协调器在回复里提醒「跑一次可以交给两个」，观察多不多再做界面。
3. **原生提问（Claude Code 的 AskUserQuestion）管不到参数**：只能靠提示词和「这需要我去操作」这个出口，不在钩子里加提醒，免得正常提问也多一轮。
4. **`end_turn` 的 `blocked` 要不要并进来**：倾向先并存，观察 `need` 里有多少其实能写成步骤。
