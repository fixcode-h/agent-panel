# 等你操作：把「请用户去做一件事」从提问框里拿出来（设计稿）

状态：待确认（只出设计，未改功能代码） · 2026-11-05

## 0. 一页结论

用户 2026-11-05 的原话：提问系统有点乱来，什么都走提问；像截图里那样等用户跑一次 PIE，应该像后台命令一样转圈表示在等，用户跑完了回来点确认或者发日志，就结束等待继续往下走。不能用提问框，属于滥用。

1. **提问框只用来让用户拿主意**。判断一句话：回答是「选哪个 / 是什么」用提问；回答是「做完了 / 这是结果」用等待操作。截图里的三个选项有两个是「你去做一件事再把东西发回来」，第三个是「不做」，这不是一个决定，是一件要用户动手的事，属于滥用。
2. **新增「等你操作」**：面板工具 `request_user_action`。Agent 写清楚要用户做什么（步骤）、为什么、要交回什么、跳过时它怎么办，然后像交出后台命令一样结束这一轮。对话在运行区多一行转圈的「等你操作」，状态归到「等你处理」。
3. **用户结束等待有四种方式**：完成了（只确认）、交回结果（贴日志 / 文本 / 附文件）、做不了（写原因）、跳过（让它按事先说好的退路继续）。直接在输入框发消息也算交回结果。结果按后台命令推回的同一条路交给 Agent，开新一轮接着做。
4. **不阻塞进程**。和 `ask_user` 一直挂在进程里等不同，等操作可能要十几分钟到几小时，工具调用立刻返回，这一轮正常结束；结束前钩子把「有未完成的等你操作」当成在等别人，放行。
5. **子对话发起的等你操作不经协调器代答，直接交给用户**。协调器的 AI 做不了用户手上的事，代答只会变成编造或者像截图那样再包装成提问。协调器收到一条通知，运行区的子对话行显示「等你操作」，用户在父对话里就能完成；协调器不再把子对话的操作需求转成提问框。
6. **怎么防止继续滥用**：工具说明、提问工具说明、协调器和子对话的提示词同时改，写清判断顺序（§2）；不靠读提问文字去拦（和「不按模型回复的文字判断状态」同一个原则），面板只在提问卡上给用户一个「这其实是要我做事」的转换按钮（§6.4）。

## 1. 现在的问题

### 1.1 截图里发生了什么

子对话查 StateFlow 条件配置，缺一个「ID=106 的路牌蓝图 / 模板 ID」，只有用户能拿到。它把问题交给协调器，协调器用 `ask_user` 问用户：

> 子对话需要 ID=106 对应的路牌蓝图 / 模板 ID，才能查它的 StateFlow 条件配置。你方便用哪种方式提供？
> ① 补跑 PIE 抓 Actor=（推荐） ② 在编辑器里选中那块路牌 ③ 不提供了，先出诊断报告

问题在于：

| 问题                       | 说明                                                                                                                                                               |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 选项不是决定，是操作       | 用户点了「补跑 PIE」之后，提问就结束了，可事情才刚开始：用户要离开去跑 PIE、过滤日志、再回来贴。贴回来是一条普通消息，面板不知道它在回答哪个问题。                 |
| 没有「在等」的状态         | 点完选项，子对话收到「补跑 PIE」，下一步只能停下等。这时对话看起来像结束了或卡住了，总览里也看不出在等用户做什么、等了多久。                                       |
| 拿数据的方法不该让用户挑   | ①和②是拿同一份数据的两种方法。Agent 应该自己选一个推荐的写成步骤，另一个作为「也可以这样」，而不是让用户先做一道选择题。                                           |
| 「不提供」是退路，不是选项 | ③其实是「跳过时你打算怎么办」。应该由 Agent 事先写好，用户点「跳过」就按它走。                                                                                     |
| 协调器转述失真             | 子对话的原始需求经过协调器改写成提问，用户看到的是协调器的话，「要贴回什么」「过滤条件」这些细节容易丢；子对话自己发起操作请求时，这些字段是结构化的、原样到用户。 |

### 1.2 现在有哪些「停下来找用户」的通道

| 通道                          | 是什么                               | 适合                                     | 现在被拿来做的事                   |
| ----------------------------- | ------------------------------------ | ---------------------------------------- | ---------------------------------- |
| `ask_user` / 原生提问         | 选项卡，阻塞在进程里等回答           | 让用户拿主意                             | 让用户去做事、确认结论、通知进度   |
| `suggest_next_step`           | 收尾时的下一步建议                   | 这一轮做完了，下一步给用户选             | —                                  |
| `end_turn`（`blocked`）       | 做不下去，`need` 写缺什么            | 卡住了，说不出具体步骤                   | 偶尔代替操作请求，但没有交回的入口 |
| `message_parent`（question）  | 子对话问父对话                       | 要父对话决定的事                         | —                                  |
| `submit_diagnosis` 等专用弹窗 | Bug 诊断报告、评审、收尾确认         | 各自的确认流程                           | —                                  |
| **缺**                        | **用户要离开对话做一件事，再交回来** | 跑 PIE、复现、登录、手动点编辑器、给文件 | 全挤进了 `ask_user`                |

## 2. 能力边界：Agent 怎么判断用哪个

按顺序问自己，命中就停：

1. **我自己能做吗？** 能跑的命令、能读的文件、能跑的测试、能启动的程序、能查的文档，自己做。不问也不等。（「能查到的事实自己查，不拿去问」本来就是规则。）
2. **这一轮做完了，要给下一步建议？** 用 `suggest_next_step`。
3. **要用户在几种做法里拍板？** 偏好、范围、取舍、不可逆或对外操作的授权，回答是一个选项或一句话，用户不用离开对话就能答 → **提问**。
4. **要用户离开对话去做一件事，做完能交回结果？** 在本机、编辑器、浏览器、设备上操作；复现一次；登录、授权、插 U 盾；给一个只在用户手里的文件、截图、日志、配置值 → **等你操作**（`request_user_action`）。
5. **做不下去，也说不出要用户做什么具体的事？** 缺需求、缺权限且不知道找谁、外部服务挂了 → `end_turn`（`blocked`）。

几条容易混的：

| 情况                                                 | 用                     | 为什么                                                                   |
| ---------------------------------------------------- | ---------------------- | ------------------------------------------------------------------------ |
| 「跑一次 PIE，把 `OnCreated hit` 那几行发回来」      | 等你操作               | 用户要离开去做，交回的是结果                                             |
| 「用 PIE 抓日志，还是在编辑器里选中 Actor 看路径？」 | 等你操作（一主一备）   | 两种都是拿同一份数据的方法，Agent 选一个当主步骤，另一个放「也可以这样」 |
| 「要不要先加日志再修？」                             | 提问                   | 是做法的取舍，答完 Agent 立刻能动手                                      |
| 「装一下 xx SDK，装好告诉我」                        | 等你操作               | 用户要动手，回来点「完成了」                                             |
| 「这个改动会删掉旧存档，确定吗？」                   | 提问                   | 不可逆操作的授权                                                         |
| 「我改好了，你看看效果对不对」                       | 等你操作（交回：确认） | 要用户实际去看；交回「没问题」或者「不对，现象是……」                     |
| 「我做完了，接下来可以 A 或 B」                      | `suggest_next_step`    | 收尾建议                                                                 |
| 「缺需求文档，不知道这个按钮该干什么」               | 提问（问清需求）       | 用户能直接回答；问不出来才 `end_turn` blocked                            |
| 提问的某个选项写着「你去……然后发给我」               | 等你操作               | 选项里出现「去做…再发回来」就说明这不是提问                              |

**一次只挂一件**：同一个对话同时最多一个未完成的等你操作。要用户做的几件事有先后关系，就写成同一个请求的几步；互不相关的，先挂最要紧的那件，另一件写进退路或下一轮。

**等的时候还能干别的**：发起之后，不依赖结果的事可以接着做完再结束这一轮（和交出后台命令一样）；依赖结果的就直接结束。

## 3. 工具：`request_user_action`

### 3.1 参数

```ts
{
  title: string,          // 一句话要用户做什么：「跑一次 PIE，抓路牌的 Actor 路径」
  why: string,            // 拿到之后用来干什么：「定位 ID=106 对应的蓝图，才能查 StateFlow 条件」
  steps: string[],        // 1~8 步，每步一个动作；可以带命令、过滤条件，界面按代码块显示
  collect: {
    kind: 'confirm' | 'text' | 'log' | 'file',  // 要交回什么：只要确认 / 一段文字 / 日志 / 文件
    what: string,         // 交回什么、长什么样：「`Actor=` 后面的蓝图路径，形如 /Game/...」
    filter?: string,      // 日志的过滤条件：界面给「复制」按钮，贴进来时只高亮匹配的行
    watch?: { file: string, match: string },   // 可选，第二期：面板盯着这个日志文件，出现匹配的行时提示交回
  },
  alternatives?: {        // 0~2 个「也可以这样」：拿同一份东西的别的办法
    title: string,
    steps: string[],
  }[],
  fallback: string,       // 必填：用户点「跳过」时它怎么继续。「先按现有证据交诊断报告，条件配置标成未定位」
}
```

- `fallback` 必填：逼 Agent 事先想好没有这份东西时的退路，用户才敢点「跳过」，也避免「用户不做就永远卡着」。
- 不设超时。等了多久显示在界面上，总览按等待时长排。
- 返回给 Agent 的话：「已登记，等用户操作。不依赖结果的事可以先做完；做完就结束这一轮，不用调用 end_turn。用户交回结果时面板会作为新消息推给你。」

### 3.2 配套

- `cancel_user_action(reason)`：Agent 自己找到别的办法了，撤掉请求。卡片收起，写一行「它不需要了：原因」。
- 计划里的步骤可以挂这个等待：`PlanWait.kind` 加 `user`，步骤显示「等你操作」，交回时按 `waitPlans` 一样收口。
- 一个对话已有未完成的等你操作时再调用：拒绝，提示「先 cancel 或合进同一个请求」。

### 3.3 和 `end_turn` 的关系

- 发起等你操作之后结束这一轮，不需要 `end_turn`：结束前钩子在「在等别人」那一档放行（和提问、后台命令、子对话同一档）。
- `end_turn`（`blocked`）留给「说不出具体步骤」的卡住。工具说明里写：能写出步骤、能说清要交回什么的，用 `request_user_action`。

## 4. 状态和数据

### 4.1 记在哪

```ts
Task.userActions?: {
  id: string
  title: string; why: string; steps: string[]
  collect: { kind; what; filter?; watch? }
  alternatives: { title; steps }[]
  fallback: string
  status: 'waiting' | 'done' | 'returned' | 'cannot' | 'skipped' | 'cancelled'
  reply?: { text: string; files: string[]; by: 'user'; at: string }
  at: string; endedAt?: string
}[]
```

最近的在最后，只留最近 20 条（和 `turnEnds` 一样截断）。

### 4.2 对话状态

- `convState`：有 `waiting` 的等你操作，归到 `needs`（等你处理），和提问、待确认请求同组；行上的说法是「等你操作：<title>」，不是「等你回答」。
- 列表和总览的图标：用 `warning` 色的转圈（和执行中的 `run` 青色转圈区分），表示「在等，但球在你这边」。
- 父对话：`childNeeds` 把子对话的等你操作算进去，父对话自己也显示「等你处理」。
- 状态诊断（`task-diagnosis.ts`）：「为什么停在这里」写「在等你操作：<title>，已等 12 分钟」。

### 4.3 结束等待时交给 Agent 的话

按后台命令结果推回的同一条路（`wakeConv` / 子对话走 `sendToChild`，`panel: 'action'`），正在跑就实时送达，空闲就开新一轮：

| 用户的操作         | 推给 Agent 的话（不翻译）                                                                                          |
| ------------------ | ------------------------------------------------------------------------------------------------------------------ |
| 完成了             | 【面板】用户完成了你请求的操作「{title}」，没有要交回的内容。接着做。                                              |
| 交回结果           | 【面板】用户完成了「{title}」并交回：\n{text}\n附件：{files}。按 why 里说的用它接着做。                            |
| 做不了             | 【面板】用户做不了「{title}」：{原因}。换个办法，或者按退路「{fallback}」继续。                                    |
| 跳过               | 【面板】用户跳过了「{title}」。按你写的退路继续：{fallback}。                                                      |
| 直接在输入框发消息 | 当成「交回结果」，消息原文照常显示在对话里；推给 Agent 的话前面加一行「（这条消息是对等你操作「{title}」的回复）」 |

- 交回的日志很长时：全文存成附件（项目根 `.tmp/` 下），消息里只放过滤后的行（有 `filter` 时）和前后各 20 行，写明附件路径，Agent 要时自己读。
- 交回只看用户点了什么按钮，不看贴的内容像不像日志（不读文字判断状态）。

## 5. 子对话和协调器

### 5.1 子对话发起

```
子对话 request_user_action ──► 子对话：卡片 + 运行区转圈「等你操作」
        │                      父对话：运行区子对话行「等你操作：跑一次 PIE…」，点开就是同一张卡
        │                      协调器 AI：收件箱一条通知（只读，不用回）
        ▼
用户在子对话或父对话里任一处交回 ──► 推给子对话，开新一轮
                                  └► 父对话的卡片同时收起；协调器收件箱换成「用户已交回」
```

- **不看「提问」开关**。提问开关管的是「拿主意的事交给谁」：关着时子对话自己决定，开着时交给父对话 / 用户。等你操作是 AI 做不了的事，谁都不能代答，所以一律到用户。
  - 子对话「提问」关着时仍然可以发起，但工具说明加一句：先确认真的只能用户做；`fallback` 要能让它不等也走得下去。
- **协调器不代答，也不转述**。协调器提示词「子对话的提问和收尾建议怎么答」那一节加一条：子对话要用户做事时，它自己会发起等你操作，直接到用户，你不用转成提问；你收到的子对话提问里如果其实是要用户去做事，用 `send_to_conversation` 让它改用 `request_user_action`，不要自己包装成提问框。
- 协调器能做的：两个子对话都在等同一类操作时（例如都要跑一次 PIE），在回复里提醒用户「跑一次可以同时交给两个」；第二期界面支持一次交回给多个（§7）。

### 5.2 协调器自己发起

和普通对话一样。协调器常见的情况：要用户提供账号、在外部系统里点一下、在设备上验证。

### 5.3 工作流节点和子任务

- 子任务（`run_agent` 派的）没有这个工具：它们是短命的执行单元，缺东西就把缺什么写进结果交回，由派它的对话发起等你操作。
- 工作流节点：第一期不给。节点需要用户操作时按现有的「人工节点」走；以后需要再说。

## 6. 界面

示例见文首链接，有五块：

### 6.1 运行区那一行（收起时）

和后台命令同一个位置、同一个高度，在消息流底部：

```
◌ 等你操作   跑一次 PIE，抓路牌的 Actor 路径          已等 12 分钟   [交回结果]  [完成了]  ⌄
```

- 左侧 `warning` 色的转圈 + 「等你操作」药丸；标题；等待时长；两个最常用的按钮直接放在行上；`⌄` 展开卡片。
- `collect.kind` 是 `confirm` 时只有「完成了」；是 `log` / `text` / `file` 时主按钮是「交回结果」，「完成了」换成「没有要交回的」放进展开卡里。

### 6.2 展开的卡片

从上到下：

1. 头部：「等你操作」药丸、发起方（「子对话 · 查路牌条件配置」或「协调器」）、等待时长、收起按钮。
2. 标题（大一号）和「为什么」（muted 一行）。
3. **步骤清单**：带序号，每步可以勾掉（只在界面上记，方便用户自己对着做，不交给 Agent）；代码和过滤条件按 inline code 显示，带「复制」。
4. **要交回什么**：一块浅底，写 `collect.what`；有 `filter` 时显示过滤条件和「复制」。
5. **交回框**：多行文本框（等宽字体，贴日志用），下方「附文件」和拖放区；有 `filter` 时贴进来的内容里匹配的行高亮，旁边写「匹配 3 行」，可以勾「只交匹配的行（全文作附件）」。
6. **也可以这样**（折叠）：备选做法的步骤。
7. 底部：左边「做不了…」（点了展开一行原因输入）、「跳过」（悬停 / 下方小字显示退路：「它会：先按现有证据交诊断报告」）；右边主按钮「交回并继续」（没内容时禁用），或 `confirm` 时「完成了，继续」。

### 6.3 结束之后

卡片收成对话里的一行记录（和工具调用行一样可以展开）：

```
✓ 你完成了：跑一次 PIE，抓路牌的 Actor 路径 · 交回日志 3 行（全文 1 个附件） · 等了 14 分钟
⤼ 你跳过了：…… · 它按退路继续：先交诊断报告
✕ 你做不了：…… · 原因：PIE 起不来，编辑器崩溃
```

### 6.4 提问卡上的「这其实是要我做事」

面板不替用户判断提问是不是滥用，只给一个出口：提问卡右下角的「不回答，让 AI 自己决定」旁边加一个次要按钮「这需要我去操作」。点了之后提问按「拒绝」结束，推给 Agent 的话是：「【面板】用户认为这不是一个选择，而是要他去做的事。改用 request_user_action，写清步骤、要交回什么和跳过时的退路。」Agent 改发等你操作。

### 6.5 父对话 / 协调器里的子对话行

运行区子对话行的状态位置显示 `warning` 转圈 +「等你操作」，标题后面跟操作的 title；点开行内展开同一张卡（不用切到子对话）。在父对话里交回和在子对话里交回效果一样。

## 7. 开放问题

1. **`watch` 自动检测**（第二期）：面板跑在用户本机，能直接盯 UE 的 `Saved/Logs/*.log`。出现匹配 `match` 的新行时卡片提示「检测到 3 行新日志」，一键交回。只读 Agent 写明的那个文件，路径显示给用户。倾向第二期做，先把手动交回做稳。
2. **一次交回给多个对话**：几个对话都在等同一件事时，卡片上能勾选「同时交给」。倾向第二期，先观察实际会不会经常重复。
3. **原生提问（Claude Code 的 AskUserQuestion）管不到参数**：只能靠提示词和 §6.4 的出口。要不要在钩子里对原生提问加一个「先想想是不是等你操作」的提醒？倾向不加：会给正常提问也增加一轮延迟。
4. **`end_turn` 的 `blocked` 要不要并进来**：blocked 的 `need` 很多时候其实也是「要用户做某件事」。倾向先并存，观察一段时间 blocked 的 `need` 有多少能写成步骤，再决定是否让 blocked 也带交回入口。
5. **Bug 确认弹窗的「等你复现」**（[设计稿](../bug-confirm-dialog/design.md) §3.3 的 `ready_for_repro` / `awaiting`）：建议直接建在这个机制上，`ready_for_repro` 内部发起一个 `collect.kind = log` 的等你操作并关联到诊断报告，弹窗里的「交日志，继续分析」和这里的「交回并继续」是同一个动作。两份设计稿确认后一起实施，免得做两套「等用户」。

## 8. 提示词要改的地方

- `ask_user` 的工具说明加：「只用来让用户拿主意。要用户离开对话去做一件事（跑程序、复现、在编辑器里操作、提供只在他手上的文件或日志）时用 request_user_action，不要把『去做…再发回来』写成选项。」
- `shared/child-ask.ts` 的 `childAskPrompt`（开着那一支）：「遇到拿不准的、需要用户确认的……用提问工具」后面补：「要用户动手做事的用 request_user_action，它直接交给用户，不经父对话。」关着那一支补：「要用户动手做事、你自己确实做不了时，仍然可以用 request_user_action，写好退路。」
- 协调器提示词（`shared/builtin/agents.ts` 第 3 条澄清、「子对话的提问和收尾建议怎么答」）：按 §5.1 加。
- `TURN_PROGRESS_RULES` / `BACKGROUND_WAIT_RULE`：「在等后台命令、子对话、子任务」那一句加上「等你操作」。
- `end_turn` 的说明：「能写出要用户做的步骤和要交回的东西时用 request_user_action，blocked 留给说不出具体步骤的卡住」。
