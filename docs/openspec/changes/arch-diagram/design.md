# 架构图：用 `/arch` 生成模块或项目的架构图（设计稿 v1）

状态：待确认 · 2026-11-05

参考 [Archify](https://github.com/tt-a1i/archify)（v3.2，Apache-2.0）：一个 Agent Skill，读代码后让模型写一份带类型的 JSON 描述，交给本地的校验器和渲染器出一张可交互的单文件 HTML 架构图，节点能点开看源码位置。下面先拆它好在哪、哪些不适合直接搬，再给面板里的做法。

## 0. 一页结论

1. **入口是 `/arch` 内置命令**，在项目里的对话中用：
   - `/arch`：整个项目的总览。
   - `/arch server`：一个模块。
   - `/arch 下单流程`：一条链路。
   - `/arch --type dataflow ...` 指定图的种类。

   不新开页面，图画在对话右栏的「架构图」页签里，对话里留一张可点开的卡片。

2. **模型只写「图的内容」，不写坐标和样式**。
   - 模型调用面板工具 `submit_diagram`，交一份带类型的图描述（下称 IR）：节点、分组、连线，每个节点挂上源码出处。
   - 面板做校验、自动布局和渲染。校验不过就把错误逐条交回去，让模型改，最多两轮。
   - 这和 Archify 一样，把「好不好看」从模型手里拿走。不同的是 Archify 让模型自己定坐标，面板改成自动布局（§3.3）。
3. **先给事实，再让模型归纳**。
   - 面板先用工具 `arch_facts` 算好静态事实：目录结构、按目录聚合的 import 依赖、入口文件、模块文档（`docs/MODULE-MAP.md` 和各模块 README）。
   - 模型在这些事实上取舍、命名、补上读代码才知道的东西（外部服务、协议、信任边界），不用每次从头把仓库翻一遍。
   - 节点和连线的出处由面板核对：文件在不在、行号是否越界。对不上的直接拒收，不会画出编出来的模块。
4. **图跟着代码版本走**。
   - 存图时记下提交号。以后打开时，面板看节点出处的文件在这之后有没有改过；改过的节点标「可能过期」，一键「按现在的代码更新」。
   - 更新后可以和上一版对比：新增、删掉、改了的节点和连线高亮出来。
5. **能分享**。
   - 导出单文件 HTML（自带数据和交互，离线能看）、PNG、SVG。
   - 可以存进项目文档目录（`docs/architecture/<名字>.arch.json`，再加一份导出的 HTML），跟着项目进版本管理。
   - 模块 README 里可以链过去。
6. **分期**（§8）：
   - 第一期：架构图一种 + 右栏查看 + 出处核对 + 导出。
   - 第二期：过期检测、版本对比、存进项目文档、点节点继续往下画。
   - 第三期：数据流、时序、状态三种图。

## 1. Archify 是怎么做的（2026-11 读了仓库的 README、SKILL.md 和 schemas）

| 方面     | Archify 的做法                                                                                                                                                                                                                                           |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 形态     | 一个 Skill（`archify/SKILL.md`），加一个零依赖的 Node 命令行（`bin/archify.mjs`）。模型读完代码，写出 `candidate.json`，再跑 `archify finalize <type> candidate.json out.html --repo-root .`                                                             |
| 中间格式 | 每种图一份 JSON Schema（draft 2020-12，`additionalProperties: false`）。架构图是 `components`、`boundaries`、`connections`，另有 `cards`（写在图下方的说明卡）。组件类型是枚举：frontend / backend / database / cloud / security / messagebus / external |
| 出处     | `meta.repository` 记仓库地址和完整提交号。节点带 1～3 条 `sources`（仓库相对路径 + 可选行号范围），渲染时只有 Git 校验过提交、文件和行号都对得上，才显示「SRC」标记                                                                                      |
| 校验     | 按 schema 严格校验，再查跨集合的引用（连线两端在不在、id 重不重复），再查布局（重叠、标签碰撞、线和标签的间距）。报错一行一条，带上是哪个节点                                                                                                            |
| 修正     | 失败后只改出错的那一片再整体跑一遍，最多两轮                                                                                                                                                                                                             |
| 布局     | **不是自动布局**：坐标、层次和间距都由模型写，连线默认自动走线                                                                                                                                                                                           |
| 输出     | 单个 HTML，可搜索、聚焦节点、看上下游、查两点之间的路径、导出 PNG / SVG / PDF                                                                                                                                                                            |
| 种类     | 架构、工作流、时序、数据流、状态、ERD、类图、树、时间线、瀑布图共 10 种，另有前后两版的对比（Architecture Delta）                                                                                                                                        |
| 明确不做 | 解析 Mermaid、通用自动布局、在线分享、所见即所得编辑                                                                                                                                                                                                     |

**值得照搬的**：

- 带类型、严格的中间格式；
- 校验失败按条交回去修，有轮数上限；
- 节点挂源码出处，并且由程序核对；
- 「概要放图上，细节放卡片」，控制节点数（它建议 8～12 个核心组件）；
- 校验全过才落盘（原子替换）。

**不适合直接搬的**：

- **装成 Skill 让 CLI 去跑**：图是 CLI 写在项目目录里的一个 HTML 文件，面板只能当附件看。没有右栏查看、点节点跳到面板的文件预览、过期检测和对比，也没法存在面板里统一管理。四种 CLI 还都得各装一份。
- **让模型写坐标**：模型对坐标、间距的把握很差，第一遍往往重叠，要靠校验来回修，浪费轮次和 token。面板已经有 `@xyflow/react` 画布，交给布局算法更稳。
- **10 种图一次做全**：用户要的是「看项目架构」，先把架构图一种做透。数据流、时序、状态放到后面（§8）。

## 2. 用户怎么用

1. 在项目里的对话中输入 `/arch`（`/` 菜单里有说明和参数提示），后面可以跟范围：
   - 不跟：整个项目的总览（按模块文档和顶层目录）。
   - 模块名或目录（`server`、`web/src/components/flow`）：这个模块内部的结构。
   - 一句话（`下单到支付的链路`）：沿这条链路画。
   - `--type architecture|dataflow|sequence|lifecycle`：第一期只有 architecture。
   - `--detail overview|standard`：overview 8～15 个节点；standard 最多 30 个，复杂模块用。
2. 对话里出现一张进度卡：读结构、归纳、校验（第几次）、完成。完成后卡片变成缩略图，点开就是右栏的「架构图」页签。
3. 右栏里能做的：
   - **看**：缩放、拖动、小地图、搜索节点（`/`）、按分组折叠展开。
   - **点节点**：右侧弹出详情，包括这个模块做什么、对外接口、关键文件（点了在面板的文件预览里打开到那一行）、出处，以及「从这里再往下画」（等于对这个节点发 `/arch <它的范围>`）。
   - **点连线**：看调用方式（HTTP / 函数调用 / 消息 / 读写存储）和出处。
   - **聚焦**：只看一个节点的上游、下游或两者，其余变淡。
   - **顶部工具**：导出（HTML / PNG / SVG）、存进项目文档、按现在的代码更新、和上一版对比。
4. 一个项目里画过的图都留着。项目侧栏和项目设置里有「架构图」列表，按范围列出每张图的时间、提交号和是否过期。

## 3. 设计

### 3.1 中间格式（IR）：shared/arch-diagram.ts

用 zod 写，前后端共用；同一份结构转成 JSON Schema，交给模型作为 `submit_diagram` 的参数说明。

```ts
ArchDiagram = {
  version: 1,
  type: 'architecture',            // 以后加 dataflow / sequence / lifecycle
  title: string,                   // 「agent-panel 总览」
  scope: { kind: 'project' | 'module' | 'path' | 'flow', target: string },
  summary: string,                 // 一段话的结论，写在图上方
  groups: {                        // 分组：层、子系统、进程、信任边界（可以嵌套一层）
    id, label, kind: 'layer' | 'subsystem' | 'process' | 'boundary', parent?
  }[],
  nodes: {
    id, label,                     // id 用 [a-z][a-z0-9_-]*
    kind: 'ui' | 'service' | 'module' | 'store' | 'queue' | 'external' | 'cli' | 'job' | 'config',
    group?: string,
    role: string,                  // 一句话职责
    details?: string,              // 卡片里的展开说明（Markdown，短）
    sources: { path, lines?: [from, to], note? }[],   // 1～3 条，仓库相对路径
    emphasis?: boolean,            // 主路径上的关键节点
    drill?: string,                // 能往下画的范围（模块名或目录）
  }[],
  edges: {
    id?, from, to,
    kind: 'call' | 'http' | 'rpc' | 'event' | 'read' | 'write' | 'spawn' | 'depends',
    label?: string,                // 「POST /api/tasks」「stdin/stdout」
    sources?: [...],               // 调用发生的地方
    primary?: boolean,             // 主路径
  }[],
  cards?: { title, body }[],       // 不适合画成线的细节：约定、注意事项
}
```

规则（校验时检查，§3.4）：

- 节点数按 `detail` 限制（overview ≤ 15，standard ≤ 30）。
- 每个节点至少一条出处，外部服务（`external`）除外。
- 连线两端必须是已有的节点，分组最多嵌套一层。
- 同一对节点之间同种连线只能有一条，`label` 写成合并后的说法。
- 每张图最多 3 条 `primary` 连线组成一条主路径（总览要有一条「数据怎么从入口走到存储」）。

不加坐标字段：布局由面板算。用户拖过的位置存在面板这边（§3.6），不进 IR。

### 3.2 静态事实：`arch_facts` 工具（server/arch-facts.ts）

`/arch` 开始时模型先调它。参数是范围（`scope`），返回一份压缩过的事实：

1. **结构**：范围内的目录树（深度和数量有上限，忽略 `node_modules`、构建产物，以及项目设置里的「搜索时跳过」）。
2. **模块文档**：有 `docs/MODULE-MAP.md` 时，带上模块表（模块名、源码、职责、入口）和范围内模块的 README 开头。项目按 ADR 0048 维护过模块文档的话，这是最好的骨架。
3. **依赖**：
   - JS / TS：复用 `scripts/lib/import-graph.mjs` 的解析，挪到 `shared/` 或 `server/` 下，读项目自己的 `tsconfig` 路径别名，不写死本仓库的 `@shared`、`@/`。
   - 把文件级的 import 聚合到目录或模块级，给出「A → B 有 n 处引用，代表文件是哪几个」。
   - 其他语言第一期只给目录和文件清单，由模型自己读。以后按语言加解析器（Python `import`、Go `import`、C++ `#include`、UE 的 `.Build.cs` 模块依赖）。
4. **入口**：`package.json` 的 `bin` / `main` / `scripts`，服务端监听端口和路由文件（按常见写法找，找不到就不给）。
5. **上一版**：这个范围画过图时，带上上一版的 IR 摘要（节点和连线的 id、label），让模型尽量沿用原来的 id，第二期的对比才对得上。

工具结果有长度上限，超出的部分按 ADR 0041 的做法写进对话目录，给出全文的指针。

### 3.3 布局和渲染：右栏的 `ArchDiagramView`

- 用现有的 `@xyflow/react` 画，不另起渲染器，和工作流画布的交互、主题保持一致。
- 自动布局用 **ELK**（`elkjs` 的 layered 算法，支持分组嵌套、正交连线、端口），在 Web Worker 里懒加载，不进首屏。
  - 方向默认从上到下，总览按「界面 → 服务 → 存储 / 外部」分层。
  - 每条 `primary` 连线的权重调高，让主路径尽量走成一条直线。
- 节点按 `kind` 用不同的图标和色调（跟随主题 token），分组画成带标题的底框，信任边界用虚线。
- 交互：
  - 点击、悬停高亮上下游。
  - 聚焦模式（只看上游、下游或两者）。
  - 搜索。
  - 小地图。
  - 节点和连线详情弹层；出处点了交给 `openFile(path, line)`，复用文件面板的预览。
- 画图不需要联网，也不需要 CLI 或 Node，在线演示版能直接看。

### 3.4 校验和修正：`submit_diagram` 工具（server/arch-diagram-tool.ts）

`submit_diagram` 挂在项目对话的面板工具里（和 `set_plan`、`submit_diagnosis` 同一套），只在这一轮由 `/arch` 发起时提供，平时不占工具清单（ADR 0028 按需）。收到后按顺序检查：

1. **结构**：用 zod 校验。报错一条一行，带上是哪个节点（`nodes[3] (router)：kind 不在可选值里`），照 Archify 的写法。
2. **引用**：连线两端、分组、`drill` 的范围是否存在；id 是否重复；节点数是否超限。
3. **出处**：
   - 路径在仓库里（不许 `..`、不许绝对路径），文件存在，行号不越界。
   - 用 `git ls-files` 判断文件是否在版本管理里；不是 git 的项目（P4、无版本管理）只查文件存在。
4. **一致性**（只提示，不拒收）：
   - 事实里依赖次数很多的两个模块之间没有画线，提示「server → shared 有 120 处引用，图里没有」，让模型决定画上还是写进卡片说明为什么不画。
   - 反过来，画了线但事实里没有任何引用的，也提示一遍。

不过关时工具返回错误清单，模型改了再交。**最多两轮**，第三次还不过，就按 AGENTS.md「错误一律显示给用户」，把图按「有问题」存下：能画的画出来，出错的项标红，并列出原因，不悄悄丢掉。

判断「图做完没有」只看 `submit_diagram` 有没有通过（不看回复文字），符合 ADR 0041 / 0049 的硬规则。`/arch` 这一轮的结束前钩子（ADR 0049）检查这一项：没交过就让它接着做。

### 3.5 在哪个对话里跑

- `/arch` 在**当前对话**里展开成一段要求，由当前角色执行。
- 这段要求只说三件事：
  - 先调 `arch_facts`；
  - 再按需读代码，补上依赖事实之外的东西；
  - 然后 `submit_diagram`。
- 「怎么画好一张图」的方法写在内置 Skill skills/docs/architecture-diagram/SKILL.md（总览控制在 8～15 个节点、主路径、细节放卡片、命名按代码里的叫法、外部服务单独一组），`/arch` 展开时点名用它，不往提示词里塞长说明。
- 权限按只读算：这一轮是 `noEdit`，不改项目文件。存进项目文档由面板做（§3.6），不让模型写文件。
- 对话已经很长时提示一句，可以新开一个对话来画。不强制，因为当前对话里的上下文也可能正是画图需要的。

### 3.6 存储

- **面板这边**：数据目录 `projects/<项目>/diagrams/<id>.json`，内容是：
  - IR；
  - 元数据：范围、提交号、生成时间、哪个对话、校验结果；
  - 用户拖过的节点位置。

  对话里的卡片只存图的 id。

- **存进项目文档**（第二期，用户点了才做）：
  - 写 `<文档根>/architecture/<名字>.arch.json`（IR，方便下次在这个基础上更新）和 `<名字>.html`（导出的单文件）。
  - 文档根按 ADR 0039 的规则（Git / 无版本管理是项目的 `docs/`，P4 是共用的 ProjectDoc）。
  - 只写本机文件，不提交、不推送（P4 文件不自己提交的约定照旧）。
- **导出 HTML**：把 IR 和一个小的只读查看器打进一个文件。查看器和右栏共用布局和渲染代码，用 Vite 单独出一个 bundle。离线可看，不带面板接口，出处只显示路径和行号，不能跳转。

### 3.7 过期检测和对比（第二期）

- **过期**：
  - 打开图时，面板用 `git diff --name-only <存图的提交号>..HEAD` 加上工作区里的改动，找出改过的文件。
  - 出处落在这些文件里的节点和连线标「可能过期」，图上方提示「n 个节点的源码在这之后改过」。
  - P4 和无版本管理的项目比文件修改时间。
- **更新**：按钮等于以同样的范围再发一次 `/arch`，`arch_facts` 里带上上一版。
- **对比**：按 id 对齐两版，新增绿、删除红（虚线留位）、改了（职责、出处、连线种类变了）黄；图上方给一行统计。

## 5. 和现有东西的关系

- **工作流画布**：共用 `@xyflow/react` 和主题，交互习惯一致；不共用数据结构，工作流是要执行的，架构图只是看。
- **Mermaid**：Markdown 里的 Mermaid 照旧。架构图不输出 Mermaid：交互（点节点看出处、聚焦、过期标记）Mermaid 做不了，大图的布局也不好控制。第三期的时序图可以考虑直接用 Mermaid 渲染（时序图的布局本来就是固定的）。
- **模块文档（ADR 0048）**：
  - 有 MODULE-MAP 时，它是总览图的骨架。
  - 画完的总览图可以反过来帮着补 MODULE-MAP：图里有、MODULE-MAP 里没有的模块，卡片里提示「模块文档里没有这个模块」，不自动改文档。
- **AI 初始化项目**：初始化写完 AGENTS.md 和模块文档后，可以顺手画一张总览图（第二期，做成初始化结果里的可选项）。

## 6. 风险和对策

| 风险                        | 对策                                                                                                       |
| --------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 模型编出不存在的模块或调用  | 出处必须核对通过；依赖事实对不上的给提示；节点数受限，逼它取舍而不是堆                                     |
| 大仓库读代码太贵            | `arch_facts` 先给聚合好的事实；总览只到模块级；往下画再按需读                                              |
| 非 JS / TS 项目没有依赖事实 | 第一期退回目录结构加模型读代码，图上标「依赖由 AI 读代码归纳」；按语言逐步补解析器，UE 的 `.Build.cs` 优先 |
| 布局难看                    | ELK 分层加主路径权重；用户拖动后的位置会存下来；节点上限 30                                                |
| 图很快过时                  | 记提交号，按出处文件判断过期，一键更新，更新时沿用 id 方便对比                                             |
| 引入新依赖                  | `elkjs` 约 1.4 MB，只在打开架构图时懒加载（Worker），正式包和演示包都要检查首屏体积不变                    |

## 7. 不做的

- 所见即所得编辑（增删节点、改文字）。图由代码生成，改图应该改代码或重画；只允许拖动位置。
- 自动发现部署和运维信息（机器、云资源、负责人），只画代码里看得到的。
- 解析用户贴来的 Mermaid 或别的图格式。
- 在线分享链接，只导出文件。
- 第一期不做数据流、时序、状态、ERD、类图。
