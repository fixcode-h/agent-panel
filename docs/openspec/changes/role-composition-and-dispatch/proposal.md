# Proposal：角色分层（基本角色 / 高级角色）与父对话分诊调度

状态：提议（2026-10-27），实施前等用户确认 `design.md` 末尾的「待确认的决策」。

## Why

现在的角色和对话位置是一一绑死的：顶层对话固定用「统筹」，子对话固定用「执行」，`spawn_agents` 不点名时固定用「子任务」。
每个角色只做一件事，文档、评审、测试验收、版本控制各是一个独立角色，要用就得派一次子任务。结果是：

- **能力太散**：一个子对话收尾要依次派「评审」「文档」「测试验收」「版本控制」，每派一次都要重新注入角色设定、通用约束、AGENTS.md、教训和技能清单（统筹的提示词里自己写着「一个只干 30 秒动作的子对话也要二十万 token 起步」）。
- **父对话不会「先想再动」**：「统筹」被规定为只统筹不动手，改一个文案也要开子对话；它也没有「先分析、不懂就问、再决定怎么处理」的固定流程，什么时候提问、什么时候直接答、什么时候开子对话、什么时候派子任务、什么时候走工作流，都散落在几段提示词里。
- **位置和职责没捋清**：父对话、子对话、子任务、工作流、工作流节点、执行计划各自是什么、能做什么、谁决定用哪个，没有一张统一的表；`canDelegate`、`canPlan`、`runIn`、`includes`、`common` 这些开关各管一块，互相之间的关系要读代码才知道。

用户要的效果是像 Claude Code 一样：在父对话里说一句话，它自己分析、需要时追问、然后决定自己做还是分出去，多个子对话协同把事做完。

## What Changes

- **角色分两层**：
  - 基本角色：专注一个能力块（调研、方案设计、开发、评审、测试验收、文档、版本控制……），可以作为子任务单独派出，也可以被高级角色挂载。
  - 高级角色：有自己的定位，下面挂载若干基本角色，并带一份「调度策略」，自己决定每件事是就地做（把能力说明按需加载进自己的上下文）还是派成子任务 / 子对话 / 工作流。
- **执行位置（容器）统一成四种**：父对话、子对话、子任务、工作流运行；每种的定位、生命周期、上下文、权限写成一张矩阵，由面板强制，不靠提示词自觉。角色只决定「怎么做」，位置决定「能做什么」。
- **父对话改用高级角色「主理」**（替代「统筹」）：每条消息走固定的流水线——理解 → 澄清（不懂就问用户） → 分诊（选位置） → 派发 → 跟踪 → 汇总 → 收尾；分诊结论画成一张可改派的卡片。允许在严格护栏内就地做微小改动。
- **子对话默认高级角色「执行」**：挂载开发、调研、测试验收、评审、文档、版本控制，评审强制派成独立子任务，其余按规则就地做或派出。
- **能力按需加载**：高级角色的提示词里只放挂载能力的索引（名字、什么时候用、怎么调），用到时再取全文，省掉每次全量注入。
- **工作流归位**：工作流是「剧本」，不是执行者；它在某个对话里运行，节点用基本角色。
- 数据模型、迁移、界面、分阶段实施和验证方案见 `design.md`。

## Non-Goals

- 不改 CLI 的接入方式、输出解析和模型档位。
- 不改子对话的合并、评审门禁、交接摘要、测试步骤分档这些已经定下的机制（ADR 0005、0007、0009、0010、0013、0018、0020、0022），只把它们放进新的位置模型里重新说明。
- 不做子对话嵌套子对话（子对话仍不能开子对话），不做子对话之间的直接通讯。
- 不在本次实现，先确认设计。
